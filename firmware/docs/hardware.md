# Echo hardware

A short map of the hardware Gnarlyr drives on the full-size Snowsky Echo, for reading the code in `platform/device`. Most of it was first worked out for the Echo Mini by the [ReChord](https://github.com/brnomt/ReChord) project, and the Echo reuses it (same SoC, boot ROM, container, load map and memory map). The Echo values come from Podium's port and its author's reading of the decompiled stock Echo 2.0.0.

What this project checked on a player: on the owner's Echo (4 GB), an earlier build based on Podium 4.5.5 lit the display, read the buttons, played music with volume control, and served internal storage and a microSD card over USB. Later Gnarlyr developer builds have also run on the owner’s player; current checks are recorded in `known-issues.md`. Observations below that are dated or described as seen on a player are EchoPod's and Podium's authors', made on their players and kept because the code depends on them; this project has not repeated them.

## Chip and memory

- Rockchip RKnano with two Cortex-M3 cores. Core 0 runs the firmware; core 1 runs a decoder program (FLAC, MP3 or M4A) loaded on demand.
- Core 0 data RAM: `0x03004000`–`0x0304C000`; the boot ROM still uses its top while loading the image, so the firmware's data must end below `0x0304A240`. Above the independent audio bank, the firmware loads its extension module into `0x0304A000`–`0x0304BFFF` at start-up. Code runs from `0x03050000` (about 157 KB).
- High RAM: `0x0307A000`–`0x0309EFFF` (148 KB). The library rescan code and the USB session code are loaded here when they run.
- Core 1 RAM: `0x01000000`–`0x0105FFFF` (384 KB). It also serves as scratch memory for the rescan while playback is stopped.
- The boot ROM starts the cores at 24 MHz. The firmware switches the PLL to 96 or 200 MHz.

## Display and keys

- 480 × 222 landscape ST7796S-class RGB565 panel (native 222 × 480 portrait) with its own image memory, so there is no framebuffer. It sits behind the SoC LCD controller at `0x60070000`, so there is no bit-banging. The window's row axis carries a 49-row offset in landscape (`MADCTL` `0x28`: swap rows and columns, BGR); in portrait the swap bit is cleared, `0x88` (mirrored rows) or `0x48` (mirrored columns) turn the picture the two ways, and the 49-line offset moves to the columns (the visible 222 lines sit 49 from each edge of the 320, so it is the same for both). No panel ID read, a single variant.
- The backlight runs from a 25 kHz PWM, channel 0 on GPIO2.4.
- ▶‖, ≡, ↩ and the volume rocker sit on a resistor ladder read through the ADC. Power is a separate input.

## Storage

- eMMC on the DW-MMC controller (4 GB on the owner's unit; an 8 GB model exists). From the start: the ID block, firmware slot 1, firmware slot 2, a SAVE block, then the FAT32 user volume that appears as the internal drive over USB. The firmware never writes the ID block, the SAVE block or the gap between them.
- Each firmware slot holds the first 5 MiB of a firmware image. Slot 1 follows the ID block; slot 2 is found as stock does, searching from the next MiB after slot 1's firmware size plus 16 KiB in 1 MiB steps (`docs/architecture.md`).
- A microSD slot on the same kind of controller, with card detect. The firmware reads and writes FAT16, FAT32 and exFAT.

## Audio

- Two Cirrus Logic DAC chips, set up over I2C0 at bus addresses `0x60` and `0x66` (7-bit `0x30` and `0x33`) and fed by I2S1 through DMA from a ring in data RAM. They are CS43198, as FiiO lists: on the owner's player both report `431980 A1.06` (ID `43 19 80`, revision `A1`, subrevision `06`). Earlier developer About rows read each chip's identification registers after a track had played; the current developer HAL retains these reads (`architecture.md`, DAC identification); `431310` would mean a CS43131, which some inherited code names still assume.
- 3.5 mm and 4.4 mm outputs. GPIO0.13 high means a 3.5 mm plug, GPIO2.8 high means 4.4 mm. Both jack pins have pull-ups set at start-up.
- An LPC accelerator next to core 1 speeds up FLAC decoding.
- No hardware equalizer: the CS43198 has none (only its digital filters and gain), and the SoC's audio path has none in use. FiiO's firmware runs its equalizer in software on core 0, and so does Gnarlyr (`docs/architecture.md`, Equalizer).

## USB

- DesignWare USB 2.0 OTG controller, high speed. The firmware presents both drives as a mass-storage device, or, in USB DAC mode, a full-speed USB Audio Class 1.0 sound card (not run on a player by this project). The core's FIFO RAM is small: at reset, RX 147 words and TX FIFO 0 128 words.
- With the buttons held at power-up, the boot ROM's maskrom mode appears as `2207:262d` (`docs/device-recovery.md`).

## Other

- **Bluetooth:** an external module with its own stack, powered from GPIO2.7 and driven over UART1 at 115,200 baud with short ASCII commands. This project has not run Bluetooth on a player. The rest of this entry is EchoPod's author's record, from their player with OnePlus Buds 3: stock streams to the headphones; EchoPod pairs, connects and, since 2026-10-29, streams to them too (see the end of this entry). Found on that player (2026-10-28, nothing in either jack, music playing): GPIO2.0 high with GPIO2.14 low (stock's connect step), both low, and GPIO2.0 low with GPIO2.14 high are all silent in the headphones; with GPIO2.14 low and GPIO2.0 low a 3.5 mm headphone still plays, so GPIO2.14 doesn't cut the wired output, and only GPIO2.0 high mutes it; and switching GPIO2.0/2.14 moves the jack-detect readings enough to fake an unplug, so `board/jack.c` ignores the jack pins while audio is routed to Bluetooth and for 500 ms after each routing change; readings taken while routed fake a plugged headphone. Also silent: stock's play-state rules for the `C 86`/`C 87` notices, pausing `CQ00` after the module's `CP`/`CC` reports and answering them with `CY0 00`/`CY0 1E`, driving GPIO0.14 high as stock's boot leaves it, and restarting the DAC path with the routing pins already set (the DAC starts normally with GPIO2.14 held low). The `CP`/`CC` flipping seen with the Buds out of the ears stops with them in. Also silent with the module powered and streaming before the DAC path starts (stock's order), and with Gain on High. Register dumps taken while streaming match stock's predicted state on every audio-path register: I2S1, the ACODEC words, the GRF pin groups, GPIO1.0–1.4, GPIO2.0/2.2/2.14 and the audio clock bits, and on both CS43131s every register except headphone output control `080000` (Gain) and PCM volume. The remaining differences are boot housekeeping (CRU gate and reset images, display, UART2 and pull settings). **Bluetooth audio played on 2026-10-29** once EchoPod, on routing to the module, also applied the stock start-up settings it had skipped: GRF `+0xC4` = `0x00010000` (bit 0 cleared), CRU `+0x84` = `0x00920092` and `+0xA0` = `0x00020002` (gates `0x11`, `0x14`, `0x17` and `0x81` off), CRU `+0xC0` = `0x00680068` (I2S0 and SPI0/1 held in reset), GPIO2.9 driven low, the GPIO0.13 and GPIO2.8 pulls set as stock sets them (GRF `+0x14`, `+0x54`), and `CY0 00` on connect before `CY0 1E`. Which of these is needed hasn't been narrowed down yet.
- **Clock chip:** this project's reading of the stock 2.0.0 main program (not yet checked on a player) finds an I2C clock chip at bus address `0xA2` (7-bit `0x51`), with the register layout of an NXP PCF8563 or a compatible part. Stock reaches it through I2C1 (controller `0x40050000`, the second of the three at `0x40040000`, `0x40050000` and `0x40060000`), with GPIO2.12 and GPIO2.13 on function 3, the I2C1 group field of GRF `+0xBC` (bits 3:2) set to 2, CRU gate `0x84` on and reset `0x1B` pulsed. At start-up (`0x03062506`) it reads 9 bytes from register 2 at 200 kHz (`0x0306193e`) as BCD seconds, minutes, hours, day, weekday, month and year (year + 2000), writes control register 0 with 0 so the oscillator runs, and checks the ranges; when they are still wrong after a second read it writes 2026-01-03 12:00:00. While running it does not read the chip again: its main loop counts seconds, minutes, hours and the date in RAM from the tick counter, with leap years (`0x030676a8`). It ignores bit 7 of the seconds register, the chip's flag that the time may be wrong. On the owner's player (developer build 0312581, `rtc read` twice, 5 s apart; `architecture.md`, Clock chip read) the chip answered at `0xA2` on I2C1, its trust flag was clear and its seconds advanced by 5. It read 2026-05-20 22:41, consistent with counting without a break, through many power-offs and a maskrom recovery, from stock's 2026-01-03 12:00 default about 137 days before; so the chip keeps time while the player is off, which needs a supply that the power switch does not cut. Nothing has set it since, so its time is not the real one. The weekday register's unused bits and the unused bits of registers `0x0D` and `0x0E` changed between the two reads.
- **Battery:** read through the ADC. The firmware shuts down below 3450 mV, as FiiO's firmware does.

## Firmware image

- `GNARLYR.IMG` is a 5 MiB `RKnanoFW` container: an outer header, a table of load rows, the code and data, a copy of the first 512 bytes at `0x44C000` and a CRC-32 trailer at `0x500000`. `tools/make_image.py` builds it, and `docs/architecture.md` describes the layout.
- FiiO's updater scans `\ECHOECHO.IMG`, then `\ECHOV100.IMG` to `\ECHOV498.IMG` at the top level of internal storage, and the highest wins. FiiO's own Echo image is 39,845,892 bytes.

## Board details

- The battery ADC (channel 0) reads the rail the player runs from, not the cell alone. On battery, or with the USB supply pins held low, it is the cell (4213 mV full on the owner's player). On USB power while the cell is charging it tracks the cell; once charging has finished it sits above it and moves with the load (4.3 to 4.8 V seen). A reading above 4.3 V on USB power therefore means the charge is complete, and a millivolt figure taken on USB power is not a battery level.
- GPIO2.0 and GPIO0.14 are the USB supply pins: GPIO2.0 high takes power from USB, GPIO0.14 high charges the battery (meanings from stock's USB audio charging modes). They follow the cable: low with no cable and before power-off, high once cable power is seen. Held high with no cable, a USB-C host does not recognise the player when it is plugged in, so it supplies no power and nothing is detected; seen on the owner's player with a Mac, where lowering GPIO2.0 in that state brought the connection up in 0.3 s.
- DAC mute is GPIO2.1 and the DAC has no reset pin.
- The 4.4 mm jack reads high when plugged (GPIO2.8); the 3.5 mm jack reads as above.
- **Headset remote:** the 3.5 mm plug's mic contact is read on ADC channel 2, as on stock 2.0.0 (the Echo Mini has none). Stock scans the ADC in the order key, key, headset, battery (one conversion every 5 ms, so the headset every 20 ms) and reads it only with a 3.5 mm plug in. Bands of the 10-bit reading: below 16 play (a button shorting the mic to ground), 16-45 volume up, 46-100 volume down, above 100 nothing pressed. Stock counts a press after two equal readings and a long press after 20 (about 400 ms); a tap of volume up or down changes the volume, a long press skips (stock skips back on volume up and forward on volume down), and play counts taps: 1 pauses or resumes, 2 next track, 3 previous track, closed after 30 SysTicks without a tap; a long play does nothing. In the decompile: `0x03060068` sets the scan order {1,1,2,0}, `0x03061ab6` decodes the bands and gestures, `0x03061e00` maps them to the volume (`0x1d5`/`0x1d6`), next (`0x1b4`), previous (`0x1b5`) and play/pause (`0x1b6`) messages, handled at `0x03081910`. The firmware follows it (`device/headset_remote`) with its own key semantics: a long volume up skips forward, a long volume down back, and taps of play close after 300 ms. Settings → About → Headset shows the live reading and the button it reads as, for example `1023 none`; for 3 s after the reading drops more than 24 below its idle value (with a remote plugged in) it shows the dip instead: `1023 min 512 40ms 3 dips` is the live reading, the lowest reading, the longest dip and the number of dips, each dip starting a new 3 s window. While the row is on screen the headset is read on three of every four scans (every 5 ms, 10 ms around a key scan) instead of every 20 ms. Podium's author reports that on a player (2026-11-04) the middle button reads 1 and works, and idle reads 1023. A plug without a mic contact (3-pole TRS, for example Meze Alba) reads 0-1, the play band; after a plug goes in, whichever of "play band" and "anything else" the line holds first for 500 ms decides whether it has a remote; a remote whose line then sits in the play band for over 1 s is taken for a swapped plug (a jack change can be quicker than the jack debounce) and counts as no mic until the line leaves the play band for 500 ms. With no mic nothing is decoded and the row shows `0 no mic`, whatever the dips. Dips are only tracked while a remote is listened to, start from a fresh idle level at each plug change, and a drop lasting over 1 s becomes the new idle level.
- **Apple remotes** (EarPods with Remote and Mic): the middle button shorts the mic line like any headset and works. Volume up and down are switched by a chip in the remote. David Carne's 2010 measurements on the iPod shuffle 3G remote: idle 2.08 V, volume up a static load to about 1.68 V, volume down to about 1.52 V, and an ultrasonic ID chirp after power-up (1.5 ms at 280 kHz, then 4.6 ms at 244 kHz) that the iPod answers with a 4.8 ms pulse; the iPod's Mikey chip demodulates the chirp, and a shuffle cuts the remote's power without an answer. The Echo can't send that answer, and its ADC reads the idle line at full scale (1023), so a drop to 81 % or 73 % of the bias may not show at all; Podium's author reports that on a player the EarPods' volume buttons only flicker the reading. Stock 2.0.0 has no Apple path either: channel 2 is read only by `0x03061a5c` and `0x03061ab6`, with the bands above, so EarPods volume buttons do nothing on stock too unless their level lands in 16-100.
