# Architecture

The design record of Doublesharp Echo, firmware for the full-size Snowsky Echo. It is built on Podium 4.5.9, which is forked from EchoPod, the Echo Mini firmware (`../UPSTREAM.md`). The app layer is portable C. It runs in a desktop simulator during development and on the device on top of a thin hardware layer.

Most of this record was written by EchoPod's and Podium's authors together with the code. Timings, failures and other results it describes as seen on a player or on a particular computer are theirs, from their players, and are kept because they explain the design; this project has not repeated them. Doublesharp itself has run only in host tests, the simulator and the emulator. What an earlier build of this project showed on the owner's player is listed in `known-issues.md`.

## Layers

```
platform/sim        platform/device
        \                  /
         implement  hal  (interfaces only)
                     |
                    app          composition root: theme, screens, player, stores, main step
           /     /       \        \
         ui   fonts    settings   hal
           \   /           |
            gfx        playback
              \            |
               \        library
                \         |    \
                 \        |   image
                   \      |    /
                      core
```

| Layer | Path | May depend on | Purpose |
|---|---|---|---|
| core | `src/core` | nothing | Pure logic: deadlines, key gestures, frame stats, UTF-8, string building, formatting, hashing, seeded random, the power policy, the DAC identification decode and text, the key-script grammar and the debug event ring |
| gfx | `src/gfx` | core | RGB565 colors and blending, rectangles, clipped canvases, strip rendering, 4-bit anti-aliased text, images drawn into perspective quads |
| fonts | `src/fonts` | gfx | Generated glyph tables (see Generated code) |
| ui | `src/ui` | core, gfx | Screen interface and stack, navigation intents, list view, menus, choice screens, messages, toasts, header and status icons, labels, marquee, fades, Cover Flow layout and motion, theme type |
| image | `src/image` | core | Cover decoding for the rescan: a bump arena, a buffered reader, the 112 px area-average grid, inflate, PNG and JPEG (see Covers on the device) |
| library | `src/library` | core, image | Byte sources, a 4×512 B block cache, the library database reader and its content fingerprint, browse queries, the favorites set and the covers file reader (see `docs/library-format.md`) |
| codec | `src/codec` | core | FLAC decoding (up to 2 channels, 24 bits, 4,608-sample blocks) from a read callback, with header and frame CRC checks, and seeking by bisection on frame headers; ALAC decoding of one MP4 packet at a time (16, 20 and 24 bit, mono and stereo) into a caller-owned 32 KB state |
| playback | `src/playback` | core, library | Play queue (list order, songs shuffle, album shuffle, repeat, gapless look-ahead, playing a stored order), the resume file format, and the storage of edited queues, the session journal and mixtapes (`docs/playback-store.md`) |
| settings | `src/settings` | core, playback | The settings values, their defaults and option tables, and the settings file format |
| hal | `src/hal` | core (types only) | Hardware interfaces: display (with power and brightness), input, clock, files, audio (with gain and output), power (battery, power off), system (firmware tag, CPU clock), Bluetooth (module power, scan, pair, disconnect, status) |
| app | `src/app` | core, gfx, fonts, ui, library, playback, settings, hal | Default and board themes, board layout (see Boards), screen tree, library, settings and favorites stores, cover cache, player controller, browse, Cover Flow, Settings and Now Playing screens, frame overlay, the main step |
| platform | `platform/*` | app, hal, codec, the OS or SDL | Implements hal and owns `main()` |

The CMake targets enforce these rules. Each module exposes only its own `include/<module>/` directory, and a module can only include headers from targets it links. Anything in a module's own directory, outside `include/`, is private.

## Screens and input

- A `Screen` is a title plus callbacks: `enter`, `handle_key`, `update` and `draw`. `handle_key` returns a `ScreenAction` (none, push, pop, or pop to root), and the app applies it to the `ScreenStack`. Screens never reach into the stack themselves.
- Raw key transitions come from `hal`. `core/key_tracker` turns them into gestures (press, long press, repeat), and `ui/navigation` maps gestures to intents (previous, next, select, back, home). Remapping buttons is a change in one place.
- Each key has a gesture type: tap-or-hold, repeat (press on down, then repeats), or tap-hold-repeat (tap on release, long press, then repeats). The volume keys repeat, except on screens that set `hold_volume_keys` (Now Playing), where they're tap-hold-repeat so a hold can skip tracks. The app switches the type whenever the top screen changes.
- Screen instances are static and owned by the app's `AppScreens`. There is no heap.
- A long Play is `NAVIGATION_OPTIONS`. Lists hand it to their `hold` action; in browse lists it toggles an album's favorite.
- Smart Play: in a browse list, ▶‖ on the track the player already has loaded (playing or paused) pushes Now Playing without restarting it. ≡ pushes Now Playing from any screen while the player has a track, and does nothing on Now Playing itself.
- Lists draw the selected row as a highlight line over a gradient, a › chevron on rows that open another screen (`ListModel.opens`), and a slim inset scrollbar thumb. Menu items can be hidden by a `shown` callback, and a menu can give the right of its content to a side panel (`MenuPanel`). Home uses that for `home_art`: the playing album's cover with a reflection, or library covers cycling every 5 s when nothing is loaded; Home lists Now Playing last and only while the player has a track.
- Settings is a menu whose rows show their current value. Every row opens the same `ChoiceScreen`, re-initialized from a table of `SettingChoice` entries (title, options, current, choose), and the current option gets a ✓. Custom EQ opens `screens/equalizer_screen` instead: a scrolling list of the ten bands with their gains and a "Save to slot" row; ▶ starts adjusting the selected band (the header reads "1 kHz: vol ±"), vol± change it by 0.5 dB within ±10 dB and apply it at once, and ▶ or ↩ stop adjusting and save. It shares its memory with the `ChoiceScreen` (a union in `SettingsScreens`), since only one of them is open at a time.

## Power

- `core/power_policy` decides what keys mean for power. A tap of Power turns the screen off or on, and a long Power asks for shutdown. With the screen off (after a tap or a timeout), ▶‖ and vol± are background keys: the app maps them as on Now Playing (tap vol± for volume, hold vol± to skip, ▶‖ to pause) and runs them without waking the screen. ≡ and ↩ do nothing. While the screen is off, the volume keys use tap-hold-repeat on every screen, so a hold skips. The policy also owns the screen timeout and the sleep timer.
- The app runs each key event through the policy before the screen sees it. When the policy turns the display on or off, the app calls `hal_display_set_power` and stops rendering while the screen is off. Settings are saved each time the screen goes off.
- Shutdown (long Power, or the sleep timer running out) saves the resume file and settings, pauses playback (the same fade to silence as Pause), turns the screen off and calls `hal_power_off()`. The simulator then quits. The device stops the audio path the way stock 2.0.0 does before the rail drops: DAC mute pin and volume muted, headphone output powered down, headphone amp and DAC supply (GPIO2.2) off, I2S stopped, then 1 s for the DAC supply to discharge before cutting power. Cutting power with the output live crackles in wired headphones.
- Battery level (`device/battery_gauge`): the battery is read once a second, and the percent comes from the average of the last 64 readings (about a minute) through RECHO's 11-point curve (3450 mV = 0 %, 4200 mV = 100 %; stock shows only 5 bars, full above 3830 mV), so short dips under load (a song starting, card reads, the backlight) don't show. While charging it reads 50 mV lower and never shows more than 99 %, since the charging current lifts the terminal voltage most near full (stock shows full on the cable only at 4250 mV or once the charger reports done). The average restarts from the latest reading when USB power comes or goes, so the charger's lift doesn't linger after unplugging. The low-battery check and Settings → About → Battery use the last 8 readings. The shown percent follows the power source: on USB power it rises with any 2-point change but only falls by 10 points or more, on battery it moves both ways after a 3-point change, so the percent sags under load (backlight, 200 MHz) and recovers when the load ends. Plugging in or unplugging therefore can't make the number jump.
- Low battery (`core/low_battery`, stock's rule): every 250 ms the app reads the battery, and if it stays below 3450 mV for 2 s without USB power, it shuts down the same way with "Battery low" in place of "Goodbye".
- CPU clock (stock's rule: the clock follows the work, never the screen): 200 MHz while the screen is on or audio is up, 96 MHz (stock's floor) only with the screen off and `HalAudioStatus.idle` true (output and core 1 down, 3 s after playback stops or 30 s after a pause: `player_update` calls `hal_audio_release`, and Play afterwards reopens the output at the saved position). The device's audio HAL raises the clock to 200 MHz before it starts core 1, so a screen change never parks core 1. A USB session runs at 96 MHz at least.
- Waking draws the first frame before the backlight comes on (stock waits for 4 frames), and on the device the backlight then fades in over 200 ms (`device/backlight` ramp, from 1 % to the level's duty on the PWM, advanced by the main loop), so the backlight's switch-on current doesn't land at once on top of the drawing and the audio load.
- With the screen off, the device's main loop runs WFI once per pass, as stock does; SysTick (1 ms) wakes it, and the audio ring holds over 80 ms.
- Auto off (Settings, stock's options: Off, 1, 5, 10 min, default 5): `core/power_policy` counts from the last key press; the app holds it off each step while a track plays or USB power is present. When it runs out, the app shuts down as for a long Power press. Settings file version 2 adds the option at byte 14; version 1 files still load, with the default. Version 3 adds USB mode (Storage or DAC, see USB DAC mode) at byte 15; version 1 and 2 files load with Storage. Version 4 adds the DAC volume at byte 16. Version 5 adds the accent color (Settings → Color) at byte 17; version 1–4 files load with Blue. Version 6 adds the equalizer (see Equalizer) and grows the file from 24 to 32 bytes, so its checksum moves from byte 20 to byte 28; files of versions 1–5 (24 bytes, checksum at 20) still load, with the equalizer off. Version 7 adds the text size (0 Small, 1 Medium, 2 Large) at byte 24, in the same 32-byte layout; files of versions 1–6 load with Medium, and a version 7 file with an unknown size is rejected. Version 8 adds the skip gesture (0 Hold vol±, 1 Double vol±, 2 Double/triple Play; Settings → Skip songs) at byte 25; files of versions 1–7 load with Hold, and a version 8 file with an unknown value is rejected. Version 9 changes the music and DAC volume (bytes 13 and 16) from 50 levels to 60 levels of 1 dB; files of versions 1–8 convert a saved level L to ⌊(12L − 5) / 10⌋ (at least 1; 0 stays mute, so 50 becomes 59), which keeps the 3.5 mm loudness, and a file before version 9 with a level above 50 is rejected. Version 10 adds the orientation (0 Landscape, 1 Portrait, 2 Portrait, flipped; Settings → Orientation) at byte 26, in the same layout; files of versions 1–9 load with Landscape, and a version 10 file with an unknown value is rejected. Version 11 stores the ten Custom gains in 0.5 dB steps (+20, so 0 to 40) at bytes 28 to 37 and grows the file from 32 to 42 bytes, so the checksum moves from byte 28 to byte 38; bytes 19 to 23 go unused. Files of versions 6–10 (32 bytes) still load: `settings_store` tries 42 bytes, then 32, and the five old gains (100 Hz, 315 Hz, 1 kHz, 3.15 kHz, 10 kHz) are fitted onto the ten bands with `settings/equalizer_fit`; versions 1–5 load with the equalizer off. `core/key_tracker` counts clicks for two behaviors: `KEY_BEHAVIOR_DOUBLE_CLICK_REPEAT` (volume keys: one click is delivered as `KEY_GESTURE_PRESS` after `click_window_ms`, two as `KEY_GESTURE_DOUBLE_PRESS` at once, a hold gives `KEY_GESTURE_LONG_PRESS` then `KEY_GESTURE_REPEAT`, each event carrying its `repeats` count; with Double vol± the app turns them into 5 s seek steps, 15 s from `NOW_PLAYING_SEEK_FAST_AFTER_REPEATS`, via `now_playing_seek_by`) and `KEY_BEHAVIOR_TRIPLE_CLICK_OR_HOLD` (Play: one, two or three clicks, long press unchanged). `app` picks the behaviors from the setting only where skipping applies (a screen with `hold_volume_keys`, or the screen off); everywhere else vol± repeat and Play taps are instant.

- Brightness 1–10 maps to a backlight duty of 20, 25, 31, 38, 46, 55, 65, 76, 88 and 100 % (`device/backlight`). Below 100 % GPIO2.4 runs a 25 kHz PWM (`BACKLIGHT_HZ`), whose period follows PCLK and is reprogrammed after every clock switch. The PWM runs as the Rockchip SDK sets it up (`PWM_CTRL` `0x10003`: continuous, duty polarity negative), so the duty register counts the part of the period the pin is **low**: `backlight_duty` writes `period − period × percent / 100`. The SDK's own backlight table works the same way (rate 10 is its brightest, 85 its dimmest). Writing the lit share there instead inverts the levels.

## Settings and favorites

- `app/settings_store` loads `/.doublesharp/settings.bin` (defaults if it's missing or invalid), applies brightness, gain and output through the HAL, and only writes when the encoded bytes changed. Settings belong to the player, not to the music: the file lives on internal storage whether the music comes from the card or from internal storage, through `hal_internal_file_read`, `hal_internal_file_write` and `hal_internal_file_reserve` (same contract as the `hal_file_*` calls, but always the internal volume). `app/card_files` reserves it there. A player upgraded from an earlier build has its settings on the music volume: when internal storage has no valid `settings.bin`, the store loads that copy and the next save writes it to internal storage; from then on the music volume's copy is ignored. On the device, `board/internal_volume` mounts the internal volume on first use, with its own `FatVolume` shared with `board/update`, and the file HAL uses the music volume itself when that already is internal storage. `storage_reset` forgets the internal mount too. In the simulator the system directory stands in for internal storage.
- `hal_dir_open`, `hal_dir_next` and `hal_dir_close` list a folder: name (UTF-8, up to 767 bytes), folder or file, size, and a hidden flag (the FAT/exFAT hidden attribute on the device, a leading dot in the simulator). `.` and `..` are never listed. On the device, `fat_open_directory` and `fat_next_entry` walk FAT16/FAT32 entries (long names, or 8.3 names with the lowercase flags) and exFAT entry sets; up to 16 folders can be open at once. macOS's `._` files are listed like any other file.
- Folder entries are read in runs of up to 8 sectors, like file data, and writes of whole sectors go out as one multi-block write without reading them first. `fat_open` remembers the last folder it found (path and entry, up to 255 bytes of path) and starts the next lookup there when the parent path matches, so opening the tracks of one album walks only the album's folder. Mounting or reserving a file forgets it. EchoPod's author reports that on a 1,563-track card this took opening files from 40 s to 1.8 s, and the track scan from 61 s to 19 s.
- On the device, `hal_file_write` overwrites an existing file in place from offset 0 (`fat_write`, FAT16, FAT32 and exFAT) and fails if the file is missing or too short; it never allocates clusters or changes a directory entry. Every reader checks its magic and accepts a longer file, so a zero-filled file reads as missing.
- The player makes its own files. `app_start` only marks the files as pending; the next `app_step` calls `hal_file_reserve` (through `app/card_files`) for `library.db` (4 MB), `covers.bin` (80 MB), the 24 MB scratch file and then the 4 KB files (`settings.bin`, `resume.bin`, `favorites.bin`, `scan.bin`, ...). Files that exist are skipped within the same step. Each missing big file is made in its own step after a "Preparing storage / File N of M" notice lights the screen, so the main loop (USB, stall watch) runs between files; while charging the files are made silently, one big file per step. `app_preparing` reports the phase. A file that exists is left alone, whatever its size. A missing one is created at its size, along with `/.doublesharp` if needed; its first 4 KB read as zero and the rest is left as the card had it, so creating 80 MB costs a few hundred writes rather than 163,840. When `library.db` was just created the app asks for a rescan, so a new card is scanned on its first start. If any file doesn't fit, the app toasts "Storage is full". `tools/save_files.py` is now only a development helper.
- `fat_reserve` looks for free clusters from an allocation hint (FSInfo's next free cluster on FAT32, else the end of the previous allocation, kept in `FatVolume`) to the end, then wraps to the start; a hint that is not a cluster is ignored. `fat_delete` removes a file: its entries (long-name entries and the short entry marked `0xE5`, exFAT entry set with the InUse bit cleared), its FAT chain in every FAT copy, the exFAT allocation bitmap bits, and updates FSInfo's free count. Directories are refused.
- On the device, `fat_reserve` (`device/fat_reserve.c`, `fat_create.c`, `exfat_create.c`) creates the missing folders and the file as one contiguous run of clusters, first fit. Names are printable ASCII up to 64 characters. FAT16/FAT32 get an 8.3 entry with the lowercase flags when the name fits (`settings.bin`), otherwise long-name entries plus a `~N` short name that's unique in the folder (`.doublesharp` → `DOUBLE~1`, `favorites.bin` → `FAVORI~1.BIN`); the chain goes into every FAT copy and FAT32's FSInfo free count and next-free hint are updated. exFAT gets a File, Stream (NoFatChain, valid length = size) and Name entry set with its name hash and set checksum, and the clusters are marked in the allocation bitmap. The write order keeps a cut-off write harmless: clusters are marked used first, then the start of the data is cleared (a new folder's whole cluster, with `.` and `..` on FAT), and the directory entry goes last (on exFAT the secondary entries before the File entry). A folder whose entries are full isn't grown; that reserve fails. Dates are 2026-01-01, since the player has no clock. While it runs, every card read beats the stall watch. `test_fat_create` creates files on all three fixture cards and saves them, and `created_cards_pass_fsck` checks the results with macOS's `fsck_msdos` and `fsck_exfat` (through `diskutil image attach --noMount`).
- At start-up the saved volume, shuffle and repeat go to the player first, and then a valid resume file overrides them. The current volume, shuffle and repeat are copied back into the settings before every save.
- The start screen setting pushes the matching path at start-up (for example Home → Music → Albums), so Back still leads home.
- `app/favorites_store` loads and saves `/.doublesharp/favorites.bin` and toggles albums by key, and counts a revision on every load and toggle. Music → Favorites is a browse screen over the Albums view that only shows the positions of favorite albums, collected in album order. The browse pool keeps the collected list and only collects again when the revision changed. Collecting reads every album's key from the card, so it calls a `between_albums` hook every 8 albums (`favorites_collect`), and the browse screen uses it to run `hal_audio_service`: before this, opening Favorites while playing starved the DMA ring for a second or two and the ring's last 0.3 s played over and over. Favorite albums show ★ before their year.
- Toasts are app-owned. Screens get a pointer to the one `Toast` and show short messages such as "Added to Favorites". The app draws the toast on top of every screen.

## Audiobooks and podcasts

- `playback/spoken` decides what is spoken word from the path alone: a track whose first folder is `Audiobooks`/`Audiobook` or `Podcasts`/`Podcast` (ASCII case-insensitive). Both indexers sort spoken word after the music and record music counts in the library header (since format version 3, see `docs/library-format.md`), so the Music lists leave it out while the shelves browse its folders. The rule itself lives in `library/spoken_path`. `spoken_shelf_folder` finds those folders among the root folder's children.
- Bookmarks are keyed by FNV-1a hashes of paths, so they outlive a rescan, like favorites: a book's key is its folder's path (`Audiobooks/<Book>`), and a book that is a single file, or a podcast episode, is keyed by its own path. Each bookmark also keeps the track's key, its chapter (its place among its folder's tracks), the position and a finished flag. A track that is a part of a file (`start_ms` or `end_ms` set: a chapter of an `.m4b` or a CUE track) is bookmarked under the file's path hash (`spoken_record_key`), its track key adds its `start_ms` to the path hash (`spoken_part_key`; the same as the path hash when `start_ms` is 0, so older bookmarks stay valid), and its chapter comes from its `number`. The book on the shelf is then the file's chapter folder, whose key (`spoken_folder_key`) is the file's path hash; "already loaded" is decided by `spoken_folder_holds`, a membership test over the folder's tracks. `playback/bookmarks` keeps the 128 most recent, newest first, in `/.doublesharp/bookmarks.bin` (4 KB, reserved by `card_files`; see `docs/library-format.md`).
- The player marks a track spoken when it starts it (`player->spoken`), after a gapless hand-over and after a restore. For a spoken track:
  - a start from 0 asks `PlayerResume.position_for`, which `app/spoken_store` answers from the bookmark when its track hash matches and it isn't finished;
  - `player_skip` becomes `player_jump`: +30 s or −15 s, and a jump past the end starts the next track. Now Playing's hold-vol± and the screen-off keys go through `player_skip`, so both follow;
  - the queue is built in order (`PlayerListStart.in_order`), and `player_set_shuffle` keeps it in order, while `player->shuffle` keeps the music setting.
- `app/spoken_store` follows the player every step: when a spoken track starts it notes its keys and chapter, puts the bookmark every 5 s and on every play/pause change, and when the track ends or changes it marks the bookmark finished if it was in its last tenth (at most 30 s). The file is written when playback stops, when the track changes, every 30 s while playing, at shutdown and before a USB session.
- Home lists Audiobooks and Podcasts after Music, shown only when the folder exists (checked once when the screens are built). Both are browse screens in shelf mode over the folder: rows get "N chapters"/"Chapter n of N"/"Finished" or "N episodes", and tracks "mm:ss left"/"Played". In Audiobooks, ▶ on a book plays its folder from the bookmarked chapter (the chapter is checked against the track hash and looked up again if the files moved); a book that is already loaded is resumed and Now Playing opens. Hold ▶ on a book or show opens its tracks.

## Library rescan on the device

- Settings → Rescan library sets a flag; on the device, the end of a USB session in which the computer wrote to either drive (internal storage or the card) sets a second flag that first runs a music check, under a "Music / Checking for changes..." notice. macOS writes `.fseventsd` and `.Spotlight-V100` on every mount, so a write alone means little: `library/music_fingerprint` walks the card from `/` with one open folder per level (each folder is opened and listed once; a folder that can't be opened counts as empty; a card deeper than 32 levels gives an incomplete fingerprint), skipping names that start with `.`, and folds every entry's path, kind, size and modification stamp into two FNV-1a hashes plus a count. On FAT the stamp is the raw write date and time and the size is the directory entry's. On exFAT the stamp is the last-modified time converted to UTC with the entry's own UTC offset byte (`fat_exfat_utc_stamp`, in 2-second units since 1970; no valid offset counts as UTC), and the size is the stream's data length, not its valid data length; files of 4 GiB or more aren't listed. That is what Windows, macOS and Linux report for the same file, so `tools/echo_sync.py` can match it without guessing time zones: on one card, 9 files written with a wrong offset (−5:30 instead of +5:30) and 3 incompletely copied files (valid length short of the size) had made every PC fingerprint differ. It is compared with the fingerprint kept in `/.doublesharp/scan.bin` (4 KB, made by `card_files`; the bytes `DSSC`, the two hashes, the count), and only a difference (or no record, or a walk that failed) asks for a rescan. Every successful rescan stores the fingerprint taken just before it. A requested rescan the next `app_step` runs `library_rescan_run`, shows "Scanning library" with the track count every 250 ms, then restarts the app on the new library and toasts "Library: N tracks" or the reason it failed (no card, no room, too big, a folder too big, a path too long, a write failure, or missing rescan code).
- `app/library_rescan` checks for a music root (`/`) and a reserved `/.doublesharp/library.db` (its size is the capacity), then asks `hal_system_load_rescan_code` for the indexer's `LibraryScanEntry` and `hal_system_borrow_scratch` for working memory, and runs the scan with the HAL adapted to `ScanFileSystem`. The database goes out through `hal_file_write_at` and is never written unless it fits.
- The indexer is its own library (`echo_library_scan`). The simulator and the tests link it and return its entry table directly. On the device it doesn't fit the 157 KB code window, so it's built as `echo_rescan_overlay`: linked at `0x0307A000` against the main ELF's symbols (`--just-symbols`, plus libgcc for the double helpers), with a 16-byte header (magic `EOVL`, size, CRC of the rest, reserved) before the entry table. `tools/make_image.py --overlay` stores it at image offset `0x200000`, beyond the `fw1 end` the header records and inside the area the trailer CRC covers and the updater writes. `board/overlay.c` loads it into HIGHRAM0 for every rescan (see Overlay loader under Device platform). It may be at most `0x18000` bytes: the top of HIGHRAM0 holds the glyph cache.
- `.m4b` files (`library/mp4_chapters`, `library/library_scan_chapters`) are scanned like `.m4a` (`tags_mp4`), and then their chapters are read in the same open: first the Nero `chpl` atom in `moov/udta` (a count byte after a 4-byte version and flags, tried with and without a 4-byte reserved word, then entries of a 64-bit start in 100 ns units, a length byte and UTF-8 text), then the QuickTime chapter text track (`tref/chap` names the track, whose `stts`, `stsz`, `stsc` and `stco`/`co64` tables give each sample's start time and place; a sample is a 16-bit length and the text). The reader keeps the start, the place and the length of at most 255 chapters in `ScanState` (about 2.5 KB) and reads titles only when a chapter is added. Entries that start no later than the one before, or at or past the file's duration, are dropped, the first chapter starts at 0, titles are cut at 63 bytes on a character boundary and an empty title becomes "Chapter n". Fewer than two chapters, or any table or atom that doesn't fit the file, means no chapters and the file is added as one ordinary track. Each chapter becomes a builder track with `start_ms`, `end_ms` (0 for the last), its own duration, `number` n and the file's tags, in a sheet folder named after the file without its extension and flagged as chapters (`LIBRARY_FOLDER_CHAPTERS`): unlike a CUE sheet the folder holding the file doesn't list the file, so the shelf shows one book. `scan_internal` keeps the folder name in `ScanState.sheet_name`. Everything above the player handles chapters as it handles CUE tracks.
- `.cue` files (`library/cue_sheet`, `library/library_scan_cue`) turn into tracks during the walk. When a folder's listing is read, every `.cue` in it is parsed once to find out whether it is usable and which audio file it names (`docs/library-format.md`, CUE tracks), and that file's listing entry is marked so the walk skips it. When the walk reaches the `.cue` it reads the audio file's tags and duration, then parses the sheet again and adds one builder track per CUE track with the sheet's fields over the file's. Each pass has at most the cue file open, so the single file handle of `ScanFileSystem` is enough. A batched listing (a folder too big for the listing memory) marks only within its batch. The parser reads through `playlist_reader` (the same decoding as playlists) and keeps two tracks (the one being read and the one waiting for its end) plus the album's texts: about 4.5 KB inside the scan's memory. `echo_rescan_overlay` stays inside its 0x18000 bytes (88,404 used).
- On the device the scratch memory is core 1's RAM (`0x01000000–0x0105FFFF`, 384 KB): playback is stopped, core 1's domain is powered up with the core held in reset, and it's powered down again afterwards.

## Covers on the device

- After a rescan writes `library.db`, `library_rescan_run` asks the same entry table for `covers` (`library/cover_build`) and passes the scan's scratch memory, the file adapters, `library.db` to read back and `/.doublesharp/covers.bin` to write in place. It shows "Finding covers" with "N of M albums". The toast then reads "Library: N tracks, M covers", or ", no covers" if `covers.bin` is missing or the cover pass failed.
- For each album (in album order) it takes the first art it finds, as `tools/cover_export.py` does: the embedded picture of the album's first track (a front cover wins over any other picture, `track_tags_read`), otherwise `cover`, `folder`, `front` or `albumart` with `.jpg`, `.jpeg` or `.png` (any case, the first by name when several share a stem) in the album's folders in track order (at most 16 different folders, each listed once per pass however many albums share it). An embedded picture that fails to decode leaves the album without a cover, as on the PC. Unlike the PC, MP4 `covr` art counts; Ogg's base64 pictures still don't. A key already stored is skipped.
- Covers are kept between rescans. Before the pass, the builder reads the old index and its art stamps into the scratch memory, keeps the entries whose album key is still in the library and frees the records of the rest. For each album it then finds the art as above and hashes where it came from into a stamp: FNV-1a over the path (`/` plus the library's path for embedded art, the folder plus the listed name for a cover file), then three little-endian `u32`s: for embedded art the track's size, the picture's length and 1; for a cover file its size, its modification stamp (the same value the music fingerprint uses, from the folder listing it already reads) and 2. A stored stamp of 0 means unknown and never matches. An album whose stamp matches keeps its record without decoding; changed art is decoded again into the album's own record, and a new album goes to the first free record. A rescan after adding a few albums therefore decodes only those albums.
- The file has a fixed layout for its size: the 16-byte header, an index with room for every record (`(capacity − 16) / (8 + 4 + 31,360)`, 2,673 for 80 MB; a 32 MB file made by an earlier build keeps working with 1,069, since an existing file is never resized), a table of 4-byte stamps parallel to the index, then the records. Header bytes 12–15 hold the stamp table's offset. echo-sync writes the same layout and stamps (see `docs/library-format.md`), so the first rescan after it keeps its covers. A file without stamps (made by an earlier build or an older echo-sync), with another layout, or with an index that isn't sorted or points outside the records is ignored, and every cover is decoded again. Records are written as albums are decoded and the old index stays valid meanwhile, so a pass that never ends leaves the previous covers; the header is zeroed only when the pass is over, then the sorted index, the stamps and the `DSCV` header go last, so a pass interrupted there reads as no covers and the next rescan decodes everything. A record that can't be written counts as a missing cover and the pass goes on.
- `image/cover_image` sniffs JPEG or PNG and decodes into `image/cover_grid`: the centred square crop is area-averaged into 112 × 112 cells per channel with 9-bit fractional weights (each source sample adds `value × wx × wy`, sums wrap without undefined behaviour), and the 56 px half is the exact average of 2 × 2 cells. Per-channel sample sizes let chroma at half resolution sit on the same grid; YCbCr converts to RGB (JFIF) per cell, then to RGB565 like the PC.
- PNG: every colour type and depth (1–16 bits, palette, grey, alpha ignored as Pillow's `convert("RGB")` does), Adam7, all five filters, IDAT across chunks, zlib through `image/inflate` (32 KB window, 9-bit fast tables). Rows below the crop stop the decode. A row up to 64 KB is allowed.
- JPEG: baseline and progressive Huffman (SOF0, 1, 2), 1 or 3 components, sampling factors that divide the maximum, restart intervals, Adobe RGB. It decodes at 1/1, 1/2, 1/4 or 1/8 scale (the largest that keeps the crop at 112 px or more); each reduced sample is the exact area average of its pixels (cosines averaged over the sample, all 64 coefficients), and 1/8 is the DC term alone. Baseline scans stop below the crop. Progressive decoding needs no coefficient store: every scan's contribution is linear, so DC first and refinement scans and AC first scans add straight into the grid; AC refinement scans, and AC bands that can't change the reduced samples, are skipped. CMYK, 12-bit, lossless and arithmetic-coded files are refused. More than 8 bytes of padding past a marker fail the scan, so a truncated or lying file can't spin through millions of empty blocks.
- Memory comes from the scan's scratch (384 KB): the builder's state with one record (about 35 KB), the index (a key, a stamp, a 16-bit record number and a claimed bit per entry, for the larger of the album count and the old file's count, plus a bit per record: about 27 KB at 2,673 albums), then the decoder's arena: the grid (154 KB), a 4 KB reader and up to 168 KB for PNG rows, the inflate window and tables (JPEG needs about 13 KB). The worst PNG (64 KB rows) needs about 327 KB of arena, which still fits beside a full index. Nothing is static, so it runs from the overlay.
- `test_cover_grid` checks the averaging, `cover_decode_matches_pillow` (`tools/check_cover_decode.py`) makes 28 images with Pillow and a hand-written PNG encoder and compares the decoder with an exact area average of Pillow's decode (PNG within one RGB565 step; JPEG mean ≤ 3 and 99 % ≤ 40, the rest is libjpeg's smoothed chroma upsampling against our block chroma), checks that broken and unsupported files are refused, and fuzzes every image (truncations and byte changes) under UBSan. `cover_build_matches_reference` builds a music folder with each art rule and checks `covers.bin` end to end, then writes `covers.bin` as echo-sync does and checks that the player's cover pass keeps every cover. `test_cover_build` runs the scan and the cover pass over an in-memory card with generated PNG covers and checks what a rescan reuses: everything when nothing changed, only the new album, a replaced cover file, a removed album's record going to a new one, and a full rebuild for a file without stamps or with a damaged index.

## Library

- The player builds the database on the card (see Library rescan on the device); `tools/library_index.py` writes the same format on a PC.
- On the device, `app/library_store` opens the database through `hal_file_*`, puts a block cache in front, and validates it with `library_open`.
- Browse queries (`library/library_browse`) answer three questions for any view: how many rows there are, what row N is, and what selecting it opens. They read records and strings on demand and never load the database into RAM.
- Browse screens come from a fixed pool of 6 levels. They share one cache of the visible rows' text, which is refreshed in `update` (never during `draw`) whenever the visible rows change.

## Playback

- `hal/audio.h` is high level: `play(path, start, token)`, `queue_next(path, token)`, pause, resume, seek, volume and status. The backend decodes; on the device that's `board/audio.c` (see Device playback).
- Gapless: when a track starts, the player queues the next one with a new token. The backend switches without a gap and reports the new token, and `player_update` then moves the queue on and queues the following track.
- CUE tracks (format version 4, `docs/library-format.md`) are parts of one file. `hal_audio_play` and `hal_audio_queue_next` take a `HalAudioTrack` (path, `start_ms`, `end_ms` with 0 for the end of the file, token); `hal_audio_play` also takes an offset into the track, and `hal_audio_seek` and `HalAudioStatus.position_ms` count from the start of the file. The player converts: it remembers the start of the playing and of the queued track and reports, saves, resumes and seeks in the track's own time (`position_ms` in `PlayerStatus`, in `/.doublesharp/resume.bin` and in bookmarks is relative; `duration_ms` is the part's length). Everything above the player works on track indices and needs no change. A chaptered `.m4b` reuses the mechanism unchanged.
- The device engine (`device/audio_engine`) stops writing samples at the end of a track's range and then either continues in the same decode stream, when the queued track is the same file starting exactly where the range ended (no reopen, no seek: the next sample goes into the ring right behind the last, and the status switches token at that sample), or finishes the stream and opens the next track as before. Boundaries are sample-exact: a range ends at the sample `end_ms * rate / 1000`, the next one starts at `start_ms * rate / 1000`, and both come from the same millisecond value. A queued track that isn't the next part (shuffle, repeat one, Up Next) is opened and seeked like any other. The simulator reads the same ranges through its decoder (`platform/sim/sim_audio.c`).
- Known gap: the engine decodes up to a ring (8,192 frames) ahead, and queueing the track after the next one only happens once the next one has started. A seek inside a track during the last ring of audio before a hand-over drops the queued track, which stops playback at the end of the track (as it does for whole-file tracks).
- Shuffle is seeded (`core/random`). The resume file (`/.doublesharp/resume.bin`, `playback/resume_state`) stores the queue plan (source list, anchor track, shuffle mode, seed), the cursor, the track and the position, so the exact same queue is rebuilt after power-off. A library fingerprint rejects resume files from an older index.
- The player saves on start, on track change, on pause, every 15 s while playing, and in `app_stop()`.
- `playback` also has the storage for a queue edited entry by entry (`docs/stored-order.md`), a session journal that publishes the resume state, the songs queued by hand and that queue together (`docs/session-journal.md`), and saved mixtapes (`docs/mixtapes.md`), all on the block format of `docs/playback-store.md` and bound to the library's content fingerprint. The player does not use them: it writes `resume.bin` and `upnext.bin`, and of this code only the part of `play_queue` that reads a stored order is linked into the image.

## Equalizer

- **Settings:** `settings` holds the preset (Off, Retro, Bass, Heavy, Pop, Jazz, Unique, Custom) and the ten Custom gains, and turns them into a curve (`settings_equalizer_curve`): bands (frequency, gain in half-dB steps) and a pre-gain in Q15. Custom has ten bands at 31, 62, 125, 250, 500 Hz and 1, 2, 4, 8, 16 kHz; gains are `int8` half-dB steps (±20) end to end (`Settings.equalizer_gains`, `HalAudioEqualizer.gain_half_db`, `AMPLITUDE`/`POWER` tables of 41 entries). `HAL_AUDIO_EQUALIZER_BANDS` is 10, so the engine holds ten sections per channel. The presets are stock 2.0.0's, on their own grid of seven frequencies (63, 100, 125 and 315 Hz, 1, 3.15 and 10 kHz; `CURVE_HZ`, `PRESET_GAINS`), two to five bands each, with stock's pre-gains (Retro 21/32, Bass 7/16, Heavy and Pop 5/8, Jazz and Unique 7/16). Bands at 0 dB are left out, so Off and a flat Custom are an empty curve. `settings_store_apply_hardware` passes the curve to `hal_audio_set_equalizer`.
- **Headroom:** Custom's pre-gain (`settings/equalizer_peak`) follows the curve's actual peak: the cascade's response is summed in power over a grid of 78 frequencies that includes the ten band centres, on the 44.1 kHz warp, and the pre-gain is the inverse of the peak plus a margin for transient overshoot: 2 dB, and 0.35 dB more per dB of the deepest cut (5.5 dB at −10 dB), because a cut's phase shift lets a full-scale square wave overshoot the response. The deepest cut is the deeper of the deepest single band and the combined curve's trough, since neighbouring low cuts act as a shelf that clips square waves. Any non-flat Custom curve gets the margin, cuts included; a flat Custom has no pre-gain. The presets keep stock's pre-gains.
- **Saved curves and files:** `settings/equalizer_slots` encodes the eight saved slots (`/.doublesharp/eq_slots.bin`, 88 bytes: `EQSL`, eight records of ten gain bytes + 20 or `0xFF` for an empty slot, FNV checksum; reserved with the other small internal files). `settings/equalizer_fit` turns points (frequency, gain) into the ten gains: a streaming text reader (numbers paired per line; `#` comment lines; `Preamp` and other odd lines drop out by having an odd number count; frequencies outside 10–30000 Hz ignored) keeps, per band, the nearest point at or below and at or above its centre, and interpolates in log2 frequency (Q8); gains round half away from zero to 0.5 dB and clamp to ±10 dB. `app/equalizer_presets` owns the slots in memory and lists the `/EQ` folder of the music volume (card if present, else internal; at most 16 files, names under 28 characters, not starting with a dot); choosing a slot or file loads its gains into Custom.
- **Where it runs:** on core 0, in `device/audio_engine`, right after a run of frames is written into the music ring (24-bit samples, after `to_output`), in place, a band and a channel at a time (wrapping at the ring's end). That is the one point every source passes: FLAC and MP3 and M4A from core 1, and WAV and the FLAC fallback on core 0. Running it on core 1 would mean three decoder programs plus the core 0 paths. Stock runs its equalizer at the same point (the I2S feeder on core 0).
- **Bypass:** with an empty curve, or above 96 kHz, `equalizer_design` reports nothing to do and the engine never calls `equalizer_run`: the ring gets the same words as before the equalizer existed (`test_audio_engine` checks this against the decoded reference for 16-bit 44.1 kHz and 24-bit 96 kHz FLAC). Setting the same curve again (any other setting changing) does nothing, so the filters aren't restarted.
- **Filters:** `device/equalizer` runs each band as an RBJ peaking biquad, Q = 1/√2, in direct form I with Q28 coefficients, 32 × 32 → 64-bit multiply-accumulates, first-order error feedback (the fraction dropped from each output is added to the next sum, which keeps the low bands quiet near the unit circle) and a 24-bit clamp per band. The pre-gain is folded into the first band's numerator. `equalizer_design` computes the coefficients on the player whenever the output rate is set (a track start, a seek, a rate change), so every rate gets its own (stock used its 44.1 kHz set at 48 and 96 kHz): ω = 2π f / rate in Q30, sine and cosine from `audio_math`'s series, 10^(dB/40) from a 41-entry table, one 64-bit division per coefficient. A design clears the filter history; a gapless hand-over at the same rate keeps it. A new curve at the same rate (a Custom gain step) goes through `equalizer_retune`, which keeps the history of every band that is still there as long as the first band is the same, so a gain step does not click; a new first band starts the filter from silence.
- **Memory:** the coefficients and history live in `.high_ram` (`board/audio.c`); only the CPU touches them, and a design rewrites them before use, so an overlay overwriting them is harmless. The engine keeps the curve in `.bss`. The Custom EQ screen costs no RAM (see Screens and input).
- **CPU:** the inner loop is 30 Thumb-2 instructions per band and sample, 5 of them SMLAL, about 55–60 cycles per section, sample and channel by instruction count. Ten sections at 96 kHz come to about 110 MHz of core 0's 200 MHz (55 %); at 44.1 and 48 kHz the 16 kHz band is skipped, and nine sections come to about 45–49 MHz (23–25 %). The presets cost two to five tenths of that. Audio already runs core 0 at 200 MHz, the highest clock the firmware uses, so the equalizer needs no clock change, and with no music nothing runs. 176.4 and 192 kHz would need more than the whole clock, so they play unchanged. These figures are estimates: the load has not been measured on a player, and the 96 kHz case is listed in `known-issues.md`.
- **Tests:** `test_equalizer` compares the coefficients with the formula in double precision at 44.1, 48 and 96 kHz, measures the gain of sines at band centres (within 0.05 dB) and an octave above (matching its own rate, not 44.1 kHz's), plays full-scale sines through every preset and some extreme Custom curves without reaching the clamp, and checks that the channels stay apart and a design restarts from silence. `test_settings`, `test_stores` and `test_app` cover the curves, the file and the screens.

## Portrait mode

- Settings → Orientation (`Settings.orientation`, saved at byte 26) picks Landscape (480 × 222), Portrait or Portrait, flipped (222 × 480). `hal_display_set_rotation` (`HalDisplayRotation`, same order as `Orientation`) turns the panel: on the device `device/panel` sends the memory access byte for the rotation (`0x28` landscape; the landscape byte without the swap bit, with rows mirrored (`0x88`) for Portrait or columns mirrored (`0x48`) for Portrait, flipped) and puts the 49-line offset on the columns instead of the rows; the simulator and the test HAL resize their frame.
- The app keeps `app.theme` in step with the setting every step: `default_theme_set_orientation` swaps the theme's screen width and height and gives portrait a two-row header (a 20 px status strip above the 30 px title row, `metrics.status_height`), with the title allowed the full width. The Orientation choice sets the theme in `choose_orientation`, as Text size does, so the lists fit their rows when the previous screen returns; `app` then rotates the panel, forgets the frame hashes (`row_hashes` holds 480 rows) and builds the notice theme again. The strip renderer's buffer is the same 11,040 pixels in both: 23 rows of 480, or 49 rows of 222.
- Lists show up to `THEME_MAX_ROWS` (13) rows, the size of the browse and Up Next row caches, so Small text in portrait shows 13 rows. A list value is drawn in the small font and gets at most the room the name leaves, but never less than 40 % of the row (`list_view`).

Its title and artist go under the stack (`cover_stack_text`).
- The volume rocker turns with the screen: in Portrait the app swaps Vol+ and Vol− before the key tracker (`settings/rocker`), remembered per key from its press so a release matches. USB DAC mode and the headset remote are not affected. The crash screen goes back to landscape before it draws.
- Not adapted: the frame time overlay (off screen).
- Tests: `test_panel` (windows and memory access bytes), `test_settings` (byte 26, version 9 files), `test_rocker`, `test_theme_layout`, `test_header`, `test_menu_screen`, `test_list_view` and `test_cover_flow` (portrait theme, header, panel below, narrow values, stacked quads), `test_board_layout` (portrait layouts fit the screen at every text size) and `test_app` (the turn, redraw, restart, rocker, Home, Now Playing and Cover Flow in portrait).

## Cover Flow

- Now Playing shows the playing album's full cover (112 px) on the left, below the header, with the text, progress and times in a column to its right. It loads the cover through the same `CoverCache` full slot in `update`. Without a cover it keeps the full-width text layout. In portrait the cover is centred under the header, with the text lines, the progress bar and the times in one full-width column below it (`BOARD_LAYOUT.now_playing_portrait`).

- Albums run by album artist, then by year, the same order as Album Artists. The screen reads each position straight from the album artists' links (`docs/library-format.md`), so it holds no album list and shows every album.
- `ui/cover_flow` holds the geometry and the motion, in fixed point (256 = one cover). The center cover is flat and 112 px. Neighbours are 42 px wide trapezoids, 84 px tall on the side facing the center and 64 px on the far side, spaced 32 px apart. Between those positions, every measure is interpolated, so a cover grows and flattens as it slides in. The position eases toward the selected album with a 70 ms time constant, at no less than about 4 covers per second, and never overshoots.
- Covers are drawn farthest first, so nearer covers overlap them. `gfx/image` draws a cover column by column with nearest-neighbour sampling, clipped to the current strip.
- `app/cover_cache` holds 7 half-size covers (56 px, 6,272 B each) for the center ±3, in slot `position % 7`, plus one full-size cover (112 px, 25,088 B) for the center, about 69 KB in total.
- Covers load in `update`, one per frame: the nearest missing half cover first, then the full cover once the motion has stopped. A cover is drawn from the full image when that's loaded for its album, otherwise from the half image, otherwise as a placeholder. Beyond ±3, covers that aren't loaded aren't drawn.
- Play opens the album's track list, a long Play toggles the favorite, and Back leaves. The screen is full screen: no header or status icons, and the title (★ for favorites) and album artist go under the cover. The first time it opens, it starts at the playing album, or at the first album.
- Position 0, before the first album, is **Random album**: its cover is a 48 px shuffle mark drawn once into a static image (white crossing arrows on dark slate), and its text is "Random album" / "Play any album". Play there picks one of the music albums with `core/random` seeded from the microsecond clock, plays it from its first track in track order (shuffle off for that queue), moves the flow to that album and opens Now Playing. The albums sit at positions 1 and up, so the cover cache slots and the playing-album lookup are offset by one.

## Rendering

The panel keeps its own image memory, so we never hold a full framebuffer. The strip renderer clears a 480×23 buffer (`BOARD_STRIP_HEIGHT` rows of the board's width; 49 rows of 222 in portrait), asks the current screen to draw into it, pushes it to the display, and moves on to the next strip. Before pushing, `gfx/frame_diff` compares a hash of every row (FNV-1a over pixel pairs) with the previous frame's (1,920 bytes for up to 480 rows), and only the span of changed rows in each strip goes to the display. An unchanged frame sends nothing, and moving a selection sends a few rows. `app_start` forgets the hashes, so the first frame is always sent whole. After the screen, the app draws the status icons (play state on the left of the header, battery on the right, both inside the header insets), the toast and the frame overlay. The overlay shows the average frame time and its split: u (input, player and screen update, including card reads), d (drawing and hashing) and s (sending to the panel). The renderer clears every strip to the theme background, so screens don't fill it again. Screens marked `full_screen` (Cover Flow) get no status icons. While the start-up or goodbye fade runs, the app draws only the fade (centred text in the title font, blended from the background to the text colour) and drops key events. `app_show_splash` starts the 1.1 s "Doublesharp Echo" fade after `app_start`. While a track plays, turning the screen on pushes Now Playing, unless the top screen sets `stays_on_wake`. Idling in a menu never leaves it. Pushing or popping a screen by key slides it (`ui/slide`, 240 ms, cubic ease-out): the title bar stays and switches its title halfway, and both screens are drawn shifted below it through `canvas_shifted`; if either screen is full screen, the whole screen slides. Waking into Now Playing doesn't slide. Browse levels keep two row caches so both sides of a slide have their text. A long Power press saves the session at once, shows "Goodbye" fading out over 1 s, then turns off. With the screen off it turns off straight away. Drawing uses screen coordinates and clips to the strip. Lists skip rows outside the strip, and glyphs outside the clip are culled. The strip buffer is 22 KB where a full framebuffer would be 213 KB.

## Boards

The board is the full-size Snowsky Echo (480×222, 221 ppi, six keys). Presets: `dev` (simulator and tests, `build/dev`), `device` and `release` (device images). `identity.json` holds the full name (Doublesharp Echo: the USB product name and the splash), the short name (Doublesharp: the Home title), the 8-character identifier (`DBLSHARP`: the image brand and the USB storage vendor) and the version (1.0.0); the build, the C code and the tools read it. The image is always named `DBLSHARP.IMG`. There is one board: Podium removed EchoPod's Echo Mini board when it forked.

- `hal/display.h` takes `HAL_DISPLAY_WIDTH` and `HAL_DISPLAY_HEIGHT` from the board.
- `app/default_theme.h` offers `BOARD_THEME`, `ECHO_THEME` (22 px Inter SemiBold titles, 22 px Inter Regular body, 16 px small text, 22 px SemiBold header title; 30 px header, 32 px rows, six rows visible). The app and its tests use `BOARD_THEME`.
- **Text size** (Settings → Text size): `default_theme_set_text_size` sets the theme's title and body fonts, row height and `metrics.text_size`. Small is Inter 18 px in 24 px rows (eight rows), Medium is `ECHO_THEME` unchanged (22 px, 32 px rows, six rows), Large is Inter 26 px in 38 px rows (five rows). The header (30 px, its own `fonts.header`, 22 px SemiBold), the 16 px small text (status bar, Now Playing details, Bluetooth hints) and the content area stay the same at every size. Choosing a size changes the app's theme at once; menus and browse lists fit their rows to it when they are shown again (`list_view_fit` in `enter`), keeping the selection on screen, and every other screen reads the theme when it draws, so no restart is needed. Toasts are capped at the screen width; longer text ends in an ellipsis, as everywhere.
- `app/board_layout.h` holds `BOARD_LAYOUT`, the per-board positions the screens read: Now Playing lines and Cover Flow text per text size (`board_now_playing_layout`, `board_cover_flow_text_layout`, picked by `metrics.text_size`), Cover Flow geometry, the Home art panel width and the Up Next detail width. `BOARD_STRIP_HEIGHT` sets the strip renderer's height in landscape (23 rows, where the last of ten strips is shorter); portrait uses the same buffer as 49 rows of 222 pixels. Portrait has its own Now Playing and Cover Flow tables (`now_playing_portrait`, `cover_stack`, `cover_stack_text`) and the Home art panel's minimum height. Covers stay 112 px; the Echo Cover Flow draws the centre cover at 128 px.
- `extra_ranges` in `fonts.json` adds code points to a font's built-in table: the 22 px fonts hold Latin-1 themselves, so each of them reads only the rest from its own glyph face.
- `test_board_layout` checks the active board's theme and layout at every text size (rows, line fit, no overlap, on-screen covers, Medium equal to `BOARD_THEME`); run it under both presets.
- `tools/target_audit.py --define ECHO_FONTS_PACKED` audits the device build's source; `ctest` runs it as `target_audit`.
- The 18, 22 and 26 px fonts are `"packed": true`: a device build (`ECHO_FONTS_PACKED`) keeps only space and `?` in their tables and reads everything else from their glyph faces (`glyph_pack.json` face numbers 2 and 3 for 22 px, 4 and 5 for 18 px, 6 and 7 for 26 px, regular then SemiBold; each holds the same ASCII, Latin-1, Cyrillic and punctuation). `FONT_PACK_FACES` is 7 and `FONT_PACK_MAX_BITMAP` 320, since the largest 26 px glyph (SemiBold `@`) takes 312 bytes; a slot is 336 bytes and the cache still holds 128 glyphs: 32 sets of 4 slots. Host builds keep the full tables. Because glyph reads stop once an install has rewritten the firmware, notices (`NOTICE_THEME`) use the built-in 16 px font, and once `hal_system_restart_pending` is true the app draws every screen, the status bar and the toast with `NOTICE_THEME` too (`board_theme` in `app.c`); the device app restarts after an install so the screens are built with it.

## Echo board on the device

- **Panel:** `board/panel_vop.c` drives the ST7796S through the SoC LCD controller (`device/vop`, registers at `0x60070000`, clock gate `0x7F`, reset `0x0D`, GPIO0.15–25 on function 1, GPIO2.15 reset pulse 50/150/30 ms). The bus timing register (`+0x08`) follows the CPU clock: a 20 ns write strobe and a 70 ns cycle rounded up to whole cycles, `0x1021` at 24 MHz (stock's fixed value), `0x1044` at 96 MHz, `0x1089` at 200 MHz, rewritten after every clock switch; Podium's author reports that stock's fixed `0x1021` at 96 MHz left the first image as noise on the panel. Commands and parameters are written in command mode (control `0x800`), pixels in pixel mode (control `2`, one 16-bit write per RGB565 pixel, the busy bit polled every 4 pixels). `device/panel` holds the init stream (memory access control `PANEL_ECHO_MADCTL` = `0x28`, the stock value; `-DECHO_PANEL_MADCTL=0x68` mirrors the columns) and the window rule: columns are x, rows are y + 49.
- **Backlight:** the PWM runs at 25 kHz (`BACKLIGHT_HZ`).
- **Pins:** `device/board_pins` holds the per-board pin facts: DAC mute on GPIO2.1 and no DAC reset pin, the power pair GPIO0.14 and GPIO2.0 (driven high at start-up and whenever the screen turns on, low before power-off), and the 4.4 mm jack reading high when plugged. The jack pull-ups are set at start-up.
- **Storage:** `emmc_layout_read_with(..., EMMC_SLOT_2_SEARCH)` finds slot 2 as stock does: from the next MiB after slot 1's firmware size plus 16 KiB, in 1 MiB steps, up to 20 tries, taking the first header with `RKnanoFW` and a matching header copy. A slot found past half of the firmware area, or no slot, leaves slot 2 at half of the area. The slot length and the write fence are unchanged.
- **Updater:** the check accepts Doublesharp images (brand `DBLSHARP`, the 5 MiB shape) and FiiO's stock Echo image (39,845,892 bytes, magic, brand `Rockchip`, fw size `0x025CC000`, header copy, CRC over the first 38 MiB, marker `ECHOV100IMG` and neither Echo Mini marker) as `UPDATE_STOCK`, and refuses images with any other brand, Podium's and EchoPod's included, and the Echo Mini's stock image. A stock install writes the 38 MiB into both slots, slot 2 first. `device/update_names` gives the file names: `/DBLSHARP.IMG`, and FiiO's `/ECHOVnnn.IMG` names so that FiiO's image can be restored.
- **Update file:** after a successful install, for a file refused as invalid and for one that is already installed, `update_after_usb` deletes the update file (`updater_should_remove_file`); a failed install keeps it. The loader request file is zeroed, not deleted.
- **Loader request:** at start-up `update_check_loader_request` looks for `/MASKROM.REQ` on internal storage. A file that starts with `MASKROM REQ` has those 11 bytes overwritten with zeros (so it fires once) and, if the write read back, the player reboots into the boot ROM's USB loader (`board/loader_reboot.c`, which also clears the boot ROM's loader flag at the next start). See `docs/device-recovery.md`.
- **Boot order:** glyph faces are attached before the low-battery check, so the 22 px text exists from the first frame.
- **Stock's boot guard** (power off at start unless USB power, the power key or `NanoCRebootFlag`) is not used; `board_power_hold` keeps the guard inherited from EchoPod (a USB-only start is a charger start).

## Generated code

- `src/library/sort_fold_table.{c,h}` is generated by `tools/fold_table.py` from Python's `unicodedata`: for each code point in Latin, IPA, Greek, Cyrillic, Latin Extended Additional, Greek Extended, punctuation, letterlike and number forms, enclosed alphanumerics, kana, CJK compatibility ideographs, ligatures and fullwidth/halfwidth forms, the NFKD-decomposed, mark-stripped, case-folded text the PC indexer's `sort_key` gives it. `library/sort_key` applies it (plus Hangul syllable decomposition and ASCII lowercasing), trims Unicode whitespace and drops a leading "the ". Regenerate with `.venv/bin/python tools/fold_table.py --output src/library --style .clang-format`; `sort_fold_up_to_date` checks it.
- `src/fonts/` is generated by `tools/font_build.py` from `assets/fonts/fonts.json` and the TTFs in `assets/fonts/`, and `src/fonts/packs/` by `tools/glyph_pack.py` from `assets/fonts/glyph_pack.json`. Never edit either by hand.
- Fonts are Inter (SIL OFL 1.1, license in `assets/fonts/inter/OFL.txt`), pre-rendered to 4-bit coverage. The built-in tables in `fonts.c` hold ASCII and common punctuation only. Everything else comes from glyph packs, read on demand (below).
- Regenerate with:

  ```sh
  .venv/bin/python tools/font_build.py --config assets/fonts/fonts.json --output src/fonts --style .clang-format
  .venv/bin/python tools/glyph_pack.py --config assets/fonts/glyph_pack.json --output src/fonts/packs
  ```

- The `fonts_up_to_date` and `glyph_packs_up_to_date` tests fail if the committed output differs from a fresh build.
- **Glyph packs:** `assets/fonts/glyph_pack.json` lists the faces in face order (face 1 first): the Latin-1 letters (U+00A0–U+00FF) of the 16 px font (about 7 KB), then the two 22 px faces, the two 18 px faces and the two 26 px faces (23–47 KB each, 212 KB for all seven). Each `Font` has one 1-based `pack_face` (0 for none). `font_find_glyph` tries the built-in table, then that pack face, then `?`.
  - A face is one blob: a 32-byte header (`EGLF`, version 1, entry size 12, 42 entries per index sector, glyph count, directory, index and data offsets, size, and the image CRC of the rest), then at `0x200` a directory with the first codepoint of every index sector, then index sectors of 42 sorted 12-byte entries (codepoint, width, height, left, top, advance, 0, bitmap offset) padded to 512 bytes, then the bitmaps, packed as in `fonts.c`. A glyph whose bitmap passes the face's limit (96 bytes; 256 for the 18 and 22 px faces, 320 for the 26 px faces) is dropped; none is.
  - `gfx/font_pack` reads them through a `FontPackReader` (face, byte offset, length) into memory the platform hands over: the face headers and directories (up to 8 index sectors each), one index sector, and a 4-way set-associative cache of slots (a glyph plus its bitmap: 336 bytes). A lookup costs the index sector and the bitmap on a miss (the header and directory once per face), and nothing on a hit. Misses are cached too, so a character no face has is read once. A glyph from a pack stays valid until the next lookup; text drawing resolves its bitmap once per glyph (`font_glyph_bitmap`), not per pixel. The memory must be 4-byte aligned; the number of sets is a power of two.
  - Device: `tools/make_image.py --glyph-face` (one per face, in face order; a missing file is an empty face) places the faces largest first into the image's free space (`0x30000`–`0x200000`, `0x2C0200`–`0x43C000`, `0x218000`–`0x240000`, `0x260200`–`0x280000`), sector-aligned, and writes a table at `0x2C0000` (`EGPT`, count, then offset and size per face). `board/glyphs.c` reads the table from slot 1 at boot, before `app_start`, and reads faces through a one-sector buffer. Its table, sector buffer and the 51 KB cache memory (0.6 KB of face state, then 32 sets of 4 slots of 336 bytes: 128 glyphs) sit in `.glyph_ram` (`0x03092000`–`0x0309EFFF`, the top of High RAM): `board/overlay.c` and `rescan_overlay.ld` cap the rescan overlay at `0x18000` bytes (it is 88,404), so a rescan never overwrites the cache. After an update, until the restart, reads are refused (glyphs already cached still draw; others show `?`), like the rescan overlay and the core 1 programs.
  - Simulator: `platform/sim/sim_glyphs.c` loads `src/fonts/packs/<face>.bin` (paths from `glyph_pack.json`, through CMake) into memory and hands the same 52 KB of cache over. `test_sim_glyphs` checks the committed packs through it.

## Memory

- No heap in `src/`. Every buffer is static and sized at compile time.
- `src/` is freestanding C11 and includes only `<stdint.h>`, `<stdbool.h>` and `<stddef.h>`.
- The `target_audit` test cross-compiles `src/` for Cortex-M3 and reports flash and static RAM per module. It fails on any heap symbol and when static RAM exceeds `ECHO_APP_RAM_BUDGET_BYTES`.
- No recursion and no VLAs. The device stack is 16 KB.
- Data RAM: `.data`, `.bss` and `.noinit` come to 264,168 bytes in the `release` build and 268,468 in `device`, 23,128 and 18,828 bytes below the `0x0304A240` limit (see Image rules); the size report prints this after every image build. The `device` build's extra 4.2 KB is the debug loop (see Debug loop). The USB sessions and the updater keep their variables in the USB overlay's own zeroed memory, not here. The equalizer's filter state lives in `.high_ram`, since only the CPU touches it and a design rewrites it before use.

## Code rules

- No comments in any code: C, CMake or Python. Names and small functions carry the intent. Prose belongs in `docs/`.
- Names:

  | Kind | Style | Example |
  |---|---|---|
  | Types | `PascalCase` | `KeyTracker`, `FrameStats` |
  | Functions and variables | `snake_case`; public functions prefixed with the module | `key_tracker_update` |
  | Constants and enum values | `UPPER_SNAKE_CASE`, prefixed | `KEY_GESTURE_PRESS`, `FONT_INTER_REGULAR_16` |
  | Files | `snake_case`, named after the module | `key_tracker.c` |

- Functions:
  - do one thing
  - stay short (aim for under 20 lines)
  - take at most 4 parameters; group anything more into a struct (`Label`, `TextStyle`, `MenuConfig`)
- Pass small value types by value and anything larger by pointer. Use `const` wherever data is read-only.
- No mutable globals in `src/`, except state owned by the composition root (`app.c`). Platform singletons live in `platform/`.
- Every rule in `core`, `gfx` and `ui` has a unit test. Test names describe the behaviour.
- `clang-format` (`.clang-format`) defines formatting. Warnings are errors (`cmake/project_options.cmake`).

## Echo image emulator test

`tests/emulator/test_echo_image.py` runs the finished `device` image (with `echo_device.elf` and `echo_usb_overlay.elf` for symbol addresses) in a Unicorn Cortex-M3 emulator (`tools/echo_emulator`, `unicorn` in `tools/requirements.txt`) before anything is flashed to a player. Each scenario is its own ctest, `device_image_boot_<scenario>` (label `echo_image`); it needs the `device` build and `.venv` and skips (exit code 77) when the image, the ELF or `unicorn` is missing. Together the scenarios take about a minute with eight jobs. Run it by hand with `.venv/bin/python tests/emulator/test_echo_image.py [--image IMG] [--elf ELF] [--usb-overlay-elf ELF] [Class.test_name]`. A function the test names must exist in one of the two ELFs, or the test fails. The USB overlay's addresses are also used by the rescan overlay and the decoder, so a name in it counts only while the window holds exactly the overlay stored in the image.

The emulator loads the image as the boot ROM does: each pair of load-table rows copies code and data to their exec addresses and zeroes bss, then the stack and reset vector come from `0x03004000`. The player then runs its own start-up code unchanged. A fake eMMC (`SparseDisk`) holds the IDB blocks (system size 96 MiB), the image in slot 1 and in slot 2 (`0x2800` sectors after slot 1) and a 300 MiB FAT32 user volume that the test fills with files (or, for the realistic scenarios, `tools/echo_emulator/real_volume.py`: 3480 MiB FAT32 with FSInfo, 4 KiB or 512 B clusters, seven 330 MiB FLAC images with CUE sheets, a `.Spotlight-V100` with 1,500 entries, macOS dot files). Scenarios:

- **Normal boot:** the ST7796S init stream equals the table in the test, every window stays inside columns 0-479 and rows 49-270 with exactly width × height pixels, the first sweep is the black clear (111 windows of 2 rows, 106,560 pixels), the second the first lit frame (10 windows, 106,560 pixels, every pixel painted), and a third full frame is the home screen. GPIO2.6 goes high before GPIO0.14 and GPIO2.0 and stays high, GPIO2.1 is never driven, the backlight PWM period gives 25 kHz at the live pclk and starts only after the first lit frame, the watchdog runs and is kicked, no fault, panic or power-off symbol is reached, and not one eMMC sector changes.
- **Loader request:** `/MASKROM.REQ` starting with `MASKROM REQ` is zeroed in place (one write, inside the user volume), then the boot-ROM flag `0xFFFF18AF`, the GRF boot select and `SYSRESETREQ` follow and no frame is drawn; other text leaves the file alone and the player boots.
- **Update:** with VBUS raised after the first frame and a host reset pending, then the cable pulled and a key pressed at "Unplugged before ejecting", a Doublesharp image with a newer date in `/DBLSHARP.IMG` is installed. Writes go only to the two 5 MiB slot ranges, all of slot 2 before slot 1, each slot starts with `0xFF` over its first 8 KiB and ends with its header chunk, every write is read back sector by sector, both slots equal the new image afterwards, and the installed slot 1 boots in a second emulator. The image already installed is not written again. An image with another firmware's brand (valid CRC) and a file of the Mini stock size are refused with no write; `updater_install` is never reached. `updater_check`, `updater_install` and `usb_session_storage_changed` are in the USB overlay, so these scenarios run its code.
- **USB overlay:** a session loads the overlay from slot 1 and the update check runs inside the window; a second session after it reads nothing from storage (the copy in the window is reused), although the first one had to load over the rescan overlay; with slot 1's copy damaged the session runs from slot 2's; with both damaged the player shows "USB code missing: reinstall the update", powers USB down, executes no instruction in the window, leaves the window zeroed and the update file in place, and writes nothing outside the user volume.

- **Deep CUE track** (`real_volume(playable=True)`: two 330 MiB albums whose FLAC images are generated frame by frame by `flac_image.py`, 12 CUE tracks each; `playback.Rig` presses keys through Music → All Songs): starting track 12 must put the first sample into the ring within 1.5 s, the volume fade-in must finish within 1.5 s, the main loop must never go quiet for 1 s, a second of playback may read at most 40 FAT sectors while it reads at least 250 data sectors, then a skip, Back and scrolling a list must leave no ring underrun, no stall panic and no gap above 1 s. `audio.py` replaces the DAC, DMA and core 1 hardware with stubs (the DMA position follows emulated time at the stream's rate; core 1 is declined, so the software FLAC decoder runs). The stub replaces `dac_path_start`, so the DAC identification read never runs in the emulator and Settings → About → DAC A and DAC B stay at `Play a track`.

- **Debug report** (see Debug loop): the first USB session creates `/.doublesharp/debug/report0.txt` and writes it after the session starts and before the host is served, entirely inside the user volume; the report names the build, an unread value reads `unknown`, and the profile is off and empty. A second session reports the first session's end. A long Power press writes a `shutdown` report between `hal_power_off` and the power cut, loading the USB overlay for it; with USB power the same press writes it on the way into charge mode. A report from the first seconds after a cold start goes into a second file, names the start-up battery sample as such, and the next one like it replaces it while the earlier report stays byte for byte. With USB sense switched to Kept by key presses, the end of a session writes the soft disconnect and none of the power-down words. With the Profiler row switched on by key presses, the next report's histogram adds up to its sample count, splits into code and idle time, and `tools/echo_debug.py` turns it into time per function with the image's ELF.

Emulated time is continuous across clock changes; the watchdog resets the machine when not kicked within its timeout (counted, and a test failure); eMMC commands take 250 µs plus 25 µs per extra block for reads and 0.9 ms plus 70 µs per block for writes. Scenarios added: an update file installed once and gone afterwards (also after restoring an older build), refused and already-installed files removed, CMD18 always followed by CMD12, and cold boots on the realistic volume (4 KiB clusters; 512 B clusters with a stale FSInfo hint) that must light the screen within 1 s, listen for USB within a second of the cable, stay under the main-loop gap limit and never reset the watchdog.

Speed: emulated time is counted in instructions (one cycle each, in slices of 4,000), so Unicorn's instruction counter runs on every instruction, and it is fast only while it is the one code hook. The emulator therefore watches a named function with a block hook on its entry address, which fires when a call or branch starts a translation block there. A slice that ends exactly on such an entry has already run its hook, so the resumed slice skips it once; a stubbed function returns through a one-instruction pad and so still costs one counted instruction. Cycle counts and storage accesses of every scenario are the same as with per-address code hooks. Only `count_window_code` keeps a code hook, in the two USB overlay scenarios that count instructions in the window. A `wfi` ends the slice, and so does each `board_input_take_key_press`, the poll `board_wait_for_key` spins on without reading the clock: a pass of that wait then costs one slice of emulated time instead of the few instructions it executes. `test_a_key_wait_that_spins_ends_like_one_that_rests` keeps that honest: it runs a refused update with the rest and with the real spin (`rest_in_waits=False`) and requires the same storage accesses, the same functions reached, the same sectors changed and the same emulated time within 1 ms, with the spinning run polling at least ten times as often.

Emulated hardware is minimal: GPIO ports, GRF and CRU (write-masked registers, PLL always locked, the clock rate follows the PLL registers), PMU boot flag, SysTick (delivered as a software exception between 4,000-instruction slices, and a read of the counter or `ICSR` advances time so delay loops end quickly), SARADC (no key, 4,000 mV battery), PWM, watchdog, VOP, DW-MMC for eMMC (CMD0-18, 24, 25; data commands complete at once) and for the SD slot (no card detected), and the DWC2 core as plain registers with soft reset and flush bits self-clearing, a bus reset raised on connect and VBUS dropped 40 ms after the firmware acknowledges it. Any other register in `0x40000000`-`0x7FFFFFFF` is a plain read-after-write page and is listed as unmodelled. Not covered: USB enumeration and mass storage (no SETUP or bulk traffic), the DAC, I2S, DMA, UART and key presses beyond one Play press, SD cards, and playback. The second core is only RAM (`0x01000000`, 384 KB), enough for the rescan overlay's working memory. With no SD card the player mounts the synthetic eMMC's user volume and builds its files and library there. The Mini stock image refusal is checked by size only: the marker check needs a CRC pass over 38 MiB, which takes minutes in the emulator.

## Device platform

`docs/hardware.md` summarises the hardware these drivers talk to.

- `platform/device/logic` holds the driver logic that doesn't touch hardware, so it builds and is tested on the host too:
  - `key_ladder`: ADC bands to keys
  - `key_scanner`: debounce over two samples, a transition queue, and ignoring the Power press still held from switching on
  - `headset_remote`: the wired headset's buttons from ADC channel 2 (`hardware.md`): stock's bands, debounce over two samples, a tap of volume up or down for the volume, a 400 ms hold to skip, play taps counted until 300 ms pass (1 play/pause, 2 next, 3 previous), nothing for a held play, no remote at all for a plug that reads only play for its first 500 ms, or a remote that reads play for over 1 s (a 3-pole plug, also after a swap the jack debounce missed), until the line leaves the play band for 500 ms; `headset_monitor` joins it with `headset_dips` for the Headset row in Settings → About, and nothing until a 3.5 mm plug has been in for 500 ms. `board/input.c` reads the channel every fourth scan (every 20 ms) and passes the jack state, which counts only while audio isn't routed to Bluetooth; `hal_input_next_headset_command` hands the commands to the app, which runs them on the player from any screen without waking it, as the background keys
  - `panel`: the init streams for both panel variants, and the window and pixel commands, sent through a `PanelBus`
  - `tick_clock`: milliseconds and microseconds from the 24-bit SysTick down-counter
  - `sd_card`: the SD setup protocol (v1 and v2 cards, the ACMD41 retries, the RCA, capacity from the CSD register, the 4-bit bus), driven through an `SdHost`
  - `vop`, `board_pins`, `update_names` and `loader_request`: the Echo board's LCD controller access, per-board pin facts, update file names and the loader request file (see Echo board on the device)
  - `emmc_layout`: finds the firmware slots (from the IDB's system size) and scans for the user volume on internal storage. It also answers whether a sector range lies inside the user volume (`emmc_layout_in_volume`, used for volume-relative reads and writes) and which internal-storage writes are allowed: only the user volume and the two firmware slots, never the IDB, the SAVE block or the gap
  - `bt_module`: the Bluetooth module's command protocol. It waits up to 5 s for the `CV1` ready report, sends `CS00` to scan (once more after 4 s if nothing answers, `CP00` after 30 s), collects `CS` scan results until `CSEN` (dropping unnamed ones; a new scan keeps the earlier results, marks in `found_now` the ones it finds again, and past 6 drops the oldest; `CP00` stops a scan early), and sends `CQ00` every 3 s while ready, scanning or connected, every second while a connect runs and every 0.5 s while a paired reply waits for the link (stock's Bluetooth screen polls in every state). Connecting sends `CL06` + the picked address, from Ready or during a scan (once more as `CH06` after 4 s if nothing but `CQ` answers arrived, `CT00` and a failure after 30 s); `CLOK` means paired, `CLER`/`CHER` failed, `CHOK` connected, `CQO` + address + name connected in any state, including while a connect runs, any other status letter while connected or `CT`/`CTOK` means the link dropped. Disconnecting sends `CT00`. While connected, starting the stream sends `CY0` + `1E` + 0 and stopping it `CY0` + `00` + 0. As in stock, the `C` `86`/`87` notices only answer the module's own reports: the play state is what the module last reported (`CP` paused, `CC` playing; nothing on a new link). Starting the stream after a `CP` sends the play notice `C` `86` `30 30` 0 first and `CY0` + `1E` + 0 100 ms later; stopping it after a `CC` sends the pause notice `C` `87` `30 30` 0 first and `CY0` + `00` + 0 100 ms later; otherwise only the `CY0` frame goes out. (Sending a notice on every pause and resume, with the play notice after `CY0` `1E`, left the headphones silent a moment after some resumes.) Every new link first gets `CY0` + `00` + 0. The module's `CP`/`CC` (pause/play) and `CA`/`CB` (previous/next) reports count presses in `HalBluetoothRemote`; a `CP`/`CC` after `CLOK` also counts as the link coming up (the Buds send them as soon as they're in the ears), and while connected `CQ00` polling pauses for 50 s after one, as in stock. A dropped link, `CT` or `CTOK` ends the stream and clears the pairing result. While the stream is on, `board/bluetooth.c` holds GPIO2.0 high and GPIO2.14 low on every service pass, as stock does on connect, and restores them when the stream stops or the module powers off. Received bytes are split into frames as soon as a frame is complete; an incomplete frame is dropped after 2 ms of silence. It also keeps the last 12 bytes, counts bytes and frames, and logs the last 12 messages (frames other than `CS` and repeated `CQ` letters, plus the `CS`, `CP`, `CL`, `CH` and `CT` commands it sent) with the seconds between them; the log and the devices found survive a power-off and power-on, so a restart keeps the evidence
  - `usb_device`: the descriptors and standard requests for a bulk-only mass-storage device (`1209:0001`, the pid.codes test ID), plus GET_MAX_LUN and the mass-storage reset. Full speed only (64-byte bulk packets; the device qualifier and other-speed configuration stall) until the board allows high speed; then it serves a device qualifier and an other-speed configuration (type 7, the opposite speed's configuration), and the configuration's bulk packet size follows the speed the board reports (512 at high speed, 64 at full speed; EP0 stays 64)
  - `usb_audio`: the USB Audio Class 1.0 device for DAC mode (`1209:0002`, the next pid.codes test ID, so hosts don't mix up its cached descriptors with mass storage's): the device and configuration descriptors, interface alternate settings, the sampling-frequency and feature-unit class requests, and the FIFO split. Everything else (address, configuration, status, strings) goes to `usb_device`. See USB DAC mode
  - `usb_audio_sink` and `stream_drift`: USB audio packets into the music ring, and the ring-level controller that keeps it near 20 ms of audio (see USB DAC mode)
  - `msc`: the bulk-only transport and SCSI commands over up to two LUNs. INQUIRY gives the firmware id as the vendor and the firmware's major.minor version as the four-character product revision (`1.0 ` for 1.0.0; `FIRMWARE_REVISION`, derived from `identity.json` by the top-level `CMakeLists.txt`). A reply shorter than the host asked for is padded with zeros and reported in the residue instead of stalling. Ejecting a LUN marks only that LUN absent. Given a buffer (`msc_use_write_buffer`), WRITE(10) data collects there and reaches the drive in one write call per full buffer, plus one for the rest; a failed call fails the whole command. Without one, each sector is its own write. READ(10) uses the same buffer the other way: when the next sector isn't loaded, one drive read fetches as many sectors as the command still needs, up to the buffer (64 sectors, 32 KB: one multi-block CMD18 on the card), and the bulk IN packets are served from it. Reading one sector per command held reads over USB at about 1.2 MB/s
  - `usb_fallback`: when to give up on high speed: watching starts at the first bus reset of a high-speed session, a working session (configured and through two SCSI commands) stops it, and 10 s without one asks for a full-speed reconnect, once
  - `card_write`: the order of a card write through a `CardWriter`: one block is CMD24 then a wait for the tran state; several are one CMD25, then CMD12 (sent even after a failed transfer, so the card leaves the receive state), then the wait, which is skipped if the stop failed
  - `image_crc` and `updater`: the image check and the slot writer. The updater has no buffers of its own: `updater_use_scratch` hands it 18 KB (two 8 KiB chunks and the header prefix), on the player the mass-storage write buffer, which is idle once the session is over; without it the check answers invalid and the install fails before any write. The check accepts our 5 MiB shape (size, magic, fw size `0x44C000`, header copy, trailer CRC, fits a slot) and reports an image already in slot 1 as installed. It also accepts FiiO's Echo stock image as `UPDATE_STOCK` (see Updater above; the CRC pass scans every 8 KiB chunk for the stock markers, including one split across two chunks) and writes it the same way, as stock's own writer does. The install fills slot 2, then copies slot 2 into slot 1. For each slot it first writes `0xFF` over the first 8 KiB, then every other 8 KiB chunk, then the first chunk last. Chunks that already match are skipped, and every write is read back. One slot is complete at every moment
  - `fat`: a read-only FAT16, FAT32 and exFAT reader over a `BlockDevice`. It reads unpartitioned cards or MBR partition 0, follows FAT long names and exFAT name entries (UTF-16, including surrogate pairs), matches path components exactly by code point and ASCII letters in either case, and reads at any offset. FAT files follow a per-file cluster cursor for short forward steps, and the file HAL gives each open file an extent map (`fat_attach_extents`, 32 entries): the first read that jumps backward or more than 128 clusters ahead scans the file's cluster chain once, in multi-sector reads, into contiguous runs, so any later position is found without touching the FAT. A file with more than 32 runs keeps a checkpoint every `clusters / 32` clusters instead and walks at most that far from the nearest one. Lookahead for multi-sector reads never moves the cursor. exFAT files marked NoFatChain are contiguous and skip the FAT. Cluster walks and directory scans are bounded, so a corrupt chain can't hang the player
- `platform/device/board` is device-only. It holds the register helpers, GPIO and pin mux, startup (the vector tables and its start-up steps), the linker script, a minimal `memcpy`/`memset`, and the HAL implementations.
- `platform/device/core1` is the program for the second core: its own startup, `main` and linker script (code at core 1 address 0, data at `0x01021000`, stack top `0x0102E000`). It builds to `core1.bin`, which is linked into the core 0 image as read-only data. `device/core1_control` holds the power-up, start and stop sequences and the shared-block layout, tested on the Mac; `board/core1.c` runs them.
- **Build:** `cmake --preset device && cmake --build --preset device` cross-compiles to `build/device/platform/device/echo_device.elf`. Then `tools/make_image.py` packs it into `build/device/DBLSHARP.IMG`. The outer header is written from format constants (magic `0x76543210` at `0x00C`, `4` and four `0x200` words at `0x050`–`0x06C`, `1` at `0x19C`, the fw size at `0x1F4`) plus our date, brand, build tag, fw1 end at `0x080` and the version from `identity.json` (major << 24 | minor << 16 at `0x004`, patch at `0x008`), with an empty part chain and zero marker bytes, so the image builds from the repo alone.
- **Release build:** `cmake --preset release && cmake --build --preset release` builds the same image into `build/release/DBLSHARP.IMG` with `ECHO_RELEASE=ON`, which links `src/app/diagnostics_menu_release.c` (Firmware, Battery, Jack 3.5, Jack 4.4, Music, Headset, CPU clock) instead of the full developer menu in `diagnostics_menu.c`. The rows both menus share live in `diagnostics_rows.c`. `tests/app/test_release_diagnostics.c` checks the short menu.
- **Code size:** the code window is `0x2666C` (157,292) bytes. `tools/size_report.py` prints the lines against the limits after every image build and reads each limit from the linker maps. With link-time optimisation and the USB overlay the `release` code is 139,020 bytes (18,272 free) and the `device` code, which also carries the debug report, event log and profiler, 140,968 (16,324 free); before the USB overlay they were 149,808 and 150,272. Libraries in `src/` that link `echo_compact` and the cold device files listed in `platform/device/CMakeLists.txt` and `platform/device/logic/CMakeLists.txt` (start-up records, the updater, the image CRC, card file creation, the Bluetooth protocol, the DAC set-up sequence, the USB descriptors and requests, the USB sessions, the MP3 probe, the M4A demuxer and its stream, the open functions of the core 1 sources, the battery gauge, the backlight table, FAT name handling, the DAC driver and the core 1 loader) are compiled with `-Os` in cross builds; the audio path (ring feeding, the engine and its sources, FAT reads), `board/usb.c`, `board/usb_port.c` and the USB audio sink stay at `-O2`.
- **Overlay loader:** `board/overlay.c` loads both overlays into the window at `0x0307A000` (`0x18000` bytes, `overlay.h`), after `board_audio_shut_down`, because the main program's `.high_ram` (the core 0 decoder workspace and the equalizer state) uses the same memory while music plays. An overlay in the image is a 16-byte header (magic, size, CRC of the rest, CRC of the main code it was linked against) and the program. The loader takes the first of these that passes every check: the copy already in the window, firmware slot 1, firmware slot 2. The checks are the magic, a size that fits the window, the code CRC against the running code (computed once per start and kept) and the CRC of the whole body. It then zeroes the window after the program. When nothing passes it zeroes the whole window and returns nothing, so a failed load leaves no header and no code behind, and the caller never jumps there. Nothing in the window has to survive a load: a track is opened again and the equalizer designed again before either is used.
- **USB overlay:** everything a USB session does after the host's bus reset (the mass-storage session with `msc`, `usb_device` and `usb_fallback`; the DAC session with `usb_audio`, `usb_audio_sink` and `stream_drift`; the update check and install with `updater`, `update_names` and `fat_delete`; and the DWC2 transfer code, `board/usb_port.c`) is linked as `echo_usb_overlay` at `0x0307A000` against the main ELF's symbols, like the rescan overlay, and stored at image offset `0x43C000` (up to `0x10000` bytes, magic `EUSB`), inside the area the trailer CRC covers and the updater writes. It is 13,364 bytes. Its entry table (`UsbOverlayEntry`: magic, storage session, DAC session) follows the header at `0x0307A010`. Unlike the rescan overlay it has a `.bss`, which the loader's zeroing provides: the 32 KB mass-storage write buffer, the ports, the mass-storage state and the update's file, 35,484 bytes, so each session starts from zeroed state. `usb_overlay.ld` has two memory regions over the same addresses, `USB_IMAGE` (`0x10000`, the program) and `HIGH_RAM` (`0x18000`, the program and its `.bss`), so the linker refuses either overflow and the size report reads both limits from the map.
  - **Resident:** listening (`board/usb.c`: VBUS, PHY power, the core reset and connect, the bus-reset check, the FIFO flush), `board/usb_listen.c` (the state kept across sessions, `UsbShared`: the link, the failed-start report, internal storage's layout, Last USB, the high-speed fallback, the DAC level and the restart-pending flag), the failed-start report (`board/usb_report.c`) and the start-up loader request (`board/update_request.c`), since they run while music plays or before the app starts.
  - **Calls into the main program:** by symbol (`--just-symbols`). LTO would make those functions local or inline them away, so `platform/device/CMakeLists.txt` lists them in `ECHO_OVERLAY_IMPORTS` and links the main program with `--require-defined` for each; a function missing from the list fails the overlay's link. `tools/make_image.py` refuses an overlay that carries its own copy of a function or table the main program has, and `tools/size_report.py` fails the image build when a library object keeps variables in both programs (the overlay would get a second copy of them).
  - **Start of a session:** once the host's reset is seen, `board/main.c` calls `app_release_audio` and `board_audio_shut_down`, loads the overlay and calls its storage or DAC entry with `UsbShared`. If the load fails, it powers USB down, shows "USB code missing: reinstall the update" ("Restart the player to finish the update" after an install) and waits for a key; music stays paused. After a failed install the copy in the window still serves the next session; if playback has overwritten it, the loader needs a slot whose overlay was built with the running code.
- **Image rules,** enforced by the linker script and the builder:
  - `.data` holds only the 8-byte entry vector; no initialised mutable globals.
  - Code stays below the row-0 end (`0x030771D4`).
  - `.data`, `.bss` and `.noinit` end below `0x0304A240`. The boot ROM zeroes the load table's data range while it still uses RAM above it: Echo images ending at `0x0304AB90` and above never started (black screen, nothing on USB), images ending at `0x0304A224` and below did. The exact ROM boundary is unknown; `0x0304A240` is the highest proven value.
  - Nothing loaded is left out of the image.
- **Run model:** the main loop polls the drivers; the 1 ms SysTick interrupt keeps time and runs the stall watch (see below). The display driver samples the keys before and after every strip it pushes, so key presses aren't missed during slow frames.
- **Storage:** `board/mmc` drives the DW-MMC controller (commands, polled single- and multi-block reads and writes, CMD12, the card clock); `board/emmc` reads through `device/block_read` in chunks of up to 64 sectors with CMD18 + CMD12, and retries a failed chunk one sector at a time; `board/sd` and `board/emmc` write through `device/card_write` and `board/sd` powers the SD slot and checks card detect. `board/emmc` starts internal storage (8-bit bus at 24 MHz) on first use and refuses any write outside what `emmc_layout` allows. The file HAL mounts the SD card (FAT16, FAT32 or exFAT) on the first open, or, when there is no card or it doesn't mount, the internal user volume through `emmc_volume_start` (reads and writes through `board/emmc` and the `emmc_layout` fence, so nothing outside the user volume is ever written); `device/storage_mount` makes that choice and `hal_file_volume` reports it (Settings → About → Music: Card, Internal or None). Everything the player keeps under `/.doublesharp` on the music volume, the music scan from `/` and the playlists follow the mounted volume. `storage_reset` makes the next open decide again (and the next settings access mount internal storage again). The file HAL can hold 8 files open at once, each with its own extent map (2.2 KB of RAM in all). Writes go in place or through `fat_reserve` (see Settings and favorites).
- **USB:** the main loop watches VBUS. When the cable is plugged in, `board/usb_session` powers the PHY and the polled DWC2 core (`board/usb`) and connects, without touching audio or the screen. It asks for high speed (DCFG speed 0) unless high speed already failed since power-on; at enumeration done it reads DSTS and uses 512-byte bulk packets at high speed and 64 at full speed, on the core's reset FIFO sizes (RX 147 words, shared TX 128), one packet per bulk OUT transfer. If a high-speed session isn't working (configured and through two SCSI commands) 10 s after the first bus reset (`device/usb_fallback`), it reconnects at full speed and stays there until the next power-on. The main loop then keeps running and checks GINTSTS for a bus reset on every pass, for up to 3 s, with the CPU clock held at 96 MHz or more. No reset means a charger: USB powers down quietly and the player carries on, playing and charging. With a host, `board/main.c` loads the USB overlay (see USB overlay) and the session runs from it:
  - `app_release_audio` saves the bookmarks and unloads the player's track (it stays paused at its position) and `board_audio_shut_down` stops the DMA and powers the DAC path down through `board/audio.c`, before the overlay is loaded and the audio power pins are silenced; then the app shows "Computer found" and its steps pause. Silencing the pins behind the audio driver's back used to leave it believing the path was still up, so nothing played after the session until a restart
  - LUN 0 is the internal-storage user volume and LUN 1 is the SD card, both read/write. Sense data is kept per LUN
  - if the controller fails to start, `board/usb_report` shows four notices (a key press moves on): the core ID and OTG control after power-up; the failed init step (with `0x10` set when internal storage started) and GHWCFG4; then GINTSTS and OTG control after the wait. It is a bring-up aid inherited with the code
  - the session ends when every LUN that was present has been ejected, or the cable is pulled. If the session wrote to either drive, the file HAL forgets its mount and open files, and `app_start` reloads the app from the changed card. If the cable was pulled while a drive was still mounted, a notice says recent changes may be lost. The session records how it ended (ejected, or unplugged with how many drives still up), the sectors written to each drive and any writes refused after an eject; no menu row shows that record at present. Then `board/update` opens the update file on internal storage (`device/update_names`) and installs it if it's valid and differs from slot 1, or if it's FiiO's stock image, showing progress and the result. After an install the player asks for USB to be unplugged and Power to be held, then turns off; the new firmware starts at the next power-on. Otherwise `app_wake` restarts the screen timeout
- **USB DAC mode** (not run on a player by this project; Podium's documentation reports it playing from Windows 11 and an Android phone): Settings → USB mode chooses Storage (the default, the session above) or DAC; `settings_store_apply_hardware` passes it to `hal_system_set_usb_mode`, and `board/main.c` reads it when the cable goes in, so a change takes effect at the next plug-in. Listening for a host, the 3 s wait and the charger case are the same as for mass storage. With a host, `board/usb_dac_session` runs instead of the mass-storage session:
  - **Class and speed:** USB Audio Class 1.0, full speed only (`usb_device_allow_high_speed(false)`, DCFG speed 1), so it needs no driver on Windows 10 and later, macOS, Linux, Android or iOS. Interface 0 is Audio Control: an input terminal (USB streaming, 2 channels) into a feature unit (ID 2: master mute and volume) into an output terminal (headphones). Interface 1 is Audio Streaming: alternate setting 0 has no endpoint, 1 is 16-bit stereo PCM, 2 is 24-bit stereo PCM (3-byte subframes), both at 44.1 and 48 kHz, on isochronous OUT endpoint 1 (adaptive, 1 ms interval) with room for 49 frames (196 and 294 bytes). 88.2 and 96 kHz are left out because their largest packet (up to 582 bytes at 24-bit) doesn't fit the RX FIFO (see FIFOs below). Android's USB audio picks the highest rate a device offers, and some Windows setups do too, so offering them meant silence on those hosts. The device descriptor says USB 1.1 and has no serial number.
  - **Synchronisation:** adaptive, by ring level, with no feedback endpoint. The I2S clock runs from the player's MCLK, so the computer's rate and the DAC's drift apart slowly (a few frames per second). `device/usb_audio_sink` converts each packet into the music ring (16-bit samples to the top half of the word, 24-bit samples shifted up by 8, two words per frame, the same format as music) and measures the fill as frames written minus frames the DMA has played. `device/stream_drift` keeps it near 20 ms: when the fill is more than 4 ms off, each packet drops its last frame (too full) or repeats it (too empty) until the fill is back within 1 ms of the target, or past it. One frame per millisecond is far faster than any drift, and a single dropped or repeated frame isn't audible. The sink also keeps the 20 ms after the newest frame silent, so if packets stop the DMA plays silence rather than old audio; if the DMA overtakes the writer (packets lost for longer than the buffer) or the ring would overflow, writing restarts 20 ms ahead of the DMA after a short silence. An asynchronous feedback endpoint would avoid the dropped frames, but it needs a second (IN) isochronous endpoint, a measured rate in 10.14 or 16.16 format and per-host quirks, none of which can be checked without hardware.
  - **Rates and formats:** the host's SET_CUR on the endpoint's sampling-frequency control (3 bytes, either of the two rates; others stall) or a new alternate setting stops the output, restarts the DAC path at the new rate through `board_audio_stream_open` (the same `dac_path_start` as music, with its ACODEC row and divider), and primes the ring again: the DMA starts once 20 ms is buffered. 100 ms without packets (the computer stopped playing) also stops the output until packets come back. GET_CUR reads the rate back.
  - **Volume:** the feature unit's volume runs from −64 dB to 0 dB in 0.5 dB steps (GET_MIN `0xC000`, GET_MAX 0, GET_RES `0x0080`); `board_audio_set_attenuation` adds it to the player's own level on the DAC's PCM volume registers (0.5 dB per unit), and mute sets them to mute. The volume keys still change the player's level by one step per press (no repeat while held) and the screen doesn't show it; the level from before the session comes back afterwards.
  - **Audio driver:** `board/audio.c` has a stream mode for this: `board_audio_stream_open` stops music (`board_audio_shut_down`), clears the music ring and starts the path at a rate; `_play` starts DMA channel 5 over the ring as for music and fades up; `_pause` clears the ring and fades down and stops the DMA; `_consumed` gives frames played; `_close` shuts the path down. While the stream is open, `hal_audio_service` and the DAC's fade waits call the session's USB service instead of the engine, so drawing a notice or fading keeps the isochronous endpoint served. The session starts with `app_release_audio()` and `board_audio_shut_down()` and ends with `board_audio_stream_close()`, so music works as before afterwards. The audio power pins are never touched directly. The CPU runs at 200 MHz: the session's first notice turns the screen on, which raises the clock as in a mass-storage session, and opening the stream raises it too if needed.
  - **DWC2 in polled mode:** the session loop polls the core (four `usb_poll` calls per pass), the audio service (jack sense) and the keys. The changes in `board/usb.c`, cited against the DWC2 register map:
    - FIFOs: the same layout as mass storage (RX FIFO 0x120 words, TX FIFO 0 0x20 words at 0x120, TX FIFO 1 at 0x140). The core accepts an isochronous OUT packet only when the RX FIFO has room for a maximum-size packet (582 bytes, 146 words) plus its status entries, so the reset size of 147 words (`GRXFSIZ` `0x93`) drops every packet: Podium's documentation records that on a player this showed as no packets received, an incomplete-ISO interrupt every frame and NAKIntrpt (DOEPINT bit 13) on endpoint 1. An earlier build computed its own split from the reset values, skipped it on this chip's layout, and so stayed at 147 words. The endpoint is therefore armed for 294 bytes (`USB_AUDIO_MAX_PACKET`, 49 frames of 24-bit stereo, which Podium's documentation records as proven on a player), the largest packet of any offered format.
    - Endpoint: at SET_CONFIGURATION, DOEPCTL1 gets MPS 294 (bits 10:0), USBActEP (bit 15) and EPType 01, isochronous (bits 19:18); DAINTMSK bit 17 and GINTMSK bit 21 are set (the core isn't wired to an interrupt, but the status bits are polled). A streaming alternate setting arms it: DOEPTSIZ1 = PktCnt 1 (bit 19) | XferSize 294, the same for every format and rate (a shorter packet ends the transfer), so it doesn't matter whether the host sends SET_CUR for the rate before or after SET_INTERFACE, then DOEPCTL1 EPEna (31) | CNAK (26) | SetOddFr (29) when DSTS bit 8 (the low bit of SOFFN, the current frame number) is 0, otherwise SetEvenFr (28), so the endpoint takes the next frame's packet. Each transfer complete (DOEPINT1 bit 0) re-arms it the same way while streaming.
    - Missed frames: GINTSTS bit 21 (incompISOOUT) means an armed isochronous OUT endpoint got no packet in a frame. If DOEPCTL1 is still enabled and its EO_FrNum (bit 16) matches the current frame's parity, the endpoint is switched to the other parity, then the bit is cleared.
    - Packets: GRXSTSP is popped once per poll; PktSts (bits 20:17) 2 with EPNum 1 is a packet for the sink, read into the port's 128-word packet buffer (the larger of a high-speed bulk packet and `USB_AUDIO_MAX_PACKET`); 3 and 4 are skipped as before.
    - Control OUT with data (SET_CUR): the request is held until its data packet (PktSts 2, EPNum 0) arrives on EP0, which `arm_setup` keeps enabled; then the reply is applied and the status stage sent (a zero-length IN, or a stall).
    - Control IN longer than 64 bytes (the 159-byte configuration descriptor): sent as 64-byte packets, each after DIEPCTL0 EPEna clears from the previous one (up to 100 ms each). Replies of 64 bytes or less go out exactly as before.
    - Mass storage is unchanged: these paths only run when the port has an audio device, and with one the bulk endpoint and MSC calls are skipped.
  - **Screen:** "USB DAC" with "Computer found. Starting...", then "Choose Doublesharp Echo as the sound output" while the host has no stream open, the format and the DAC volume, such as "48 kHz 24-bit · Volume 35", while it has, or "The audio output didn't start." The notice is drawn only when the format changes, because drawing delays the polling (the audio service is called after each strip, so the endpoint is still served between strips).
  - **Ending:** pulling the cable, or holding Back for 1 s and releasing it (the player then stays a charger until the next plug-in). The session powers USB down and `app_wake` restarts the screen timeout. Nothing touches the card, so there's no rescan or update check. The last-session record isn't updated.
  - **Memory:** no new buffers: the music ring holds the stream. The port, the audio state and the sink add about 1 KB of `.bss`.
- **Firmware tag:** `hal_system_version` (`hal/system.h`) returns the version and the build tag from slot 1's header on the device (for example `1.0.0-1a2b3c4`) and "simulator" in the simulator. Settings → About shows it as Firmware.
- **CPU clock:** `hal_system_clock_mhz` and `hal_system_set_clock_mhz` (`hal/system.h`). On the device, `board/clock_switch.c` follows stock's PLL order with the register words from `device/pll` (96 and 200 MHz). It waits up to 200 ms for lock and stays at 24 MHz without it. After a switch it rescales the SysTick clock (`tick_clock_set_rate`). The device switches to 96 MHz right after reading the boot clocks (see Device playback). In the developer build, Settings → About → CPU clock cycles 24 → 96 → 200 → 24 MHz.
- **Test tone:** `hal_audio_test_tone` (`hal/audio.h`) blocks for about 5 s. On the device, `board/dac.c` runs the SoC side of the audio path (gates, I2C0, ACODEC mux, I2S1, polled FIFO feed) and `device/dac_sequence` runs the CS43131 side (power pins, probe, register sequence, output on and off) through a `DacBus`. It plays one sine period of 100 samples (441 Hz at a true 44.1 kHz) at amplitude 9000 (ReChord's level, about −11 dBFS): 2 s with the I2S divider from the formula (MCLK / (64 × rate) − 1, truncated, which gives 2), then 2 s with it rounded (3). It reports No DAC, Setup failed, Not ready or I2S stalled when a step fails; No DAC adds the I2C step (s1 start, s2 send, s3 NAK, s4 stop, s5 receive) and the I2C pending bits in hex. `hal_system_boot_clocks` gives the low halves of CRU `+0x10`, `+0x14` and `+0x18` as the ROM left them, read first thing in `board_main`. The simulator returns Played. No menu row runs the tone or shows the boot clocks at present.
- **DAC identification:** the first time the DAC path starts after power-on, `board/dac.c` reads Cirrus's identification registers from each of the two chips, once the power pins and I2C0 are up and before the probe write: `0x010000`–`0x010002` (device ID), `0x010004` (revision) and `0x010005` (subrevision), through the driver's ordinary register read (`dac_read_identity` in `device/dac_sequence`). `0x010003` is reserved and is not read. The read writes no register, changes no pin and adds no wait; it leaves a chip at its first register that fails and is never repeated before the next power-on, and the I2C step kept for a failed start (`hal_audio_tone_detail`) is put back afterwards, so a failed identification neither fails nor mislabels the start-up. `test_dac_sequence` checks on a recording bus that exactly those reads happen and that every write, pin change and wait of the start-up is the same with a complete, a partial and a failed identification. `hal_audio_dac_identity` returns the kept bytes. `core/dac_identity` names the part from the ID (`43 19 8x` CS43198, `43 13 1x` CS43131) and writes the text of Settings → About → DAC A (bus address `0x60`) and DAC B (`0x66`), shown in both builds: `431980 A0.00` is the three ID bytes, then the revision and the subrevision; a leading `?` marks an ID that is neither part; `--` stands for a register that was not read (`4319-- --.--`); `Read failed` means no register answered; `Play a track` means the DAC has not started since power-on; the simulator shows `Simulated`. The names A and B follow the bus address, since which chip plays which channel is not established. Every value fits beside its name at every text size in landscape, and the words and a known part's value at Small and Medium in portrait. At Large in portrait the value has about 100 px, and the end of a known part's value can be cut (`431980 A0.…`); an unrecognised part can lose its subrevision in portrait at any size. The ID bytes are never cut (`test_diagnostics_values`). No player has been read yet (`known-issues.md`).
- **Jack pins:** `hal_audio_jack_pins` (`board/jack.c`) records how the ROM left GPIO0.13 and GPIO2.8 (function, direction, pull), then makes both GPIO inputs and reads them. Settings → About → Jack 3.5 and Jack 4.4 show the live level and the boot state (GPIO0.13 high = 3.5 mm, GPIO2.8 low = 4.4 mm; Podium's documentation records the 3.5 mm pin as confirmed on a player). `hal_audio_jack` gives the debounced jack: `device/jack_sense` names it (GPIO2.8 low wins) and takes a change after 7 matching readings, one every 10 ms from `hal_audio_service`. With Output set to Auto, the volume curve follows the jack (level n of 60 is 2 × (60 − n) PCM-volume units, 1 dB per level, level 60 = 0 dB on 3.5 mm; 4.4 mm adds 10 units, 5 dB, as stock's balanced table does: stock's `0x82 − n` against `0x78 − n` for 3.5 mm in `FUN_03061262`); a fixed Output setting overrides it. Both jacks are driven by the same two CS43131s (one per channel), and no switch between them is known, so Output can't route sound to one jack: it only chooses the volume table, 1.5 dB apart at the top. Settings shows the detected jack next to Auto ("Auto (4.4 mm)"), and choosing an option says what it does. The player pauses when the jack goes from plugged to none and doesn't resume on its own.
- **Device playback:** `board/audio.c` implements the audio HAL with `device/audio_engine` (host-tested). The engine opens a track through the file HAL and takes decoded frames from an `AudioSource`. `board/audio.c` picks the source from the file's first 12 bytes, not its name: `fLaC` goes to FLAC, `ftyp` at byte 4 to M4A (see below), `RIFF`…`WAVE` to `device/wav_source` (PCM or extensible PCM, 1–2 channels, 8/16/24/32-bit, any chunk order before `data`, 4,096-frame blocks read on core 0 into buffers that share memory with core 0's FLAC decoder), an ID3 tag or an MPEG audio frame header to MP3, anything else is refused as an unsupported file type. MP3 is decoded on core 1 by libmad (`third_party/libmad`, 0.16.4 pinned in `VERSION`, built with 64-bit fixed point and `OPT_ACCURACY`; on the device `third_party/libmad_libc` stands in for the missing C headers and `core1/no_heap.c` makes `malloc` always fail, since `device/mp3_decoder` hands libmad static main-data and overlap buffers before its first frame). Core 0 runs `device/mp3_probe` (ID3v2/ID3v1/APE tags skipped, the first frame confirmed by the next one, length from Xing/Info or VBRI, else from size and bitrate; seeking through the Xing table or proportionally) and streams the file into the same core 1 ring; `device/core1_mp3` turns each frame into a block of 24-bit samples. Core 1 runs one program at a time, as stock does: the programs are packed by `tools/make_image.py`, MP3 (about 65 KB) at image offset `0x240000`, FLAC (about 9 KB) at `0x280000` and M4A (about 61 KB) at `0x2A0200` (a 512-byte header with `EC1M`, size and CRC, then the program) and read from slot 1 on eMMC straight into core 1's RAM through a 4 KB staging buffer, with the CRC checked on the way. Switching between FLAC, MP3 and M4A tracks restarts core 1 with the other program; after an update, until the restart, all programs are refused like the rescan overlay (FLAC then decodes on core 0). On core 1 the FLAC decoder can hand LPC subframes of order 3 and up to the hardware accelerator (`device/flac_accel`) through `flac_set_lpc_hook`, but only for the classes (narrow or wide accumulator) that passed its self-test; a timeout turns the hook off. Core 0 runs the self-test once per boot, before the first FLAC stream, and passes the passing classes to every later core 1 FLAC run. libmad's `III_decode` keeps a 7 KB frame on the stack, so `core1/core1_mp3.ld` keeps the program's `.bss` below `0x0102B000`, leaving 12 KB of stack. The engine records why it refused a track (unreadable, or the sample rate with the rate), `hal_audio_refusal` reports it, the player counts refusals, and the app shows a toast such as "192 kHz isn't supported yet". On the device that is `device/core1_stream`: core 0 opens and seeks with its own decoder, streams the file into a 128 KB ring in core 1 RAM, and core 1 decodes frames into two slots; if core 1 doesn't start, `device/flac_source` decodes on core 0. Each frame is copied into a 28,000-word ring in data RAM as two words, left then right, each a 24-bit sample shifted to the top of its word (stock's music mode, TXCR `0x401F`; 16-bit sources are shifted up, nothing is rounded). Volume is set in the DAC's PCM volume registers; the engine's software gain stays at unity on the device. The engine keeps a list of segments (token, start frame, start position, rate) so the token and position follow what the DMA has played. DMA channel 5 loops over the ring through seven linked items of 4,000 words (a DW block holds at most 4,088 items; `device/dma_loop` refuses more); the HAL turns its read address into a running count of consumed frames. The app calls `hal_audio_service()` at the start of each step and after each strip, so drawing can't starve the ring (14,000 frames is 73 ms at 192 kHz, 146 ms at 96 kHz and 317 ms at 44.1 kHz). Playback starts once 100 ms of audio is buffered (at most three quarters of the ring) or after 1 s. Supported rates are 44.1, 48, 88.2, 96, 176.4 and 192 kHz, each with its ACODEC row and the rounded I2S divider. A queued track at the same rate follows without a gap; a different rate waits for the ring to drain, then the path restarts at the new rate. Volume changes fade on the DAC: 6 PCM-volume units (3 dB) every 2 ms (`dac_ramp_next`), and `board/dac.c` keeps the ring fed between steps through a service hook, so a fade never starves the ring. Starting output fades up from mute after the DMA starts; stopping, pausing, seeking and skipping fade down to mute before the channel stops. A seek while paused stays silent. Pause fades out, mutes the DAC and suspends the channel (nesting with the clock switch's suspend). Seek and play restart the ring. Three seconds after playback stops, the DAC path powers down. `hal_audio_service` polls the I2S underrun flag (INTSR bit 1, cleared through INTCR bit 2; INTCR keeps TXUIE set with the NVIC line off) and counts it in the stats, shown as `o` on the frame overlay. The ring must stay in data RAM (`0x03004000`–`0x0304C000`): High RAM (`0x0307A000`) shares its SRAM with the code at `0x03050000`, and with the screen on core 0's instruction fetches starve the DMA's ring reads at 192 kHz (I2S underruns, an audible crackle). Core 0's FLAC header and seek decoder, which shares its memory with the WAV buffers, sits in High RAM instead (`.high_ram`, no-load): only the CPU touches it, and audio is stopped before an overlay overwrites it. The device starts at 96 MHz (`START_CLOCK_MHZ`) right after reading the boot clocks.
- **M4A (AAC-LC and ALAC):** `device/mp4_demux` walks the boxes through the read callback without loading any of them: it finds `moov` before or after `mdat`, the first `soun` track, its sample description (`mp4a` with the `esds` AudioSpecificConfig, or `alac` with its 24-byte cookie; `wave` wrappers and 64-bit box sizes are not read), the `stts` total, and the chunk, run and size tables of `stbl`, which stay in the file. A configuration other than AAC-LC (or AAC-LC with SBR or PS signalled, which ffmpeg writes as a backward-compatible `0x2B7` extension with the SBR flag clear) is refused. The encoder delay and the number of valid samples come from the `iTunSMPB` tag under `moov/udta/meta/ilst`, else the delay is zero and all samples are valid. `Mp4Cursor` finds sample N by walking the `stsc` runs, reading one `stco` or `co64` entry and adding up at most one chunk's worth of `stsz` entries (read 64 at a time), then walks forward with one table read per 64 samples and one per chunk. `device/m4a_stream` turns that walk into a byte stream for the second core, read through the same fill loop as the other formats: a configuration record (`u32` length, the codec byte, the AudioSpecificConfig or ALAC cookie), then one record per packet (`u32` length, the packet read from the file), then a zero length and zeros. Core 1 runs `core1/m4a_main.c` (`device/core1_m4a`): it reads the configuration record, starts FAAD2 (`third_party/faad2`, fixed point, LC only, 24-bit output) or `codec/alac`, and decodes a packet per block. The program is about 63 KB (FAAD2 and its tables 55 KB, ALAC 2.6 KB) at image offset `0x2A0200` (`make_image.py --core1-m4a`, at most `0x1FC00` bytes so that it ends at the glyph table). It runs with a 64 KB ring (`M4A_RING_BYTES`) so that the upper 64 KB of core 1's ring area can serve as a bump heap for FAAD2's allocations, the ALAC state and the packet buffer (`device/core1_heap`; `malloc` in `core1/heap.c`); the heap resets at each stream start. Core 1's `.bss` is 24.6 KB (FAAD2's element scratch, which `third_party/faad2/syntax.c` keeps static) and the stack has the remaining 27 KB, of which FAAD2's deepest call chain uses about 21 KB. The first packet of a seek is the one before the target, because AAC needs the overlap of the previous frame; packets before the target are decoded and dropped by the engine's skip. After a seek the output position is exact to the sample. The playable length is the `iTunSMPB` valid count, so tracks end where the encoder's padding starts. FAAD2 is told to return the first frame (it normally suppresses it). The library needs no change: `.m4a` was already indexed with its tags, duration and cover art, and the scanner and `tools/library_index.py` agree on `tests/fixtures/m4a_music`.
- **DMA tone:** `hal_audio_dma_tone_start`, `_stop` and `_status`. On the device it checks COMP_TYPE at `0x600003F8`, brings up the same audio path with the rounded divider and INTCR `0x01F00100` and without XFER, then runs DMA channel 5 (`board/dmac.c`) over the music ring filled with a sine (16-bit samples in the top half of each word, two words per frame, the same format as music) through the same seven linked items as music (`device/dma_loop`), with every channel interrupt masked. Then DMACR = `0x110` and XFER = 1. The call returns at once; `_status` reports "Playing" with channel 5's read position, "Ended" if the channel stopped by itself, or the failed step, and `_stop` suspends the channel, disables it, and closes the audio path. No menu row starts it at present. A clock switch suspends and resumes the channel around it.
- **Start record:** `hal_system_start_info` (`hal/system.h`). On the device, `device/start_record` keeps a record in `.noinit` RAM: the start count, the uptime (every 5 ms), a power-off mark, fault registers, the last battery reading (every second) and the last risky step (backlight on or off, clock switch, core 1 start or stop, card write) with its start time and whether it finished. It reads, for example, "#3 reset after 41 s", "In clock switch at 41 s" and "3712 mV". No menu row shows it at present.
- **Stall and fault screen:** a power loss wipes the Last start record, so a freeze that ends in a power cut reads Cold start. On the device the main loop beats a `device/stall_watch` each pass, and the 1 ms SysTick checks it every 5 ms. A loop silent for 10 s (paused during start-up, USB sessions, updates and power-off) trips it once: the interrupt silences the audio pins, clears the panel, turns the backlight full on and draws, in a 5×7 font scaled ×2 (`device/panic_text`), "STALL", the interrupted PC and LR (from SysTick's exception frame via `device_systick_entry`), and "UP \<s> STEP \<n> [U] MV \<mV>" (U = the step never finished; step numbers follow `HalStartStep`). A fault draws "FAULT" with PC, LR and CFSR the same way. After either, holding Power for 2 s cuts power from the interrupt. In the developer build, Settings → About → Stall test freezes the main loop on purpose to check the screen. A loop stuck with interrupts masked isn't caught.
- **Power taps:** in the developer build, Settings → About → Power taps (Normal/Ignored, not saved) makes the app drop Power taps so a test can tell an electrical effect of the press from the app's reaction to it; a long Power press still shuts down.
- **Switching off:** `hal_power_off` and `board_power_cut` drive the Bluetooth module's power and UART pins low before dropping GPIO2.6; a powered module otherwise kept the player from switching off after an update, so Power did nothing until RST.
- **Charge screen:** with USB power, GPIO2.6 low doesn't cut power (`hardware.md`), so a switch-off on a cable used to leave the player dark and deaf until RST. Now the app's shut-down checks `hal_power_battery().usb_power` and, when it's set, enters charge mode instead of `hal_power_off`: it pauses and releases the output, puts Bluetooth to sleep and draws `screens/charge_screen` (a large battery, the bolt while charging, "Charging 64%" or "Charged", "Hold Power to turn on"). The screen goes dark after 5 s and any key lights it; holding Power for 2 s leaves charge mode (Bluetooth restarts, the splash plays); losing USB power calls `hal_power_off`, which now cuts power. A USB session still runs as usual and returns to the charge screen. `board_power_hold` records VBUS and the Power key level at boot ; `hal_power_take_usb_start` reports, once, a start with VBUS present, the key up and GPIO2.6 not left driven high by the ROM, and the app then opens charge mode straight after `app_start`. The backlight stays off from boot until the app's first frame, so the panel's power-on noise never shows, and `board_display_service` also runs inside the USB, DAC, update and wait-for-key loops so a backlight fade-in started there finishes.
- **High RAM:** `hal_system_high_ram_test` writes and reads back a pattern over `0x0307A000–0x0309EFFF` (HIGHRAM0, 148 KB, where the rescan and USB overlays run and the glyph cache lives) and calls a 4-instruction function copied there. Afterwards it restarts the glyph pack reader, since the test overwrote its cache. It reports "OK 148 KB, call works", "Bad at \<address>" or "Call gave \<value>". No menu row calls it at present.
- **Bluetooth:** `hal/bluetooth.h` powers the module, scans, connects to a device, turns the stream on and off and reports the module's state, the devices found, link counters and counts of the headphones' button presses. On the device, `board/bluetooth.c` follows stock's sequence: GPIO2.7, 2.16 and 2.17 are driven low at boot; power-on opens UART1 (group A, 115,200 8N1, divisor 13, FIFOs on, polled, no interrupts) and drives GPIO2.7 high; power-off drives all three low again, as does a module that never sends `CV1`. `hal_bluetooth_service` runs where `hal_audio_service` does (each step and after each strip): it drains the RX FIFO into `device/bt_module`, counts overruns, records the FIFO's peak level and depth, and sends any frame the protocol asks for. `bt_module` connects with `CL06` + the address, `CH06` after 4 s and `CT00` and a failure after 30 s, polling `CQ00` every second meanwhile so a link the module reports only as `CQO` (a remembered device sends no `CLOK`, and headphones may connect on their own) shows within a second; a paired reply (`CLOK`) waits for the next `CQ00` answer to report the link (`CQO`). It sends `CY0 00` on connect, `CY0 1E`/`CY0 00` to start and stop the stream, and stock's `C 86`/`C 87` play notices. The module's `CP`/`CC` (pause/play, sent by the headphones' taps and in-ear sensors) and `CA`/`CB` (previous/next) only count presses in `HalBluetoothRemote`; polling pauses for 50 s after a `CP`/`CC`, as stock does. While streaming, the board routes audio to the module: the first time it applies the stock start-up settings listed in `hardware.md`, then GPIO2.0 goes high and GPIO2.14 low (and back on stop), and the DAC driver keeps those two pins while routed. `app/bluetooth_link` runs every step after `player_update`. It keeps the On/Off choice and up to 6 devices, most recently connected first (stock also keeps 6), in `/.doublesharp/bluetooth.bin` (`BT`, version 2, the On byte, the count, then 6 × the 6-byte address and 32-byte name; version 1 files, with one device, still load), written only when they change. When Bluetooth is on it powers the module at start and connects to the first device as soon as the module is ready, retrying 5 s after each failed attempt. It connects only from Ready or from a scan that found a remembered device: never while a connect is running or while a paired reply waits for `CQO`. A pairing that hasn't reported the link 10 s after `CLOK` is dropped with `CT00` and tried again 2 s later, which brings up a link the module left half-made. With the Bluetooth screen open, each failed attempt is followed by one scan to list nearby devices. Stock only ever scans a freshly powered module (its rescan power-cycles it first), so a scan after the module has paged a device power-cycles it too: off for 500 ms, on, wait for `CV1`, then `CS00`; the first scan after a power-on goes straight out, and the screen says Searching… throughout. A scan that finds a remembered device connects to it at once with `CL06` while the scan still runs, as stock's screen does when an entry is picked (one try per scan), unless the user disconnected or chose Pair new device; then its row shows "Nearby". Each new connection moves its device to the front of the list and shows "Connected to \<name>"; a dropped link pauses playback and shows "Disconnected from \<name>". A device the user disconnects stays disconnected (no automatic reconnect) until it or another device is chosen, Bluetooth is turned off and on, or the player restarts. Choosing another device while one is connected disconnects it and connects the chosen one 2 s later; "Pair new device" disconnects too, then scans. It streams while connected, playing and nothing is in either jack. The jack can't be read while audio is routed to the module (the readings fake a plugged headphone), so `board/jack.c` holds its last state then and for 500 ms after each routing change: headphones plugged in while paused take the sound, and Bluetooth waits for the next pause and play before taking it again. The headphones' next and previous skip. Their pause pauses and their play resumes only what they paused, and both are ignored for 3 s after a connection, a stream change or a play or pause on the player, because the module sends the same `CP`/`CC` reports then on its own; a pause the headphones cause shows "Paused by \<name>". With no connection and the Bluetooth screen closed, the module switches itself off after 5 minutes (Bluetooth stays on for the next start); opening the screen wakes it. Settings → Bluetooth (third, after Shuffle and Repeat) shows the link's state as its value: Off, Starting…, Searching…, Connecting…, the connected device's name, Not connected or On. It opens `screens/bluetooth_screen`: a Bluetooth On/Off row; the remembered devices, each with its state (Playing, Connected, Connecting… or nothing); a "Pair new device" row (Searching… while scanning); then, while not connected, the devices a scan found that aren't remembered; and a hint for the selected row at the bottom. ▶ toggles Bluetooth, disconnects the connected device or connects a remembered one, starts a search, or pairs with a found device (which shows Connecting… or Didn't connect); holding ▶ on a remembered device forgets it. In the developer build, Settings → About → Bluetooth opens the same screen with four more lines: the module state (version, status letter, pairing result, streaming), the link counters and, over two lines, the module's last 12 messages: frames other than `CS` and repeated `CQ` answers, shown as `C` + two letters (a new `CQ` letter shows as `CQ` + it), plus the `CS`, `CP`, `CL`, `CH` and `CT` commands the firmware sent, shown as `>S`, `>P`, `>L`, `>H`, `>T` (`CQ00` polls aren't listed); each is followed by `+n` when n seconds passed since the one before. The log and the devices found survive Bluetooth off and on, so one photo after a failed or slow attempt shows the whole exchange. The status bar shows a Bluetooth mark next to the play icon, dim while on and bright while connected. The simulator reports ready after 300 ms, finds two devices over 3 s, keeps them across a power cycle and connects 1.5 s after a pick.

## Debug loop

A developer aid for checking a build on the player without pressing buttons and reading numbers off the screen. It exists only where `ECHO_RELEASE` is off: the `device` preset, the simulator and the host tests, which compile with `ECHO_DEBUG_LOOP`. The `release` preset has none of it: its size-report lines are those of the commit before the debug loop, and its ELF holds no symbol of it. Nothing here has run on a player; what the emulator cannot show is listed in `known-issues.md`.

- **Report:** `board/debug_report_file.c` (in the USB overlay) writes a report to `/.doublesharp/debug/` on internal storage at two kinds of moment. At the start of every USB storage session, after "Computer found" and before the port and the drives are prepared (`report.reason: usb_session`). And whenever the player shuts down: a long Power press (`shutdown`), auto off (`auto_off`), the sleep timer (`sleep_timer`), the low-battery cut-off (`low_battery`), and losing USB power on the charge screen (`unplugged`). For a shutdown the app names the reason (`debug_loop_shutdown`), and `hal_power_off` (after the audio path is down, before the one-second DAC discharge) or, with USB power present, the entry into charge mode loads the USB overlay and calls its report entry (`UsbOverlayEntry.report`, `hal_system_save_report`); a shutdown during a USB session or after an install (when the overlay in the slot no longer matches the running code) writes none. The text is built in the mass-storage write buffer, which is idle at all of these moments, by `device/debug_report`. A report that cannot be reserved or written is skipped and the session or shutdown goes on as usual. In the emulator the first report of a session (which also creates the folder and the file) takes about 40 ms and the session reaches the host 46 ms after it starts.
- **Kept reports:** there are three files, `report0.txt` to `report2.txt`, each reserved once at 16,384 bytes (`DEBUG_REPORT_BYTES`) and rewritten whole, the rest filled with line feeds. Every report carries `report.sequence`, one more than the highest on the drive (the writer reads the first 128 bytes of each file, so the number survives power cycles without any state in RAM). A new report replaces the file with the lowest sequence, with one exception: a report written within 10 s of a cold start (`report.cold_start: 1`, `DEBUG_REPORT_COLD_MS`) replaces the newest file when that is a cold-start report too. Plugging a switched-off player into a computer cold-starts it and writes such a report from a RAM that holds nothing yet; with this rule any number of those in a row costs one file, and the two reports before them stay. Nothing collected in RAM survives a power cycle, so a cold-start report carries only what the start record does (after a warm reset: the previous run's uptime, last step and fault registers); the rings and the profile reach the drive in the shutdown report before it. They are not kept in no-init RAM across a warm restart: a planned restart writes its report first, and what the boot ROM leaves of that RAM has not been checked on this player (`start.warm` in the first reports from one will show it).
- **Format** (schema 1): plain ASCII, one `key: value` per line, `debug_report: 1` first, then `report.sequence`, `report.reason` and `report.cold_start`. A value that could not be read is the word `unknown`, never a number. Lines are added in later versions without a new schema number; the number changes when an existing line changes its meaning or form, and `tools/echo_debug.py` refuses a number it does not know. The last two lines are `truncated: 0` or `1` (the text is cut at a line when it would pass the file's size; with every ring and every bucket full it is just under 16 KB) and `end: N`, where N is the number of bytes before the `truncated` line, so a reader can tell a whole report from a torn one.

  | `profile.state`, `profile.samples`, `profile.idle`, `profile.overlay`, `profile.other`, `profile.code_base`, `profile.bucket_bytes`, `profile.buckets`, `profile.row: <first bucket> <count> ...` | the profiler; rows are in hex and list runs of up to 32 used buckets |

- **Event log:** `core/debug_log` is a ring of the last 48 events, 16 bytes each: the time in ms, a value, the kind and the first 7 bytes of a text. `app/debug_loop` records them from the main loop: `key <name> <gesture>` for every key gesture except repeats (names as in the key script: `up` is the volume-down key), `screen <depth> <title>` when the top screen changes, `player <idle|playing|paused> <track>` when the player's state or track changes, `underrun <count>` and `output_underrun <count>` when either count grew (looked at every 100 ms), `refusal <problem>` for a track the audio HAL refused (`HalAudioProblem`), `storage 1` for a full volume and `storage 256+<ScanResult>` for a failed rescan, `usb_start <0 storage, 1 DAC>` and `usb_end <how it ended>` from `board/main.c`, and `power <VBUS> <charge pin>` when either level changes (and once after the start). Recording is a clock read and a 16-byte copy. Nothing is recorded from interrupt context: the ring has no lock, the SysTick handler never touches it, and a key is logged when the main loop turns it into a gesture, not when the interrupt samples it. A stall or fault therefore leaves no event; the start record covers those.
- **Power history:** `board/debug_session.c` keeps 128 samples of 6 bytes (`device/power_history`), one a minute, so a report covers the last two hours: the voltage trend while plugged in and after unplugging. It only reads: the SysTick handler notes each raw battery reading as the gauge takes it and raises a flag every 250 ms; `board_display_service`, which the main loop and every USB, update and key-wait loop call, then compares the cable bit and the raw charge pin with their last levels and takes a sample when a minute has passed; each sample also notes whether USB is powered up and the USB sense mode, so a report shows what the cable bit does across a power-down and a power-up. Nothing is sampled before the firmware first reads the battery (the pin is not set up until then), and "playing" is the player's state as the app last saw it. No power behaviour changes.
- **USB sense:** a test aid for one question: does the cable bit only report while the USB hardware is powered? Settings → About → USB sense shows the mode, the raw cable bit and whether USB is powered up, for example `Auto 0 off` or `Kept 1 on` (the wording is the longest that fits a portrait row at the largest text size), and refreshes with the screen. Play switches between Auto (the report's `normal`: USB is powered up to listen and fully down afterwards, as always) and Kept (`kept_on`): `usb_power_down` then still sets the soft disconnect but leaves the PHY words, the three resets and the two clock gates alone, and switching to Kept while USB is down powers it up with the soft disconnect set, so nothing connects. Switching back powers USB down unless a session runs or the player is listening. The mode is in RAM only and is Auto after every start. Nothing else changes: the main loop still decides from the cable bit, so if the bit comes alive with the hardware powered, a plug-in while running starts a session as usual. The emulator has no PHY and a cable bit that is a plain flag, so it shows only which registers are written: in Kept the power-down writes none of the nine PHY, reset and gate words; in Auto it writes exactly those nine, in today's order.
- **Profiler:** while switched on, the 1 ms SysTick handler passes the interrupted program counter from its exception frame to `device/pc_profile` right after it has counted the tick, so timekeeping and the stall watch run as before. An address inside `board_profile_wait` (the main loop's WFI, kept as its own 4-byte function for this) counts as idle; one inside the code window counts in a 16-bit bucket of 128 bytes; one in the high-RAM window (the rescan and USB overlays) counts in a single counter; anything else in another. The linker script reserves the buckets behind `.bss`, two bytes for every 128 bytes of `CODE_RAM` (1,229 buckets, 2,460 bytes), only when the build passes `device_profile_bucket_shift`; the code reads the count and the window from linker symbols. A bucket that reaches 65,535 stops the profiler (`full`), so the shares stay true; code that runs with interrupts masked is counted where it unmasks them. By the disassembly the handler spends 6 more instructions with the profiler off and at most 30 with it on (about 45 core cycles, under 0.5 µs at 96 MHz); this is an instruction count, not a measurement on a player. It is off after every start. Settings → About → Profiler switches it (Off, On, and Full, where a press clears it and starts again); `hal_system_set_profiling`, `hal_system_reset_profile` and `hal_system_profile_state` are the HAL calls.
- **Host tool:** `../tools/echo_debug.py` at the repository root (standard library only) prints one JSON object per command, errors included. `status` says whether the player is on USB, which volume is its internal drive, and which report is the newest; when that one is a cold-start report it sets `cold_start_only` and advises leaving the player switched on. `report` reads and parses every kept report, newest first, each with its file, sequence, reason and cold-start flag (`reports`), and repeats the newest as `report`; and `profile --elf echo_device.elf` shares each bucket's samples among the functions in it by their bytes (`arm-none-eabi-nm -S -l -f sysv`, with the linker map for functions without line information) and sums them per source file: per-function times are estimates at 128-byte resolution, per-file times less so. It finds the player by its USB identity (`1209:0001` and the product name from `identity.json`) and the internal drive by its medium name, volume name (`ECHO`, or `--volume-name`) and size; anything else is an error, and it never reads the microSD card's volume. `--volume PATH` names the internal drive's folder instead, for the tests and for a volume taken from an emulator run. The discovery has only run against made-up device listings.
- **Cost in the `device` build:** 2,056 bytes of the code window (event recording in the app, the frame figures, the sample and switch code of the profiler, the two About rows, the power sampler, the shutdown hooks, and `hal_system_start_info`, which the report is the first to call), 4,292 bytes of static RAM (2,460 for the buckets, 772 for the event ring, 772 for the power history, the rest the profiler's state, the audio snapshot and the modes) and 6,344 bytes of the USB overlay.

## Simulator audio

- Windowed mode plays through SDL audio. dr_flac, dr_mp3 and dr_wav decode (vendored, pinned in `third_party/dr_libs/COMMIT`). Each track feeds an `SDL_AudioStream` that resamples to the 48 kHz device rate. Two decoder slots (current and queued) make the hand-over gapless.
- Headless mode uses a silent virtual backend that advances on the simulated clock, so scripted runs, track transitions and resume are deterministic.
- `SDL_AUDIODRIVER=dummy` runs the real-time path without sound.
- Settings → About → DAC A and DAC B show `Simulated`: there are no DAC chips to identify.
- Third-party code lives in `third_party/` and compiles without our warning flags. The comment and format checks skip it.

## Simulator storage

`--card DIR` maps the card root `/` to a host folder, which is only ever read. Open files are read unbuffered, because `hal_file_write_at` writes through its own handle: on Windows a buffered reader kept serving the old bytes, so the scan's scratch file read back stale data and every rescan stopped with "Library too big for the player's memory". `hal_file_write` writes a `.tmp` file and renames it over the old one, removing the old one first on Windows, where `rename` won't replace a file. `--system-dir DIR` maps `/.doublesharp/` to a separate folder, so the database, covers, resume file, settings and favorites can live in `build/` without touching your music folder. Writes are refused outside `--system-dir`:

```sh
.venv/bin/python tools/library_index.py --music ~/Music --output build/library/library.db
build/dev/platform/sim/echo_sim --card ~/Music --system-dir build/library
```

## Simulator power and display

- `hal_display_set_power(false)` blanks the window. Brightness dims the window (level 1 is about a quarter of full), but screenshots hold the undimmed panel.
- The battery is fixed: 80 % by default, or `--battery N` and `--charging`.
- Gain, output and the equalizer are stored but don't change the sound.
- `hal_power_off()` ends the run loop, and the simulator exits normally.

## Simulator automation

In headless mode the simulator uses a virtual clock (16 ms per frame), so runs are deterministic. `--keys` plays a comma-separated script (`up`, `down`, `play`, `menu`, `back`, `power`, each optionally `:long` or `:held`) for driving screens in screenshot runs. The grammar and the hold times (a tap 32 ms, `:long` 1,120 ms, `:held` 4,800 ms, 128 ms between keys) are `core/key_script`, shared with the debug loop. For example:

```sh
build/dev/platform/sim/echo_sim --headless --frames 120 --keys down,down,down,play --screenshot shot.bmp
```
