# Architecture

The design record of Gnarlyr, firmware for the full-size Snowsky Echo. It is built on Podium 4.5.9, which is forked from EchoPod, the Echo Mini firmware (`../UPSTREAM.md`). The app layer is portable C. It runs in a desktop simulator during development and on the device on top of a thin hardware layer.

Most of this record was written by EchoPod's and Podium's authors together with the code. Timings, failures and other results it describes as seen on a player or on a particular computer are theirs, from their players, and are kept because they explain the design; this project has not repeated them. Gnarlyr developer builds have run on the owner's full-size Echo; the checks actually repeated on that unit are listed in `known-issues.md`.

## Layers

```
platform/sim        platform/device
        \                  /
         implement  hal  (interfaces only)
                     |
                    app          composition root: theme, screens, player, stores, main step
           /     /       \        \
         ui   fonts    settings   hal
           \   /           |
            gfx        playback
              \            |
               \        library
                \         |    \
                 \        |   image
                   \      |    /
                      core
```

| Layer | Path | May depend on | Purpose |
|---|---|---|---|
| core | `src/core` | nothing | Pure logic: deadlines, key gestures, frame stats, UTF-8, string building, formatting, hashing, seeded random, the power policy, the DAC identification decode and text, the key-script grammar, the debug event ring, the string catalogue and the language pack reader (see Languages) |
| gfx | `src/gfx` | core | RGB565 colors and blending, rectangles, clipped canvases, strip rendering, 4-bit anti-aliased text, images drawn into perspective quads |
| fonts | `src/fonts` | gfx | Generated glyph tables (see Generated code) |
| ui | `src/ui` | core, gfx | Screen interface and stack, navigation intents, list view, menus, choice screens, messages, toasts, header and status icons, the icon set, labels, marquee, fades, Cover Flow layout and motion, theme type |
| image | `src/image` | core | Cover decoding for the rescan: a bump arena, a buffered reader, the 112 px area-average grid, inflate, PNG and JPEG (see Covers on the device) |
| library | `src/library` | core, image | Byte sources, a 4×512 B block cache, the library database reader and its content fingerprint, browse queries, the favorites set and the covers file reader (see `docs/library-format.md`) |
| codec | `src/codec` | core | FLAC decoding (up to 2 channels, 24 bits, 4,608-sample blocks) from a read callback, with header and frame CRC checks, and seeking by bisection on frame headers; ALAC decoding of one MP4 packet at a time (16, 20 and 24 bit, mono and stereo) into a caller-owned 32 KB state; bounded, CRC-checked [Ogg packet input](ogg-packets.md) for decoder integration |
| playback | `src/playback` | core, library | Play queue (list order, songs shuffle, album shuffle, repeat, gapless look-ahead, playing a stored order), the resume file format, and the storage of edited queues, the session journal and mixtapes (`docs/playback-store.md`) |
| settings | `src/settings` | core, playback | The settings values, their defaults and option tables, and the settings file format |
| hal | `src/hal` | core (types only) | Hardware interfaces: display (with power and brightness), input, clock, files, audio (with gain and output), power (battery, power off), system (firmware tag, CPU clock), Bluetooth (module power, scan, pair, disconnect, status), language (the pack memory and the packs built into the image) |
| app | `src/app` | core, gfx, fonts, ui, library, playback, settings, hal | Default and board themes, board layout (see Boards), screen tree, library, settings and favorites stores, the language loader, cover cache, player controller, browse, Cover Flow, Settings and Now Playing screens, frame overlay, the main step |
| platform | `platform/*` | app, hal, codec, the OS or SDL | Implements hal and owns `main()` |

The CMake targets enforce these rules. Each module exposes only its own `include/<module>/` directory, and a module can only include headers from targets it links. Anything in a module's own directory, outside `include/`, is private.

## Screens and input

- A `Screen` is a title plus callbacks: `enter`, `handle_key`, `update` and `draw`. `handle_key` returns a `ScreenAction` (none, push, pop, or pop to root), and the app applies it to the `ScreenStack`. Screens never reach into the stack themselves.
- Raw key transitions come from `hal`. `core/key_tracker` turns them into gestures (press, long press, repeat), and `ui/navigation` maps gestures to intents (previous, next, select, back, home). Remapping buttons is a change in one place.
- Each key has a gesture type: tap-or-hold, repeat (press on down, then repeats), or tap-hold-repeat (tap on release, long press, then repeats). The volume keys repeat, except on screens that set `hold_volume_keys` (Now Playing), where they're tap-hold-repeat so a hold can skip tracks. The app switches the type whenever the top screen changes.
- Screen instances are static and owned by the app's `AppScreens`. There is no heap.
- **Status bar (`ui/status_bar`):** resident code draws fixed-size playback, Bluetooth, shuffle and lock icons, optional speaker plus player volume (0–60), repeat, queue position and battery percentage, the known wall clock, and the battery. Text uses the 16 px small font in all three text sizes; icons use `status_icon_size` in both orientations. Repeat Off draws nothing, All uses the repeat glyph at the status size, and One adds the same small song badge used by shuffle. Volume and repeat follow `PlayerStatus`. The USB screens draw their own header, and the USB DAC screen shows the player-side `dac_volume` in its details whatever the status-bar choice.
  - `status_bar_layout` computes the selected items and their rectangles once per draw. It preserves the battery, existing left icons (playback, Bluetooth, lock and shuffle) and any landscape title, then admits volume, position, clock, repeat and percent in that order. A lower-priority item may use space a wider higher-priority item could not use, but never displaces an admitted item. Optional items keep a full padding from the left group and any centred content, with half-padding gaps within groups. Repeat sits after shuffle and before volume when it fits. Portrait centres position in the status band; landscape shows it only when the title is absent or empty. A present landscape title suppresses position and reserves its measured width before fitting other items. `status_bar_clock_fits` uses this same selection. `status_bar_position_text` formats `STR_STATUS_PLACE` (`{0}/{1}`) and accepts an optional prefix followed by a space, allowing a future tape side such as `A 3/8`; an empty queue has no label.
  - The battery body frames the icon height with one pixel above and below, is thirteen eighths as wide as it is tall, and adds a nub a fifth of its height wide. At the 14 px icon size it is 26×16 px, 29 px including the nub, fitting portrait's 20 px band. The border is an eighth of the body height, with a one-pixel gap before the fill. Solid remains the default; its fill is proportional with a three-pixel minimum for nonzero charge. Segmented uses five bars: zero at 0%, then one for 1–20%, two for 21–40%, through five for 81–100%. Healthy segments take the success tint; at 15% or less the fill takes danger, and at 5% or less the outline and nub do too. Tints mix one third toward header text for contrast. USB power uses success fill. Both styles reuse the clipped Bolt: header text with a background halo while charging, plain header background once charging stops, preserving the border. There is no time-driven status-bar battery animation. The larger charging screen retains its own breathing animation.
  - `current_status_bar` reads the settings switches, formats volume and position into resident `AppState` buffers and formats the known wall clock through `clock_face`. `view_stamp` includes volume, repeat, queue number/total, the status switches, percent switch, battery/USB/charging state and wall-clock minute; unchanged values do not request a new frame. Settings UI and choice handlers stay in the settings module. E13 below stores the status choices, and the companion and language tools validate the installed build's layout before accepting them.
- A long Play is `NAVIGATION_OPTIONS`. Lists hand it to their `hold` action; in browse lists it toggles an album's favorite.
- Smart Play: in a browse list, ▶‖ on the track the player already has loaded (playing or paused) pushes Now Playing without restarting it. ≡ pushes Now Playing from other screens while the player has a track; on Now Playing it opens Quick Settings.
- Lists draw the selected row on a flat tinted surface with an accent rail and two accent end caps, a › chevron on rows that open another screen (`ListModel.opens`), and a slim inset scrollbar thumb. Menu items can be hidden by a `shown` callback, and a menu can give the right of its content to a side panel (`MenuPanel`). Home uses that for `home_art`: the playing album's cover, or library covers cycling every 5 s when nothing is loaded, over a theme backdrop clipped to the panel. Captions have a solid background for readability; Home lists Now Playing last and only while the player has a track.
- Now Playing uses Menu for Quick Settings and hold Menu for Lyrics. All its single-button tap and hold gestures were occupied, so Up Next moves into the panel and stays on Home; Menu keeps its existing tap/hold timing. `screens/quick_settings_screen` belongs to `views`, with only its target pointer and command dispatch resident. It shares `settings_actions` source with the Settings module, compiled separately into both modules, and uses `headphone_store_commit` for profile changes. Panel state lives in `AppScreens.modules.views`, and each entry refreshes saved EQ slots. The list uses shared theme metrics, a value below each label and a footer with the Play/Back actions. `QuickSettingsSpeed` supplies availability, current text and cycle callbacks for a future speed implementation; an absent hook hides the row. The power policy retains the selected sleep duration so both screens show the same timer, which remains session-only.
- Settings is a menu whose rows show their current value. Every row opens the same `ChoiceScreen`, re-initialized from a table of `SettingChoice` entries (title, options, current, choose), and the current option gets a ✓. Custom EQ opens `screens/equalizer_screen` instead: a scrolling list of the ten bands with their gains and a "Save to slot" row; ▶ starts adjusting the selected band (the header reads "1 kHz: vol ±"), vol± change it by 0.5 dB within ±10 dB and apply it at once, and ▶ or ↩ stop adjusting and save. It shares its memory with the `ChoiceScreen` (a union in `SettingsScreens`), since only one of them is open at a time.

## Power

- `core/power_policy` decides what keys mean for power. A tap of Power turns the screen off or on, and a long Power asks for shutdown. With the screen off (after a tap or a timeout), ▶‖ and vol± are background keys: the app maps them as on Now Playing (tap vol± for volume, hold vol± to skip, ▶‖ to pause) and runs them without waking the screen. ≡ and ↩ do nothing. While the screen is off, the volume keys use tap-hold-repeat on every screen, so a hold skips. The policy also owns the screen timeout and the sleep timer.
- The app runs each key event through the policy before the screen sees it. When the policy turns the display on or off, the app calls `hal_display_set_power` and stops rendering while the screen is off. Settings are saved each time the screen goes off.
- Shutdown (long Power, or the sleep timer running out) saves the resume file and settings, pauses playback (the same fade to silence as Pause), turns the screen off and calls `hal_power_off()`. The simulator then quits. The device stops the audio path the way stock 2.0.0 does before the rail drops: DAC mute pin and volume muted, outputs and serial port powered down (see Pause standby), headphone amp and DAC supply (GPIO2.2) off, I2S stopped, then 1 s for the DAC supply to discharge before cutting power. Cutting power with the output live crackles in wired headphones.
- Battery level (`device/battery_gauge`): the battery is read once a second, and the percent comes from the average of the last 64 readings (about a minute) through RECHO's 11-point curve (3450 mV = 0 %, 4200 mV = 100 %; stock shows only 5 bars, full above 3830 mV), so short dips under load (a song starting, card reads, the backlight) don't show. While charging it reads 50 mV lower and never shows more than 99 %, since the charging current lifts the terminal voltage most near full (stock shows full on the cable only at 4250 mV or once the charger reports done). The average restarts from the latest reading when USB power comes or goes, so the charger's lift doesn't linger after unplugging. The low-battery check and Settings → About → Battery use the last 8 readings. The shown percent follows the power source: on USB power it rises with any 2-point change but only falls by 10 points or more, on battery it moves both ways after a 3-point change, so the percent sags under load (backlight, 200 MHz) and recovers when the load ends. Plugging in or unplugging therefore can't make the number jump.
- Low battery (`core/low_battery`, stock's rule): every 250 ms the app reads the battery, and if it stays below 3450 mV for 2 s without USB power, it shuts down the same way with "Battery low" in place of "Goodbye".
- CPU clock (stock's rule: the clock follows the work, never the screen): 200 MHz while the screen is on or audio is up, 96 MHz (stock's floor) only with the screen off and `HalAudioStatus.idle` true (output and core 1 down, 3 s after playback stops or in pause standby, below). The device's audio HAL raises the clock to 200 MHz before it starts core 1, so a screen change never parks core 1. A USB session runs at 96 MHz at least.
- Pause standby: 30 s after a pause (`PLAYER_PAUSE_RELEASE_MS`), `player_update` saves the position (`player_release_output`) and calls `hal_audio_release`. On the device that powers down everything the paused output still held: the DAC path stops (the DMA channel stops, I2S1 is held in reset with its pins back to GPIO inputs, both CS43198 power their outputs down, the headphone amplifier enable and the DAC supply GPIO2.2 go low and the DAC reset is held), and core 1 is parked with its clocks gated and its power domain off. With the screen off the clock then drops to 96 MHz. The player stays paused with its queue, Up Next, track and position; the volume, gain, output and equalizer stay in the audio HAL and ReplayGain is read again from the library at the resume. `player_in_standby` reports the state and the debug event log records it as `player standby <track>`. The Bluetooth link follows the player's paused state as before, so standby leaves it connected. Play (▶‖, the headset button or the earbuds) reopens the track at the saved position through the same path as a cold resume and fades in from 40 dB below the volume; a skip starts the next track, and a seek only moves the saved position. Positions are kept in milliseconds, so the resume repeats at most 1 ms of audio and skips none; MP3 seeks are approximate (Xing table or byte proportion), so an MP3 can resume a little away from where it paused. The emulator scenario `test_a_long_pause_rests_in_standby_and_play_resumes_at_the_same_sample_with_a_fade` measured 23 ms from the key release to the DMA starting again for a WAV (6 ms for a resume within the 30 s), with the DAC start-up stubbed. That start-up holds about 214 ms of waits and about 150 I2C transfers at 100 kHz, so on the player a resume from standby should take roughly 300 ms more before the fade begins; this estimate has not been measured on the player. Standby does not touch the power policy: auto off still counts from the last key, and the sleep timer runs on. While a USB DAC session streams, `hal_audio_release` leaves the output alone, and the player has already handed the output over (`app_release_audio`), so its timer cannot fire. The 30 s grace keeps the resume instant for short pauses while the two DACs' playback quiescent draw (Cirrus DS1156F2 table 3-17: about 26 mW each at 1.8 V, against 11 µW with the supplies off) stops soon after a longer one.
- DAC power-down order (Cirrus DS1156F2, example 5-1): with the mute pin high and both PCM volumes at mute, the status registers (`0x0F0000`, sticky and read-to-clear) are read once, PDN_HP (`0x020000` bit 4) is set by read-modify-write on both chips, each chip's PDN_DONE_INT (status bit 0, which latches even while masked) is polled every 1 ms for up to 150 ms in all, and only then PDN_ASP (bit 6) is set, before the Class H write, the amplifier enable, the reset and the DAC supply. The power-up order (`dac_configure`) already follows example 5-3: the pop-free settings `0x010010` = `0x99` and `0x080032` = `0x20`, ASP then HP powered up, 12 ms, then both restored.
- Waking draws the first frame before the backlight comes on (stock waits for 4 frames), and on the device the backlight then fades in over 200 ms (`device/backlight` ramp, from 1 % to the level's duty on the PWM, advanced by the main loop), so the backlight's switch-on current doesn't land at once on top of the drawing and the audio load.
- With the screen off, the device's main loop runs WFI once per pass, as stock does; SysTick (1 ms) wakes it, and the audio ring holds over 80 ms.
- Auto off (Settings, stock's options: Off, 1, 5, 10 min, default 5): `core/power_policy` counts from the last key press; the app holds it off each step while a track plays or USB power is present.   `Settings.status_items` retains the complete E13 byte. This feature reads and changes only bits 0–3; the other branches' bits 4–7 round-trip unchanged. Battery percent remains solely in byte 5 bit 3. Clock always appears when its time is known and it fits. An old zero E13 keeps today's defaults. Status choices do not use E0–E3 or E11–E12. Controls remains the last Settings row; Status bar opens its own five-choice submenu in the settings module.

  The Home item indices are those of `APP_HOME_ITEMS` (`app/app_screens.c`): 0 Music, 1 Audiobooks, 2 Podcasts, 3 Settings (`SETTINGS_HOME_SETTINGS_ITEM`), 4 Now playing, 5 Up next, 6 Mixtapes, 7 Listening, 8 USB mode, 9 Clock. Settings can never be hidden, so Home always keeps an item. `rewind_on_resume` drives Rewind on resume (see Playback) and `safe_start_volume` with its level drives Safe start volume (see Settings and favorites); `track_transition` and `transition_tenths` drive Transitions (see Playback); `clock_24h` drives Clock format through `wall_time_24h` for Clock and status-bar time (see Wall clock).

  **Home order rule.** A build has N Home items (`SETTINGS_HOME_ITEM_COUNT`, 10 today, at most 10 `SETTINGS_HOME_ORDER_SLOTS`). The stored order is the longest run of leading nibbles that is a permutation of 0..L−1 with every later nibble zero; its length L is the number of items the saving build had. The order is valid when L is at least 9 (`SETTINGS_HOME_FIRST_ITEM_COUNT`) and `home_hidden` sets only bits below L other than bit 3. A build with more items than the file (L < N) appends items L..N−1 at the end, visible; the next save writes all N. A build with fewer items than the file (L > N, a file from a newer build) drops the items it does not know, keeps the others in their saved relative order and clears the hidden bits of the dropped items; the rest of the file loads as saved. A new Home item therefore takes the next index, never reuses or renumbers one, and the tenth item uses the high nibble of E8 and bit 9 of the mask. `settings_home_unpack` implements the rule; `tools/echo_language.py` applies the same rule with N read from the installed build's `settings.h`. The ten persisted IDs stay stable: Music 0, Audiobooks 1, Podcasts 2, Settings 3, Now playing 4, Up next 5, Mixtapes 6, Stats 7, USB Mode 8 and Clock 9. ID 4 remains in the stored permutation for format compatibility, but its position and hidden bit are ignored: Home always prepends Now playing while a track is loaded, including paused playback. Home keeps its compact list rows; the existing artwork caption shows the track title when its panel has room. Settings → Home screen omits ID 4, edits the other nine items and writes ID 4 at the end on a change. Reset uses order `0,6,7,8,9,1,2,5,3,4` and mask `0x0026`, so the visible default is Music, Mixtapes, Stats, USB Mode, Clock, Settings. Home filters hidden items, shows Up next only with a track, and shows Audiobooks and Podcasts only when their shelf exists. The two shelves are also available after the library views in Music, with the same presence rule.

  On settings load, after unpacking, an ascending order `0..9` with a zero hidden mask adopts the new default. This includes the old nine-item default after Clock is appended. A changed order or any hidden bit preserves the saved order and mask; the automatic Now playing rule still applies. The migration changes only the Home fields and needs no new settings bytes or version. `settings_home_unpack` and the host tools continue to validate the persisted ten-ID format, including old ID 4 positions and masks.
- Brightness 1–10 maps to a backlight duty of 20, 25, 31, 38, 46, 55, 65, 76, 88 and 100 % (`device/backlight`). Below 100 % GPIO2.4 runs a 25 kHz PWM (`BACKLIGHT_HZ`), whose period follows PCLK and is reprogrammed after every clock switch. The PWM runs as the Rockchip SDK sets it up (`PWM_CTRL` `0x10003`: continuous, duty polarity negative), so the duty register counts the part of the period the pin is **low**: `backlight_duty` writes `period − period × percent / 100`. The SDK's own backlight table works the same way (rate 10 is its brightest, 85 its dimmest). Writing the lit share there instead inverts the levels.

## Wall clock

`hal_clock_wall` (`hal/clock.h`) gives the time of day as seconds since 1970-01-01 in UTC, the local offset from UTC in minutes and where the time came from: `HAL_WALL_UNKNOWN` (no time; the seconds and offset are 0), `HAL_WALL_COMPUTER` (set by the companion on the computer) or `HAL_WALL_PLAYER` (set in Settings or restored from the clock chip). The app never derives a date from uptime; whatever is shown or recorded comes from this call, so a further source (the clock chip, `hardware.md`) only has to set it.

- **Device:** `board/wall_time.c` keeps a `device/wall_clock`: the UTC seconds and the millisecond count at the last whole second. Each read moves both on by the whole seconds since, so the time follows `hal_clock_milliseconds`, which the SysTick clock keeps through every CPU clock change and coasting (`tick_clock_set_rate`). The main loop reads it every pass, so the 32-bit millisecond count wrapping after 49.7 days costs nothing; a read must come at least that often, and the USB session loop, during which the main loop is idle, never lasts that long. The running time is restored from the battery-backed clock chip after restart or power-off, then advances in RAM. The offset is kept separately in settings.
- **Startup recovery:** `board_wall_time_start` schedules one attempt two seconds after startup has finished, after `board_power_hold`, `app_start`, splash setup and the main-loop handoff. `board_wall_time_keep` services it on an idle main-loop pass only after storage preparation and busy UI work have finished and `hal_audio_status` reports stopped with its output idle. A USB session owns the main thread and cannot run this service. The resident `hal_clock_restore_wall` wrapper skips a missing extension; the extension calls the existing `hal_system_rtc_read`, including its 10 ms waits and complete bus restoration. A clear VL flag, valid BCD fields and calendar date, a weekday below seven and a year from 2024 to 2099 are required. Otherwise time stays unknown, with no retry that boot. Valid UTC is combined with the saved offset and installed as `HAL_WALL_PLAYER`, which the listening log treats as known UTC. A Mac time file or manual save that already made time known cancels the pending recovery, so startup never overwrites a newer source.
- **Offset persistence:** settings v15 E11–E12 hold the exact signed UTC offset in minutes, under the existing settings checksum and internal-volume write pattern; the file stays 58 bytes. Existing files default to UTC. A manual RTC write must pass readback and save the offset before updating wall time. The Mac time-file path saves the offset before applying its running time, and reports a settings-save error if that write fails. Other stored settings keep their existing fields. The companion validates these bytes against the installed build and preserves them when changing another setting or language.
- **Time file:** the companion writes `/.gnarlyr/time.bin` on internal storage just before it ejects the drive. When a storage session ends with every drive ejected, the USB overlay (`board/time_file_take.c`) reads the file, deletes it whatever it holds, and sets the clock if `device/time_file` accepts it; this comes before the update check, so an update's checks do not delay it. A session that ends by unplugging deletes the file unread: how long ago it was written is unknown, so a stale time is never applied later. A time written while the drive stays mounted waits for the eject, so the companion writes it only right before one. At start-up, after `app_start`, the extension module deletes any time file it finds on internal storage: one that is there at power-on was written before it, for example while an earlier firmware that ignores the file was running, and is never applied at boot. If extension code is missing, boot cleanup waits for a later boot; an ejected USB session still reads any file present then. The clock is set to the file's time at the moment the overlay reads it, so it runs late by the time between the companion writing the file and the drive being ejected, a few seconds. The file is 32 bytes, little-endian:

  | Offset | Bytes | Content |
  |---|---|---|
  | 0 | 4 | `DSTM` |
  | 4 | 2 | version, 1 |
  | 6 | 2 | offset from UTC in minutes, signed, −720 to 840 |
  | 8 | 4 | seconds since 1970-01-01 00:00 UTC, 2025-01-01 to 2099-12-31 |
  | 12 | 16 | 0 |
  | 28 | 4 | FNV-1a of bytes 0–27 |

  A file of any other size, marker, version, reserved bytes, checksum or range is ignored.
- **On-device setting:** Settings → Date & time follows Clock format and precedes Brightness; Controls stays last. The cold settings module owns `app/screens/set_clock_screen`, its staged year/month/day/hour/minute/UTC-offset fields and its short summary buffer. It uses the shared resident `core/calendar` conversion and month-length functions and `core/clock_face` formatting; The views module and extension call the same conversion helpers; Calendar alone keeps grid building and month stepping in the views module. Years clamp to 2024–2099, changing month/year clamps the day, hours and minutes wrap, and the offset steps by 15 minutes between −720 and +840. Vol± changes the field, Menu advances, hold Menu goes back, Play saves and Back cancels. The local fields convert to UTC by subtracting the offset; seconds are zero. `hal_clock_set_wall` dispatches through the verified extension entry to the existing `hal_system_rtc_set` bus transaction and readback. Only success calls `board_wall_time_set` with `HAL_WALL_PLAYER`; missing extension, no acknowledgement, timeout or mismatch leaves the running wall clock unchanged and shows an error. A later accepted Mac time file replaces both the UTC value and offset; a later manual save replaces the last file. Daylight-saving changes remain manual; startup uses the persisted offset. The listening store snapshots UTC and offset at each new play, so later plays use the new time and earlier/in-progress play timestamps remain unchanged.
- **Simulator:** the clock is unknown unless `--clock now` (the computer's time and offset) or `--clock UTC_SECONDS` with an optional `--utc-offset MINUTES` (a fixed start that runs with the simulator's clock, for deterministic captures) is given. The same `hal_clock_set_wall` entry writes the simulated RTC registers and changes the simulator's running wall clock, also when it started unknown or with `--clock now`.
- **App:** `app/wall_time` turns `hal_clock_wall` into local seconds (`WallNow`) and is the one place that decides 12- or 24-hour time, `wall_time_24h(settings)`; it reads `Settings.clock_24h`, selected by Settings → Clock format after Screen timeout. The default is 24-hour; 12-hour uses the translated AM/PM markers. The stored version-15 extension bit is unchanged, and Controls remains the last Settings row. `core/clock_face` splits local seconds into the hour, minute and second and formats `09:41`, or `9:41 AM` through `STR_CLOCK_12_HOUR`, `STR_CLOCK_AM` and `STR_CLOCK_PM`. The app's redraw stamp (see When a frame is drawn) includes the local minute while the time is known, so anything showing the time is drawn once when the minute changes and otherwise rests.
- **Clock and Calendar:** two screens in the `views` module (`app/screens/clock_screen`, `app/screens/calendar_screen`). Clock shows the weekday, the time in the title font enlarged to the largest of 1×, 2× or 3× that fits (with AM or PM beside it in 12-hour time), the date (`STR_CLOCK_DATE`, in the small font where the body font does not fit) and `Play: calendar`; Play opens Calendar. Calendar opens on the current month with the month and year as its title, a row of short weekday names from Monday, and the days in up to six weeks; today has the selection colour behind it. Volume moves a month at a time between January 1970 and December 2105 and Play returns to the current month. Its rows grow up to a line of the body font plus the padding and the grid sits centred, and the days use the small font where the body font's widest day would not leave a gap. Without a known time both show `Time not set` and how to set the clock, centred above the hint. `core/calendar` converts days since 1970 to dates and back (Gregorian leap years), gives the weekday from Monday, a month's grid and steps months. `test_calendar` (leap years, day zero, known dates, every day from 1970 to 2105 both ways, grids that start on Monday including 4- and 6-week months and leap Februaries, stepping across years and the limits), `test_clock_face` (24- and 12-hour text, midnight and noon, the offset) and `test_clock_screen` (weekday and date, the offset deciding the date, the unknown state on both screens, Play and Back, month stepping and Play returning to today, today's mark only in its month, the layouts at every size and orientation, the captures) cover them.
- **Tests:** the deferred-read, cold-restart, no-ack and boot/first-audio timing emulator scenarios cover recovery, including no output underruns while a read is held off for playback. `test_stores` covers durable offset writes and failures, `test_settings` covers signed offsets and bounds, and `test_rtc_registers` covers VL, malformed BCD, out-of-range years and leap dates. `test_time_file` (the layout, every byte of the seal, the marker, version and reserved bytes under a fresh seal, the ranges), `test_wall_clock` (never set, whole seconds, frequent reads, the millisecond count wrapping, a year of uptime read once a day, CPU clock changes and coasting through `tick_clock`), `test_set_clock` (local/UTC conversion, editing, range and leap-day clamping, hour formats, cancel, errors, missing extension and all six layouts), `test_clock_write` (extension dispatch and absence), the app/status-bar and listening timestamp checks, and the emulator scenarios for Settings writes with chip registers/status-bar checks and for a valid and a damaged time file at the end of an ejected session.

## Settings and favorites

- **ReplayGain:** Opus R128 track/album tags are fallback gains in the library scanner and desktop indexer, converted from Q7.8 dB at -23 LUFS to the -18 LUFS ReplayGain reference (+5 dB before centidecibel rounding). Valid standard ReplayGain gain comments override the corresponding R128 value regardless of comment order. Header output gain stays in the decoder. The optional checked library extension supplies Q16 track/album and peak-limited amplitudes. `player` selects a value per current/queued token, and the engine combines it with digital volume outside the PCM loop. Live changes retain buffered audio and do not reopen the source. Settings version 14 stores mode and clipping flags at byte 5 while keeping the 42-byte layout (version 15 keeps byte 5 and grows the file to 58 bytes); earlier versions default to Off with peak protection enabled. See [ReplayGain](replay-gain.md) for cache validation, metadata mappings and migration.
- `app/settings_store` loads `/.gnarlyr/settings.bin` (defaults if it's missing or invalid), applies brightness, gain and output through the HAL, and only writes when the encoded bytes changed. Settings belong to the player, not to the music: the file lives on internal storage whether the music comes from the card or from internal storage, through `hal_internal_file_read`, `hal_internal_file_write` and `hal_internal_file_reserve` (same contract as the `hal_file_*` calls, but always the internal volume). `app/card_files` reserves it there. A player upgraded from an earlier build has its settings on the music volume: when internal storage has no valid `settings.bin`, the store loads that copy and the next save writes it to internal storage; from then on the music volume's copy is ignored. On the device, `board/internal_volume` mounts the internal volume on first use, with its own `FatVolume` shared with `board/update`, and the file HAL uses the music volume itself when that already is internal storage. `storage_reset` forgets the internal mount too. In the simulator the system directory stands in for internal storage.
- `hal_dir_open`, `hal_dir_next` and `hal_dir_close` list a folder: name (UTF-8, up to 767 bytes), folder or file, size, and a hidden flag (the FAT/exFAT hidden attribute on the device, a leading dot in the simulator). `.` and `..` are never listed. On the device, `fat_open_directory` and `fat_next_entry` walk FAT16/FAT32 entries (long names, or 8.3 names with the lowercase flags) and exFAT entry sets; up to 16 folders can be open at once. macOS's `._` files are listed like any other file.
- Folder entries are read in runs of up to 8 sectors, like file data, and writes of whole sectors go out as one multi-block write without reading them first. `fat_open` remembers the last folder it found (path and entry, up to 255 bytes of path) and starts the next lookup there when the parent path matches, so opening the tracks of one album walks only the album's folder. Mounting or reserving a file forgets it. EchoPod's author reports that on a 1,563-track card this took opening files from 40 s to 1.8 s, and the track scan from 61 s to 19 s.
- On the device, `hal_file_write` overwrites an existing file in place from offset 0 (`fat_write`, FAT16, FAT32 and exFAT) and fails if the file is missing or too short; it never allocates clusters or changes a directory entry. Every reader checks its magic and accepts a longer file, so a zero-filled file reads as missing.
- The player makes its own files. `app_start` only marks the files as pending; the next `app_step` calls `hal_file_reserve` (through `app/card_files`) for `library.db` (4 MB), `covers.bin` (80 MB), the 24 MB scratch file and then the 4 KB files (`settings.bin`, `resume.bin`, `favorites.bin`, `scan.bin`, ...). Files that exist are skipped within the same step. Each missing big file is made in its own step after a "Preparing storage / File N of M" notice lights the screen, so the main loop (USB, stall watch) runs between files; while charging the files are made silently, one big file per step. `app_preparing` reports the phase. A file that exists is left alone, whatever its size. A missing one is created at its size, along with `/.gnarlyr` if needed; its first 4 KB read as zero and the rest is left as the card had it, so creating 80 MB costs a few hundred writes rather than 163,840. When `library.db` was just created the app asks for a rescan, so a new card is scanned on its first start. If any file doesn't fit, the app toasts "Storage is full". `tools/save_files.py` is now only a development helper.
- `fat_reserve` looks for free clusters from an allocation hint (FSInfo's next free cluster on FAT32, else the end of the previous allocation, kept in `FatVolume`) to the end, then wraps to the start; a hint that is not a cluster is ignored. `fat_delete` removes a file: its entries (long-name entries and the short entry marked `0xE5`, exFAT entry set with the InUse bit cleared), its FAT chain in every FAT copy, the exFAT allocation bitmap bits, and updates FSInfo's free count. Directories are refused.
- On the device, `fat_reserve` (`device/fat_reserve.c`, `fat_create.c`, `exfat_create.c`) creates the missing folders and the file as one contiguous run of clusters, first fit. Names are printable ASCII up to 64 characters. FAT16/FAT32 get an 8.3 entry with the lowercase flags when the name fits (`settings.bin`), otherwise long-name entries plus a `~N` short name that's unique in the folder (`.gnarlyr` → `FRESHB~1`, `favorites.bin` → `FAVORI~1.BIN`); the chain goes into every FAT copy and FAT32's FSInfo free count and next-free hint are updated. exFAT gets a File, Stream (NoFatChain, valid length = size) and Name entry set with its name hash and set checksum, and the clusters are marked in the allocation bitmap. The write order keeps a cut-off write harmless: clusters are marked used first, then the start of the data is cleared (a new folder's whole cluster, with `.` and `..` on FAT), and the directory entry goes last (on exFAT the secondary entries before the File entry). A folder whose entries are full isn't grown; that reserve fails. Dates are 2026-01-01, since the player has no clock. While it runs, every card read beats the stall watch. `test_fat_create` creates files on all three fixture cards and saves them, and `created_cards_pass_fsck` checks the results with macOS's `fsck_msdos` and `fsck_exfat` (through `diskutil image attach --noMount`).
- At start-up the saved volume, shuffle and repeat go to the player first, and then a valid resume file overrides them. The current volume, shuffle and repeat are copied back into the settings before every save.
- **Safe start volume** (`app.c`, `settings_safe_start_volume`): at power-on, also when the player is turned on from the charging screen, after the resume file has set the volume, and whenever the app sees headphones arrive, a music volume above `safe_start_volume_level` is lowered to that level. It is never raised, and nothing happens with the setting off. Headphones arrive when `hal_audio_jack` reports a jack other than the one it reported on the previous step and not none (so plugging into either jack, or swapping one jack for the other, counts; unplugging does not; a jack already plugged in at start-up is not an arrival), and when `BluetoothLink.connected` turns true, which happens when the link first sees the module report the connection. Bluetooth plays through the same DAC volume, so the same level applies. A rescan's restart of the app is not a power-on. The USB DAC keeps its own saved level (`dac_volume`) and is not capped. Nothing re-applies the cap until the next power-on or arrival, so the user can turn the volume up again. A lowered volume asks for a "Volume lowered to N" toast, shown once the screen is on, the splash is over and no other toast is showing (a Bluetooth connection's "Connected to …" toast comes first); it is dropped if the volume has changed by then. The lowered volume is saved with the next settings save. Settings → Safe start volume offers Off, 12, 18, 24, 30 and 36 (the stored level can be any step from 0 to 60; the row shows it, and the ✓ marks the nearest choice).
- The start screen setting pushes the matching path at start-up (for example Home → Music → Albums), so Back still leads home.
- `app/favorites_store` loads and saves `/.gnarlyr/favorites.bin` and toggles albums by key, and counts a revision on every load and toggle. Music → Favorites is a browse screen over the Albums view that only shows the positions of favorite albums, collected in album order. The browse pool keeps the collected list and only collects again when the revision changed. Collecting reads every album's key from the card, so it calls a `between_albums` hook every 8 albums (`favorites_collect`), and the browse screen uses it to run `hal_audio_service`: before this, opening Favorites while playing starved the DMA ring for a second or two and the ring's last 0.3 s played over and over. Favorite albums show ★ before their year.
- Toasts are app-owned. Screens get a pointer to the one `Toast` and show short messages such as "Added to Favorites". The app draws the toast on top of every screen. A toast that does not fit one line in the small font wraps at word boundaries onto up to three lines (`TOAST_MAX_LINES`) and grows upward by a line each; only what is left after the third line ends in an ellipsis.

## Languages

Every text a user reads comes from a language pack. English is the only language shipped. A translation is a text file and a build setting, or a file copied to the player; no code changes. The mechanism follows EchoPod 0.9.0 to 0.11.1; what differs is said below.

- **Catalogue.** `assets/lang/en.txt` is the English source and the catalogue: one `STR_NAME = text` line per string, in ID order, `#` lines as notes for translators. `tools/lang_pack.py` generates the `StringId` enum (`core/strings.h`) from it. Code names a string by its ID and reads it with `i18n_text`; a text built around a value is one pattern with `{0}`..`{9}` placeholders filled by `i18n_format` (`i18n_format_text` and `i18n_format_counts` for one text or two numbers), so a language can reorder the words. Singular and plural are separate strings (`STR_ONE_CHAPTER`, `STR_CHAPTERS`); a language with more plural forms is not served. `\n` in a text starts a new line in a notice. The firmware's name is passed in as a placeholder from `identity.json` and appears in no pack (`tools/tests/test_lang_pack.py` checks that).
- **Pack format** (version 1, little-endian, at most 18,432 bytes):

  | Bytes | Field |
  |---|---|
  | 0–3 | `DSLP` |
  | 4–5 | format version, 1 |
  | 6–7 | string count |
  | 8–11 | size of the whole pack |
  | 12–15 | catalogue hash: FNV-1a over every string name and a zero byte, in ID order |
  | 16–19 | checksum: FNV-1a over bytes 0–15 and 20 to the end |
  | 20–27 | language code, zero padded (1 to 5 letters, digits or dashes) |
  | 28–55 | the language's own name, zero padded UTF-8 (the pack's `STR_LANGUAGE_NAME`) |
  | 56… | one 16-bit offset per string, from the end of the offset table |
  | … | the strings, UTF-8, each ended by a zero byte |

  `i18n_attach` uses a pack only if the magic, the version, the count, the catalogue hash, the size (no larger than the bytes given, larger than the header and table), the checksum, every offset and the final zero byte are right, and the code and name fields end in a zero. The catalogue hash ties a pack to one catalogue: a pack built before a string was added, removed, renamed or moved is refused, never shown shifted. `i18n_pack_info` reads the header alone, for listing. EchoPod's pack had the magic, version, count and size only.
- **Building packs.** `tools/lang_pack.py --pack <code> --output <file>` builds one pack from `assets/lang/<code>.txt` (same `STR_NAME = text` lines, any order; a name left out keeps the English text). It refuses an unknown name, a name given twice, placeholders that differ from the English ones, a code that is not 1 to 5 letters, digits or dashes, a name over 27 bytes, a character some text size cannot draw (see Scripts) and a pack over 18,432 bytes. The CMake cache variable `ECHO_LANGUAGES` (default `en`) lists the packs an image gets, the default language first; each is built into `build/<preset>/lang/`.
- **Three ways to choose a language,** cheapest first:
  1. **Build.** `cmake --preset release -DECHO_LANGUAGES="de;en"` builds an image with two packs whose default language is German. `tools/make_image.py --language-pack` (one per pack, at least one, or the image is refused) stores them.
  2. **Settings → Language.** The row comes after Orientation and is shown only when more than one language is present: a choice of one is not a choice, and a row that cannot change anything is noise on a list that is already long. It lists the packs of the image, then the files in the data folder, each by the name its own pack gives, with ✓ on the loaded one. Choosing saves the code (settings byte 19), loads the pack and rebuilds the screens at once, back in Settings with the Language row selected and the music still playing; EchoPod needed a restart there. If the chosen pack fails a check, the loaded language stays, the setting goes back to it and a toast says "Couldn't load language".
  3. **A file in the data folder.** `/.gnarlyr/lang/<code>.pack` on the music volume (the card, or internal storage without one) adds a language the image does not have, or replaces one it has, without reinstalling. The file's name must be its code. It is read only when that language is chosen, checked like any other pack, and at most 8 languages are listed. A file that is cut short, damaged, too large, built for another catalogue or named for another language is skipped; with the card out, a language that lived on it falls back to the image's default until the card is back. A new firmware version whose catalogue changed refuses older files, so a file must be rebuilt for it.
- **Loading** (`app/language`, called by `app_start` after the settings are read): the chosen language's file, else that language in the image, else the image's first pack, each tried from firmware slot 1 and then slot 2. A candidate is copied into the pack memory only after its header passed, and attached only after the whole pack passed; a pack that cannot be replaced stays loaded. While an installed update waits for its restart nothing is read (the slots hold the new image, whose catalogue may differ) and the loaded pack stays, as the glyph reader refuses reads then.
- **Fallback.** A host build (simulator and tests) has the English text compiled in (`ECHO_BUILTIN_ENGLISH`, `core/strings_english.h`) and shows it when no pack is attached, so tests need no pack. A device build has no English in its code: that is where the code space comes from. If no pack passes its checks on the player, `i18n_text` returns `?` for every string (never an empty one, so rows stay visible and selectable, as a missing glyph shows `?`) and `board/main.c` shows the built-in notice "Text is missing: reinstall the update" at start-up and waits for a key. The second slot makes that state hard to reach: an install interrupted in slot 1 leaves slot 1 with a pack of another catalogue while the boot ROM runs slot 2, and the loader then takes slot 2's pack. `make_image.py` refuses to build an image without a sound pack.
- **In the image.** The packs are placed after the glyph faces in the same free space, sector-aligned, in the order given. The second half of the glyph table's sector (`0x2C0100`) is their table: `DSLT`, count, then offset and size per pack, room for 31. The faces, the overlays and the core 1 programs keep their offsets (`tools/tests/test_make_image.py` builds an image with and without packs and compares), and the packs lie inside the area the trailer CRC covers and the updater writes. `board/language.c` reads the table and a pack's bytes through the glyph reader's one-sector buffer.
- **In memory.** A pack is used from RAM as a whole because menus keep string pointers. The bounded 18 KiB language window is `0x0309A800`–`0x0309EFFF`. The adjacent glyph region is 26 KiB at `0x03094000`–`0x0309A7FF`; it keeps 64 packed glyphs in the unchanged four-way cache. Built-in ASCII bypasses that cache. The linker checks both boundaries and their top-of-RAM limit. The decoder workspace, module slot and application static RAM allocations are unchanged by this repartition. The size report checks every built-in pack against 18 KiB. The format remains version 1: matching-catalogue packs made for the earlier 16 KiB window load unchanged. The companion reads `I18N_PACK_CAPACITY` from the installed build before validating or writing a pack; it refuses a larger pack for an older build before changing any file. The 16-bit text offsets already cover the larger window, so no pack conversion is needed.
- **Scripts.** The base faces cover ASCII, Latin-1 and Cyrillic (U+0400–U+045F, U+0490 and U+0491). Separate Noto Sans CJK faces cover the Simplified Chinese and Japanese characters in the current draft catalogs. The renderer tries the Japanese face first for `ja` and the Chinese face first for other languages, then tries the other face. The subsets are not full CJK fonts: adding characters requires regenerating the subsets and glyph faces. Arabic and Indic scripts require font and shaping support. `lang_pack.py` accepts a character only when every text size can draw it.
- **Text that stays in code.** `tools/literal_allowlist.txt` lists every one with its reason:
  - "Battery low" / "Charge the player to turn it on", shown at start-up before storage is used, and "Text is missing: reinstall the update", shown when no pack could be loaded;
  - the crash screen (`STALL`, `FAULT`, register names), which draws with its own font;
  - the boot trace build's step names;
  - unit symbols (`kHz`, `kbps`, `dB`, `Hz`, `mV`, `MHz`, `ms`), codec names, digits and the equalizer's band names;
  - engineering read-outs in Settings → About: the firmware tag, the jack pin states (`high, boot fn0 in pull`), the headset line's readings, the DAC bytes. Their state words ("Play a track", "Read failed", "Simulated", "No reading", "Not read", "Card", "Internal", "None", "charging", "full") are in the pack;
  - the developer build's extra Bluetooth lines and the frame overlay;
  - the USB bring-up reports and the transfer counters a storage session shows (`USB R… W… E…`);
  - the drive names a computer reads over USB, file names, and library data (tags, the indexer's `Unknown Artist`, `Chapter n` titles, the letters of the fast-scroll index).
- **Layout.** A translation can be longer than its English. Lists cut a row's name and value with an ellipsis and scroll the selected row; titles end in an ellipsis; notices, empty-screen messages (`message_draw`), toasts and the Bluetooth hint wrap at word boundaries (`label_draw_wrapped`, `label_draw_paragraph`) and end in an ellipsis only when their lines run out. A text cut by a full buffer never ends inside a UTF-8 character (`string_builder_append`).
- **Checks.**
  - `test_i18n` builds packs in C and breaks them one field at a time; `test_i18n_fallback` compiles `i18n.c` as the player has it and checks the `?`; `test_language_packs` attaches the built English pack, compares it byte for byte with a pack built by the test's own writer, and checks that the test language changes, brackets and lengthens every string and keeps its placeholders.
  - `test_language` covers the loader: default, chosen, file adds, file replaces, each kind of bad file, slot 2 for a damaged or foreign slot 1, nothing loadable, a pending restart, and the list. `test_app_language` covers the Language row and the switch.
  - **The test language** `qps` is made by `lang_pack.py` from the catalogue: every string in brackets, vowels accented, a third longer. It is built for the host tests only; CMake refuses it in `ECHO_LANGUAGES` and `make_image.py` refuses it in an image. `test_pseudo_language` loads it, walks the screens at the three text sizes in both orientations and reads every text they draw through a spy that stands in for `gfx/text`: a text must have its words inside the brackets, be a unit or codec name, or come from the library, and a bracket left open means a buffer cut the text. It cannot see screens it does not walk (the audiobook shelves, the board's USB and update notices) or text without two letters in a row.
  - `no_text_literals` (`tools/check_literals.py`) fails on a string literal with a word of two or more letters in `src/app`, `src/ui`, `src/core`, `src/settings`, `src/playback`, `library_browse.c` or the board code that the allowlist does not name, and on a listed literal that is gone. It cannot see text assembled from single characters, text in other directories, or a listed literal put to a new use.
  - `test_english_layout` measures the English titles, notices, empty-screen messages, toasts and Bluetooth hints against the header, the notice and the toast at every text size in both orientations.
  - Three emulator scenarios boot the device image with a sound, a damaged and no pack (see Echo image emulator test).
- **Debug loop.** Profiler remains a developer row. USB sense is controlled through the `usb_sense` debug-script command; the obsolete USB sense and Connect USB menu rows are removed. A script `set` line names its setting and option using the loaded language. Update and restart notices read the language pack.
- **Adding a language.** Copy `assets/lang/en.txt` to `assets/lang/<code>.txt`, translate the texts (keep the names and every placeholder; set `STR_LANGUAGE_NAME` to the language's own name), then either build it in (`-DECHO_LANGUAGES="en;<code>"`) or build the one file with `tools/lang_pack.py --pack <code> --output <code>.pack` and copy it to `/.gnarlyr/lang/` on the player. The simulator offers a file in `<system-dir>/lang/` the same way.
- Nothing of this has run on a player (`known-issues.md`).

## Audiobooks and podcasts

- `library/spoken_path` classifies named top-level `Audiobooks`/`Audiobook` and `Podcasts`/`Podcast` folders (ASCII case-insensitive), with `.m4b` files elsewhere recognized as audiobooks. An explicit Podcast folder keeps its type. Both indexers sort spoken word after music and record music counts in the unchanged version-6 library header, so Music lists exclude it. `playback/spoken_shelf` merges the named roots and external M4B books without rewriting their file paths. Chaptered files appear once, as their chapter folder; whole files remain individual books. Home checks this projection when deciding whether to show a shelf.
- Shelf enumeration first visits the named roots, then the spoken partition of the track table. Counting skips chapter-folder lookup; fetching a chaptered book resolves its existing folder only when needed. A forward cursor and last-item cache avoid restarting the scan for sequential visible rows, and a service callback keeps playback fed during enumeration. Independent whole-file books use `BROWSE_SINGLE_TRACK`, which the resume record accepts without changing its format; selecting a paused loaded book continues the existing stream.
- Bookmarks are keyed by FNV-1a hashes of paths, so they outlive a rescan, like favorites: a book's key is its folder's path (`Audiobooks/<Book>`), and a book that is a single file, or a podcast episode, is keyed by its own path. Each bookmark also keeps the track's key, its chapter (its place among its folder's tracks), the position and a finished flag. A track that is a part of a file (`start_ms` or `end_ms` set: a chapter of an `.m4b` or a CUE track) is bookmarked under the file's path hash (`spoken_record_key`), its track key adds its `start_ms` to the path hash (`spoken_part_key`; the same as the path hash when `start_ms` is 0, so older bookmarks stay valid), and its chapter comes from its `number`. The book on the shelf is then the file's chapter folder, whose key (`spoken_folder_key`) is the file's path hash; "already loaded" is decided by `spoken_folder_holds`, a membership test over the folder's tracks. `playback/bookmarks` keeps the 128 most recent, newest first, in `/.gnarlyr/bookmarks.bin` (4 KB, reserved by `card_files`; see `docs/library-format.md`).
- The player marks a track spoken when it starts it (`player->spoken`), after a gapless hand-over and after a restore. For a spoken track:
  - a start from 0 asks `PlayerResume.position_for`, which `app/spoken_store` answers from the bookmark when its track hash matches and it isn't finished;
  - `player_skip` becomes `player_jump`: +30 s or −15 s, and a jump past the end starts the next track. Now Playing's hold-vol± and the screen-off keys go through `player_skip`, so both follow;
  - the queue is built in order (`PlayerListStart.in_order`), and `player_set_shuffle` keeps it in order, while `player->shuffle` keeps the music setting.
- `app/spoken_store` follows the player every step: when a spoken track starts it notes its keys and chapter, puts the bookmark every 5 s and on every play/pause change, and when the track ends or changes it marks the bookmark finished if it was in its last tenth (at most 30 s). The file is written when playback stops, when the track changes, every 30 s while playing, at shutdown and before a USB session.
- Home lists Audiobooks and Podcasts after Music, shown only when the folder exists (checked once when the screens are built). Both are browse screens in shelf mode over the folder: rows get "N chapters"/"Chapter n of N"/"Finished" or "N episodes", and tracks "mm:ss left"/"Played". In Audiobooks, ▶ on a book plays its folder from the bookmarked chapter (the chapter is checked against the track hash and looked up again if the files moved); a book that is already loaded is resumed and Now Playing opens. Hold ▶ on a book or show opens its tracks.

## Library rescan on the device

- Settings → Rescan library sets a flag; on the device, the end of a USB session in which the computer wrote to either drive (internal storage or the card) sets a second flag that first runs a music check, under a "Music / Checking for changes..." notice. macOS writes `.fseventsd` and `.Spotlight-V100` on every mount, so a write alone means little: `library/music_fingerprint` walks the card from `/` with one open folder per level (each folder is opened and listed once; a folder that can't be opened counts as empty; a card deeper than 32 levels gives an incomplete fingerprint), skipping names that start with `.`, and folds every entry's path, kind, size and modification stamp into two FNV-1a hashes plus a count. On FAT the stamp is the raw write date and time and the size is the directory entry's. On exFAT the stamp is the last-modified time converted to UTC with the entry's own UTC offset byte (`fat_exfat_utc_stamp`, in 2-second units since 1970; no valid offset counts as UTC), and the size is the stream's data length, not its valid data length; files of 4 GiB or more aren't listed. That is what Windows, macOS and Linux report for the same file, so `tools/echo_sync.py` can match it without guessing time zones: on one card, 9 files written with a wrong offset (−5:30 instead of +5:30) and 3 incompletely copied files (valid length short of the size) had made every PC fingerprint differ. It is compared with the fingerprint kept in `/.gnarlyr/scan.bin` (4 KB, made by `card_files`; the bytes `DSSC`, the two hashes, the count), and only a difference (or no record, or a walk that failed) asks for a rescan. Every successful rescan stores the fingerprint taken just before it. A requested rescan the next `app_step` runs `library_rescan_run`, shows "Scanning library" with the track count every 250 ms, then restarts the app on the new library and toasts "Library: N tracks" or the reason it failed (no card, no room, too big, a folder too big, a path too long, a write failure, or missing rescan code).
- **Scans that stop.** `app/scan_guard` keeps a 32-byte record at byte 512 of `/.gnarlyr/scan.bin`, the sector after the fingerprint (little-endian): `DSSG`, a running flag, the number of attempts in a row, a write index for the skip list, the mark of the file being read, the mark of a suspect batch and four skipped marks. A card from an earlier build has zeros there, which reads as no scan running, so neither the file size nor the fingerprint changes. A mark is FNV-1a over the path the scan opens (`/Album/01.flac`), then `(hash ^ size) × 16777619`, with its low 3 bits replaced by the phase: 1 a batch of plain tracks, 2 tags (a playlist, or a track named on a second try), 3 a CUE sheet, 4 an `.m4b` (its tags and chapters are read in one open), 5 the cover pass. The overlay opens `scan.bin` once per rescan, sets the flag and then rewrites the record through that open handle (`hal_file_write_open`, so the FAT layer's folder cache stays on the music) before it reads each CUE sheet, `.m4b`, playlist and cover-pass file, and before the first of every 8 plain tracks. A scan that ends, with or without an error, clears the flag.
- At the next start a set flag means the scan stopped (a fault, a stall, power loss), and `app.c` asks for it again by itself. The overlay first moves the mark it finds: an exact mark joins the skip list (the oldest of four drops out); a batch mark makes the scan write a mark before each of those 8 tracks, so a track that stops it again is named and skipped at the start after that. A skipped file is refused when opened: a track, sheet, `.m4b` or playlist counts as unreadable (skipped like a file that can't be read; a sheet's audio file then lists as plain audio), and a cover-pass mark costs only that album its cover. A file whose size changed has a new mark and is read again. Each refusal adds a `storage` event to the debug report whose value is the skipped mark. After three stopped scans in a row the next one leaves out the cover pass (the toast ends ", no covers"); if that one stops too, nothing starts by itself, not even the check after a firmware update, until Settings → Rescan library or a USB session whose music check finds a change, which start the count again. While `/GNARLYR.IMG` waits on internal storage the start asks for no scan at all: the update is installed when the next USB session ends, before that session's music check, as always.
- Cost in the emulator (`test_marking_files_costs_under_half_a_millisecond_per_track`): a guard write takes 1.1 ms; the scan pass of 40 tracks in 4 album folders takes 7 writes (start, end and one per batch of 8 tracks); the background cover pass adds one or two per album. A card of 4,000 tracks in 400 albums takes 2 + 500 writes in the scan pass (about 0.6 s) and 400 to 800 in the cover pass (0.4 to 0.9 s). Writing a mark before every track would have cost 4,000 writes and moved every music open's folder lookup off the cache.
- `app/library_rescan` checks for a music root (`/`) and a reserved `/.gnarlyr/library.db` (its size is the capacity), opens its reserved scratch file and asks `hal_system_load_rescan_code` for a `RescanModuleEntry`. The entry runs `app/library_rescan_job` beside the indexer: HAL callbacks, borrowed scan/listing memory, track and cover passes, progress and timing all live in the overlay. Resident code keeps preflight checks and result messages. Temporary file handles, directory entries and timing counters occupy private BSS after the code; the loader clears it on each load, and the linker and image builder bound code plus BSS to the overlay window. The database goes out through `hal_file_write_at` and is never written unless it fits.
- The indexer is its own library (`echo_library_scan`). The simulator and the tests link it together with `app/library_rescan_job` and return the same rescan entry table directly. On the device it doesn't fit the 157 KB code window, so it's built as `echo_rescan_overlay`: linked at `0x0307A000` against the main ELF's symbols (`--just-symbols`, plus libgcc for the double helpers), with a 16-byte header (magic `EOVL`, size, body CRC, running-code CRC) before the entry table. `tools/make_image.py --overlay` stores it at image offset `0x200000`, beyond the `fw1 end` the header records and inside the area the trailer CRC covers and the updater writes. `board/overlay.c` loads it into HIGHRAM0 for every rescan (see Overlay loader under Device platform). It may be at most `0x18000` bytes: the top of HIGHRAM0 holds the glyph cache.
- `.m4b` files (`library/mp4_chapters`, `library/library_scan_chapters`) are scanned like `.m4a` (`tags_mp4`), and then their chapters are read in the same open: first the Nero `chpl` atom in `moov/udta` (a count byte after a 4-byte version and flags, tried with and without a 4-byte reserved word, then entries of a 64-bit start in 100 ns units, a length byte and UTF-8 text), then the QuickTime chapter text track (`tref/chap` names the track, whose `stts`, `stsz`, `stsc` and `stco`/`co64` tables give each sample's start time and place; a sample is a 16-bit length and the text). The reader keeps the start, the place and the length of at most 255 chapters in `ScanState` (about 2.5 KB) and reads titles only when a chapter is added. Entries that start no later than the one before, or at or past the file's duration, are dropped, the first chapter starts at 0, titles are cut at 63 bytes on a character boundary and an empty title becomes "Chapter n". Fewer than two chapters, or any table or atom that doesn't fit the file, means no chapters and the file is added as one ordinary track. Each chapter becomes a builder track with `start_ms`, `end_ms` (0 for the last), its own duration, `number` n and the file's tags, in a sheet folder named after the file without its extension and flagged as chapters (`LIBRARY_FOLDER_CHAPTERS`): unlike a CUE sheet the folder holding the file doesn't list the file, so the shelf shows one book. `scan_internal` keeps the folder name in `ScanState.sheet_name`. Everything above the player handles chapters as it handles CUE tracks.
- `.cue` files (`library/cue_sheet`, `library/library_scan_cue`) turn into tracks during the walk. When a folder's listing is read, every `.cue` in it is parsed once to find out whether it is usable and which audio file it names (`docs/library-format.md`, CUE tracks), and that file's listing entry is marked so the walk skips it. When the walk reaches the `.cue` it reads the audio file's tags and duration, then parses the sheet again and adds one builder track per CUE track with the sheet's fields over the file's. Each pass has at most the cue file open, so the single file handle of `ScanFileSystem` is enough. A batched listing (a folder too big for the listing memory) marks only within its batch. The parser reads through `playlist_reader` (the same decoding as playlists) and keeps two tracks (the one being read and the one waiting for its end) plus the album's texts: about 4.5 KB inside the scan's memory. `echo_rescan_overlay` stays inside its 0x18000 bytes (95,528 code and BSS bytes used).
- On the device the scratch memory is core 1's RAM (`0x01000000–0x0105FFFF`, 384 KB): playback is stopped, core 1's domain is powered up with the core held in reset, and it's powered down again afterwards.

## Covers on the device

- **Covers come after the library.** The rescan overlay's `run` builds `library.db` only; the app restarts on the new library straight away (browsable and playable) and sets the spare byte of the scan guard record (byte 7, `covers_pending`), which `music_check_covers_pending` also reads at start-up. `continue_covers` in `app.c` then runs the cover pass through the overlay's second entry, `covers` (`covers_run`, `library/cover_build`), whenever covers are pending, no key has been pressed for 3 s (`app.power.last_activity_ms`), no key is waiting, and either no track is loaded or the track has been paused for 60 s (past the 30 s standby, so a short pause keeps its sample-exact resume). A paused track is released first (`app_release_audio`, as before a USB session) because the overlay and the scratch memory take the decoder workspace and core 1's RAM. The pass runs at 200 MHz with the scan's scratch memory and the file adapters, reads `library.db` back and writes `/.gnarlyr/covers.bin` in place through its open handle. Its stop callback (`hal_input_waiting`, or a USB cable that wasn't there when the pass began, `hal_system_usb_sense`) is checked before each album and before every image read, so a key press stops it within one read of the image. A stopped pass writes the index for the albums it finished, keeps every older cover it hasn't looked at, reports the album it stopped at (`CoverStats.next_album`) and leaves `covers_pending` set; the next idle moment resumes from that album (`CoverJob.first_album`). When the pass finishes, or fails for good, the byte is cleared. The app reopens `covers.bin` after every run, so covers appear without a restart. The rescan toast reads "Library: N tracks".
- **Bookkeeping that survives a stop or a resume.** Every index entry still in the library starts kept (`claimed`); an album that is processed and has no usable art, or whose record can't be written, loses its entry, unless the pass is stopping. A separate `placed` set marks albums handled in this pass, so an album key that occurs twice is decoded once. A crash during the background pass is handled like one during the scan: the next start rescans by itself and the cover file joins the skip list; the attempt count the scan left in the guard record carries into the cover pass, so after three stops in a row no covers are built.
- **Settings → Rescan library** runs the music check first. When the music fingerprint matches, the library opens, `scan.bin` names the running firmware and the guard record shows a scan that wasn't cut short (`music_check_settled`: not running, at most one attempt), it shows "Library is up to date" and rebuilds nothing; otherwise it rescans. A no-change request on 4,003 tracks therefore takes 1.5 s in the emulator (the 1.2 s fingerprint walk) instead of a 27 s scan pass.
- For each album (in album order) it takes the first art it finds, as `tools/cover_export.py` does: the embedded picture of the album's first track (a front cover wins over any other picture, `track_tags_read`), otherwise `cover`, `folder`, `front` or `albumart` with `.jpg`, `.jpeg` or `.png` (any case, the first by name when several share a stem) in the album's folders in track order (at most 16 different folders, each listed once per pass however many albums share it). An embedded picture that fails to decode is replaced by the folder image; echo-sync applies the same rule, refusing what the player can't decode. A key already stored is skipped.
- Embedded art is read through `tag_picture_open` (`library/tags_picture`), which hands the decoder an `ImageSource`: raw bytes for most formats; for Ogg and Opus, the base64 `METADATA_BLOCK_PICTURE` text decoded 64 characters at a time straight from the Ogg pages (`tags_ogg_stream_read`, the reader the tag scan uses), skipping the FLAC picture header, so a picture of any size is never held in memory; for unsynchronised ID3 tags, a view that drops each `0x00` after `0xFF` (whole tag for v2.2 and v2.3, per frame for v2.4; reads past the region's end return zeros).
- Covers are kept between rescans. Before the pass, the builder reads the old index and its art stamps into the scratch memory, keeps the entries whose album key is still in the library and frees the records of the rest. For each album it then finds the art as above and hashes where it came from into a stamp: FNV-1a over the path (`/` plus the library's path for embedded art, the folder plus the listed name for a cover file), then three little-endian `u32`s: for embedded art the track's size, the picture's length and 1; for a cover file its size, its modification stamp (the same value the music fingerprint uses, from the folder listing it already reads) and 2. A stored stamp of 0 means unknown and never matches. An album whose stamp matches keeps its record without decoding; changed art is decoded again into the album's own record, and a new album goes to the first free record. A rescan after adding a few albums therefore decodes only those albums.
- The file has a fixed layout for its size: the 16-byte header, an index with room for every record (`(capacity − 16) / (8 + 4 + 31,360)`, 2,673 for 80 MB; a 32 MB file made by an earlier build keeps working with 1,069, since an existing file is never resized), a table of 4-byte stamps parallel to the index, then the records. Header bytes 12–15 hold the stamp table's offset. echo-sync writes the same layout and stamps (see `docs/library-format.md`), so the first rescan after it keeps its covers. A file without stamps (made by an earlier build or an older echo-sync), with another layout, or with an index that isn't sorted or points outside the records is ignored, and every cover is decoded again. Records are written as albums are decoded and the old index stays valid meanwhile, so a pass that never ends leaves the previous covers; the header is zeroed only when the pass is over, then the sorted index, the stamps and the `DSCV` header go last, so a pass interrupted there reads as no covers and the next rescan decodes everything. A record that can't be written counts as a missing cover and the pass goes on.
- `image/cover_image` sniffs JPEG or PNG and decodes into `image/cover_grid`: the centred square crop is area-averaged into 112 × 112 cells per channel with 9-bit fractional weights (each source sample adds `value × wx × wy`, sums wrap without undefined behaviour), and the 56 px half is the exact average of 2 × 2 cells. Per-channel sample sizes let chroma at half resolution sit on the same grid; YCbCr converts to RGB (JFIF) per cell, then to RGB565 like the PC.
- PNG: every colour type and depth (1–16 bits, palette, grey, alpha ignored as Pillow's `convert("RGB")` does), Adam7, all five filters, IDAT across chunks, zlib through `image/inflate` (32 KB window, 9-bit fast tables). Rows below the crop stop the decode. A row up to 64 KB is allowed.
- JPEG: baseline and progressive Huffman (SOF0, 1, 2), 1, 3 or 4 components, sampling factors that divide the maximum, restart intervals, Adobe RGB. Four-component files take a 49 KB black plane from the arena (the black component must share the first component's sampling) and convert as Pillow does: Adobe CMYK as inverted inks, YCCK through YCbCr first, CMYK without an Adobe marker as plain inks, each channel times the black level. The EXIF orientation (APP1, IFD0 tag 0x0112, at most 64 entries read) is applied when the grid is rendered, by reading cells through the orientation's swap and flips. It decodes at 1/1, 1/2, 1/4 or 1/8 scale (the largest that keeps the crop at 112 px or more); each reduced sample is the exact area average of its pixels (cosines averaged over the sample, all 64 coefficients), and 1/8 is the DC term alone. Baseline scans stop below the crop. Progressive decoding needs no coefficient store: every scan's contribution is linear, so DC first and refinement scans and AC first scans add straight into the grid; AC refinement scans, and AC bands that can't change the reduced samples, are skipped. 12-bit, lossless and arithmetic-coded files are refused, and so is a file that ends before its EOI marker. More than 8 bytes of padding past a marker fail the scan, so a truncated or lying file can't spin through millions of empty blocks.
- Memory comes from the scan's scratch (384 KB): the builder's state with one record (about 35 KB), the index (a key, a stamp, a 16-bit record number and a claimed and a placed bit per entry, for the larger of the album count and the old file's count, plus a bit per record: about 27 KB at 2,673 albums), then the decoder's arena: the grid (154 KB), a 4 KB reader (grown to 16 KB, at the end of the arena, once the file is known to be a JPEG) and up to 1616 KB for PNG rows, the inflate window and tables (JPEG needs about 13 KB). The worst PNG (64 KB rows) needs about 327 KB of arena, which still fits beside a full index. Nothing is static, so it runs from the overlay.
- Speed: AC coefficients are decoded in one loop (`jpeg_decode_ac`) whose refill takes bytes straight from the reader's buffer until it meets `0xFF`; a 512-entry table per AC table (`fast_ac`) gives the run, the value and the bit count of codes whose code and value fit in 9 bits, so most coefficients take one lookup. At 1/8 scale only the DC term is kept, so whole blocks skip storing and clearing AC coefficients; skipped progressive scans look for markers with a tight loop over the buffer. The inverse transform's row pass works in 32 bits (coefficients clamped to ±32,767, so eight products of a 12-bit kernel fit). Samples go into the grid a block at a time: column spans are computed once per block and the last row span is cached in the grid. A cover record is written with one call. On the generated 400-track library of the scan bench these bring a decode from 67.6 to 51.0 million emulated instructions.
- `test_cover_grid` checks the averaging, `cover_decode_matches_pillow` (`tools/check_cover_decode.py`) makes 33 images with Pillow and a hand-written PNG encoder and compares the decoder with an exact area average of Pillow's decode (PNG within one RGB565 step; JPEG mean ≤ 3 and 99 % ≤ 40, the rest is libjpeg's smoothed chroma upsampling against our block chroma), checks that broken and unsupported files are refused, and fuzzes every image (truncations and byte changes) under UBSan. `cover_corpus_player_matches_echo_sync` (`tools/check_cover_corpus.py`) builds 55 albums covering JPEG variants (progressive, CMYK, YCCK, greyscale, EXIF orientations, restart markers, every subsampling, 8.5 MB 3000 × 3000 baseline and 6 MB progressive, 4000 × 1000, 1 × 1), PNG variants (palette, transparency, grey, alpha, 16-bit, interlaced, 2500 × 2500), FLAC pictures with several types, ID3 v2.3/v2.4 with and without unsynchronisation, MP4 `covr`, Ogg and Opus pictures (one of 1.9 MB over many pages), folder names in odd case and unusable embedded art, runs the player's scan and cover pass and echo-sync's exporter, and checks that both show the expected picture for every album. `cover_build_matches_reference` builds a music folder with each art rule and checks `covers.bin` end to end, then writes `covers.bin` as echo-sync does and checks that the player's cover pass keeps every cover. `test_cover_build` runs the scan and the cover pass over an in-memory card with generated PNG covers and checks what a rescan reuses: everything when nothing changed, only the new album, a replaced cover file, a removed album's record going to a new one, and a full rebuild for a file without stamps or with a damaged index.

## Library

- The player builds the database on the card (see Library rescan on the device); `tools/library_index.py` writes the same format on a PC.
- On the device, `app/library_store` opens the database through `hal_file_*`, puts a block cache in front, and validates it with `library_open`.
- Browse queries (`library/library_browse`) answer three questions for any view: how many rows there are, what row N is, and what selecting it opens. They read records and strings on demand and never load the database into RAM.
- Browse screens come from a fixed pool of 6 levels. They share one cache of the visible rows' text, which is refreshed in `update` (never during `draw`) whenever the visible rows change.

## Playback

- `hal/audio.h` is high level: `play(path, start, token)`, `queue_next(path, token)`, pause, resume, seek, volume and status. The backend decodes; on the device that's `board/audio.c` (see Device playback).
- Gapless: when a track starts, the player queues the next one with a new token. The backend switches without a gap and reports the new token, and `player_update` then moves the queue on and queues the following track.
- CUE tracks (format version 4, `docs/library-format.md`) are parts of one file. `hal_audio_play` and `hal_audio_queue_next` take a `HalAudioTrack` (path, `start_ms`, `end_ms` with 0 for the end of the file, token); `hal_audio_play` also takes an offset into the track, and `hal_audio_seek` and `HalAudioStatus.position_ms` count from the start of the file. The player converts: it remembers the start of the playing and of the queued track and reports, saves, resumes and seeks in the track's own time (`position_ms` in `PlayerStatus`, in `/.gnarlyr/resume.bin` and in bookmarks is relative; `duration_ms` is the part's length). Everything above the player works on track indices and needs no change. A chaptered `.m4b` reuses the mechanism unchanged.
- The device engine (`device/audio_engine`) stops writing samples at the end of a track's range and then either continues in the same decode stream, when the queued track is the same file starting exactly where the range ended (no reopen, no seek: the next sample goes into the ring right behind the last, and the status switches token at that sample), or finishes the stream and opens the next track as before. Boundaries are sample-exact: a range ends at the sample `end_ms * rate / 1000`, the next one starts at `start_ms * rate / 1000`, and both come from the same millisecond value. A queued track that isn't the next part (shuffle, repeat one, Up Next) is opened and seeked like any other. The simulator reads the same ranges through its decoder (`platform/sim/sim_audio.c`).
- Known gap: the engine decodes up to a ring (16,384 frames) ahead, and queueing the track after the next one only happens once the next one has started. A seek inside a track during the last ring of audio before a hand-over drops the queued track, which stops playback at the end of the track (as it does for whole-file tracks).
- **Track transitions:** `HalAudioTrack.fade_ms` asks for a fade into a queued track. `playback/track_transition` decides it when the player queues the next track: only with Settings → Transitions on (Fade, or a stored crossfade value) and shuffle on, never between consecutive tracks of one album in album order (the next number, the first track of the next disc, or an album without numbers), between parts of one file, for spoken word or for tracks under 2 s; the length is the setting, at most a third of the shorter track. Manual play, skips and seeks pass no fade; they keep the DAC's short volume ramp. In `device/audio_engine` each block written to the ring passes one gain stage (`shape_block`) after `to_output` (volume and ReplayGain) and before the equalizer. The fade-out of the decoding track starts when its remaining output frames (input frames left to the range end or `total_samples`, times the conversion factor, plus the interpolator's pending frames) fall below the fade length; frames past that predicted end get zero gain, and an unknown length skips the fade-out. The fade-in counts output frames from the next segment's start, and the interpolator's tail of the previous track, before that start, gets zero gain. A fade-out that has begun finishes even if the queue changes; a fade-in follows only a fade-out, and the engine refuses both when the queued path equals the current one. The ramp is the smoothstep 3x² − 2x³ (within 1 % of a raised cosine, zero slope at both ends), computed per sample in Q15 and applied to the 24-bit ring words; outside a fade the stage changes nothing. The loops and the ring wrap live in audio processing module 7 (`device/audio_fade`), which source opening already requires; the resident engine keeps the end prediction and the two ramp records. In the emulator the ramp costs about 38 instructions per faded output frame (16 kHz WAV converted to 48 kHz, measured before 8 and 16 kHz sources moved to a 32 kHz output: core 0 14.6 % busy before a fade, 15.5 % during it). The USB DAC path and the simulator do not fade.
- **No crossfade:** an overlap needs the next track decoding while the current one finishes. Core 1 runs one program and its 384 KB are allocated: 128 KB code, 48 KB data and stack (each program's static state and its stack reserve), 72 KB of output slots and a 128 KB ring area that the FLAC ring, MP3 ring and tail (about 102 KB), M4A ring and heap, Vorbis ring and workspace and Opus ring and workspace fill. A second decoder state plus its own output slots and input ring does not fit beside any of them, and two decoders would also double core 1's work during the overlap. Decoding the next opening ahead needs 288 KB for 1.5 s of 48 kHz stereo at 16 bits; that is far beyond what core 0's static RAM or the decoder workspace has free. Different formats would need two programs at once. A stored crossfade choice therefore plays as a fade.
- Shuffle is seeded (`core/random`). The resume file (`/.gnarlyr/resume.bin`, `playback/resume_state`) stores the queue plan (source list, anchor track, shuffle mode, seed), the cursor, the track and the position, so the exact same queue is rebuilt after power-off. A library fingerprint rejects resume files from an older index.
- The player saves on start, on track change, on pause, every 15 s while playing, and in `app_stop()`.
- **Rewind on resume** (`playback/resume_rewind`, `player_toggle_pause`): resuming a paused track first moves back by an amount that grows with the pause. A pause is timed from `hal_clock_milliseconds` when the track is paused or its output is released while playing (USB, charging), so any pause shorter than about 49 days is timed correctly, including across the wrap of the counter, as long as the player stays on. The curve is piecewise linear through these points and flat after the last: 10 s or less of pause, no rewind; 1 min, 3 s; 10 min, 10 s; 1 h, 20 s. Audiobooks and podcasts (`player->spoken`) rewind half as much again: 4.5 s, 15 s and 30 s. The player has no clock that survives power-off, so the first resume of a session restored from the saved state (`player_restore`, which also follows a rescan's restart) rewinds a fixed 20 s, 30 s for spoken word. The rewind is measured in the track's own time and stops at 0, so it never goes before the start of a track or of a CUE or chapter part. On a loaded track it is a `hal_audio_seek` before `hal_audio_resume`, skipped when it would not move; on a released one the track starts at the rewound position, and a rewind to 0 then starts at 0 rather than at the spoken bookmark. A seek, a jump, a restart or a new track while paused cancels the pending rewind, since the user chose the place. Now Playing's position shows the jump; there is no other feedback. Settings → Rewind on resume (On by default) turns it off.
- `app/player_storage` and `player_queue` use stored orders and the session journal to publish queue edits and resume state together (`docs/stored-order.md`, `docs/session-journal.md`). They share the block format of `docs/playback-store.md` with the mixtape catalogue, tapes and moments. Orders and sessions are bound to the library's content fingerprint; saved mixtapes and moments resolve path and part identities after a rescan. Legacy `resume.bin` and `upnext.bin` remain readable when no journal exists.

## Saved moments

The listening module owns `screens/moments_screen` and `playback/moments`, including their store jobs and bounded identity resolver. `ListeningModuleWork` lends its union to the Moments screen while it is open. ## Lower-rate playback

The engine accepts standard decoded rates from 8 to 192 kHz. Every converted rate uses factor 4 or 2: 8 and 16 kHz map to 32 kHz, 11.025 and 22.05 kHz to 44.1 kHz, and 12 and 24 kHz to 48 kHz. Rates of 32 kHz and above retain their existing PCM samples and rate. Playing 8 and 16 kHz at 32 kHz instead of 48 kHz computes two thirds as many output frames and needs only two filter phase sets; a converted file next to a file on another clock family restarts the output clock as described below, and next to a 32 kHz file it stays gapless. The CS43198 documents 32 kHz in `ASP_SPRATE` as code 0; the driver uses the 48 kHz clock family with a divider of 6 to produce that rate ([CS43198 data sheet](https://statics.cirrus.com/pubs/proDatasheet/CS43198_DS1156F2.pdf), register `0x1000B`). Driver values and divider arithmetic have host regressions; physical clock and output behavior remain player checks.

`device/audio_resample` keeps a bounded 64-frame stereo history, written twice so the 48-tap window is always contiguous, and holds converted input to 24 bits. Its independent-module kernel uses Q30 coefficients, 64-bit accumulators and a 24-bit output clamp. Four fractional phases (0, 1/4, 1/2 and 3/4) cover both conversion factors. The windowed-sinc design uses a Kaiser window with beta 8.6 and cutoff 0.475 cycles per input sample; each phase has exact unity DC gain, and the rounding correction is split across equal peaks so phases 0 and 1/2 are exactly symmetric and each pair p and 1-p are exact mirrors. The kernel computes all of an input frame's phases at once: phase 0 and phase 1/2 fold to 24 multiplies each, and the mirrored quarter phases come from one folded sum and one folded difference (48 multiplies for two outputs), 24 multiply-accumulates per output frame and channel instead of 48. The two channels share each coefficient load, and until a stream's channels first differ only one is filtered. For 24-bit input the folded kernel gives the same samples as the direct 48-tap filter. Zero padding at the edges emits exactly the input-frame count times the factor. `tools/audio_resample_table.py --output platform/device/logic/audio_resample_table.h --style .clang-format` regenerates the folded tables, and CTest checks them for drift.

Core 0 does the conversion, so the main loop keeps the full clock while a stereo stream, or a stream converted to 44.1 or 48 kHz, is playing (`audio_engine_needs_full_clock`); mono 8 and 16 kHz speech converted to 32 kHz and native-rate playback coast. The rule comes from the player's measured cost of this code, about 3.3 cycles per emulated instruction (16 kHz mono AAC and 8 kHz WAV at 36 % and 33 % of core 0 at 200 MHz with the previous 48 kHz output). Applied to the emulator's instruction counts for the conversion, it projects about 35 to 39 % of core 0 at the coasting clock for mono speech at 32 kHz, but 51 % for 16 kHz stereo, 53 % for 22.05 kHz mono and 75 % for 24 kHz stereo, against the 73 to 91 % that gave underruns before. The emulator plays every converted rate while coasting at three cycles per instruction without underruns; it does not reproduce the player's per-instruction cost, so these shares need a player check. On the player, the unfolded kernel at the coasting clock left 16 kHz AAC and 8 kHz WAV playback with core 0 73 to 91 % busy and repeated engine underruns, against 23 % for 44.1 kHz AAC. In the emulator, which counts one cycle per instruction, the pump's share of core 0 during 16 kHz playback fell from 33 % to 11 % (mono) and 14 % (stereo); native 48 kHz AAC is 5 %.

Seeks and range limits use decoded input samples; ring positions and EQ use the physical output clock. Adjacent chapters and queued separate files at the same decoded rate preserve filter history and place their segment boundary after pending interpolated frames. A changed input rate drains the previous filter before starting the new one; an output-clock change waits for that tail before switching clocks. Closing a file does not end pending filter output, and underrun accounting continues until it drains. A failed next-file open restores the audio kernel before finishing the current tail; unavailable code ends with an error without calling it. Native-rate playback keeps its direct copy and does not need the interpolation module.

The engine writes the ring in contiguous spans. It works out each span's ring position once, converts 16- and 24-bit input at unity gain (no ReplayGain; the volume is applied in the DAC) with dedicated loops, converts mono input once for both channels, and uses the general gain conversion for other depths and gains. Converted streams go to the interpolation module in blocks of up to 41 input frames, and the module renders whole spans straight into the ring. A host test compares the ring byte for byte with the previous per-frame conversion for 750 combinations of rate, depth, channel layout, gain, volume and ring wrap position. In the emulator, at one cycle per instruction, the output stage for 44.1 kHz 16-bit stereo fell from 4.65 to 0.87 million instructions per second of audio, for 96 kHz 24-bit stereo from 10.1 to 2.0 million, and for 16 kHz mono (with the move to a 32 kHz output) from 21.2 to 11.1 million; the PCM captured from the emulated ring was identical before and after for WAV at 8, 16, 44.1 and 96 kHz and for Opus. M4A demuxing requires the module at every rate.

The player resolves the initial upcoming track before calling `hal_audio_play`. The HAL receives both tracks, publishes the engine queue before prefill/fade and, in the simulator, opens the next slot under the audio lock. This prevents short files from ending unqueued during output startup. Queue-restart decisions consider the requested edit: clearing an already-empty queue preserves prefetched audio and the consumed position. Replacing a buffered next file still rebuilds from the current audible position.

Native tests compare complete resampled FLAC playback with the separately tested kernel, exact duration, seek/range limits, continuous chapters, queued files at all six converted rates, queued clock changes and refusal when optional code is unavailable. Short files, small rings, final-tail underruns, queue cancellation during drain and evicted-kernel failures have regressions. Kernel tests cover block boundaries, backpressure, short streams, channel isolation, saturation and reset. Independent sine correlations at five input frequencies from 0.01 to 0.4 cycles per sample measure, for every converted rate, less than 0.01 dB passband error and every image below the output Nyquist frequency below -80 dB. ARM scenarios exercise the actual module while Settings replaces a UI module, slot-2 fallback, refusal of two damaged copies, native-rate playback without loading it, and real AAC parsing/seeking through its ABI. A full player scenario checks the waveform around a converted WAV file boundary and requires one DMA start across both short files. Another plays a 16 kHz stereo WAV, compares the first 14,400 output frames with the direct 48-tap filter sample for sample, and requires the audio pump to stay under a fifth of core 0's instructions. These checks do not measure analog output or hardware CPU load.

## Headphone profiles

Settings → Headphones edits four named slots, selects one or disables them with Off. Names are 1–23 UTF-8 bytes, without control characters or line separators. The editor offers six translated name presets, trim from 0 to 24 half-dB attenuation steps, balance from −100 to 100 and a logical volume ceiling from 0 to 60. The editor and all save/edit code live in the settings module; initial empty slots acquire names when that editor opens. Published models, the selected slot and the active Q16 parameters remain in `app.c`; the device HAL, music engine and USB sink keep the parameters they use independently of UI module replacement.

`settings/headphone_profile` has the strict 148-byte `DSHP` v1 payload: magic at 0, little-endian version at 4, count at 6, selected index at 7 (4 means Off), eight reserved zero bytes, four 32-byte records at 16 and an FNV-1a checksum at 144. Each used record has a zero-padded 24-byte UTF-8 name, trim at 24, ceiling at 25, signed balance at 26 and five reserved zero bytes. Unused records are zero. Decoding rejects unsupported versions, lengths, noncanonical padding, corrupt checksums, invalid UTF-8 and out-of-range values without replacing the caller's model.

`settings/headphone_file` publishes that payload inside `playback/store` inline records in `/.gnarlyr/headphones.bin` on internal storage. The file is 1,024 bytes: two 512-byte banks with outer magic `DSHF`, version 1, count and binding zero, a wrapping generation and the 148-byte payload at byte 28. `store_pair_open` validates both banks and falls back from a damaged newest copy; unreadable or future-version headers block saving. `store_publish` writes the spare and decides success from its readback, including a write call that reported failure after completing the write. Uncertain readback blocks further saves until the file is reopened at restart or after a storage-session reload. The settings file stays at version 15 and 58 bytes; no extension or reserved settings byte is assigned to profiles.

The music engine composes the resident per-channel Q16 gains with digital volume and ReplayGain before signed sample conversion and saturation, including before interpolation for converted rates. Neutral gains keep its direct-copy paths. The USB sink bypasses that engine and applies the same signed conversion helper to both 16- and 24-bit packets before writing the shared ring; rate restarts keep its profile. The simulator also applies both channel gains. Trim and balance never increase the incoming gain, and balance only attenuates the opposite channel.

The player and USB volume keys bound logical levels; the device HAL independently applies the ceiling before `dac_volume_value` and then adds USB host attenuation. On a profile change, `headphone_audio_switch_volume` calculates a volume no greater than either ceiling and lowers it enough to offset a gain rise in either channel, using conservative upward-rounded 1 dB factors. Restoring a fully attenuated channel requires mute. The app lowers and saves both mode volumes, including the playback session when loaded, before publishing the new profile. A failed or uncertain publication therefore leaves the old audio parameters with safely lowered volumes. A successful publication changes active parameters only after that ordering. Buffered music keeps its old trim until consumed; the hardware volume reduction precedes the new trim.

Analog Gain defaults and CS43198 gain writes are unchanged. The inherited Low value `0x10` uses a reserved OUT_FS setting, and runtime gain changes lack the documented PDN_HP sequence. Profiles do not control those registers; a separate change needs readback and output/transient measurements on the owner's exact hardware.

Native tests cover the codec, every bank-write cut point, uncertain saves, serial wrap, bounds, settings independence, channel gains, no-rise volume calculation, music conversion and both USB PCM widths. An ARM scenario selects a 6 dB profile during playback, switches back to neutral, and requires lower saved volume and a lower DAC target before the gain change, one DMA start and no ring underruns. Its DAC startup is stubbed, so the target is a software observation. The editor uses the shared list layout at all text sizes and orientations; its fields are included in the pseudo-language walk. Hardware output and cold-restart validation remain owner checks.

## Equalizer

- **Settings:** `settings` holds the preset (Off, Retro, Bass, Heavy, Pop, Jazz, Unique, Custom) and the ten Custom gains, and turns them into a curve (`settings_equalizer_curve`): bands (frequency, gain in half-dB steps) and a pre-gain in Q15. Custom has ten bands at 31, 62, 125, 250, 500 Hz and 1, 2, 4, 8, 16 kHz; gains are `int8` half-dB steps (±20) end to end (`Settings.equalizer_gains`, `HalAudioEqualizer.gain_half_db`, `AMPLITUDE`/`POWER` tables of 41 entries). `HAL_AUDIO_EQUALIZER_BANDS` is 10, so the engine holds ten sections per channel. The presets are stock 2.0.0's, on their own grid of seven frequencies (63, 100, 125 and 315 Hz, 1, 3.15 and 10 kHz; `CURVE_HZ`, `PRESET_GAINS`), two to five bands each, with stock's pre-gains (Retro 21/32, Bass 7/16, Heavy and Pop 5/8, Jazz and Unique 7/16). Bands at 0 dB are left out, so Off and a flat Custom are an empty curve. `settings_store_apply_hardware` passes the curve to `hal_audio_set_equalizer`.
- **Headroom:** Custom's pre-gain (`settings/equalizer_peak`) follows the curve's actual peak: the cascade's response is summed in power over a grid of 78 frequencies that includes the ten band centres, on the 44.1 kHz warp, and the pre-gain is the inverse of the peak plus a margin for transient overshoot: 2 dB, and 0.35 dB more per dB of the deepest cut (5.5 dB at −10 dB), because a cut's phase shift lets a full-scale square wave overshoot the response. The deepest cut is the deeper of the deepest single band and the combined curve's trough, since neighbouring low cuts act as a shelf that clips square waves. Any non-flat Custom curve gets the margin, cuts included; a flat Custom has no pre-gain. The presets keep stock's pre-gains.
- **Saved curves and files:** `settings/equalizer_slots` encodes the eight saved slots (`/.gnarlyr/eq_slots.bin`, 88 bytes: `EQSL`, eight records of ten gain bytes + 20 or `0xFF` for an empty slot, FNV checksum; reserved with the other small internal files). `settings/equalizer_fit` turns points (frequency, gain) into the ten gains: a streaming text reader (numbers paired per line; `#` comment lines; `Preamp` and other odd lines drop out by having an odd number count; frequencies outside 10–30000 Hz ignored) keeps, per band, the nearest point at or below and at or above its centre, and interpolates in log2 frequency (Q8); gains round half away from zero to 0.5 dB and clamp to ±10 dB. `app/equalizer_presets` owns the slots in memory and lists the `/EQ` folder of the music volume (card if present, else internal; at most 16 files, names under 28 characters, not starting with a dot); choosing a slot or file loads its gains into Custom.
- **Where it runs:** on core 0, in `device/audio_engine`, right after a run of frames is written into the music ring (24-bit samples, after `to_output`), in place, a band and a channel at a time (wrapping at the ring's end). That is the one point every source passes: FLAC and MP3 and M4A from core 1, and WAV on core 0. Running it on core 1 would mean three decoder programs plus the core 0 paths. Stock runs its equalizer at the same point (the I2S feeder on core 0).
- **Bypass:** with an empty curve, or above 96 kHz, `equalizer_design` reports nothing to do and the engine never calls `equalizer_run`: the ring gets the same words as before the equalizer existed (`test_audio_engine` checks this against the decoded reference for 16-bit 44.1 kHz and 24-bit 96 kHz FLAC). Setting the same curve again (any other setting changing) does nothing, so the filters aren't restarted.
- **Filters:** `device/equalizer` runs each band as an RBJ peaking biquad, Q = 1/√2, in direct form I with Q28 coefficients, 32 × 32 → 64-bit multiply-accumulates, first-order error feedback (the fraction dropped from each output is added to the next sum, which keeps the low bands quiet near the unit circle) and a 24-bit clamp per band. The pre-gain is folded into the first band's numerator. `equalizer_design` computes the coefficients on the player whenever the output rate is set (a track start, a seek, a rate change), so every rate gets its own (stock used its 44.1 kHz set at 48 and 96 kHz): ω = 2π f / rate in Q30, sine and cosine from `audio_math`'s series, 10^(dB/40) from a 41-entry table, one 64-bit division per coefficient. A design clears the filter history; a gapless hand-over at the same rate keeps it. A new curve at the same rate (a Custom gain step) goes through `equalizer_retune`, which keeps the history of every band that is still there as long as the first band is the same, so a gain step does not click; a new first band starts the filter from silence.
- **Memory:** the coefficients and history live in `.high_ram` (`board/audio.c`); only the CPU touches them, and a design rewrites them before use, so an overlay overwriting them is harmless. The engine keeps the curve in `.bss`. The Custom EQ screen costs no RAM (see Screens and input).
- **CPU:** the inner loop is 30 Thumb-2 instructions per band and sample, 5 of them SMLAL, about 55–60 cycles per section, sample and channel by instruction count. Ten sections at 96 kHz come to about 110 MHz of core 0's 200 MHz (55 %); at 44.1 and 48 kHz the 16 kHz band is skipped, and nine sections come to about 45–49 MHz (23–25 %). The presets cost two to five tenths of that. Audio already runs core 0 at 200 MHz, the highest clock the firmware uses, so the equalizer needs no clock change, and with no music nothing runs. 176.4 and 192 kHz would need more than the whole clock, so they play unchanged. These figures are estimates: the load has not been measured on a player, and the 96 kHz case is listed in `known-issues.md`.
- **Tests:** `test_equalizer` compares the coefficients with the formula in double precision at 44.1, 48 and 96 kHz, measures the gain of sines at band centres (within 0.05 dB) and an octave above (matching its own rate, not 44.1 kHz's), plays full-scale sines through every preset and some extreme Custom curves without reaching the clamp, and checks that the channels stay apart and a design restarts from silence. `test_settings`, `test_stores` and `test_app` cover the curves, the file and the screens.

## Cover Flow

- Now Playing shows the playing album's full cover (112 px) on the left, below the header, with the text, progress and times in a column to its right. It loads the cover through the same `CoverCache` full slot in `update`. Without a cover it keeps the full-width text layout. In portrait the cover is centred under the header, with the text lines, the progress bar and the times in one full-width column below it (`BOARD_LAYOUT.now_playing_portrait`).

- Albums run by album artist, then by year, the same order as Album Artists. The screen reads each position straight from the album artists' links (`docs/library-format.md`), so it holds no album list and shows every album.
- `ui/cover_flow` holds the geometry and the motion, in fixed point (256 = one cover). The center cover is flat and 112 px. Neighbours are 42 px wide trapezoids, 84 px tall on the side facing the center and 64 px on the far side, spaced 32 px apart. Between those positions, every measure is interpolated, so a cover grows and flattens as it slides in. The position eases toward the selected album with a 70 ms time constant, at no less than about 4 covers per second, and never overshoots.
- Covers are drawn farthest first, so nearer covers overlap them. `gfx/image` draws a cover column by column with nearest-neighbour sampling, clipped to the current strip.
- `app/cover_cache` holds 7 half-size covers (56 px, 6,272 B each) for the center ±3, in slot `position % 7`, plus one full-size cover (112 px, 25,088 B) for the center, about 69 KB in total.
- Covers load in `update`, one per frame: the nearest missing half cover first, then the full cover once the motion has stopped. A cover is drawn from the full image when that's loaded for its album, otherwise from the half image, otherwise as a placeholder. Beyond ±3, covers that aren't loaded aren't drawn.
- An album without artwork gets a generated cover. After each load, `app/cover_placeholders` (views module) paints every slot the cache marked `COVER_MISSING` and marks it `COVER_PLACEHOLDER`, so the tile is drawn, lit and reflected like a decoded cover and is made once per load. `ui/placeholder_art` draws it: a vertical gradient from one of the theme's colours (accent, alternate accent, selection, success, danger or scrollbar), picked from the album key (artist and title hash), mixed toward the theme background until the theme's text colour differs from it by at least 112 in luma, with one or two initials in Inter Semibold (26 or 22 px, drawn at twice size on the full tile) that fit within 4/5 of the width and 2/5 of the height. Initials are the first letter or digit of the first two words after a leading "The", skipping punctuation; words split at spaces, `/`, `-`, `_`, `&` and `+`; letters are upper-cased (Latin, Greek, Cyrillic); a syllabic script gives one character; a letter the font lacks is passed over. A title with no usable initials, or "Unknown Album", falls back to the album artist; without one either, the tile shows the album icon. Entering Cover Flow repaints placeholder tiles when the theme colours changed. Home and Now Playing treat a placeholder as no artwork: their code is resident and the painter lives in the views module.
- Play opens the album's track list, a long Play toggles the favorite, and Back leaves. The screen is full screen: no header or status icons, and the title (★ for favorites) and album artist go under the cover. The first time it opens, it starts at the playing album, or at the first album.
- Position 0, before the first album, is **Random album**: its cover is a 48 px shuffle mark drawn once into a static image (white crossing arrows on dark slate), and its text is "Random album" / "Play any album". Play there picks one of the music albums with `core/random` seeded from the microsecond clock, plays it from its first track in track order (shuffle off for that queue), moves the flow to that album and opens Now Playing. The albums sit at positions 1 and up, so the cover cache slots and the playing-album lookup are offset by one.

## Rendering

The panel keeps its own image memory, so we never hold a full framebuffer. The strip renderer clears a 480×23 buffer (`BOARD_STRIP_HEIGHT` rows of the board's width; 49 rows of 222 in portrait), asks the current screen to draw into it, pushes it to the display, and moves on to the next strip. Before pushing, `gfx/frame_diff` compares a hash of every row (FNV-1a over pixel pairs) with the previous frame's (1,920 bytes for up to 480 rows), and only the span of changed rows in each strip goes to the display. An unchanged frame sends nothing, and moving a selection sends a few rows. `app_start` forgets the hashes, so the first frame is always sent whole. After the screen, the app draws the status icons (play state on the left of the header, battery on the right, both inside the header insets), the toast and the frame overlay. The overlay shows the average frame time and its split: u (input, player and screen update, including card reads), d (drawing and hashing) and s (sending to the panel). The renderer clears every strip to the theme background, so screens don't fill it again. Screens marked `full_screen` (Cover Flow) get no status icons. While the start-up or goodbye fade runs, the app draws only the fade (centred text in the title font, blended from the background to the text colour) and drops key events. `app_show_splash` starts the 1.1 s "Gnarlyr" fade after `app_start`. While a track plays, turning the screen on pushes Now Playing, unless the top screen sets `stays_on_wake`. Idling in a menu never leaves it. Pushing or popping a screen by key slides it (`ui/slide`, 240 ms, cubic ease-out): the title bar stays and switches its title halfway, and both screens are drawn shifted below it through `canvas_shifted`; if either screen is full screen, the whole screen slides. Waking into Now Playing doesn't slide. Browse levels keep two row caches so both sides of a slide have their text. A long Power press saves the session at once, shows "Goodbye" fading out over 1 s, then turns off. With the screen off it turns off straight away. Drawing uses screen coordinates and clips to the strip. Lists skip rows outside the strip, and glyphs outside the clip are culled. The strip buffer is 22 KB where a full framebuffer would be 213 KB.

### When a frame is drawn

Drawing a frame costs time even when nothing is sent, so the app draws only when it has a reason:

- **Passive transport:** Now Playing and Home show playing progress in whole-second snapshots. Cassette tape amounts use the same position on Now Playing. Short tracks therefore do not keep the active redraw pace merely because their progress advances a pixel every few milliseconds. Scrubbing, paused/end positions and volume feedback retain their exact position.
- **Input and animation:** a key event, a fade or a slide asks for a frame at once, and `core/frame_pacer` then keeps the active pace (16 ms) for six frames. Three changed frames in a row count as an animation and keep that pace.
- **Changes with no input behind them:** every 50 ms `app.c` hashes what any screen may show without a key press (play state, track, elapsed second, volume, shuffle and repeat, queue place, battery, Bluetooth, lock, toast). A changed stamp draws one frame at once and does not start the active pace. A screen that shows something else that changes by itself must add it to the stamp.
- **Otherwise:** one check 100 ms after the last change, then one frame a second as a safety net.

On the owner's player, bounding passive progress for a 20-second WAV in the medium landscape cassette view reduced drawing from 211 to 20 frames per 10 seconds and core 0 busy time from 98 % to 38 %, with zero ring or output underruns.

The main loop follows the same idea. Keys are sampled in the 1 ms tick interrupt, so a pass of the app is not needed on every tick: `app_pass_interval_ms()` asks for 1 ms passes while the screen animates, Bluetooth is on, the charge screen shows or a rescan is pending, 4 ms on an idle screen or while music plays (the audio path keeps about 300 ms buffered), and 10 ms with the screen off and nothing playing. `board/main.c` sleeps in between.

Measured on the owner's player at 200 MHz with the developer build: an idle Home screen fell from 28 % of core 0 busy to 2 %, a paused Now Playing screen from 23 % to 2 %, and MP3 playback on Now Playing from 28 % to 11 %, with no underruns.

### Motion during waits

On the player both files live in the extension module (see Device platform, Extension module); without it every wait keeps its plain notice.

`gfx/wireframe` projects small wireframe models in fixed point: a 65-entry quarter-wave sine table (256 angle steps a turn, exact to half a step of 1/16384), a part placement (spin, size and offset in model units, where 127 is the model's radius), yaw and pitch, and perspective from 384 units away, to points in 1/16 pixel with a depth. Its line rasteriser shares each pixel's ink between the two nearest rows or columns (`canvas_blend_pixel`) and clips the major axis to the canvas clip first, so a line drawn strip by strip matches one drawn whole and costs nothing in strips it misses.

`ui/wire_figure` holds the three figures (a cassette with turning reels and two tape packs, an icosahedron, a tilted disc with a turning hub) and draws one at a turn in any rectangle; `ui/wire_motion` runs them as the wait motion. The figures are all inside the unit sphere and drawn in the theme's accent and secondary text colours, with farther edges fainter. A screen with a wait calls `wire_motion_run` with itself as owner from its update and `wire_motion_end` when the work ends; `wire_motion_progress` makes it determinate (the cassette's tape moves between packs, the disc's rim and the icosahedron's edges light in order). It draws nothing until the wait has lasted 300 ms. Its square is at most 104 pixels a side, so one frame of it fits the strip buffer, and `message_draw_working` lays a message out under it. There is one `WireMotion` (36 bytes), owned by `app.c` and handed to screens through `AppScreensContext`.

Frames of the motion are separate from the frames above:

- `app_step` ticks the motion when it is due: its owner is the top screen (or the scan notice), the display is on and no slide or fade runs. Ticks follow a 72 ms grid from the start (about 14 a second) and the turn follows the clock, so a late pass skips motion rather than slowing it.
- A tick renders only the motion's square: the strip renderer draws the screen's ordinary `draw` into a canvas of that square and the result is written straight to that window of the panel. The same draw code makes full frames and motion frames, so they always agree.
- While the motion shows, `frame_diff` leaves the square's columns out of its row hashes (`frame_diff_mask`). Full frames therefore send only what changed around it and the frame pacer sees no change from the motion, so the screen keeps resting at one check a second. Setting or clearing the mask forgets the rows it covers, so those rows are sent whole once when the motion starts and again after it stops.
- Blocking work with a progress callback (library scan and cover finding) ticks the notice's motion from the callback between its 250 ms notice updates. Work with no callback (the music check, storage preparation, language changes) keeps a plain notice: no frame can be drawn during it.

Now Playing never owns a motion, so it never animates over playing music. In the emulator, holding Export plays in its working state while music plays, the motion added 2.9 points of core 0 busy time with a 44.1 kHz FLAC (38.3 % against 35.4 %) and 1.6 points with a 22.05 kHz WAV converted to 44.1 kHz (25.6 % against 24.0 %), at 12 to 14 frames a second and with no underruns (`device_image_boot_test_export_motion_*`, whose waits count as idle time). These are emulator figures, not player measurements.

## Icons

`ui/icons` draws every icon from one table (`GLYPHS` in `src/ui/icons.c`). An icon is a short list of 32-bit operations on a grid of cells: a filled or outlined rectangle (square, or with its corner cells cut), a stroke one to three cells thick, a disc, a ring or any of its quarters, and a triangle pointing left, right, up or down. Each operation takes the icon's main ink or its accent ink (`IconInk`); a caller that wants one colour passes it twice. `icon_draw(canvas, icon, area, ink)` is the only drawing call.

| Box | Icons |
|---|---|
| Large, 20×20 cells | Music, Audiobook, Podcast, Now Playing, Mixtape, Audio, Settings, Cover Flow, Artist, Album Artist, Album, Genre, Folder, Song, Playlist, Favorite, Shuffle, Repeat, Display, Theme, Power, Sleep, Timeout, Controls, Start, Rescan, Diagnostics, Gain, Jack, USB, Bluetooth, Key Plus, Key Minus, Key Play, Key Menu, Disc, Hub |
| Small, 14×14 cells | Play, Pause, Next, Previous, Seek, Queue, Speaker, Album (small), Shuffle (small) |
| Narrow, 9×14 cells | Bolt, Bluetooth (small), Lock, Song (small) |

The names are the `IconId` values in that order (`ICON_MUSIC` … `ICON_SONG_SMALL`). The status bar draws Play, Pause, Bluetooth (small), Lock, Song (small) or Album (small) beside Shuffle (small), and Bolt inside the battery on USB power; the Now Playing feedback badge draws Play, Pause, Next and Previous; the charge screen draws Bolt. No screen draws the others yet.

Sizes:

- An icon keeps its proportions. `icon_draw` scales its box to the largest size that fits `area` and centres it there; `icon_rows(icon)` is the box's height in cells and `icon_width(icon, height)` its width at a given height, for laying out a slot.
- At a whole multiple of the grid (14, 28 or 20, 40 pixels high) every cell is a whole number of pixels. Use these sizes. The theme's `status_icon_size` is 14 at every text size, and a large icon at 20 fits the list row of every text size.
- At any other size edges round to the nearest pixel, every stroke of the icon gets the same thickness (its cells times the scale, rounded, at least one pixel), and discs, rings and triangles are drawn at pixel resolution, not enlarged from the grid. Parts that only touch at the grid size can then sit one pixel apart, and a symmetric icon can be one pixel off balance.
- Drawing fills whole runs of pixels: equal neighbouring rows of a shape go out as one rectangle, a horizontal or vertical stroke is one rectangle, and a slanted stroke is one rectangle per pixel row.

Adding an icon:

1. Choose the box by use: large for list rows, menus and cards, small for the status bar and badges, narrow for small upright marks. Add the `IconId` inside its group (large, then small, then narrow) and the glyph at the same place in `GLYPHS`.
2. Build it from the existing operation macros. An operation costs 4 bytes and no code. Coordinates are cells, both ends included; a stroke's thickness extends right and down from its cells.
3. Accent ink marks the part that carries the meaning and the rest is main ink. The icon must still read when both inks are the same colour, as in the status bar.
4. Overlap parts that join by a cell, so they stay joined at every size.
5. In `tests/ui/test_icons.c`, list it in `MIRRORED` or `FLIPPED` if the design is symmetric left to right or top to bottom, and add its entry to `SHAPES`: put 0 there, run `test_icons`, and copy the number the failing check prints. A changed number for any other icon means its pixels changed.
6. Look at it at every size on the contact sheet: `build/dev/tests/icon_sheet FILE.png` draws all icons, ten to a row in `IconId` order, at 0.8, 1, 1.3, 2 and 3 times their grid, each on a panel the size of its box. Write the file to the Scratch volume, never into the repository.

## Boards

The board is the full-size Snowsky Echo (480×222, 221 ppi, six keys). Presets: `dev` (simulator and tests, `build/dev`), `device` and `release` (device images). `identity.json` holds the name (Gnarlyr: the USB product name and the splash), the short name (also Gnarlyr: the Home title), the maker's name (Doublesharp: the USB manufacturer name), the identifier (`GNARLYR`: the image brand, zero-padded to 8 bytes, and the USB storage vendor, space-padded to 8 characters), the version (1.0.0) and the names of the data folder, the update file and the playlist directive; the build, the C code and the tools read it, and the `no_identity_literals` test fails when source spells one of them anywhere else. The image is always named `GNARLYR.IMG`. There is one board: Podium removed EchoPod's Echo Mini board when it forked.

- `hal/display.h` takes `HAL_DISPLAY_WIDTH` and `HAL_DISPLAY_HEIGHT` from the board.
- `app/default_theme.h` offers `BOARD_THEME`, `ECHO_THEME` (22 px Inter SemiBold titles, 22 px Inter Regular body, 16 px small text, 22 px SemiBold header title; 30 px header, 32 px rows, six rows visible). The app and its tests use `BOARD_THEME`.
- **Text size** (Settings → Text size): `default_theme_set_text_size` sets the theme's title and body fonts, row height and `metrics.text_size`. Small is Inter 18 px in 24 px rows (eight rows), Medium is `ECHO_THEME` unchanged (22 px, 32 px rows, six rows), Large is Inter 26 px in 38 px rows (five rows). The header (30 px, its own `fonts.header`, 22 px SemiBold), the 16 px small text (status bar, Now Playing details, Bluetooth hints) and the content area stay the same at every size. Choosing a size changes the app's theme at once; menus and browse lists fit their rows to it when they are shown again (`list_view_fit` in `enter`), keeping the selection on screen, and every other screen reads the theme when it draws, so no restart is needed. Toasts are capped at the screen width; a longer one wraps (see Settings and favorites).
- `app/board_layout.h` holds `BOARD_LAYOUT`, the per-board positions the screens read: Now Playing lines and Cover Flow text per text size (`board_now_playing_layout`, `board_cover_flow_text_layout`, picked by `metrics.text_size`), Cover Flow geometry, the Home art panel width and the Up Next detail width. `BOARD_STRIP_HEIGHT` sets the strip renderer's height in landscape (23 rows, where the last of ten strips is shorter); portrait uses the same buffer as 49 rows of 222 pixels. Portrait has its own Now Playing and Cover Flow tables (`now_playing_portrait`, `cover_stack`, `cover_stack_text`) and the Home art panel's minimum height. Covers stay 112 px; the Echo Cover Flow draws the centre cover at 128 px.
- `extra_ranges` in `fonts.json` adds code points to a font's built-in table: the 22 px fonts hold Latin-1 themselves, so each of them reads only the rest from its own glyph face.
- `test_board_layout` checks the active board's theme and layout at every text size (rows, line fit, no overlap, on-screen covers, Medium equal to `BOARD_THEME`); run it under both presets.
- `tools/target_audit.py --define ECHO_FONTS_PACKED` audits the device build's source; `ctest` runs it as `target_audit`.
- The 18, 22 and 26 px Inter fonts are `"packed": true`: device builds keep space and `?` in their tables and read other glyphs from their seven base faces. Fourteen Noto CJK fallback faces follow in the same size and weight order, Chinese first and Japanese second. `FONT_PACK_FACES` is 21 and `FONT_PACK_MAX_BITMAP` is 352 bytes. The device cache holds 64 packed glyphs in four-way sets. Host builds keep their base font tables. After an install rewrites the firmware, notices and screens use `NOTICE_THEME` until restart; uncached packed glyphs are unavailable.

## Echo board on the device

- **Panel:** `board/panel_vop.c` drives the ST7796S through the SoC LCD controller (`device/vop`, registers at `0x60070000`, clock gate `0x7F`, reset `0x0D`, GPIO0.15–25 on function 1, GPIO2.15 reset pulse 50/150/30 ms). The bus timing register (`+0x08`) follows the CPU clock: a 20 ns write strobe and a 70 ns cycle rounded up to whole cycles, `0x1021` at 24 MHz (stock's fixed value), `0x1044` at 96 MHz, `0x1089` at 200 MHz, rewritten after every clock switch; Podium's author reports that stock's fixed `0x1021` at 96 MHz left the first image as noise on the panel. Commands and parameters are written in command mode (control `0x800`), pixels in pixel mode (control `2`, one 16-bit write per RGB565 pixel, the busy bit polled every 4 pixels). `device/panel` holds the init stream (memory access control `PANEL_ECHO_MADCTL` = `0x28`, the stock value; `-DECHO_PANEL_MADCTL=0x68` mirrors the columns) and the window rule: columns are x, rows are y + 49.
- **Backlight:** the PWM runs at 25 kHz (`BACKLIGHT_HZ`).
- **Pins:** `device/board_pins` holds the per-board pin facts: DAC mute on GPIO2.1 and no DAC reset pin, the USB supply pins GPIO2.0 and GPIO0.14 (they follow the cable: high while cable power is seen, low otherwise and before power-off), and the 4.4 mm jack reading high when plugged. The jack pull-ups are set at start-up.
- **Storage:** `emmc_layout_read_with(..., EMMC_SLOT_2_SEARCH)` finds slot 2 as stock does: from the next MiB after slot 1's firmware size plus 16 KiB, in 1 MiB steps, up to 20 tries, taking the first header with `RKnanoFW` and a matching header copy. A slot found past half of the firmware area, or no slot, leaves slot 2 at half of the area. The slot length and the write fence are unchanged.
- **Updater:** the check accepts Gnarlyr images (brand `GNARLYR` followed by two zero bytes, the 5 MiB shape) and FiiO's stock Echo image (39,845,892 bytes, magic, brand `Rockchip`, fw size `0x025CC000`, header copy, CRC over the first 38 MiB, marker `ECHOV100IMG` and neither Echo Mini marker) as `UPDATE_STOCK`, and refuses images with any other brand, Podium's and EchoPod's included, and the Echo Mini's stock image. A stock install writes the 38 MiB into both slots, slot 2 first. `device/update_names` gives the file names: `/GNARLYR.IMG`, and FiiO's `/ECHOVnnn.IMG` names so that FiiO's image can be restored.
- **Update file:** after a successful install, for a file refused as invalid and for one that is already installed, `update_after_usb` deletes the update file (`updater_should_remove_file`); a failed install keeps it. The loader request file is zeroed, not deleted.
- **Loader request:** at start-up `update_check_loader_request` looks for `/MASKROM.REQ` on internal storage. A file that starts with `MASKROM REQ` has those 11 bytes overwritten with zeros (so it fires once) and, if the write read back, the player reboots into the boot ROM's USB loader (`board/loader_reboot.c`, which also clears the boot ROM's loader flag at the next start). See `docs/device-recovery.md`.
- **Boot order:** glyph faces are attached before the low-battery check, so the 22 px text exists from the first frame.
- **Stock's boot guard** (power off at start unless USB power, the power key or `NanoCRebootFlag`) is not used; `board_power_hold` keeps the guard inherited from EchoPod (a USB-only start is a charger start).

## Generated code

- `src/library/sort_fold_table.{c,h}` is generated by `tools/fold_table.py` from Python's `unicodedata`: for each code point in Latin, IPA, Greek, Cyrillic, Latin Extended Additional, Greek Extended, punctuation, letterlike and number forms, enclosed alphanumerics, kana, CJK compatibility ideographs, ligatures and fullwidth/halfwidth forms, the NFKD-decomposed, mark-stripped, case-folded text the PC indexer's `sort_key` gives it. `library/sort_key` applies it (plus Hangul syllable decomposition and ASCII lowercasing), trims Unicode whitespace and drops a leading "the ". Regenerate with `.venv/bin/python tools/fold_table.py --output src/library --style .clang-format`; `sort_fold_up_to_date` checks it.
- `src/core/include/core/strings.h` (the `StringId` enum and the catalogue hash) and `src/core/strings_english.h` (the English table host builds fall back on) are generated by `tools/lang_pack.py` from `assets/lang/en.txt`: `.venv/bin/python tools/lang_pack.py --sources src/core --style .clang-format`. `strings_up_to_date` checks them. The packs themselves are built into the build folder (`build/<preset>/lang/<code>.pack`) and are not committed.
- `src/fonts/` is generated by `tools/font_build.py` from `assets/fonts/fonts.json` and the TTFs in `assets/fonts/`, and `src/fonts/packs/` by `tools/glyph_pack.py` from `assets/fonts/glyph_pack.json`. Never edit either by hand.
- Fonts are Inter (SIL OFL 1.1, license in `assets/fonts/inter/OFL.txt`), pre-rendered to 4-bit coverage. The built-in tables in `fonts.c` hold ASCII and common punctuation only. Everything else comes from glyph packs, read on demand (below).
- Regenerate with:

  ```sh
  .venv/bin/python tools/font_build.py --config assets/fonts/fonts.json --output src/fonts --style .clang-format
  .venv/bin/python tools/glyph_pack.py --config assets/fonts/glyph_pack.json --output src/fonts/packs
  ```

- The `fonts_up_to_date` and `glyph_packs_up_to_date` tests fail if the committed output differs from a fresh build.
- **Glyph packs:** `assets/fonts/glyph_pack.json` lists 21 faces in order: seven Inter faces, seven Simplified Chinese fallbacks and seven Japanese fallbacks. `font_find_glyph` tries the base face and then the locale-preferred CJK face followed by the other CJK face. Glyph bitmaps are loaded on demand, not kept in RAM as full fonts.
  - A face is one blob: a 32-byte header (`EGLF`, version 1, entry size 12, 42 entries per index sector, glyph count, directory, index and data offsets, size, and the image CRC of the rest), then at `0x200` a directory with the first codepoint of every index sector, then index sectors of 42 sorted 12-byte entries (codepoint, width, height, left, top, advance, 0, bitmap offset) padded to 512 bytes, then the bitmaps, packed as in `fonts.c`. A glyph whose bitmap passes the face's limit (128 bytes for the 16 px Inter face, 160 for the 16 px CJK faces, 256 for the 18 and 22 px faces, 320 for the 26 px Inter faces and 352 for the 26 px CJK faces) is dropped; none is.
  - `gfx/font_pack` reads them through a `FontPackReader` (face, byte offset, length) into memory the platform hands over: the face headers and directories (up to 16 index sectors each), one index sector, and a 4-way set-associative cache of slots (a glyph plus its bitmap: 368 bytes). A lookup costs the index sector and the bitmap on a miss (the header and directory once per face), and nothing on a hit. Misses are cached too, so a character no face has is read once. A glyph from a pack stays valid until the next lookup; text drawing resolves its bitmap once per glyph (`font_glyph_bitmap`), not per pixel. The memory must be 4-byte aligned; the number of sets is a power of two.
  - Device: `tools/make_image.py --glyph-face` (one per face, in face order; a missing file is an empty face) places the faces largest first into the image's free space (`0x30000`–`0x200000`, `0x2E0400`–`0x43C000` after the Opus program bank, `0x218000`–`0x240000`), sector-aligned, and writes a table at `0x2C0000` (`EGPT`, count, then offset and size per face, in the first 256 bytes of the sector: room for 31 faces; the second 256 bytes are the language pack table, see Languages). `board/glyphs.c` reads the table from slot 1 at boot, before `app_start`, and reads faces through a one-sector buffer. Its table, sector buffer and the 28 KiB cache region (face state and 16 sets of 4 slots of 368 bytes: 64 packed glyphs) sit in `.glyph_ram` (`0x03094000`–`0x0309AFFF`); the 16 KB above it, to the top of High RAM, hold the language pack (see Languages): `board/overlay.c` and `rescan_overlay.ld` cap the rescan overlay at `0x18000` bytes, so a rescan never overwrites the cache. After an update, until the restart, reads are refused (glyphs already cached still draw; others show `?`), like the rescan overlay and the core 1 programs.
  - Simulator: `platform/sim/sim_glyphs.c` loads `src/fonts/packs/<face>.bin` (paths from `glyph_pack.json`, through CMake) into memory and hands the same 28 KiB of cache over. `test_sim_glyphs` checks the committed packs through it, and that the memory still caches 64 packed glyphs.

Track-tag duration arithmetic uses integer mantissas and exponents in `library/tag_duration.c`. Each conversion, division, subtraction and final millisecond rounding preserves the former binary precision and ties-to-even behavior, including sequential WAV/DFF divisions and ASF preroll cancellation. The rescan overlay carries no double-precision runtime. Native differential checks compare the old formulas across half-millisecond boundaries, saturation and a deterministic integer corpus; an ARM rescan checks the stored boundary durations.

## Memory

- No heap in `src/`. Every buffer is static and sized at compile time.
- `src/` is freestanding C11 and includes only `<stdint.h>`, `<stdbool.h>` and `<stddef.h>`.
- The `target_audit` test cross-compiles `src/` for Cortex-M3 and reports flash and static RAM per module. It fails on any heap symbol and when static RAM exceeds `ECHO_APP_RAM_BUDGET_BYTES` (144 KiB). This allocation takes 16 KiB of previously unused device RAM; it changes no address or physical boundary. The device linker and size report independently enforce the complete-image static RAM limit of 278,528 bytes, including platform buffers and profiler storage.
- No recursion and no VLAs. The device stack is 16 KB.
- Data RAM: `.data`, `.bss` and `.noinit` must end below the independent audio module at `0x03048000` (see Image rules). The `device` build also holds the debug loop (see Debug loop). The USB sessions and the updater keep their variables in the USB overlay's own zeroed memory, not here. The equalizer's filter state lives in `.high_ram`, since only the CPU touches it and a design rewrites it before use.

## Code rules

- No comments in any code: C, CMake or Python. Names and small functions carry the intent. Prose belongs in `docs/`.
- Names:

  | Kind | Style | Example |
  |---|---|---|
  | Types | `PascalCase` | `KeyTracker`, `FrameStats` |
  | Functions and variables | `snake_case`; public functions prefixed with the module | `key_tracker_update` |
  | Constants and enum values | `UPPER_SNAKE_CASE`, prefixed | `KEY_GESTURE_PRESS`, `FONT_INTER_REGULAR_16` |
  | Files | `snake_case`, named after the module | `key_tracker.c` |

- Functions:
  - do one thing
  - stay short (aim for under 20 lines)
  - take at most 4 parameters; group anything more into a struct (`Label`, `TextStyle`, `MenuConfig`)
- Pass small value types by value and anything larger by pointer. Use `const` wherever data is read-only.
- No mutable globals in `src/`, except state owned by the composition root (`app.c`). Platform singletons live in `platform/`.
- Every rule in `core`, `gfx` and `ui` has a unit test. Test names describe the behaviour.
- `clang-format` (`.clang-format`) defines formatting. Warnings are errors (`cmake/project_options.cmake`).

## Echo image emulator test

`tests/emulator/scenarios/test_*.py`, using the shared `echo_image_harness.py`, run the finished `device` image (with `echo_device.elf` and `echo_usb_overlay.elf` for symbol addresses) in a Unicorn Cortex-M3 emulator (`tools/echo_emulator`, `unicorn` in `tools/requirements.txt`) before anything is flashed to a player. Each scenario is its own ctest, `device_image_boot_<scenario>` (label `echo_image`); it needs the `device` build and `.venv` and skips (exit code 77) when the image, the ELF or `unicorn` is missing. The measured full-suite time and integration gate are documented in `../CLAUDE.md`, Integration. Run it by hand with `.venv/bin/python tests/emulator/test_echo_image.py [--image IMG] [--elf ELF] [--usb-overlay-elf ELF] [Class.test_name]`. A function the test names must exist in one of the two ELFs, or the test fails. The USB overlay's addresses are also used by the rescan overlay and the decoder, so a name in it counts only while the window holds exactly the overlay stored in the image.

The emulator loads the image as the boot ROM does: each pair of load-table rows copies code and data to their exec addresses and zeroes bss, then the stack and reset vector come from `0x03004000`. The player then runs its own start-up code unchanged. A fake eMMC (`SparseDisk`) holds the IDB blocks (system size 96 MiB), the image in slot 1 and in slot 2 (`0x2800` sectors after slot 1) and a 300 MiB FAT32 user volume that the test fills with files (or, for the realistic scenarios, `tools/echo_emulator/real_volume.py`: 3480 MiB FAT32 with FSInfo, 4 KiB or 512 B clusters, seven 330 MiB FLAC images with CUE sheets, a `.Spotlight-V100` with 1,500 entries, macOS dot files). Scenarios:

- **Normal boot:** the ST7796S init stream equals the table in the test, every window stays inside columns 0-479 and rows 49-270 with exactly width × height pixels, the first sweep is the black clear (111 windows of 2 rows, 106,560 pixels), the second the first lit frame (10 windows, 106,560 pixels, every pixel painted), and a third full frame is the home screen. GPIO2.6 goes high before GPIO0.14 and GPIO2.0 and stays high, GPIO2.1 is never driven, the backlight PWM period gives 25 kHz at the live pclk and starts only after the first lit frame, the watchdog runs and is kicked, no fault, panic or power-off symbol is reached, and not one eMMC sector changes.
- **Loader request:** `/MASKROM.REQ` starting with `MASKROM REQ` is zeroed in place (one write, inside the user volume), then the boot-ROM flag `0xFFFF18AF`, the GRF boot select and `SYSRESETREQ` follow and no frame is drawn; other text leaves the file alone and the player boots.
- **Update:** with VBUS raised after the first frame and a host reset pending, then the cable pulled and a key pressed at "Unplugged too soon", a Gnarlyr image with a newer date in `/GNARLYR.IMG` is installed. Writes go only to the two 5 MiB slot ranges, all of slot 2 before slot 1, each slot starts with `0xFF` over its first 8 KiB and ends with its header chunk, every write is read back sector by sector, both slots equal the new image afterwards, and the installed slot 1 boots in a second emulator. The image already installed is not written again. An image with another firmware's brand (valid CRC) and a file of the Mini stock size are refused with no write; `updater_install` is never reached. `updater_check`, `updater_install` and `usb_session_storage_changed` are in the USB overlay, so these scenarios run its code.
- **Output diagnostics:** injected latched I2S flags exercise the actual ARM accounting during active output, mute/fade, pause, resume, start and USB handoff. Quiet pauses clear flags without incrementing the counter; pending genuine faults and unmuted DMA interruptions still count. The audio model freezes the source cursor during nested suspension.
- **Independent audio modules:** module 5 holds the resampling kernel and MP4 demuxer; module 6, the Ogg module, holds the same kernel with the checked Ogg record stream, page seek and the Vorbis and Opus probes and source openers. They share `0x03048000`–`0x03049FFF`, an 8 KiB bank reserved from data RAM. Both have zero BSS and keep all state in the engine or caller. A common entry prefix lets converted WAV/FLAC/MP3 reuse either loaded resampler, while MP4 and Ogg explicitly load their own file operations. The engine drains the previous resampler before changing sources. Resident read dispatch never retains a pointer into an evicted module. Loading checks the numbered table, body CRC, main-code binding and both firmware slots. Audio-bank loading does not reenter audio service; screen-module loading continues to serve it. UI modules replace one another independently. Native and ARM scenarios exercise Vorbis and Opus opening, switching between the two core-1 programs, saved-position startup, pause/resume, converted WAV transitions and damaged-module refusal.
- **Independent audio processing:** module 7 occupies `0x0308F000`–`0x03093FFF`, the 20 KiB between the shortened UI slot and the glyph cache. It holds EQ design (with its fixed-point sine and cosine), history-preserving retuning, PCM filtering and the track-transition fade ramp (`device/audio_fade`), with private BSS bounded after its code. Filter state stays in the existing decoder workspace; the music ring, decoder allocation and boot-ROM scatter rows do not change. PCM filtering retains `-O2`. Source opening requires a checked module before decoding starts; missing code refuses playback rather than silently bypassing processing. USB/rescan loading and the high-RAM diagnostic invalidate its resident readiness flag before overwriting the window. The next source open reloads from either checked firmware slot, while UI and file-adapter module changes leave it in place. Packaging, size reporting and emulator symbol loading use its separate address/capacity. The profiler covers the full shared high-RAM window, including the processing slot. ARM scenarios cover EQ execution during menu changes, USB eviction/reload and damaged-slot fallback/refusal. The glyph arena gives up 8 KiB of unused allocation slack; the same 64 font slots remain, while the processing bank can now hold tempo state alongside processing kernels.
- **USB plug-in prompt:** scenarios run as if When plugged in were File transfer (the emulator rewrites the argument of the `CORE_SEAM` `hal_system_set_usb_answer`) unless they ask for the firmware's own Ask. Under Ask: a cable plugged into a running player brings `app_ask_usb_mode` after the bus reset, the soft disconnect follows within 10 ms, no reset is acknowledged and neither session entry runs, and File transfer then connects and serves a session; on the charge screen a wall charger listens for 10 s without asking, a host arriving wakes the prompt, a quiet prompt ends with the display powered down and no further connection, and File transfer starts a session. The restart after an install and a script reconnect run under Ask and connect without asking. The emulated DWC2 core clears its pending interrupts on a core soft reset.
FLAC source opening, stream-info validation and frame-header seeking also run in the processing bank. The resident opener dispatches after that bank is prepared. The file owner and decoder workspace stay resident, and closing a source never depends on loaded code, so USB eviction can always release it. The FLAC codec sources remain in the core-1 library as well; the module source catalogue marks these shared sources so banking the cold core-0 operations does not remove or change core-1 decoding.

- **Headphone profile placement:** the extension module loads the internal profile file, checks the alternating banks and derives the selected audio parameters. The settings module owns editing, selection and readback-verified saves. Resident audio code keeps the applied trim, balance and volume ceiling. If extension code is missing, the resident loader applies a zero volume ceiling and refuses profile edits so an unread saved ceiling cannot be bypassed. File callbacks stay in the extension, whose lifetime spans every settings-module load.
- **USB overlay:** a session loads the overlay from slot 1 and the update check runs inside the window; a second session after it reads nothing from storage (the copy in the window is reused), although the first one had to load over the rescan overlay; with slot 1's copy damaged the session runs from slot 2's; with both damaged the player shows "USB missing: reinstall update" (the test reads the expected text from `assets/lang/en.txt`), powers USB down, executes no instruction in the window, leaves the window zeroed and the update file in place, and writes nothing outside the user volume.

- **Language pack:** a normal boot reads the pack from slot 1 into the pack memory at `0x0309A800` (the memory then equals the pack in the image) and reads nothing of slot 2's; with slot 1's pack damaged the same bytes come from slot 2; with both damaged the player shows the built-in notice "Text is missing: reinstall the update", waits for a key and then runs its main loop, with no fault and no write outside the user volume.

- **Bluetooth** (`test_21_bluetooth.py`, a playable volume with a remembered device): Play before the last headphones connect pauses with "Connecting to Buds…" and streams once they connect; headphones that stay away leave the player paused with "Buds didn't connect" and no stream, and a balanced plug then plays on the jack and records the jack as the last output; a sink that pauses each new stream gets `CY0 1E`, the play notice and `CY0 1E` again; headphones that return after a loss reconnect without streaming until Play. With Bluetooth on, the app runs a pass every millisecond to serve the UART, so these scenarios cost about 20 s of host time per emulated second.
- **Deep CUE track** (`real_volume(playable=True)`: two 330 MiB albums whose FLAC images are generated frame by frame by `flac_image.py`, 12 CUE tracks each; `playback.Rig` presses keys through Music → All Songs): starting track 12 must put the first sample into the ring within 1.5 s, the volume fade-in must finish within 1.5 s, the main loop must never go quiet for 1 s, a second of playback may read at most 40 FAT sectors while it reads at least 250 data sectors, then a skip, Back and scrolling a list must leave no ring underrun, no stall panic and no gap above 1 s. `audio.py` replaces the DAC, DMA and core 1 hardware with stubs (the DMA position follows emulated time at the stream's rate; the firmware loads and CRC-checks the core-1 FLAC program from either firmware slot, and the bridge runs that program on the second emulated core). The stub replaces `dac_path_start`, so the DAC identification read never runs in the emulator.

- **Scan recovery** (`test_21_scan_recovery`, faults injected by sending the program counter to an unmapped address when `hal_file_read` reads a named file, or at `hal_system_borrow_listing`): a fault while a cover file is read leaves its mark in `scan.bin`; the next start rescans by itself, skips that file, builds every track, clears the flag and lists the mark as a `storage` event in the report the next USB session writes. A fault inside a batch of tracks names the batch; the second start faults on the same track with its exact mark; the third skips that track and builds the rest. Three faults in a row before any file give a fourth scan without the cover pass (`covers.bin` is never opened); with a fourth stop recorded, the start runs no scan. A waiting newer `/GNARLYR.IMG` with a stopped scan recorded is installed at the end of the USB session and no scan runs before it; the same card without the update rescans at the start.
- **Debug report** (see Debug loop): the first USB session creates `/.gnarlyr/debug/report0.txt` and writes it after the session starts and before the host is served, entirely inside the user volume; the report names the build, an unread value reads `unknown`, and the profile is off and empty. A second session reports the first session's end. A long Power press writes a `shutdown` report between `hal_power_off` and the power cut, loading the USB overlay for it; with USB power the same press writes it on the way into charge mode. A report from the first seconds after a cold start goes into a second file, names the start-up battery sample as such, and the next one like it replaces it while the earlier report stays byte for byte. With the Profiler row switched on by key presses, the next report's histogram adds up to its sample count, splits into code and idle time, and `tools/echo_debug.py` turns it into time per function with the image's ELF.
- **Battery soak** (see Debug loop, Soak): a script takes the USB supply away, darkens the screen and soaks for a minute; GPIO0.14 and GPIO2.0 are low and the backlight pin is low during it, both pins are high again when the script ends, and the report's `script.soak` line shows one minute, `end=done`, the supply override at both ends and the 96 MHz idle clock. A key pressed during a soak brings the pins back at once and the line reads `end=key` with the script line `cut_short`. Pulling and replugging the cable during a soak starts a session, which stops the script (`end=stopped`) and leaves the pins following the cable. A long Power press during a soak ends in charge mode with the pins high and a `shutdown` report that holds the soak.

Emulated time is continuous across clock changes; the watchdog resets the machine when not kicked within its timeout (counted, and a test failure); eMMC commands take 250 µs plus 25 µs per extra block for reads and 0.9 ms plus 70 µs per block for writes. Scenarios added: an update file installed once and gone afterwards (also after restoring an older build), refused and already-installed files removed, CMD18 always followed by CMD12, and cold boots on the realistic volume (4 KiB clusters; 512 B clusters with a stale FSInfo hint) that must light the screen within 1 s, listen for USB within a second of the cable, stay under the main-loop gap limit and never reset the watchdog.

Speed: emulated time is counted in instructions (one cycle each, in slices of 4,000), so Unicorn's instruction counter runs on every instruction, and it is fast only while it is the one code hook. The emulator therefore watches a named function with a block hook on its entry address, which fires when a call or branch starts a translation block there. A slice that ends exactly on such an entry has already run its hook, so the resumed slice skips it once; a stubbed function returns through a one-instruction pad and so still costs one counted instruction. Cycle counts and storage accesses of every scenario are the same as with per-address code hooks. Only `count_window_code` keeps a code hook, in the two USB overlay scenarios that count instructions in the window. A `wfi` ends the slice, and so does each `board_input_take_key_press`, the poll `board_wait_for_key` spins on without reading the clock: a pass of that wait then costs one slice of emulated time instead of the few instructions it executes. `test_a_key_wait_that_spins_ends_like_one_that_rests` keeps that honest: it runs a refused update with the rest and with the real spin (`rest_in_waits=False`) and requires the same storage accesses, the same functions reached, the same sectors changed and the same emulated time within 1 ms, with the spinning run polling at least ten times as often.

Emulated hardware is minimal: GPIO ports, GRF and CRU (write-masked registers, PLL always locked, the clock rate follows the PLL registers), PMU boot flag, SysTick (delivered as a software exception between 4,000-instruction slices, and a read of the counter or `ICSR` advances time so delay loops end quickly), SARADC (no key, 4,000 mV battery), PWM, watchdog, VOP, DW-MMC for eMMC (CMD0-18, 24, 25; data commands complete at once) and for the SD slot (no card detected), and the DWC2 core as plain registers with soft reset and flush bits self-clearing, a bus reset raised on connect and VBUS dropped 40 ms after the firmware acknowledges it. Any other register in `0x40000000`-`0x7FFFFFFF` is a plain read-after-write page and is listed as unmodelled. UART1 at `0x400B0000` is the Bluetooth module (`tools/echo_emulator/bluetooth.py`): it powers with GPIO2.7, reports `CV15` 300 ms later, answers `CQ00` with `CQO` and the headphones or `CQI`, `CL06`/`CH06` with `CLOK`/`CHOK` after 1.5 s for the one remembered device in range (`CLER`/`CHER` otherwise), `CT00` with `CTOK` and `CS00` with `CSEN`, logs every command, and can let the headphones leave and come back or pause each new stream once; the balanced jack sense can be set plugged. Not covered: USB enumeration and mass storage (no SETUP or bulk traffic), the DAC, I2S, DMA, other UARTs and key presses beyond one Play press, SD cards, and playback. The second core is only RAM (`0x01000000`, 384 KB), enough for the rescan overlay's working memory. With no SD card the player mounts the synthetic eMMC's user volume and builds its files and library there. The Mini stock image refusal is checked by size only: the marker check needs a CRC pass over 38 MiB, which takes minutes in the emulator.

### Scan and album-art timing

`tools/scan_bench.py` times the library scan and cover display of a `device` build in the emulator: `firmware/.venv/bin/python firmware/tools/scan_bench.py --tracks 4000 --build-dir firmware/build/device --report <json>`. `tools/echo_emulator/music_library.py` generates the music volume from the track count and seed alone (artist and album folders, FLAC, MP3 and M4A with full tags and some non-ASCII text, about 7 % CUE images and 3 % M4B books with Nero chapters, embedded JPEG and PNG art of 500 to 1,500 px, some progressive, folder art under the names the cover pass accepts, albums without art) as a sparse FAT32 image with 32 KiB clusters on the card size that fits, and keeps it under `/Volumes/Scratch/SnowskyEcho/data/scan-bench`. The image stores metadata, pictures and tails; FLAC and MP3 frames are produced as they are read, so files have realistic sizes and the first FLAC songs by title play. The tool times the first scan (until the library is browsable, the moment of its toast, and until the background cover pass ends), Settings → Rescan library with nothing changed (pressed through the menu; a build that answers "Library is up to date" is timed from the key to that toast), the music check after a USB session in which the host wrote, then the cover loads behind Home, Cover Flow (open, single steps, a tap burst, a held key) and Now Playing, with and without `covers.bin`. `tools/echo_emulator/scan_profile.py` hooks the entries and returns of named functions in the rescan overlay and the main program, charges every stretch of emulated time and every eMMC command to the innermost phase (walk, tags, CUE, chapters, builder steps, finding art, decoding, `covers.bin` writes) and kind of access, and samples the program counter after each 4,000-instruction slice for the busiest functions. Times are emulated: one cycle per instruction at the clock the firmware sets, plus the eMMC model's waits; a hooked call is exact to a slice. A missing name is reported, not fatal. `test_22_scan_timing.py` runs the plumbing on a 24-track library.

## Device platform

`docs/hardware.md` summarises the hardware these drivers talk to.

- `platform/device/logic` holds the driver logic that doesn't touch hardware, so it builds and is tested on the host too:
  - `key_ladder`: ADC bands to keys
  - `key_scanner`: debounce over two samples, a transition queue, and ignoring the Power press still held from switching on
  - `headset_remote`: the wired headset's buttons from ADC channel 2 (`hardware.md`): stock's bands, debounce over two samples, a tap of volume up or down for the volume, a 400 ms hold to skip, play taps counted until 300 ms pass (1 play/pause, 2 next, 3 previous), nothing for a held play, no remote at all for a plug that reads only play for its first 500 ms, or a remote that reads play for over 1 s (a 3-pole plug, also after a swap the jack debounce missed), until the line leaves the play band for 500 ms; `headset_monitor` joins it with `headset_dips` for the Headset row in Settings → About, and nothing until a 3.5 mm plug has been in for 500 ms. `board/input.c` reads the channel every fourth scan (every 20 ms) and passes the jack state, which counts only while audio isn't routed to Bluetooth; `hal_input_next_headset_command` hands the commands to the app, which runs them on the player from any screen without waking it, as the background keys
  - `panel`: the init streams for both panel variants, and the window and pixel commands, sent through a `PanelBus`
  - `tick_clock`: milliseconds and microseconds from the 24-bit SysTick down-counter
  - `sd_card`: the SD setup protocol (v1 and v2 cards, the ACMD41 retries, the RCA, capacity from the CSD register, the 4-bit bus), driven through an `SdHost`
  - `vop`, `board_pins`, `update_names` and `loader_request`: the Echo board's LCD controller access, per-board pin facts, update file names and the loader request file (see Echo board on the device)
  - `emmc_layout`: finds the firmware slots (from the IDB's system size) and scans for the user volume on internal storage. It also answers whether a sector range lies inside the user volume (`emmc_layout_in_volume`, used for volume-relative reads and writes) and which internal-storage writes are allowed: only the user volume and the two firmware slots, never the IDB, the SAVE block or the gap
  - `bt_module`: the Bluetooth module's command protocol. It waits up to 5 s for the `CV1` ready report, sends `CS00` to scan (once more after 4 s if nothing answers, `CP00` after 30 s), collects `CS` scan results until `CSEN` (dropping unnamed ones; a new scan keeps the earlier results, marks in `found_now` the ones it finds again, and past 6 drops the oldest; `CP00` stops a scan early), and sends `CQ00` every 3 s while ready, scanning or connected, every second while a connect runs and every 0.5 s while a paired reply waits for the link (stock's Bluetooth screen polls in every state). Connecting sends `CL06` + the picked address, from Ready or during a scan (once more as `CH06` after 4 s if nothing but `CQ` answers arrived, `CT00` and a failure after 30 s); `CLOK` means paired, `CLER`/`CHER` failed, `CHOK` connected, `CQO` + address + name connected in any state, including while a connect runs, any other status letter while connected or `CT`/`CTOK` means the link dropped. Disconnecting sends `CT00`. While connected, starting the stream sends `CY0` + `1E` + 0 and stopping it `CY0` + `00` + 0. As in stock, the `C` `86`/`87` notices only answer the module's own reports: the play state is what the module last reported (`CP` paused, `CC` playing; nothing on a new link). Starting the stream after a `CP` sends the play notice `C` `86` `30 30` 0 first and `CY0` + `1E` + 0 100 ms later; stopping it after a `CC` sends the pause notice `C` `87` `30 30` 0 first and `CY0` + `00` + 0 100 ms later; otherwise only the `CY0` frame goes out. (Sending a notice on every pause and resume, with the play notice after `CY0` `1E`, left the headphones silent a moment after some resumes.) Every new link first gets `CY0` + `00` + 0. A `CP` within 3 s of a stream start (`BT_MODULE_STREAM_SETTLE_MS`) while the stream is on means the sink suspended the stream it was just given (reported by owners of the stock Echo for a JBL speaker: connected, silent until play was pressed on the speaker); it is answered once per start with the play notice and `CY0` + `1E` + 0 100 ms later, as a start after a reported pause is. The protocol known to this project has no separate AVDTP start or suspend acknowledgement: `CP`/`CC` are the module's only reports of the sink's play state, and `CQ` the only report of the link. The module's `CP`/`CC` (pause/play) and `CA`/`CB` (previous/next) reports count presses in `HalBluetoothRemote`; a `CP`/`CC` after `CLOK` also counts as the link coming up (the Buds send them as soon as they're in the ears), and while connected `CQ00` polling pauses for 50 s after one, as in stock. A dropped link, `CT` or `CTOK` ends the stream and clears the pairing result. While the stream is on, `board/bluetooth.c` holds GPIO2.0 high and GPIO2.14 low on every service pass, as stock does on connect, and restores them when the stream stops or the module powers off. Received bytes are split into frames as soon as a frame is complete; an incomplete frame is dropped after 2 ms of silence. It also keeps the last 12 bytes, counts bytes and frames, and logs the last 12 messages (frames other than `CS` and repeated `CQ` letters, plus the `CS`, `CP`, `CL`, `CH` and `CT` commands it sent) with the seconds between them; the log and the devices found survive a power-off and power-on, so a restart keeps the evidence
  - `usb_device`: the descriptors and standard requests for a bulk-only mass-storage device (`1209:0001`, the pid.codes test ID), plus GET_MAX_LUN and the mass-storage reset. Full speed only (64-byte bulk packets; the device qualifier and other-speed configuration stall) until the board allows high speed; then it serves a device qualifier and an other-speed configuration (type 7, the opposite speed's configuration), and the configuration's bulk packet size follows the speed the board reports (512 at high speed, 64 at full speed; EP0 stays 64)
  - `usb_audio`: the USB Audio Class 1.0 device for DAC mode (`1209:0002`, the next pid.codes test ID, so hosts don't mix up its cached descriptors with mass storage's): the device and configuration descriptors, interface alternate settings, the sampling-frequency and feature-unit class requests, and the FIFO split. Everything else (address, configuration, status, strings) goes to `usb_device`. See USB DAC mode
  - `usb_audio_sink` and `stream_drift`: USB audio packets into the music ring, and the ring-level controller that keeps it near 20 ms of audio (see USB DAC mode)
  - `msc`: the bulk-only transport and SCSI commands over up to two LUNs. INQUIRY gives the firmware id as the vendor and the firmware's major.minor version as the four-character product revision (`1.0 ` for 1.0.0; `FIRMWARE_REVISION`, derived from `identity.json` by the top-level `CMakeLists.txt`). A reply shorter than the host asked for is padded with zeros and reported in the residue instead of stalling. Ejecting a LUN marks only that LUN absent. Given a buffer (`msc_use_write_buffer`), WRITE(10) data collects there and reaches the drive in one write call per full buffer, plus one for the rest; a failed call fails the whole command. Without one, each sector is its own write. READ(10) uses the same buffer the other way: when the next sector isn't loaded, one drive read fetches as many sectors as the command still needs, up to the buffer (64 sectors, 32 KB: one multi-block CMD18 on the card), and the bulk IN packets are served from it. Reading one sector per command held reads over USB at about 1.2 MB/s
  - `usb_fallback`: when to give up on high speed: watching starts at the first bus reset of a high-speed session, a working session (configured and through two SCSI commands) stops it, and 10 s without one asks for a full-speed reconnect, once
  - `card_write`: the order of a card write through a `CardWriter`: one block is CMD24 then a wait for the tran state; several are one CMD25, then CMD12 (sent even after a failed transfer, so the card leaves the receive state), then the wait, which is skipped if the stop failed
  - `image_crc` and `updater`: the image check and the slot writer. The updater has no buffers of its own: `updater_use_scratch` hands it 116 KB (two 8 KiB chunks and the header prefix), on the player the mass-storage write buffer, which is idle once the session is over; without it the check answers invalid and the install fails before any write. The check accepts our 5 MiB shape (size, magic, fw size `0x44C000`, header copy, trailer CRC, fits a slot) and reports an image already in slot 1 as installed. It also accepts FiiO's Echo stock image as `UPDATE_STOCK` (see Updater above; the CRC pass scans every 8 KiB chunk for the stock markers, including one split across two chunks) and writes it the same way, as stock's own writer does. The install fills slot 2, then copies slot 2 into slot 1. For each slot it first writes `0xFF` over the first 8 KiB, then every other 8 KiB chunk, then the first chunk last. Chunks that already match are skipped, and every write is read back. One slot is complete at every moment
  - `fat`: a FAT16, FAT32 and exFAT reader/writer over a `BlockDevice`. It reads unpartitioned cards or MBR partition 0, follows FAT long names and exFAT name entries (UTF-16, including surrogate pairs), matches path components exactly by code point and ASCII letters in either case, and reads at any offset. FAT files follow a per-file cluster cursor for short forward steps, and the file HAL gives each open file an extent map (`fat_attach_extents`, 32 entries): the first read that jumps backward or more than 128 clusters ahead scans the file's cluster chain once, in multi-sector reads, into contiguous runs, so any later position is found without touching the FAT. A file with more than 32 runs keeps a checkpoint every `clusters / 32` clusters instead and walks at most that far from the nearest one. Lookahead for multi-sector reads never moves the cursor. exFAT files marked NoFatChain are contiguous and skip the FAT. Cluster walks and directory scans are bounded, so a corrupt chain can't hang the player
- `platform/device/board` is device-only. It holds the register helpers, GPIO and pin mux, startup (the vector tables and its start-up steps), the linker script, a minimal `memcpy`/`memset`, and the HAL implementations.
- `platform/device/core1` is the program for the second core: its own startup, `main` and linker script (code at core 1 address 0, data at `0x01021000`, stack top `0x0102E000`). It builds to `core1.bin`, which is linked into the core 0 image as read-only data. `device/core1_control` holds the power-up, start and stop sequences and the shared-block layout, tested on the Mac; `board/core1.c` runs them.
- **Build:** `cmake --preset device && cmake --build --preset device` cross-compiles to `build/device/platform/device/echo_device.elf`. Then `tools/make_image.py` packs it into `build/device/GNARLYR.IMG`. The outer header is written from format constants (magic `0x76543210` at `0x00C`, `4` and four `0x200` words at `0x050`–`0x06C`, `1` at `0x19C`, the fw size at `0x1F4`) plus our date, brand, build tag, fw1 end at `0x080` and the version from `identity.json` (major << 24 | minor << 16 at `0x004`, patch at `0x008`), with an empty part chain and zero marker bytes, so the image builds from the repo alone.
- **Release build:** `cmake --preset release && cmake --build --preset release` builds the same image into `build/release/GNARLYR.IMG` with `ECHO_RELEASE=ON`, which links `src/app/diagnostics_menu_release.c` (Firmware, Battery, Jack 3.5, Jack 4.4, Music, Headset, CPU clock) instead of the full developer menu in `diagnostics_menu.c`. The rows both menus share live in `diagnostics_rows.c`. `tests/app/test_release_diagnostics.c` checks the short menu.
- **Code size:** the code window is `0x2666C` (157,292) bytes. `tools/size_report.py` reads each limit from the linker maps. From the repository root, `python3 tools/firmware.py sizes` prints current code, RAM, overlay, module, core-1 and language-pack usage for both presets and fails on an overflow or a code floor below the budget; each image build prints the same table for its preset and saves `build/<preset>/size-summary.txt` on Scratch; use `--target echo_size_report` for the full breakdown. Report current figures in the commit or handoff instead of updating these reference docs. Keep at least 4 KB free in the `release` code window and at least 1 KB in the `device` one. The `device` build is what the debug loop installs, so it has to link; the free space is a margin for the next change, not something the hardware needs. Libraries in `src/` that link `echo_compact` and the cold device files listed in `platform/device/CMakeLists.txt` and `platform/device/logic/CMakeLists.txt` (start-up records, the start-up sequence and main loop in `board/main.c`, power hold and battery reading, jack polling, the loader reboot, the internal volume mount, the updater, the image CRC, card file creation, the Bluetooth protocol, the DAC set-up sequence, the USB descriptors and requests, the USB sessions, the MP3 probe, the M4A demuxer and its stream, the open functions of the core 1 sources, the battery gauge, the backlight table, FAT name handling, the DAC driver and the core 1 loader) are compiled with `-Os` in cross builds; the audio path (ring feeding, the engine and its sources, FAT reads), `board/usb.c`, `board/usb_port.c` and the USB audio sink stay at `-O2`.
- **Overlay loader:** `board/overlay.c` loads both overlays into the window at `0x0307A000` (`0x18000` bytes, `overlay.h`), after `board_audio_shut_down`, because the main program's `.high_ram` (the core 0 decoder workspace and the equalizer state) uses the same memory while music plays. An overlay in the image is a 16-byte header (magic, size, CRC of the rest, CRC of the main code it was linked against) and the program. The loader takes the first of these that passes every check: the copy already in the window, firmware slot 1, firmware slot 2. The checks are the magic, a size that fits the window, the code CRC against the running code (computed once per start and kept) and the CRC of the whole body. It then zeroes the window after the program. When nothing passes it zeroes the whole window and returns nothing, so a failed load leaves no header and no code behind, and the caller never jumps there. Nothing in the window has to survive a load: a track is opened again and the equalizer designed again before either is used.
- **Demand-loaded UI modules:** `cmake/screen_modules.cmake` assigns code to `playing` (Cover Flow with its lit, smooth and reflected quad drawing, queues and charging artwork), `views` (Mixtapes and cassette-side controls, catalog/resolution code, Clock and Calendar calling shared resident date conversion with `core/calendar_view`, and About), `settings` (settings, language enumeration, live theme/EQ previews, EQ preset text parsing, response plots, the Bluetooth screen and its link actions, and the Home screen editor), `library` (search/sort/filter, personal tags and the fingerprint walk), and `listening` (history/export, lyrics and the smart lists, `smart-lists.md`). UI module numbers 1–4 and 11 share a 44,032-byte slot at `0x03084400`, above the 41,984-byte decoder workspace. Persistent screen state stays in `AppScreens`; private discovery/tag/sort work lives in the library module's BSS and is rebuilt after eviction; the listening, lyrics and smart list screens share one work area in the listening module's BSS (`screens/listening_work`), claimed by whichever screen is on top. Cancellation precedes leaving active work, and published playback orders use resident file owners. Live EQ previews restore the saved curve before global navigation, another module, USB or shutdown. The host RAM audit counts resident state plus the largest cold BSS, while checking every source for forbidden heap use; each UI module stays below the independent processing bank. Card formatting adds a validation volume to the settings module and borrows the decoder workspace for its formatter state and buffer while audio is released; [card-format.md](card-format.md) defines its layout, write order and safety checks. A source a module takes from a library that is built with `-O2` (`ECHO_SCREEN_MODULE_FAST_SOURCES`, today `gfx/image_quad.c`) keeps `-O2` in the module, and the helpers it shares with resident code are `static inline`, so moving it out of the code window adds no call to its inner loops. A function moves into a module only when no resident code calls it; the call graph of the main ELF and each module's undefined symbols show which those are. Each module has a numbered magic, body CRC and binding to the main-code CRC; either slot may supply a valid copy. Cross-module transitions skip slides because the programs share one slot. The builder stores modules behind the image table at `0x218000`; its 31 rows include the independent audio, processing and extension banks, with empty rows for reserved module numbers. Each ELF identifies its own row; the builder rejects duplicate numbers and the loader refuses an empty row. Playing uses row 11 without moving the UI window. Now Playing stays resident, and returning from Up Next reuses playing without a storage read.
- **Home artwork:** every UI module includes `home_art` and `home_art_backdrop` through `ECHO_SCREEN_MODULE_UI_SOURCES`; its common `SCREEN_MODULE_ENTRY` supplies the update and draw callbacks. Home keeps its state in resident `HomeArt` and reuses whichever UI module is loaded, including while a slide draws Home beside another screen. - **Independent audio module:** module 5 holds the resampling kernel and MP4 demuxer at `0x03048000`–`0x03049FFF`, in 8 KiB reserved from unused data RAM. It has no mutable globals; all state belongs to the resident engine or MP4 caller. Loading uses the existing numbered module table at `0x218000`, body CRC, main-code binding and slot fallback. It stays loaded while UI modules replace one another. Main wrappers keep the MP4 APIs and dispatch through its entry table; the MP4 signature check stays resident. The linker, image builder and size report enforce its separate window and zero BSS. This changes no boot-ROM scatter row or container layout.
- **Processing banks:** module 7 has a 12 KiB window at `0x0308F000` for equalizer design and processing; module 12 has an independent 8 KiB window at `0x03092000` for fade kernels and the device debug payload. Both can remain loaded while the DSP/Ogg audio bank and the UI slot change. This gives the tempo stage a full module 7 and leaves a concurrent home for further per-block processing in module 12. Both permit bounded private BSS, which is cleared on a fresh load. USB and rescan invalidate both ready flags before reusing their RAM. The glyph cache begins at `0x03094000` and retains all 64 slots.
- **Cold source module:** module 14 shares the 8 KiB DSP/Ogg window at `0x03048000` only while FLAC opens or seeks to its initial position. It holds the FLAC metadata and seek parser; core 1 still decodes audio. The engine closes the previous decoder before opening its queued successor, and reloads DSP before any remaining converted-rate tail is rendered. Ogg page reads therefore finish before the cold-source load. No resident PCM or resampler state points into this module. A corrupt first copy falls back to the second slot; two invalid copies refuse FLAC without starting output. Converted WAV-to-FLAC and Ogg-to-FLAC emulator checks exercise continuous PCM, one DMA session and no underruns.
- **Extension module:** module 8 is loaded once at start-up into its own 8 KiB window at `0x0304A000`–`0x0304BFFF`, the top of core 0 data RAM above the independent audio bank, and then stays for the rest of the run while UI modules, audio modules and the overlays come and go. The boot ROM uses that RAM only while it loads the image, and nothing in the image is loaded there, so it is free once the firmware runs; no other module, overlay or decoder shares it. It holds optional app features called after `app_start`: the wait motion (`gfx/wireframe`, `ui/wire_figure`, `ui/wire_motion`) and file removal on the music volume (`hal_file_remove` in `board/file_remove.c`, which only the views, library and listening modules use). `device/fat_delete` lives here with boot-time cleanup of a leftover time file after `app_start` (see Wall clock). Both presets hold the clock-chip read and write (`board/debug_rtc`, with `device/rtc_time`) here for the Date & time editor and deferred startup recovery. The USB overlay carries its own copy, so USB deletion stays available when extension code is missing. A failed extension load leaves the boot-time file for a later boot to remove. In the `device` preset the debug script runner's steps (`app/debug_steps`), register probes (`board/debug_poke`), clock chip read and write (`board/debug_rtc`, with `device/rtc_time`) and screenshot writer live in the independent effects bank, module 12, beside the fade kernels. It has zero BSS: all state stays in the main program. `hal_system_load_debug_code` requires an intact extension and then loads or reuses the effects bank through its CRC checks and slot fallback. Failure aborts the script and reconnects. UI module swaps preserve that bank; USB and rescan reuse its memory and invalidate its resident ready flag before another load. `board_main` calls `board_extension_start` after `board_power_hold`, the display, the glyph faces, the loader-request check and the empty-battery check, just before `app_start`; it reads the module through the module loader from either firmware slot, with the usual magic, body CRC and main-code binding, so this is also where the running code's CRC is first computed. The functions keep their names in the main program as small wrappers (`app/extension_calls.c`, device builds only) that call through the entry table; the module's copies are renamed by compile definitions in `platform/device/CMakeLists.txt`, as the audio modules' are. When no slot has an intact copy the window is left zeroed and every wrapper does nothing: waits show their plain notice (no motion is started, `wire_motion_fit` gives an empty square and nothing is drawn), removing a file fails as it does on a full or missing card (the callers already report that), boot-time time-file cleanup is skipped, the clock cannot be set and startup recovery is skipped, and in the `device` preset a script ends as `aborted` and the player still reconnects. Nothing before `app_start` calls into it. The runner's state, the key hand-off, beginning and aborting a script (the USB overlay calls these) and the event log stay resident, so the debug loop records and reports before any script and at start-up without the module. Using this RAM at run time has been checked in the emulator only, not yet on the player.
- **USB overlay:** everything a USB session does after the host's bus reset (the mass-storage session with `msc`, `usb_device` and `usb_fallback`; the DAC session with `usb_audio`, `usb_audio_sink` and `stream_drift`; the update check and install with `updater`, `update_names` and `fat_delete`; and the DWC2 transfer code, `board/usb_port.c`) is linked as `echo_usb_overlay` at `0x0307A000` against the main ELF's symbols, like the rescan overlay, and stored at image offset `0x43C000` (up to `0x10000` bytes, magic `EUSB`), inside the area the trailer CRC covers and the updater writes. The `device` overlay also includes the debug loop's report and script code.   - **Drawing:** `app/screens/usb_screen.c` (layout, header with battery, stage, storage and warning states), `usb_screen_dac.c` (level meter, DAC details and menu list) and `usb_dac_menu.c` (the DAC menu's rows and keys) draw every USB screen from an `AppUsbStatus` whose `scene` (`screens/usb_scene.h`) carries the state, the cassette's turn, the drives, the bytes copied and the DAC readings. Host builds link them directly for simulator and native checks; device builds link them, `gfx/wireframe` and `ui/wire_figure`, only into the USB overlay. The cassette is the wait motion's figure (`ui/wire_figure`, split out of `ui/wire_motion` so it can be drawn larger than the wait motion's 104-pixel square), drawn in the accent colour, or the danger colour for a warning, over the theme's backdrop with the Home perspective floor under it. If the load fails, it powers USB down, shows "USB missing: reinstall update" ("Restart to finish the update" after an install) and waits for a key; music stays paused. After a failed install the copy in the window still serves the next session; if playback has overwritten it, the loader needs a slot whose overlay was built with the running code.
- **Image rules,** enforced by the linker script and the builder:
  - `.data` holds only the 8-byte entry vector; no initialised mutable globals.
  - Code stays below the row-0 end (`0x030771D4`).
  - `.data`, `.bss` and `.noinit` end below `0x03048000`, where the independent audio module begins. That module ends at `0x0304A000`, below the retained boot-ROM boundary of `0x0304A240`. The extension module's window follows it up to `0x0304C000`, the end of core 0 data RAM; it is loaded at run time and is never part of the load table. The ROM zeroes the load table's data range while it still uses RAM above it: Echo images ending at `0x0304AB90` and above never started (black screen, nothing on USB), images ending at `0x0304A224` and below did. The exact ROM boundary is unknown; `0x0304A240` is the highest proven value.
  - Nothing loaded is left out of the image.
- **Run model:** the main loop polls the drivers; the 1 ms SysTick interrupt keeps time and runs the stall watch (see below). The display driver samples the keys before and after every strip it pushes, so key presses aren't missed during slow frames.
- **Storage:** `board/mmc` drives the DW-MMC controller (commands, polled single- and multi-block reads and writes, CMD12, the card clock); `board/emmc` reads through `device/block_read` in chunks of up to 64 sectors with CMD18 + CMD12, and retries a failed chunk one sector at a time; `board/sd` and `board/emmc` write through `device/card_write` and `board/sd` powers the SD slot and checks card detect. `board/emmc` starts internal storage (8-bit bus at 24 MHz) on first use and refuses any write outside what `emmc_layout` allows. The file HAL mounts the SD card (FAT16, FAT32 or exFAT) on the first open, or, when there is no card or it doesn't mount, the internal user volume through `emmc_volume_start` (reads and writes through `board/emmc` and the `emmc_layout` fence, so nothing outside the user volume is ever written); `device/storage_mount` makes that choice and `hal_file_volume` reports it (Settings → About → Music: Card, Internal or None). Everything the player keeps under `/.gnarlyr` on the music volume, the music scan from `/` and the playlists follow the mounted volume. `storage_reset` makes the next open decide again (and the next settings access mount internal storage again). The file HAL can hold 8 files open at once, each with its own extent map (2.2 KB of RAM in all). Writes go in place or through `fat_reserve` (see Settings and favorites). `device/fat` reads and writes through an 8-sector cache, except that a transfer of more than 8 whole sectors to or from a word-aligned buffer goes straight between the card and the buffer, up to 32 contiguous sectors per command (the emulator's FIFO count wraps at 8,192 words, so 64 is not used); a direct write drops a cached copy of the sectors it covers, and a read that leads into a direct run fetches only its first sector through the cache.
- **USB:** the main loop watches VBUS. When the cable is plugged in, `board/usb_session` powers the PHY and the polled DWC2 core (`board/usb`) and connects, without touching audio or the screen. It asks for high speed (DCFG speed 0) unless high speed already failed since power-on; at enumeration done it reads DSTS and uses 512-byte bulk packets at high speed and 64 at full speed, on the core's reset FIFO sizes (RX 147 words, shared TX 128), one packet per bulk OUT transfer. If a high-speed session isn't working (configured and through two SCSI commands) 10 s after the first bus reset (`device/usb_fallback`), it reconnects at full speed and stays there until the next power-on. The main loop then keeps running and checks GINTSTS for a bus reset on every pass, for up to 3 s, with the CPU clock held at 96 MHz or more. No reset means a charger: USB powers down quietly and the player carries on, playing and charging. With a host, `board/main.c` loads the USB overlay (see USB overlay) and the session runs from it:
  - `app_release_audio` saves the bookmarks and unloads the player's track (it stays paused at its position) and `board_audio_shut_down` stops the DMA and powers the DAC path down through `board/audio.c`, before the overlay is loaded and the audio power pins are silenced; then the app shows "Computer found" and its steps pause. Silencing the pins behind the audio driver's back used to leave it believing the path was still up, so nothing played after the session until a restart
  - LUN 0 is the internal-storage user volume and LUN 1 is the SD card, both read/write. Sense data is kept per LUN
  - if the controller fails to start, `board/usb_report` shows four notices (a key press moves on): the core ID and OTG control after power-up; the failed init step (with `0x10` set when internal storage started) and GHWCFG4; then GINTSTS and OTG control after the wait. It is a bring-up aid inherited with the code
  - **Plug-in answer.** Settings → When plugged in (`UsbConnect`, byte 5 bits 4–5) reaches the board through `hal_system_set_usb_answer`. A connection is *requested* when `UsbReconnect.requested` or `.forced` is set: the restart after `install --restart`, a script's `reconnect` or end-of-script reconnect, and a mode chosen in the USB mode chooser. `device/usb_plug` decides: a requested connection always listens and is served; otherwise Charge only never listens (the plug is marked served, so no pull-up is presented until the cable is pulled), File transfer listens in storage mode and serves as before, and Ask listens in the remembered mode and, at the host's first bus reset, `board/main.c` marks the plug served, sets soft disconnect and powers USB down (`stop_listening`) in the same main-loop pass, before the core has been given an address or answered a descriptor request, then calls `app_ask_usb_mode`. In the emulator the soft disconnect follows the bus reset within 10 ms. A wall charger never resets the bus, so it keeps the pull-up as before and never asks. The host sees a device attach, reset and leave; whether a computer reports that brief attach is for the player to show.
  - **The prompt** (`app_ask_usb_mode`, the settings module's `UsbChooser`) is the USB mode chooser with the title "USB connected" and a 15 s countdown in the Charge only row's detail column (`ChoiceConfig.detail`); a key restarts it. It has its own `ChoiceScreen`, outside the settings screens' shared choice, so it never disturbs a setting being edited underneath. Charge only, Back, the countdown or the display going dark pop it with no request (the board already stopped); File transfer and USB DAC call `hal_system_request_usb_mode`, the same request the chooser makes by hand, so the next pass reconnects as a requested connection. On the charge screen the prompt (and the chooser opened with Menu) leaves charge mode without starting Bluetooth or the splash; when it closes, `resume_charging` returns to charge mode, lit after a key and dark after the countdown or a dark screen.
  - the session ends when every LUN that was present has been ejected, or the cable is pulled. If the session wrote to either drive, the file HAL forgets its mount and open files, and `app_start` reloads the app from the changed card. If the cable was pulled while a drive was still mounted, a notice says recent changes may be lost. The session records how it ended (ejected, or unplugged with how many drives still up), the sectors written to each drive and any writes refused after an eject; no menu row shows that record at present. Then `board/update` opens the update file on internal storage (`device/update_names`) and installs it if it's valid and differs from slot 1, or if it's FiiO's stock image, showing progress and the result. After an install the player asks for USB to be unplugged and Power to be held, then turns off; the new firmware starts at the next power-on. Otherwise `app_wake` restarts the screen timeout
  - **Leaving from the player** (`device/usb_activity`, `device/usb_leave`): the session tracks host traffic from the MSC counters: sectors read, sectors written and SYNCHRONIZE CACHE commands (`MscStats.flushes`). A write or flush marks the host busy; after `USB_ACTIVITY_QUIET_MS` (3 s) without one it counts as quiet. Holding Back for 1 s asks to leave. A quiet host gets `msc_remove_media`: every present LUN answers TEST UNIT READY, READ, WRITE and READ CAPACITY with CHECK CONDITION, sense NOT READY / MEDIUM NOT PRESENT (02h/3Ah/00h), INQUIRY and REQUEST SENSE still answer, and a command already under way finishes. No UNIT ATTENTION is raised: SPC uses UNIT ATTENTION 28h for a medium becoming ready, and a removed medium is reported by NOT READY on the next access, which is what an ejected LUN already answers. After `USB_LEAVE_GRACE_MS` (2 s) the session ends exactly as an eject does (time file applied, update check, scripts, mode selector), whatever the host does meanwhile, so a host that keeps reading cannot hold it. A WRITE refused during that grace means the host still had data to write; the session then ends as below. If the host wrote within the quiet period, the screen says the computer is still writing and the session waits for quiet; Back held for another 3 s ends it at once (`USB_SESSION_STOPPED`): recorded as unplugged, the time file is discarded, the "Disconnected too soon" warning waits for a key, and the mode selector opens because the cable is still in. Both ways reload the app and check the music as after an eject when anything was written. The 3 s quiet period was chosen from how hosts flush: Windows mounts removable drives for quick removal and writes through, Linux desktops mount FAT with `flush`, so their writes are done when the copy finishes, while macOS writes its buffers back on its own schedule after the copy; any later write starts the quiet period again, and a write refused after the removal is caught as above. How macOS reports the removal, and whether 3 s covers its write-back, is still to be checked on the player.
- **USB DAC mode** (not run on a player by this project; Podium's documentation reports it playing from Windows 11 and an Android phone): the USB mode chooser (and the plug-in prompt) chooses File transfer (the session above) or USB DAC; the choice is saved, `settings_store_apply_hardware` passes it to `hal_system_set_usb_mode`, and `board/main.c` reads it when it starts listening (When plugged in = File transfer always listens for storage). Listening for a host, the 3 s wait and the charger case are the same as for mass storage. With a host, `board/usb_dac_session` runs instead of the mass-storage session:
  - **Class and speed:** USB Audio Class 1.0, full speed only (`usb_device_allow_high_speed(false)`, DCFG speed 1), so it needs no driver on Windows 10 and later, macOS, Linux, Android or iOS. Interface 0 is Audio Control: an input terminal (USB streaming, 2 channels) into a feature unit (ID 2: master mute and volume) into an output terminal (headphones). Interface 1 is Audio Streaming: alternate setting 0 has no endpoint, 1 is 16-bit stereo PCM, 2 is 24-bit stereo PCM (3-byte subframes), both at 44.1 and 48 kHz, on isochronous OUT endpoint 1 (adaptive, 1 ms interval) with room for 49 frames (196 and 294 bytes). 88.2 and 96 kHz are left out because their largest packet (up to 582 bytes at 24-bit) doesn't fit the RX FIFO (see FIFOs below). Android's USB audio picks the highest rate a device offers, and some Windows setups do too, so offering them meant silence on those hosts. The device descriptor says USB 1.1 and has no serial number.
  - **Synchronisation:** adaptive, by ring level, with no feedback endpoint. The I2S clock runs from the player's MCLK, so the computer's rate and the DAC's drift apart slowly (a few frames per second). `device/usb_audio_sink` converts each packet into the music ring (16-bit samples to the top half of the word, 24-bit samples shifted up by 8, two words per frame, the same format as music) and measures the fill as frames written minus frames the DMA has played. `device/stream_drift` keeps it near 20 ms: when the fill is more than 4 ms off, each packet drops its last frame (too full) or repeats it (too empty) until the fill is back within 1 ms of the target, or past it. One frame per millisecond is far faster than any drift, and a single dropped or repeated frame isn't audible. The sink also keeps the 20 ms after the newest frame silent, so if packets stop the DMA plays silence rather than old audio; if the DMA overtakes the writer (packets lost for longer than the buffer) or the ring would overflow, writing restarts 20 ms ahead of the DMA after a short silence. An asynchronous feedback endpoint would avoid the dropped frames, but it needs a second (IN) isochronous endpoint, a measured rate in 10.14 or 16.16 format and per-host quirks, none of which can be checked without hardware.
  - **Rates and formats:** the host's SET_CUR on the endpoint's sampling-frequency control (3 bytes, either of the two rates; others stall) or a new alternate setting stops the output, restarts the DAC path at the new rate through `board_audio_stream_open` (the same `dac_path_start` as music, with its ACODEC row and divider), and primes the ring again: the DMA starts once 20 ms is buffered. 100 ms without packets (the computer stopped playing) also stops the output until packets come back. GET_CUR reads the rate back.
  - **Volume:** the feature unit's volume runs from −64 dB to 0 dB in 0.5 dB steps (GET_MIN `0xC000`, GET_MAX 0, GET_RES `0x0080`); `board_audio_set_attenuation` adds it to the player's own level on the DAC's PCM volume registers (0.5 dB per unit), and mute sets them to mute. The volume keys change the DAC mode's own level (held keys repeat), limited by the active headphone profile's ceiling; the level from before the session comes back afterwards.
  - **Screen and menu:** the DAC screen shows the stream state (choose the output, no sound, playing, or the output failed), the format from the host's alternate setting and rate, the player's DAC volume, the host's volume or mute (0 dB until the host sets it), the plugged jack (`hal_audio_jack`), the ring fill in milliseconds (frames written minus frames played), the clock correction in parts per million (frames repeated minus frames dropped by `stream_drift`, over the frames played), DAC underruns since the session started (`HalAudioStats.output_underruns`), the time since the host arrived and the bus speed. The level meter reads the peak of each channel from the sink after the headphone trim (`usb_audio_sink_take_peaks`, one compare per sample), maps it over the top 48 dB (`device/usb_level`) and falls at 400 steps of 255 a second. Menu opens a list in the shared list style: Volume (Play, then Vol± to change), Gain, Output, Headphones, File transfer and Charge only. Only settings that act on the USB path are offered: the sink writes the host's samples straight into the output ring, so the equalizer, ReplayGain and the music engine do not apply; the DAC volume, the host's attenuation, analog Gain (`hal_audio_set_gain`), Output (the volume table, `hal_audio_set_output`) and the headphone profile's trim, balance and ceiling do. A profile chosen here is applied at once (the DAC volume is first lowered by `headphone_audio_switch_volume`, then the HAL and the sink get the new trim); when the session ends the app commits it through the settings module (`headphone_store_choose_for_dac`), which also lowers the music volume, and keeps the DAC volume the session chose. Volume, Gain and Output are saved with the settings when the session ends (`app_remember_dac`). File transfer and Charge only end the session and make the same request as the mode selector (`hal_system_request_usb_mode`). Back held for a second still ends the session with the mode selector.
  - **Audio driver:** `board/audio.c` has a stream mode for this: `board_audio_stream_open` stops music (`board_audio_shut_down`), clears the music ring and starts the path at a rate; `_play` starts DMA channel 5 over the ring as for music and fades up; `_pause` clears the ring and fades down and stops the DMA; `_consumed` gives frames played; `_close` shuts the path down. While the stream is open, `hal_audio_service` and the DAC's fade waits call the session's USB service instead of the engine, so drawing a notice or fading keeps the isochronous endpoint served. The session starts with `app_release_audio()` and `board_audio_shut_down()` and ends with `board_audio_stream_close()`, so music works as before afterwards. The audio power pins are never touched directly. The CPU runs at 200 MHz: the session's first notice turns the screen on, which raises the clock as in a mass-storage session, and opening the stream raises it too if needed.
  - **DWC2 in polled mode:** the session loop polls the core (four `usb_poll` calls per pass), the audio service (jack sense) and the keys. The changes in `board/usb.c`, cited against the DWC2 register map:
    - FIFOs: the same layout as mass storage (RX FIFO 0x120 words, TX FIFO 0 0x20 words at 0x120, TX FIFO 1 at 0x140). The core accepts an isochronous OUT packet only when the RX FIFO has room for a maximum-size packet (582 bytes, 146 words) plus its status entries, so the reset size of 147 words (`GRXFSIZ` `0x93`) drops every packet: Podium's documentation records that on a player this showed as no packets received, an incomplete-ISO interrupt every frame and NAKIntrpt (DOEPINT bit 13) on endpoint 1. An earlier build computed its own split from the reset values, skipped it on this chip's layout, and so stayed at 147 words. The endpoint is therefore armed for 294 bytes (`USB_AUDIO_MAX_PACKET`, 49 frames of 24-bit stereo, which Podium's documentation records as proven on a player), the largest packet of any offered format.
    - Endpoint: at SET_CONFIGURATION, DOEPCTL1 gets MPS 294 (bits 10:0), USBActEP (bit 15) and EPType 01, isochronous (bits 19:18); DAINTMSK bit 17 and GINTMSK bit 21 are set (the core isn't wired to an interrupt, but the status bits are polled). A streaming alternate setting arms it: DOEPTSIZ1 = PktCnt 1 (bit 19) | XferSize 294, the same for every format and rate (a shorter packet ends the transfer), so it doesn't matter whether the host sends SET_CUR for the rate before or after SET_INTERFACE, then DOEPCTL1 EPEna (31) | CNAK (26) | SetOddFr (29) when DSTS bit 8 (the low bit of SOFFN, the current frame number) is 0, otherwise SetEvenFr (28), so the endpoint takes the next frame's packet. Each transfer complete (DOEPINT1 bit 0) re-arms it the same way while streaming.
    - Missed frames: GINTSTS bit 21 (incompISOOUT) means an armed isochronous OUT endpoint got no packet in a frame. If DOEPCTL1 is still enabled and its EO_FrNum (bit 16) matches the current frame's parity, the endpoint is switched to the other parity, then the bit is cleared.
    - Packets: GRXSTSP is popped once per poll; PktSts (bits 20:17) 2 with EPNum 1 is a packet for the sink, read into the port's 128-word packet buffer (the larger of a high-speed bulk packet and `USB_AUDIO_MAX_PACKET`); 3 and 4 are skipped as before.
    - Control OUT with data (SET_CUR): the request is held until its data packet (PktSts 2, EPNum 0) arrives on EP0, which `arm_setup` keeps enabled; then the reply is applied and the status stage sent (a zero-length IN, or a stall).
    - Control IN longer than 64 bytes (the 159-byte configuration descriptor): sent as 64-byte packets, each after DIEPCTL0 EPEna clears from the previous one (up to 100 ms each). Replies of 64 bytes or less go out exactly as before.
    - Mass storage is unchanged: these paths only run when the port has an audio device, and with one the bulk endpoint and MSC calls are skipped.
  - **Screen:** "USB DAC" with "Starting USB...", then "Choose Gnarlyr as output" with "Volume 35" on the line below while the host has no stream open (the prompt wraps onto two lines in portrait), the format and the DAC volume, such as "48 kHz 24-bit · Volume 35", while it has, or "Output didn't start". The notice is drawn only when the format changes, because drawing delays the polling (the audio service is called after each strip, so the endpoint is still served between strips).
  - **Ending:** pulling the cable, or holding Back for 1 s and releasing it (the player then stays a charger until the next plug-in). The session powers USB down and `app_wake` restarts the screen timeout. Nothing touches the card, so there's no rescan or update check. The last-session record isn't updated.

- **CPU clock:** `hal_system_clock_mhz` and `hal_system_set_clock_mhz` (`hal/system.h`). On the device, `board/clock_switch.c` follows stock's PLL order with the register words from `device/pll` (96 and 200 MHz). It waits up to 200 ms for lock and stays at 24 MHz without it. - **Test tone:** `hal_audio_test_tone` (`hal/audio.h`) blocks for about 5 s. On the device, `board/dac.c` runs the SoC side of the audio path (gates, I2C0, ACODEC mux, I2S1, polled FIFO feed) and `device/dac_sequence` runs the CS43131 side (power pins, probe, register sequence, output on and off) through a `DacBus`. It plays one sine period of 100 samples (441 Hz at a true 44.1 kHz) at amplitude 9000 (ReChord's level, about −11 dBFS): 2 s with the I2S divider from the formula (MCLK / (64 × rate) − 1, truncated, which gives 2), then 2 s with it rounded (3). It reports No DAC, Setup failed, Not ready or I2S stalled when a step fails; No DAC adds the I2C step (s1 start, s2 send, s3 NAK, s4 stop, s5 receive) and the I2C pending bits in hex. `hal_system_boot_clocks` gives the low halves of CRU `+0x10`, `+0x14` and `+0x18` as the ROM left them, read first thing in `board_main`. The simulator returns Played. No menu row runs the tone or shows the boot clocks at present.
- **DAC identification:** the first time the DAC path starts after power-on, `board/dac.c` reads Cirrus's identification registers from each of the two chips, once the power pins and I2C0 are up and before the probe write: `0x010000`–`0x010002` (device ID), `0x010004` (revision) and `0x010005` (subrevision), through the driver's ordinary register read (`dac_read_identity` in `device/dac_sequence`). `0x010003` is reserved and is not read. The read writes no register, changes no pin and adds no wait; it leaves a chip at its first register that fails and is never repeated before the next power-on, and the I2C step kept for a failed start (`hal_audio_tone_detail`) is put back afterwards, so a failed identification neither fails nor mislabels the start-up. `test_dac_sequence` checks on a recording bus that exactly those reads happen and that every write, pin change and wait of the start-up is the same with a complete, a partial and a failed identification. `hal_audio_dac_identity` returns the kept bytes. The cached identification HAL remains available for diagnostics and future verified DAC controls; DAC A and DAC B are no longer About rows. Earlier developer builds on the owner's unit read both chips as `431980 A1.06` (CS43198).
- **Jack pins:** `hal_audio_jack_pins` (`board/jack.c`) records how the ROM left GPIO0.13 and GPIO2.8 (function, direction, pull), then makes both GPIO inputs and reads them. Settings → About → Jack 3.5 and Jack 4.4 show the live level and the boot state (GPIO0.13 high = 3.5 mm, GPIO2.8 low = 4.4 mm; Podium's documentation records the 3.5 mm pin as confirmed on a player). `hal_audio_jack` gives the debounced jack: `device/jack_sense` names it (GPIO2.8 low wins) and takes a change after 7 matching readings, one every 10 ms from `hal_audio_service`. With Output set to Auto, the volume curve follows the jack (level n of 60 is 2 × (60 − n) PCM-volume units, 1 dB per level, level 60 = 0 dB on 3.5 mm; 4.4 mm adds 10 units, 5 dB, as stock's balanced table does: stock's `0x82 − n` against `0x78 − n` for 3.5 mm in `FUN_03061262`); a fixed Output setting overrides it. Both jacks are driven by the same two CS43131s (one per channel), and no switch between them is known, so Output can't route sound to one jack: it only chooses the volume table, 1.5 dB apart at the top. Settings shows the detected jack next to Auto ("Auto (4.4 mm)"), and choosing an option says what it does. The player pauses when the jack goes from plugged to none and doesn't resume on its own.
- **Device playback:** `board/audio.c` implements the audio HAL with `device/audio_engine` (host-tested). The engine opens a track through the file HAL and takes decoded frames from an `AudioSource`. `board/audio.c` picks the source from the file's first 32 bytes, not its name: `fLaC` goes to FLAC, `ftyp` at byte 4 to M4A (see below), `OggS` to Opus when the first packet (byte 28) starts with `Opus` and to Vorbis otherwise, `RIFF`…`WAVE` to `device/wav_source` (PCM or extensible PCM, 1–2 channels, 8/16/24/32-bit, any chunk order before `data`, 4,096-frame blocks read on core 0 into buffers that share memory with core 0's FLAC decoder), an ID3 tag or an MPEG audio frame header to MP3, anything else is refused as an unsupported file type. MP3 is decoded on core 1 by libmad (`third_party/libmad`, 0.16.4 pinned in `VERSION`, built with 64-bit fixed point and `OPT_ACCURACY`; on the device `third_party/libmad_libc` stands in for the missing C headers and `core1/no_heap.c` makes `malloc` always fail, since `device/mp3_decoder` hands libmad static main-data and overlap buffers before its first frame). Core 0 runs `device/mp3_probe` (ID3v2/ID3v1/APE tags skipped, the first frame confirmed by the next one, length from Xing/Info or VBRI, else from size and bitrate; seeking through the Xing table or proportionally) and streams the file into the same core 1 ring; `device/core1_mp3` turns each frame into a block of 24-bit samples. MP3 partitions the existing 128 KB input region into a 64 KB compressed ring and a 37,744-byte stereo tail buffer. The producer retains up to 3,566 decoded samples per channel, publishes earlier PCM and discards only the retained padding at end of stream. `StreamControl.tail_trim` follows the existing slots, so their offsets stay fixed. This keeps end trimming after approximate Xing/proportional seeks and part-way resume; the consumer still removes encoder/decoder lead-in on a start from zero. A generation change resets retained PCM. Untagged MP3 bypasses the tail buffer, and FLAC/M4A publish zero tail trim. Core 1 runs one program at a time, as stock does: the programs are packed by `tools/make_image.py`, MP3 at image offset `0x240000`, FLAC at `0x280000` and M4A at `0x2A0200` (a 512-byte header with `EC1M`, size and CRC, then the program) and read from either checked firmware slot on eMMC straight into core 1's RAM through a 4 KB staging buffer, with the CRC checked on the way. Switching between FLAC, MP3 and M4A tracks restarts core 1 with the other program; after an update, until the restart, all programs are refused like the rescan overlay. On core 1 the FLAC decoder can hand LPC subframes of order 3 and up to the hardware accelerator (`device/flac_accel`) through `flac_set_lpc_hook`, but only for the classes (narrow or wide accumulator) that passed its self-test; a timeout turns the hook off. Core 0 runs the self-test once per boot, before the first FLAC stream, and passes the passing classes to every later core 1 FLAC run. libmad's `III_decode` keeps a 7 KB frame on the stack, so `core1/core1_mp3.ld` keeps the program's `.bss` below `0x0102B000`, leaving 12 KB of stack. The engine records why it refused a track (unreadable, or the sample rate with the rate), `hal_audio_refusal` reports it, the player counts refusals, and the app shows a toast such as "192 kHz isn't supported yet". On the device that is `device/core1_stream`: core 0 opens and seeks with its own decoder, streams the file into a 128 KB region in core 1 RAM, and core 1 decodes frames into two slots; if neither checked program copy loads or core 1 cannot start, the track is refused like the other compressed formats. `device/flac_source` keeps only header reading and seeking on core 0; frame decoding runs on core 1. Each frame is copied into a 28,000-word ring in data RAM as two words, left then right, each a 24-bit sample shifted to the top of its word (stock's music mode, TXCR `0x401F`; 16-bit sources are shifted up, nothing is rounded). Volume is set in the DAC's PCM volume registers; the engine's software gain stays at unity on the device. The engine keeps a list of segments (token, start frame, start position, rate) so the token and position follow what the DMA has played. DMA channel 5 loops over the ring through seven linked items of 4,000 words (a DW block holds at most 4,088 items; `device/dma_loop` refuses more); the HAL turns its read address into a running count of consumed frames. The app calls `hal_audio_service()` at the start of each step and after each strip, so drawing can't starve the ring (14,000 frames is 73 ms at 192 kHz, 146 ms at 96 kHz and 317 ms at 44.1 kHz). Playback starts once 100 ms of audio is buffered (at most three quarters of the ring) or after 1 s. Native output rates are 32, 44.1, 48, 88.2, 96, 176.4 and 192 kHz, each with its ACODEC row and the rounded I2S divider. Standard 8–24 kHz recordings use the conversion described under Lower-rate playback. A queued track at the same rate follows without a gap; a different rate waits for the ring to drain, then the path restarts at the new rate. Volume changes fade on the DAC: 6 PCM-volume units (3 dB) every 2 ms (`dac_ramp_next`), and `board/dac.c` keeps the ring fed between steps through a service hook, so a fade never starves the ring. Starting output fades up from mute after the DMA starts; stopping, pausing, seeking and skipping fade down to mute before the channel stops. A seek while paused stays silent. Pause fades out, mutes the DAC and suspends the channel (nesting with the clock switch's suspend). Seek and play restart the ring. Three seconds after playback stops, the DAC path powers down. `hal_audio_service` takes and clears the I2S underrun flag (INTSR bit 1, cleared through INTCR bit 2; INTCR keeps TXUIE set with the NVIC line off). It increments the output count unless DMA is both intentionally suspended and the DAC is muted. `dmac_running` still means enabled; `dmac_suspended` separately reports its nested suspend depth. Sampling before pause/stop retains pending genuine faults. Transfer start and a quiet resume clear stale flags before unmuting. An unmuted interruption remains a fault. The count is shown as `o` on the frame overlay. The ring must stay in data RAM (`0x03004000`–`0x0304C000`): High RAM (`0x0307A000`) shares its SRAM with the code at `0x03050000`, and with the screen on core 0's instruction fetches starve the DMA's ring reads at 192 kHz (I2S underruns, an audible crackle). Core 0's FLAC header and seek decoder, which shares its memory with the WAV buffers, sits in High RAM instead (`.high_ram`, no-load): only the CPU touches it, and audio is stopped before an overlay overwrites it. The device starts at 96 MHz (`START_CLOCK_MHZ`) right after reading the boot clocks.
- **Vorbis decoder program:** a guarded fixed-workspace Tremor program occupies the reserved image bank at `0x260200`. The player selects it for Ogg input and module 6 completes configuration before publishing audio. Its 64 KiB input ring and 64 KiB setup/scratch workspace use core 1's ring area; planar PCM uses the existing output slots. Its static state is limited to 36 KiB, including a private 32 KiB packet snapshot, below a 16 KiB stack reserve; the image bank holds at most 130,048 code bytes. Native and Cortex-M3 reference comparisons cover normalization, seeking, ring wrapping and failures. A cooperative two-core emulator connects the player to the actual ARM decoder for functional tests; it does not measure physical throughput. See [the decoder protocol and bounds](ogg-vorbis.md).

- **Opus decoder program:** the fixed-point libopus 1.6.1 decoder runs on core 1 from its own image bank at `0x2C0200`, directly after the glyph table; glyph faces, language packs and modules are placed after it. The player selects it when an Ogg file's identification header says `OpusHead`, and module 6 opens the file. Its 40 KiB input ring, 32 KiB packet snapshot, 32 KiB decoder scratch and 120 ms PCM stage use core 1's ring area; the decoder state is in its BSS. The program image bank holds at most 131,072 code bytes, with at most 28 KiB of static state below the 16 KiB stack reserve. See [Opus playback](opus.md).
- **M4A (AAC-LC and ALAC):** `device/mp4_demux` walks the boxes through the read callback without loading any of them: it finds `moov` before or after `mdat`, the first `soun` track, its sample description (`mp4a` with the `esds` AudioSpecificConfig, or `alac` with its 24-byte cookie; `wave` wrappers and 64-bit box sizes are not read), the `stts` total, and the chunk, run and size tables of `stbl`, which stay in the file. A configuration other than AAC-LC (or AAC-LC with SBR or PS signalled, which ffmpeg writes as a backward-compatible `0x2B7` extension with the SBR flag clear) is refused. The encoder delay and the number of valid samples come from the `iTunSMPB` tag under `moov/udta/meta/ilst`, else the delay is zero and all samples are valid. `Mp4Cursor` finds sample N by walking the `stsc` runs, reading one `stco` or `co64` entry and adding up at most one chunk's worth of `stsz` entries (read 64 at a time), then walks forward with one table read per 64 samples and one per chunk. `device/m4a_stream` turns that walk into a byte stream for the second core, read through the same fill loop as the other formats: a configuration record (`u32` length, the codec byte, the AudioSpecificConfig or ALAC cookie), then one record per packet (`u32` length, the packet read from the file), then a zero length and zeros. Core 1 runs `core1/m4a_main.c` (`device/core1_m4a`): it reads the configuration record, starts FAAD2 (`third_party/faad2`, fixed point, LC only, 24-bit output) or `codec/alac`, and decodes a packet per block. The program is stored at image offset `0x2A0200` (`make_image.py --core1-m4a`, at most `0x1FC00` bytes so that it ends at the glyph table). It runs with a 64 KB ring (`M4A_RING_BYTES`) so that the upper 64 KB of core 1's ring area can serve as a bump heap for FAAD2's allocations, the ALAC state and the packet buffer (`device/core1_heap`; `malloc` in `core1/heap.c`); the heap resets at each stream start. Core 1's `.bss` includes FAAD2's element scratch, which `third_party/faad2/syntax.c` keeps static; its deepest call chain needs about 21 KB of stack. The first packet of a seek is the one before the target, because AAC needs the overlap of the previous frame; packets before the target are decoded and dropped by the engine's skip. After a seek the output position is exact to the sample. The playable length is the `iTunSMPB` valid count, so tracks end where the encoder's padding starts. FAAD2 is told to return the first frame (it normally suppresses it). The library needs no change: `.m4a` was already indexed with its tags, duration and cover art, and the scanner and `tools/library_index.py` agree on `tests/fixtures/m4a_music`.
- **DMA tone:** `hal_audio_dma_tone_start`, `_stop` and `_status`. On the device it checks COMP_TYPE at `0x600003F8`, brings up the same audio path with the rounded divider and INTCR `0x01F00100` and without XFER, then runs DMA channel 5 (`board/dmac.c`) over the music ring filled with a sine (16-bit samples in the top half of each word, two words per frame, the same format as music) through the same seven linked items as music (`device/dma_loop`), with every channel interrupt masked. Then DMACR = `0x110` and XFER = 1. The call returns at once; `_status` reports "Playing" with channel 5's read position, "Ended" if the channel stopped by itself, or the failed step, and `_stop` suspends the channel, disables it, and closes the audio path. No menu row starts it at present. A clock switch suspends and resumes the channel around it.
- **Start record:** `hal_system_start_info` (`hal/system.h`). On the device, `device/start_record` keeps a record in `.noinit` RAM: the start count, the uptime (every 5 ms), a power-off mark, fault registers, the last battery reading (every second) and the last risky step (backlight on or off, clock switch, core 1 start or stop, card write) with its start time and whether it finished. - **Stall and fault screen:** a power loss wipes the Last start record, so a freeze that ends in a power cut reads Cold start. On the device the main loop beats a `device/stall_watch` each pass, and the 1 ms SysTick checks it every 5 ms. A loop silent for 10 s (paused during start-up, USB sessions, updates and power-off) trips it once: the interrupt silences the audio pins, clears the panel, turns the backlight full on and draws, in a 5×7 font scaled ×2 (`device/panic_text`), "STALL", the interrupted PC and LR (from SysTick's exception frame via `device_systick_entry`), and "UP \<s> STEP \<n> [U] MV \<mV>" (U = the step never finished; step numbers follow `HalStartStep`). A fault draws "FAULT" with PC, LR and CFSR the same way. After either, holding Power for 2 s cuts power from the interrupt. In the developer build, Settings → About → Stall test freezes the main loop on purpose to check the screen. A loop stuck with interrupts masked isn't caught.

- **Charge screen:** with USB power, GPIO2.6 low doesn't cut power (`hardware.md`), so a switch-off on a cable used to leave the player dark and deaf until RST. Now the app's shut-down checks `hal_power_battery().usb_power` and, when it's set, enters charge mode instead of `hal_power_off`: it pauses and releases the output, puts Bluetooth to sleep and draws `screens/charge_screen`. The views module draws the charging artwork (`charge_art`): the theme's header band, the backdrop gradient (with the horizon floor below the readout in themes that have one, left out when less than two small text lines of room remain), a large battery in the status bar's style (outline, nub, fill in the success colour on USB power, at least two strokes wide for any charge above zero; the Bolt inside with a halo while charging, cut into the fill once charged), the percentage at twice the title size and the state ("Charging", "Charged", "USB power") in the title font, tinted toward success while charging or charged, above "Menu: mode" and "Hold Power: turn on". While actually charging, every 200 ms frame of an eight-frame cycle the empty part of the battery breathes faintly toward the fill colour and the next tenth more strongly; with an unknown reading the Bolt breathes instead. Only the inside of the battery changes between frames, so the frame diff sends only those rows. Charged, USB-power and battery states are still and redraw only when the reading changes. An unknown reading shows "Reading battery" without a percentage or fill. When the module can't be loaded, the resident fallback draws the slim-gauge layout below. USB storage and DAC share that layout with their actual mode, drive or audio details and the appropriate exit instruction; voltage is hidden while USB-powered. The screen goes dark after 5 s and any key lights it; holding Power for 2 s leaves charge mode (Bluetooth restarts, the splash plays); losing USB power calls `hal_power_off`, which now cuts power. A computer found while charging wakes the screen to the plug-in prompt (see USB, Plug-in answer); a session it starts returns to the charge screen. `board_power_hold` records VBUS and the Power key level at boot ; `hal_power_take_usb_start` reports, once, a start with VBUS present, the key up and GPIO2.6 not left driven high by the ROM, and the app then opens charge mode straight after `app_start`. The backlight stays off from boot until the app's first frame, so the panel's power-on noise never shows, and `board_display_service` also runs inside the USB, DAC, update and wait-for-key loops so a backlight fade-in started there finishes.
- **High RAM:** `hal_system_high_ram_test` writes and reads back a pattern over `0x0307A000–0x0309CFFF` (140 KB of HIGHRAM0, where the rescan and USB overlays run and the glyph cache lives; it stops below the language pack, which must survive it) and calls a 4-instruction function copied there. Afterwards it restarts the glyph pack reader, since the test overwrote its cache. It reports "OK 140 KB, call works", "Bad at \<address>" or "Call gave \<value>". No menu row calls it at present.
- **Bluetooth:** `hal/bluetooth.h` powers the module, scans, connects to a device, turns the stream on and off and reports the module's state, the devices found, link counters and counts of the headphones' button presses. On the device, `board/bluetooth.c` follows stock's sequence: GPIO2.7, 2.16 and 2.17 are driven low at boot; power-on opens UART1 (group A, 115,200 8N1, divisor 13, FIFOs on, polled, no interrupts) and drives GPIO2.7 high; power-off drives all three low again, as does a module that never sends `CV1`. `hal_bluetooth_service` runs where `hal_audio_service` does (each step and after each strip): it drains the RX FIFO into `device/bt_module`, counts overruns, records the FIFO's peak level and depth, and sends any frame the protocol asks for. `bt_module` connects with `CL06` + the address, `CH06` after 4 s and `CT00` and a failure after 30 s, polling `CQ00` every second meanwhile so a link the module reports only as `CQO` (a remembered device sends no `CLOK`, and headphones may connect on their own) shows within a second; a paired reply (`CLOK`) waits for the next `CQ00` answer to report the link (`CQO`). It sends `CY0 00` on connect, `CY0 1E`/`CY0 00` to start and stop the stream, and stock's `C 86`/`C 87` play notices. The module's `CP`/`CC` (pause/play, sent by the headphones' taps and in-ear sensors) and `CA`/`CB` (previous/next) only count presses in `HalBluetoothRemote`; polling pauses for 50 s after a `CP`/`CC`, as stock does. While streaming, the board routes audio to the module: the first time it applies the stock start-up settings listed in `hardware.md`, then GPIO2.0 goes high and GPIO2.14 low (and back on stop), and the DAC driver keeps those two pins while routed. `app/bluetooth_link` runs every step after `player_update`. It keeps the On/Off choice, up to 6 devices, most recently connected first (stock also keeps 6), and where music last went in `/.gnarlyr/bluetooth.bin` (`BT`, version 2, the On byte, the count, 6 × the 6-byte address and 32-byte name, then one output byte: 1 when music last streamed to Bluetooth, 0 when it last played into a jack; a version 2 record without that byte reads as 0, and version 1 files, with one device, still load), written only when they change. When Bluetooth is on it powers the module at start and connects to the first device as soon as the module is ready, retrying 5 s after each failed attempt. It connects only from Ready or from a scan that found a remembered device: never while a connect is running or while a paired reply waits for `CQO`. A pairing that hasn't reported the link 10 s after `CLOK` is dropped with `CT00` and tried again 2 s later, which brings up a link the module left half-made. With the Bluetooth screen open, each failed attempt is followed by one scan to list nearby devices. Stock only ever scans a freshly powered module (its rescan power-cycles it first), so a scan after the module has paged a device power-cycles it too: off for 500 ms, on, wait for `CV1`, then `CS00`; the first scan after a power-on goes straight out, and the screen says Searching… throughout. A scan that finds a remembered device connects to it at once with `CL06` while the scan still runs, as stock's screen does when an entry is picked (one try per scan), unless the user disconnected or chose Pair new device; then its row shows "Nearby". Each new connection moves its device to the front of the list and shows "Connected to \<name>"; a dropped link pauses playback and shows "Disconnected from \<name>". A device the user disconnects stays disconnected (no automatic reconnect) until it or another device is chosen, Bluetooth is turned off and on, or the player restarts. Choosing another device while one is connected disconnects it and connects the chosen one 2 s later; "Pair new device" disconnects too, then scans. It streams while connected, playing and nothing is in either jack. The jack can't be read while audio is routed to the module (the readings fake a plugged headphone), so `board/jack.c` holds its last state then and for 500 ms after each routing change: headphones plugged in while paused take the sound, and Bluetooth waits for the next pause and play before taking it again. The headphones' next and previous skip. Their pause pauses and their play resumes only what they paused, and both are ignored for 3 s after a connection, a stream change or a play or pause on the player, because the module sends the same `CP`/`CC` reports then on its own; a pause the headphones cause shows "Paused by \<name>". With no connection and the Bluetooth screen closed, the module switches itself off after 5 minutes (Bluetooth stays on for the next start). Connected and paused, the stream is off (`CY0` `00`), audio is routed back to the DACs, and the output goes to pause standby after 30 s; the module itself stays on and is asked for its status every 3 s, since the protocol known to this project has no lower-power command and dropping the link would lose the headphones. **Waiting for the headphones** (`bluetooth_link_step`): when playback starts (any play, from ▶, a list or a remote) while music last went to Bluetooth, remembered headphones exist, none is connected, the user hasn't disconnected them and nothing is in either jack, the link pauses the player in the same pass, wakes a module that switched itself off, and shows "Connecting to \<name>…" (shown again whenever the toast has gone, until the wait ends). The connection that follows resumes playback, which starts the stream; a plug in either jack ends the wait and plays there; the user disconnecting or searching ends it quietly; after 10 s (`BLUETOOTH_LINK_AWAIT_MS`, covering a module start, `CL06` and the `CH06` retry 4 s later) the player stays paused and shows "\<name> didn't connect · Play: retry". Play during the wait starts it again. The same applies at power-on, since Bluetooth starts with the player and playback always starts paused: the first ▶ waits for the headphones the module is already reconnecting. Headphones that come back in range after a loss reconnect, but playback stays paused until Play, as with a dropped link on most players. With the module switched itself off, the Bluetooth screen no longer wakes it on opening: its hint line says "Off to save battery · Play: reconnect" on every row, and ▶ wakes the module first (on the On/Off row it only wakes it; on a device it connects that device; on Pair new device it searches). Settings → Bluetooth (third, after Shuffle and Repeat) shows the link's state as its value: Off, Starting…, Searching…, Connecting…, the connected device's name, Not connected or On. It opens `screens/bluetooth_screen`: a Bluetooth On/Off row; the remembered devices, each with its state (Playing, Connected, Connecting… or nothing); a "Pair new device" row (Searching… while scanning); then, while not connected, the devices a scan found that aren't remembered; and a hint for the selected row at the bottom (one line in landscape; in portrait the hint area is as many lines as the longest hint needs, three in English, and the hint wraps). ▶ toggles Bluetooth, disconnects the connected device or connects a remembered one, starts a search, or pairs with a found device (which shows Connecting… or Didn't connect); holding ▶ on a remembered device forgets it. In the developer build, Settings → About → Bluetooth opens the same screen with four more lines: the module state (version, status letter, pairing result, streaming), the link counters and, over two lines, the module's last 12 messages: frames other than `CS` and repeated `CQ` answers, shown as `C` + two letters (a new `CQ` letter shows as `CQ` + it), plus the `CS`, `CP`, `CL`, `CH` and `CT` commands the firmware sent, shown as `>S`, `>P`, `>L`, `>H`, `>T` (`CQ00` polls aren't listed); each is followed by `+n` when n seconds passed since the one before. The log and the devices found survive Bluetooth off and on, so one photo after a failed or slow attempt shows the whole exchange. The status bar shows a Bluetooth mark next to the play icon, dim while on and bright while connected. The simulator reports ready after 300 ms, finds two devices over 3 s, keeps them across a power cycle and connects 1.5 s after a pick.

## Debug loop

A developer aid for checking a build on the player without pressing buttons and reading numbers off the screen. It exists only where `ECHO_RELEASE` is off: the `device` preset, the simulator and the host tests, which compile with `ECHO_DEBUG_LOOP`. The `release` preset has none of it: its size-report lines are those of the commit before the debug loop, and its ELF holds no symbol of it. Reports, scripts and the `peek`, `poke` and `gpio` lines have run on the owner's player; the `supply`, `screen` and `soak` lines have not. What the emulator cannot show is listed in `known-issues.md`.

- **Report:** `board/debug_report_file.c` (in the USB overlay) writes a report to `/.gnarlyr/debug/` on internal storage at two kinds of moment. At the start of every USB storage session, after "Computer found" and before the port and the drives are prepared (`report.reason: usb_session`). And whenever the player shuts down: a long Power press (`shutdown`), auto off (`auto_off`), the sleep timer (`sleep_timer`), the low-battery cut-off (`low_battery`), and losing USB power on the charge screen (`unplugged`). For a shutdown the app names the reason (`debug_loop_shutdown`), and `hal_power_off` (after the audio path is down, before the one-second DAC discharge) or, with USB power present, the entry into charge mode loads the USB overlay and calls its report entry (`UsbOverlayEntry.report`, `hal_system_save_report`); a shutdown during a USB session or after an install (when the overlay in the slot no longer matches the running code) writes none. The text is built in the mass-storage write buffer, which is idle at all of these moments, by `device/debug_report`. A report that cannot be reserved or written is skipped and the session or shutdown goes on as usual. In the emulator the first report of a session (which also creates the folder and the file) takes about 40 ms and the session reaches the host 46 ms after it starts.
- **Kept reports:** there are three files, `report0.txt` to `report2.txt`, each reserved once at 16,384 bytes (`DEBUG_REPORT_BYTES`) and rewritten whole, the rest filled with line feeds. Every report carries `report.sequence`, one more than the highest on the drive (the writer reads the first 128 bytes of each file, so the number survives power cycles without any state in RAM). A new report replaces the file with the lowest sequence, with one exception: a report written within 10 s of a cold start (`report.cold_start: 1`, `DEBUG_REPORT_COLD_MS`) replaces the newest file when that is a cold-start report too. Plugging a switched-off player into a computer cold-starts it and writes such a report from a RAM that holds nothing yet; with this rule any number of those in a row costs one file, and the two reports before them stay. Nothing collected in RAM survives a power cycle, so a cold-start report carries only what the start record does (after a warm reset: the previous run's uptime, last step and fault registers); the rings and the profile reach the drive in the shutdown report before it. They are not kept in no-init RAM across a warm restart: a planned restart writes its report first, and what the boot ROM leaves of that RAM has not been checked on this player (`start.warm` in the first reports from one will show it).
- **Format** (schema 1): plain ASCII, one `key: value` per line, `debug_report: 1` first, then `report.sequence`, `report.reason` and `report.cold_start`. A value that could not be read is the word `unknown`, never a number. Lines are added in later versions without a new schema number; the number changes when an existing line changes its meaning or form, and `tools/echo_debug.py` refuses a number it does not know. The last two lines are `truncated: 0` or `1` (the text is cut at a line when it would pass the file's size; with every ring and every bucket full it is just under 16 KB) and `end: N`, where N is the number of bytes before the `truncated` line, so a reader can tell a whole report from a torn one.

- **Event log:** `core/debug_log` is a ring of the last 48 events, 16 bytes each: the time in ms, a value, the kind and the first 7 bytes of a text. `app/debug_loop` records them from the main loop: `key <name> <gesture>` for every key gesture except repeats (names as in the key script: `up` is the volume-down key), `screen <depth> <title>` when the top screen changes, `player <idle|playing|paused|standby> <track>` when the player's state or track changes (`standby` is a pause whose output has been powered down), `underrun <count>` and `output_underrun <count>` when either count grew (looked at every 100 ms), `refusal <problem>` for a track the audio HAL refused (`HalAudioProblem`), `storage 1` for a full volume and `storage 256+<ScanResult>` for a failed rescan, `storage <mark>` for a file a rescan skipped because a scan stopped on it (see Library rescan on the device), `usb_start <0 storage, 1 DAC>` and `usb_end <how it ended>` from `board/main.c`, and `power <VBUS> <charge pin>` when either level changes (and once after the start). Recording is a clock read and a 16-byte copy. Nothing is recorded from interrupt context: the ring has no lock, the SysTick handler never touches it, and a key is logged when the main loop turns it into a gesture, not when the interrupt samples it. A stall or fault therefore leaves no event; the start record covers those.
- **Power history:** `board/debug_session.c` keeps 128 samples of 6 bytes (`device/power_history`), one every 90 seconds, so a report covers the last 192 minutes: the voltage trend while plugged in and after unplugging, and the whole of a 180-minute soak. (One a minute would need 192 samples for that; with them the fullest report no longer fitted its 16 KB file.) It only reads: the SysTick handler notes each raw battery reading as the gauge takes it and raises a flag every 250 ms; `board_display_service`, which the main loop and every USB, update and key-wait loop call, then compares the cable bit and the raw charge pin with their last levels and takes a sample when 90 seconds have passed; each sample also notes whether USB is powered up and the USB sense mode, so a report shows what the cable bit does across a power-down and a power-up. Nothing is sampled before the firmware first reads the battery (the pin is not set up until then), and "playing" is the player's state as the app last saw it. No power behaviour changes.
- **USB sense:** an engineering test aid exposed through `usb_sense normal` and `usb_sense kept_on` in debug scripts. Kept-on mode still soft-disconnects USB but retains supply power; normal mode permits the ordinary power-down path. The report retains `usb.sense_mode` and the associated power readings. No everyday Settings row exposes this override.
- **Profiler:** while switched on, the 1 ms SysTick handler passes the interrupted program counter from its exception frame to `device/pc_profile` right after it has counted the tick, so timekeeping and the stall watch run as before. An address inside `board_profile_wait` (the main loop's WFI, kept as its own 4-byte function for this) counts as idle; one inside the code window counts in a 16-bit bucket of 128 bytes; one in the high-RAM window (the rescan and USB overlays) counts in a single counter; anything else, including the audio and extension modules in data RAM, in another. The linker script reserves the buckets behind `.bss`, two bytes for every 128 bytes of `CODE_RAM` (1,229 buckets, 2,460 bytes), only when the build passes `device_profile_bucket_shift`; the code reads the count and the window from linker symbols. A bucket that reaches 65,535 stops the profiler (`full`), so the shares stay true; code that runs with interrupts masked is counted where it unmasks them. By the disassembly the handler spends 6 more instructions with the profiler off and at most 30 with it on (about 45 core cycles, under 0.5 µs at 96 MHz); this is an instruction count, not a measurement on a player. It is off after every start. Settings → About → Profiler switches it (Off, On, and Full, where a press clears it and starts again); `hal_system_set_profiling`, `hal_system_reset_profile` and `hal_system_profile_state` are the HAL calls. While a report is being formatted the handler takes no samples (`board_profile_hold`), so the samples, the idle, overlay and other counts and the buckets of one report always add up; without it a tick between two of those lines made the sum one more than `profile.samples`.
- **Scripts:** a script is a text file the computer writes as `/.gnarlyr/debug/run.txt` (at most 640 bytes, 40 lines and 48 steps; `#` starts a comment). When a storage session ends with every drive ejected and the cable still in, the USB overlay reads the file, deletes it and compiles it into steps (`core/debug_script`); the app's main loop then runs one step at a time (`app/debug_runner`, which takes the steps from the effects bank loaded on demand; see Device platform, Extension module) while everything else goes on as usual. If the session also brought an update, the install comes first and the script waits for the next ejected session. The first line must be `build TAG` with the running build's tag, or `build any`; a script for another build is refused and reported, never run. A script may not run longer than 300 s plus the minutes of its soaks. When it ends, by its last line, a `reconnect` line, the time limit or a USB session, the player connects again by itself (two seconds after the last line when there is no `reconnect`), and the report of that session carries the results. While a script is pending or running the auto-off timer is held off; a shutdown stops it.

  Addresses and values are `0x` hex or decimal. `peek` and `poke` take whole words in the first `0x400` bytes of the three GPIO banks (`0x40160000`, `0x40170000`, `0x50030000`), the GRF (`0x50010000`) and the CRU (`0x40180000`); `gpio` takes ports 0 to 2. Anything else is not touched and its line is reported as `refused`. A script keeps 16 probes and 16 address or value words. These three lines exist for hardware experiments: they found that the USB supply pins held high without a cable keep a USB-C host from recognising the player (`hardware.md`).
- **Soak:** `supply off`, `screen off` and `soak` measure battery drain without anyone at the player and with the cable still in. `supply off` sets a developer-only flag (`board/debug_session.c`); `check_usb` in `board/main.c` then tells the owner of the two supply pins, `board_power_usb_supply_follow` in `board/power.c`, that no cable power is wanted, so the pins go low on the next pass of the main loop and nothing else writes them. The flag is cleared when the script ends, is aborted or times out, when a USB session starts, at power-off, and at once when a soak is cut short. Whether GPIO2.0 low really stops USB from powering the player is not known; the voltage trace of a soak is what shows it. During a soak the script only waits. It ends early, with its line reported as `cut_short`, when a key is pressed (the script's own key presses do not count) or when the battery has read under 3,600 mV at seven checks ten seconds apart; the app's own low-battery cut-off does not act while the cable bit reads 1. Each soak adds one line to the report:

  `script.soak: line=N minutes=M end=done|key|low_battery|stopped samples=S first_mv=A last_mv=B mv_per_hour=R busy_percent=P` followed by `cable`, `charge_pin`, `supply_off`, `audio`, `screen` and `clock_mhz`, each as `_start=` and `_end=`.

  `samples` counts the power history's samples taken during the soak (found by the ring's running count at both ends), `first_mv` and `last_mv` are the means of the first three and the last three, and `mv_per_hour` is the slope between them by the minutes the samples carry; it is `unknown` with fewer than four samples, and all three are `unknown` when the soak's first samples have already left the ring. `busy_percent` is the share of the soak the main loop did not sleep. `end=stopped` means the script itself was stopped. A script keeps two soaks.
- **Clock chip read:** `rtc read` asks `hal_system_rtc_read` (`board/debug_rtc.c`, in the extension module) for registers 0 to 15 of the clock chip that stock firmware 2.0.0 reads (`hardware.md`, Clock chip). The Date & time editor and the deferred startup recovery use the same bus path. Nothing touches I2C1 before startup has finished: when a read or write runs, the reader notes the GPIO2.12 and GPIO2.13 functions, the I2C1 group field of GRF `+0xBC` (bits 3:2) and the I2C1 clock gate (CRU gate `0x84`) and reset (`0x1B`); it then ungates and resets the controller at `0x40050000`, routes the two pins to function 3 and the group field to 2 as stock does, and sets 100 kHz. On the bus it sends the chip's address with the register index 0 and nothing after it, which only moves the chip's register pointer, then reads 16 bytes; no chip register is written. Every wait for the controller gives up after 10 ms, so the line takes at most about 60 ms. Whatever the result, the controller is switched off and the pins, the group field, the reset and the gate go back to what they were. A missing answer ends the line as failed with the status `no_ack`, a controller that never finishes with `timeout`. `rtc set` takes the wall clock (`hal_clock_wall`; a script sent by the companion runs after the session that set it) and, with the same bus set-up and restore, writes its UTC date and time as BCD to registers 2 to 8 in one transfer: bit 7 of the seconds register (the trust flag) cleared, the weekday from 0 for Sunday, the year counted from 2000 (`device/rtc_time`, `device/rtc_registers`). No control, alarm, clock-output or timer register is written. It then reads the 16 registers back; the line is `ok` only when the trust flag is clear and the time read back is the one written or up to two seconds later, `mismatch` otherwise, and `no_time` without touching the bus when the wall clock is unknown or outside 2000 to 2099. Each read or write becomes one report line, at most four to a script:

  `script.rtc: line=N ms=T action=read|set written_s=S|unknown status=ok|no_ack|timeout|no_time|mismatch registers=<32 hex digits> vl=0|1 time=YYYY-MM-DDTHH:MM:SS|invalid weekday=W century=C`

  `registers` gives registers 0 to 15 in order. The rest is `device/rtc_registers` decoding registers 2 to 8 as the PCF8563 layout: `vl` is bit 7 of the seconds register (set when the chip cannot vouch for the time), `time` is the BCD time with the year counted from 2000 as stock does, or `invalid` when a digit or a field is out of range, and `century` is bit 7 of the month register. `written_s` is the UTC time a `set` wrote. Without registers to show every field after `status` is `unknown`. The weekday register's unused bits (and those of the clock-output and timer control registers) read differently from one read to the next on the owner's player, as the PCF8563 allows for bits it does not use; the decoding masks them and the firmware takes the weekday from the date, not from the chip. The emulator models I2C1 with a chip that answers at `0xA2`, so its scenarios check the bus traffic, the decoding and the restored state; `no_ack` is covered by switching the chip off. `rtc read` has run on the owner's player (see `hardware.md`, Clock chip); `rtc set` has not.
- **Reconnect, restart and Connect USB:** `hal_system_usb_reconnect` asks the main loop for a storage session without a new plug-in: at least a second after the last session ended it powers USB up and listens, and the session that follows treats a cable bit of 0 as "still plugged in" until a drive is ejected or a minute passes without a command from the computer (`device/usb_forced`). A request made by a script gives up after six seconds without the cable bit and writes a `no_host` report. `tools/echo_debug.py install --restart` leaves `/.gnarlyr/debug/restart.req`; after a successful install the overlay answers in that file, writes a `restart` report and restarts the player, and the new image connects once it is up. A refused or failed install never restarts. `hal_system_usb_connect` makes the same request without a time limit; with the Connect USB row gone from About, only the debug loop calls it, to cancel (`loop.last_connect: cancelled`). Every one of these is a requested connection, so the plug-in prompt never stands in its way (see USB, Plug-in answer).
- **Host tool:** `../tools/echo_debug.py` at the repository root (standard library only) prints one JSON object per command, errors included. `status` says whether the player is on USB, which volume is its internal drive, and which report is the newest; when that one is a cold-start report it sets `cold_start_only` and advises leaving the player switched on. `report` reads and parses every kept report, newest first, each with its file, sequence, reason and cold-start flag (`reports`), and repeats the newest as `report`; and `profile --elf echo_device.elf` shares each bucket's samples among the functions in it by their bytes (`arm-none-eabi-nm -S -l -f sysv`, with the linker map for functions without line information) and sums them per source file: per-function times are estimates at 128-byte resolution, per-file times less so. It finds the player by its USB identity (`1209:0001` and the product name from `identity.json`) and the internal drive by its medium name, volume name (`ECHO`, or `--volume-name`) and size; anything else is an error, and ordinary debug commands do not read the microSD card's volume. `--volume PATH` names the internal drive's folder instead, for the tests and for a volume taken from an emulator run. `install IMAGE [--restart]` copies an image as the update file, reads it back, ejects and, with `--restart`, waits for the player to come back and says which build it then runs. `run SCRIPT` sends a script (adding the `build` line of the running build when the script has none), ejects, waits for the player to reconnect and returns the script section of the new report: lines with their status, `measures`, `screenshots`, `probes` (each with its line's text, a `gpio` word also taken apart), `soaks` and `rtc` (each clock chip read with its registers as numbers). It waits 420 s plus the minutes of the script's `soak` lines unless `--timeout` says otherwise. `wait` waits for the player and prints its status; `screenshots --out DIR` converts the last run's screenshots to PNG. Ordinary debug commands write only the update file, files in the debug folder and, just before every eject, the time file (see Wall clock); `set-time` sends the time and ejects on its own. Separate language operations validate packs against the installed build, write only the active music volume's language folder and select languages through the same debug loop; see [language-pack tools](../../docs/language-packs.md). `../tools/echo_debug_mcp.py` offers the same operations as MCP tools (`echo_status`, `echo_report`, `echo_profile`, `echo_install`, `echo_run`, `echo_wait`, `echo_screenshots`, `echo_set_time`).
- **Developer-only paths:** reports, profiling, scripts and restart handling add resident code, static RAM, USB-overlay code and extension-module code to the `device` build.

## MP4 presentation trim

`device/mp4_demux` reads a selected sound track's single unity-rate `edts/elst` edit, version 0 or 1. Media start is converted from `mdhd` units, and presentation duration from `mvhd` units, to output samples with checked integer arithmetic. The edited range is intersected with available audio, including durations rounded by the movie clock. AAC frame length comes from its configuration and ALAC frame length from its cookie, so a coarse media clock cannot change decoder packet boundaries.

A valid positive-length `iTunSMPB` range takes precedence over the edit. Missing, malformed, overflowing and zero-length tags leave the validated edit in effect. Negative media times, multiple edits, non-unit rates, unknown versions, missing clocks and truncated edits are not applied. Without usable trim metadata, the decoder retains the whole media range. Timing-table bounds and totals are checked; more than 64 timing runs are refused rather than silently counting a prefix.

The edit-list field units follow [Apple's encoder-delay description](https://developer.apple.com/documentation/quicktime-file-format/using_track_structures_to_represent_encode_delay_explictly) and the versioned entry layout in [FFmpeg's MOV parser](https://svn.ffmpeg.org/doxygen/6.1/mov_8c_source.html).

## Simulator audio

- Windowed mode plays through SDL audio. dr_flac, dr_mp3 and dr_wav decode (vendored, pinned in `third_party/dr_libs/COMMIT`). Each track feeds an `SDL_AudioStream` that resamples to the 48 kHz device rate. Two decoder slots (current and queued) make the hand-over gapless.
- Headless mode uses a silent virtual backend that advances on the simulated clock, so scripted runs, track transitions and resume are deterministic.
- `SDL_AUDIODRIVER=dummy` runs the real-time path without sound.
- Settings → About → DAC A and DAC B show `Simulated`: there are no DAC chips to identify.
- Third-party code lives in `third_party/` and compiles without our warning flags. The comment and format checks skip it.

## Simulator storage

`--card DIR` maps the card root `/` to a host folder, which is only ever read. Open files are read unbuffered, because `hal_file_write_at` writes through its own handle: on Windows a buffered reader kept serving the old bytes, so the scan's scratch file read back stale data and every rescan stopped with "Library too big for memory". `hal_file_write` writes a `.tmp` file and renames it over the old one, removing the old one first on Windows, where `rename` won't replace a file. `--system-dir DIR` maps `/.gnarlyr/` to a separate folder, so the database, covers, resume file, settings and favorites can live in `build/` without touching your music folder. Writes are refused outside `--system-dir`:

```sh
.venv/bin/python tools/library_index.py --music ~/Music --output build/library/library.db
build/dev/platform/sim/echo_sim --card ~/Music --system-dir build/library
```

## Simulator power and display

- `hal_display_set_power(false)` blanks the window. Brightness dims the window (level 1 is about a quarter of full), but screenshots hold the undimmed panel.
- The battery is fixed: 80 % by default, or `--battery N` and `--charging`.
- Gain, output and the equalizer are stored but don't change the sound.
- `hal_power_off()` ends the run loop, and the simulator exits normally.

## Simulator automation

In headless mode the simulator uses a virtual clock (16 ms per frame), so runs are deterministic. `--keys` plays a comma-separated script (`up`, `down`, `play`, `menu`, `back`, `power`, each optionally `:long` or `:held`) for driving screens in screenshot runs. The grammar and the hold times (a tap 32 ms, `:long` 1,120 ms, `:held` 4,800 ms, 128 ms between keys) are `core/key_script`, shared with the debug loop. `--notice TITLE --notice-text MESSAGE` shows a notice as the last frame, which is how a notice gets into a capture. `--usb-host FRAME` calls `app_ask_usb_mode` before that frame, as the board does when a computer is found, so the plug-in prompt can be captured (the simulator has no USB of its own). `--clock` sets the wall clock (see Wall clock). A language file in `<system-dir>/lang/` is offered like on the player. For example:

```sh
build/dev/platform/sim/echo_sim --headless --frames 120 --keys down,down,down,play --screenshot shot.bmp
```

### Settings version 16

Version 16 writes 78 bytes. E15 (absolute byte 53) is the presence marker 16,
covered by the existing checksum at 54–57. F0–F15 occupy 58–73; 74–77
hold a little-endian FNV-1a checksum of only those 16 bytes. F0 bit 0 is
`status_bar_compact` (false), bit 1 is `standby_enabled` (false), and bits
2–3 are `standby_power_off_option` (0: 30 minutes, 1: 2 hours, default,
2: 8 hours). F1 bits 0–2 are `long_press_action` (default 0, current behaviour).
Remaining bits and F2–F15 are free and written zero. Older versions migrate
with F defaults. Missing, corrupt or invalid F data uses F defaults while
preserving validated base settings. The store also tries the 58-byte v15 size.

Downgrade to v15 rejects version 16 even when reading only its 58-byte prefix;
it also rejects nonzero E15. The old store falls back to defaults, and saving
with old firmware replaces the file, losing v16 settings. Preserve a copy
before downgrade. No older firmware interprets F as existing settings.

## Instant-on standby

Settings → Power offers Standby when switched off (Off by default) and Power off after
(30 min, 2 h by default, or 8 h). The v16 settings fields are `standby_enabled` and
`standby_power_off_option`. With standby enabled, a short Power press or auto-off enters
standby. Screen timeout still only blanks the display; a long Power press and the sleep
timer still request shutdown. Standby expires at its own deadline, independently of
activity and USB power. Existing low-battery protection requests shutdown below 3450 mV
for 2 seconds when on battery.

Standby releases the track output through the existing pause-standby path, retaining the
queue and saved position. It powers down the DACs and core 1, switches Bluetooth off,
turns the panel and backlight off, and selects the existing 24 MHz crystal clock path.
The main loop rests in WFI between 20 ms passes. SysTick remains enabled: the existing
interrupt path feeds the watchdog, advances uptime and samples the Power key and battery.
GPIO2.5 has no configured wake interrupt in this base. Interrupt-only Power/VBUS wake,
clock gating beyond the existing crystal path, and a paused watchdog require hardware
validation before replacing this polling fallback. Standby remains Off by default.
Power wakes the display; playback stays paused at the saved position until Play.

The debug report adds `standby.entries`, `standby.wakes`, `standby.entry_ms`,
`standby.wake_ms`, `standby.entry_mv`, `standby.wake_mv` and `standby.wake_latency_ms`.
The voltage fields are unknown before a known reading. Latency runs from processing the
wake transition to presenting the first frame and requesting the backlight; the existing
backlight ramp adds 200 ms. Entry and wake timestamps are uptime milliseconds and wrap
at 2^32; subtract modulo 2^32 for a drain window.

Run `python3 tools/echo_debug.py run tools/debug-scripts/instant-standby.txt` only with
owner approval for debug-loop access. The script enables standby, records RTC reads,
measures a short idle window, rests for an hour, wakes with Power and reconnects.
Read the fields afterwards with `python3 tools/echo_debug.py report`.
Use an entry/wake voltage pair only when the entry and wake counts match.
For battery drain, unplug USB during the soak and reconnect after the wake; a powered
USB cable can charge the battery. The debug loop's reconnect timeout can leave its report
on disk until the next connection. Compare the entry/wake voltages and elapsed time,
confirm no watchdog reset, compare RTC and uptime intervals, and measure visible Power
to UI latency on the player. Check panel/backlight, both output rails, core 1 and Bluetooth
are off; test physical Power and VBUS wake separately. Check queue and exact paused
position before Play, then both outputs after Play, plus the three shutdown deadlines and
low-battery cutoff. Emulator and host checks do not establish physical wake or drain.
