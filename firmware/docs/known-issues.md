# Gnarlyr known issues

Gnarlyr 1.0.0 is not released. The developer firmware runs on the owner's full-size Echo; the recorded checks below include Gnarlyr and its earlier foundation. It comes with no warranty: use it at your own risk. Read this before you install a build, and keep a way back ([`device-recovery.md`](device-recovery.md)).

## What has been checked

- **Software checks:** host tests, the simulator and the ARM emulator cover boot and updates, memory bounds, queue/session persistence, mixtapes, controls, Listening and lyrics. They do not reproduce analog output, Bluetooth radio operation or full USB host traffic.
- **On the owner's Echo (full size, 4 GB):** the owner confirmed display, menus, buttons, music playback, volume, internal/microSD USB storage and quiet audio on the earlier Podium 4.5.5-based build. The rebuilt Podium 4.5.9 foundation was then confirmed for file-copy installation, USB storage, playback, quiet audio and portrait mode. Later developer builds exercised reports, scripts, automatic update/restart/reconnect and frame/load measurements. The developer build `33757eb` and the demand-loaded-module build `6d027ed` were installed through the file-copy loop and returned on USB with their build reports confirmed. The unit was also restored to FiiO 2.0.0 and back through maskrom; the recovery steps in [`device-install.md`](device-install.md) and [`device-recovery.md`](device-recovery.md) are the ones used.
- **Gnarlyr on the owner's Echo:** file-copy installation and automatic restart/reconnect report the expected build. Home, Now Playing, Up Next, Mixtapes, Listening, Controls and the missing-lyrics view were checked on the display at medium text size in landscape. A named mixtape was saved before an update, survived the restart and loaded into playback and Up Next afterward. A 10-second WAV playback window had zero ring or output underruns.
- **Canonical Gnarlyr identity:** the owner's full-size ECHO completed both file-copy update hops to developer build `7075642`, with matching copy readbacks, automatic restart/reconnect and live build reports. The original data folder and an independent backup were preserved; copied settings and saved-mixtape files match their originals. Hardware captures show the saved queue order and paused position restored after testing. A ten-second active 24-bit, 44.1 kHz FLAC window decoded 107 blocks with zero ring or output underruns. This does not establish listening quality on both outputs.
- **Everything else** that Podium's and EchoPod's authors tested on their own players has not been repeated by this project. Where this document mentions such a result, it says whose it is.

## Safety

- **Volume:** the top volume is the DAC's full level, and sensitive earphones can be very loud. Turn the volume down before you put them in.
- **Battery:** install only with the battery charged. The code switches the player off when the battery runs low and refuses to start on an empty one ("Battery low: Charge the player to turn it on"); neither has been seen on a player with Gnarlyr.
- **Bricking:** a broken image can leave the player unable to start. The updater writes one firmware slot at a time and reads every chunk back, but a power cut during an install is still a risk. The only recovery for a player that doesn't start is the chip's maskrom mode ([`device-recovery.md`](device-recovery.md)), which needs a patched tool and care. Prepare it before the first install.

## Not proven on a player

- **Battery scheduling and runtime.** Screen-off scheduling, input-ring read batching, longer decoder sleep intervals, the minute discharge recorder, the 5 ms tick on a resting screen and screen-off standby on the 24 MHz crystal with the PLL powered down have software coverage. How long the PLL takes to lock again when a key wakes the player from crystal standby has not been timed on a player. Runtime, current, SD-card idle behavior, Bluetooth radio drain and audio margin at the changed scheduling cadence need player measurements. No new hours-of-playback claim is made. Follow [the parent measurement procedure](battery-measurements.md), including validation that supply-off actually removes USB power.

- **12/24-hour clock choice.** Software checks cover the setting, midnight/noon, local-time rollover and layouts. Display and persistence on the player remain to be checked.

These checks remain incomplete on the owner's unit; the observed developer flows above do not replace them.

- **The USB screens.** Native checks draw every storage, warning and DAC state, the overview and the details pages, in all five themes, both orientations and three text sizes, and check that the graph, the cassette and the meter redraw only their own areas; ARM scenarios cover registration, session return, damaged copies, the connect prompt, the graph's drawing cost and paging with Back. The look, the rates against a real copy, free space on the owner's volumes, copy speeds while the graph redraws and the DAC figures still need a player check.
- **Leaving Connect to computer from the player.** ARM scenarios cover a quiet disconnect ending like an eject, a disconnect that waits for the computer's writes and a forced one ending like an unplug, with host traffic simulated. What macOS, Windows and Linux show after the drives disappear, and whether a 3-second quiet period covers macOS's write-back of a large copy, are unchecked; check files copied just before a disconnect.
- **The plugged-in modes.** Native checks cover the chooser's rows, cursor, check mark, low-battery line, countdown and hold-to-save, and draw the prompt, USB mode and When plugged in in all five themes, both orientations and three text sizes; ARM scenarios cover the prompt's Charge & play, Run from USB power until unplugging, a saved USB audio (DAC) answer and Menu on the charge screen. None of it has run on the player, and Run from USB power still needs a charger and load check on the player.

It has not formatted a physical card on the player. Card-specific allocation-unit reporting, write latency, power loss, charging and reinsertion need device checks. Cards smaller than 64 MiB and capacities beyond the block driver's 32-bit sector count are refused.
- **USB compatibility beyond the owner's Mac.** Storage enumeration and automatic reconnect with the overlay have worked on that Mac; broader host compatibility and sustained transfer checks remain.
- **USB DAC mode:** UAC2, explicit feedback, all rates/widths and HID remote controls still need physical host and player checks. Software tests cannot establish physical USB timing margin or analog output.
- **Headphone profiles.** Native tests cover file publication, restart loading, trim/balance in music and USB PCM, ceilings and safe switching; physical output level, clicks, both jacks and cold power-cycle persistence still need the owner's player. Names use presets in the editor, with UTF-8 names supported by the file format. - **Bluetooth reconnect on Play.** Host tests and emulator scenarios with a simulated module cover the wait for the last headphones after the 5-minute switch-off and at power-on, the 10 s limit, wired headphones taking the sound, the return after a loss without resuming, and restarting a stream a sink pauses as it starts. None of this has been checked on a player with real headphones, a speaker or a car stereo. Whether a JBL-type speaker's silence after connecting is the module's `CP` report (which the restart answers) has not been confirmed. How long real headphones take to reconnect after the module wakes decides whether 10 s is enough. The Bluetooth UART is now drained into a ring by the 1 ms SysTick, so Bluetooth on no longer holds the main loop at 1 ms passes or core 0 at 200 MHz; the emulator shows no overruns or underruns, but a real module's bursts (scan results, long device names) have not been checked against the 256-byte ring on a player.
- **Remaining developer-loop and power checks.** File-copy installs, saved reports, scripts, restart/reconnect and frame/load measurements have run on the player. Recorded 15-minute playback and idle battery soaks completed and returned reports; the cable bit remained 1 with the supply override active. These short voltage observations do not establish battery runtime or complete isolation from USB power. Low-battery abort/report behavior, charging from a low battery, charger-pin interpretation and profiler attribution to individual functions still need hardware validation. - **The 4.4 mm output.**
- **Smart lists.** Covered by host tests and simulator captures only. How long the first library check and each list take with the owner's library and listening history, and the new 1.5 MB `track_keys.bin` being reserved on an existing card, still need a player check.
- **Pause standby and the DAC power-down order.** After 30 s paused the output and core 1 power down, and Play reopens the track at the saved position; the emulator covers the position, the fades and the timing. The datasheet power-down order (PDN_HP, then PDN_DONE, then the serial port), the resume time, the absence of clicks on both outputs and the battery saved have not been checked on the player.

## Known trade-offs

- **A plain track that crashes the scan takes two stops to find.** Plain tracks are marked in batches of 8 to keep the scan fast; the start after a stop marks that batch track by track, and the start after that skips the track. CUE sheets, `.m4b` files, playlists and cover-pass files are skipped at the first restart. The scan-stop protection has run only in the emulator.
- **echo-sync leaves the scan record alone.** If a scan on the player stopped and the card is then rebuilt with echo-sync, the player still rescans once at the next start.
- **A failed install followed by music.** If an install fails partway through slot 1 and music is then played, the next plug-in shows "Restart to finish the update" and does not serve USB. Whether the restart then starts slot 2 depends on the boot ROM falling back for an invalid slot 1, which has not been tried on the player.
- **A trial build that is never confirmed** stays unconfirmed: slot 2 keeps the previous build until a USB session with the new one ends with an eject. A player used without the computer is not rolled back, because starts that run 20 s are not counted.
- **A trial update dated before slot 2's build** may never run if the boot ROM prefers the newer slot; the backup build then counts the starts and rolls the update back.
- **Audio module damaged in both slots.** Lower-rate conversion and M4A demuxing require this module. If both copies fail validation, those tracks are refused; native-rate FLAC, MP3 and WAV remain available. A healthy copy in either slot is enough.
- **Extension module damaged in both slots.** The updater's slot writing lives in the extension module, so with no intact copy an update copied over USB is refused ("Update failed") and recovery is through maskrom.
- **USB code damaged in both slots.** The USB overlay is stored in both firmware slots. If it were damaged in both while the main code stayed intact, USB storage would be unavailable ("USB missing: reinstall update") and recovery would be through maskrom only.
- **Language packs are bounded to 16 KB.** The glyph cache keeps 64 packed glyphs; built-in ASCII bypasses it. Additional script coverage still depends on the selected fonts.

- **Text right after an install.** Until the restart, every screen uses the built-in 16 px font, which is ASCII only: accented and Cyrillic letters show as `?`.

## Installing

The canonical `GNARLYR` identity has been installed through the two-hop file-copy transition on the owner's full-size ECHO. The installation and bounded persistence/playback checks are recorded above; the remaining device checks still apply.

- **File-copy updates between this project's developer builds are proven** ([`device-install.md`](device-install.md)). The debug loop has checked the copied image, ejected storage, installed the update and confirmed the build after automatic restart/reconnect. Maskrom recovery is also proven on the owner's unit.
- **Installing by file copy from FiiO's firmware is not verified.** FiiO's updater only reads files named `ECHOVnnn.IMG`, so `GNARLYR.IMG` would have to be renamed. Whether FiiO's 2.0.0 accepts it is not known. Podium's documentation reports that FiiO's updater installs Podium from a file copy.
- **The Echo Mini isn't supported.** The updater refuses its firmware.
- **Other custom firmware can't be installed from Gnarlyr.** Its updater takes only its own images and FiiO's Echo image; it refuses Podium and EchoPod images. To switch, go back to FiiO's firmware first.
- **Going back to FiiO's firmware through the updater** writes both slots. Keep a maskrom path ready ([`device-recovery.md`](device-recovery.md)).

## Portrait mode

- **The frame time overlay stays a landscape drawing.** In portrait the overlay (developer build, Settings → About → Frame time) is off screen.
- **Small text shows 13 rows in portrait**, not the 17 that fit, because the browse and Up Next row caches hold 13.

## Audiobook chapters (.m4b)

- Chapters are checked in tests on synthetic files and one ffmpeg-made `.m4b`, not with Libation or Audible files. Gapless continuation from one chapter into the next is checked as one decoder stream, not by ear.
- **Only `.m4b` files are split.** Chapters in `.m4a` and other files are ignored.
- **M4B books appear on Audiobooks wherever they are stored.** Named audiobook roots keep their author/title hierarchy; books elsewhere appear directly on the shelf. Chaptered files appear once and whole-file books retain independent bookmarks. Rescan or rerun echo-sync to update an existing library. Selecting a folder containing book chapters resumes that book at any depth; holding ▶ opens the chapters. Separate chapter files and chaptered `.m4b` files use the same action. Native button journeys cover nested paths; this flow still needs a check on the player.
- **A chaptered book remembers one place.** Choosing another chapter moves the bookmark to it.
- **At most 255 chapters** are read; a longer chapter list ends with the 255th chapter running to the file's end. UTF-16 chapter titles of a text track show as "Chapter n". The desktop indexer now preserves the same chapter layout as the device scanner; the synthetic and ffmpeg-derived fixture libraries match in native comparisons.
- **Titles are cut at 63 bytes.**

## CUE sheets

- Gapless continuation between CUE tracks of one file is checked in tests (one decoder stream, no reopen), not by ear.
- **Quotes inside a title** can't be escaped in a sheet, so a `\"` ends the title there. The player cuts texts from a sheet at 255 bytes; echo-sync doesn't.
- **Two sheets for the same audio file** both make tracks, so the album appears twice. Sheets in a folder too big for the library scan's listing memory (thousands of entries in one folder) are matched with the audio files of the same batch only.
- **A playlist entry that names a CUE image** (the FLAC) resolves to one of its tracks, not necessarily the first.
- **Text from sheets isn't recomposed to NFC on the player**, as with tags; echo-sync does recompose it. Sheets in decomposed form make the player's and the computer's libraries differ in those strings only.

## USB

- **Eject both drives, or hold Back on the player, before you unplug.** Unplugging first can lose the last changes, and the player warns you ("Unplugged too soon"). Holding Back on until the player disconnects while the computer is still writing loses the same changes ("Disconnected too soon").
- **Some file managers only unmount.** The player finishes a USB session when the computer ejects the drive. Finder and `diskutil eject` send that; a file manager that only unmounts leaves the player waiting. Eject in Finder, run `diskutil eject` on the disk, or hold Back on the player.
- **macOS leaves `._` files** beside everything it copies. The library scan ignores them, but they take space. `dot_clean` on the drive removes them.
- **USB DAC mode limits:** high-speed UAC2 offers 16/24/32-bit stereo through 192 kHz, with a 5 ms device priming target; full-speed UAC1 retains 16/24-bit 44.1/48 kHz and a 20 ms target. The host adds its own buffers. The 44.1 kHz clock family uses documented inherited fractional settings rather than established exact nominal clocks. No physical host, feedback, HID or 192 kHz load acceptance has been completed. Hosts without UAC2 need a full-speed connection for fallback. The session uses continuous polling; hardware core 0 load remains unmeasured.
- **The USB product IDs are test IDs** (`1209:0001` for storage, `1209:0002` for DAC mode, from pid.codes). An assigned ID is still to be requested.
- **Reports in Podium's documentation, not repeated here:** the first connection to a new Windows computer can fail with "Device Descriptor Request Failed" and works on the second try; a computer twice reported the card's exFAT volume as not cleanly closed, with nothing lost; on Windows 11 copying ran at about 3.7 MB/s to the SD card and 5 MB/s to internal storage; USB DAC mode played from Windows 11 and an Android phone.

## Music and library

- **Characters:** song, artist and album names show Latin letters with accents and Cyrillic. Chinese, Japanese and Korean names show as `?`; glyph packs for them are planned. Emoji and other scripts (Arabic, Hebrew, Thai, Greek…) show as `?` too.
- **Paused-output diagnostics:** installed build `7075642` can count expected I2S starvation after a muted DMA pause. The source correction clears these flags without counting them, retains genuine faults and clears stale flags before start/resume; ARM regressions cover it. The correction still needs a player check. The total is not a count of audible dropouts.
- **Formats:** FLAC, MP3, WAV, AAC-LC and ALAC (`.m4a`, `.m4b`) accept 8, 11.025, 12, 16, 22.05, 24, 32, 44.1, 48, 88.2, 96, 176.4 and 192 kHz. Rates below 32 kHz are converted to 32, 44.1 or 48 kHz; the others use their original rate. The 32 kHz output clock has host and emulator checks only; whether the DACs play it cleanly, and how a change between 32 kHz and the 44.1 or 48 kHz clocks sounds, still need a player check. Converted tracks have no extra output frames. Queued files at the same decoded rate retain interpolation history, as do adjacent chapters. Different input rates drain and restart the filter. Seamless transitions between converted files still need listening checks. Ogg Vorbis playback is connected in source and covered by native/reference and two-core ARM tests. It accepts mono/stereo setup within the 64 KiB decoder workspace and a 32 KiB compressed-packet limit; larger setups are refused. Independent Xiph, aoTuV and ffmpeg-native encoder output, including 192 kHz and 500 kbit/s, matches reference PCM in native tests. Chained files play only the first link; interleaved other serials are ignored when Vorbis is first. The normal core-1 clock is 100 MHz (two million cycles per 20 ms); Vorbis above 96 kHz requests 200 MHz (four million). The previous blanket 200 MHz budget was incorrect. Emulated q10 stereo costs about 0.81/1.34/2.31 million instructions per 20 ms at 48/96/192 kHz; actual cycle cost and physical playback remain unmeasured, especially at 192 kHz. Ogg Opus (`.opus`, mono or stereo, channel mapping family 0) is connected the same way: header gain, pre-skip and end trimming, nonzero start granules and seeking with 80 ms pre-roll have native tests against an independent libopus decode, and the two-core ARM emulator plays, seeks and switches between the Vorbis and Opus programs. Opus has not been heard on a player; its real-time margin on core 1 is unmeasured (about 0.83 to 0.99 million emulated instructions per 20 ms of stereo at 64–256 kbit/s against its normal 100 MHz / two-million-cycle budget, against 0.28 million for Vorbis and 0.54 million for AAC). Multichannel Opus (mapping families 1 and 255) and packets above 32 KiB are refused. Opus `R128_TRACK_GAIN` and `R128_ALBUM_GAIN` tags are read with a +5 dB reference conversion; valid `REPLAYGAIN_*_GAIN` comments take precedence. Fixture and numeric tests cover this mapping; normalized Opus playback still needs listening checks on the player. The simulator plays Vorbis and Opus through native builds of the firmware decoders. APE is connected through a separate core-1 program with bit-exact native and ARM comparisons and sample-precise seeks. It accepts Fast through 192 kHz, Normal through 192 kHz mono or 96 kHz stereo, and High through 96 kHz mono or 48 kHz stereo; Fast stereo above 96 kHz and Normal stereo above 48 kHz request 200 MHz, keeping at least a fifth of the ideal instruction budget in reserve. Extra High/Insane, Normal stereo above 96 kHz and High stereo above 48 kHz are refused. High-rate physical throughput, gapless listening and playback on both outputs remain untested. WMA Standard v1/v2 is connected through a separate core-1 program with ASF tags, covers and timestamp-guided seeking. Native and ARM fixtures match ffmpeg within 12 LSB16 for low-rate mono and 2 LSB16 for stereo; queued fixtures add no engine gap. WMA Pro/Lossless/Voice and encrypted streams are refused. WMA files without encoder padding information keep their encoded padding. WMA physical playback and real-time margin remain untested. The other formats FiiO lists appear in the library but don't play; the player says so.
- **AIFF:** mono/stereo 16/24-bit AIFF and AIFF-C `NONE`/`sowt` use the WAV path, including seeking and queue transitions. Generated native tests cover standard 8–192 kHz rates, byte order, SSND offsets, tags and APIC art. Compressed AIFF-C and float samples are refused. Physical playback remains unchecked.
- **DSD:** DSF and uncompressed DFF have a dedicated core-1 PCM converter. Mono/stereo DSD64 and DSD128 and mono DSD256 pass the instruction screen; stereo DSD256, DST and multichannel files are refused. Output is 88.2 kHz PCM, with no DoP. The loader starts core 1 at 100 MHz. All accepted DSD except mono DSD64 requests 200 MHz during decode, with at least 20% ideal instruction reserve; physical real-time playback remains unverified. Native reference and ARM tests cover decoding, seeking, endpoints, queued DSF/DFF transitions, ID3/APIC and DIIN fallback. Separate files pad their own filter edges. [Filter, level and limits](dsd.md).
- **Gapless MP3** needs the LAME tag that LAME and ffmpeg write. MP3s without one keep a short gap between tracks. End padding is trimmed after a seek or part-way resume too. Seek positions remain approximate because they use the Xing table or a proportional byte offset.
- **M4A:** HE-AAC (AAC with SBR or PS) and xHE-AAC are refused with "Only AAC-LC and ALAC M4A play", because the decoder has no SBR; the message also shows for a damaged M4A. Only mono and stereo play. Priming trim uses a valid `iTunSMPB` tag or a single unity-rate edit list (`elst`, version 0 or 1) for the sound track. Files with neither retain their priming silence. Empty, multiple or non-unit-rate edits are not applied; timing tables longer than 64 runs are refused. Files over 4 GB and 64-bit box sizes are refused.
- **Building the library takes time,** on the first start and after music changes over USB. The library comes first: you can browse and play as soon as it is built, and album covers follow while the player is idle and not playing (a key press, playback or a USB cable pauses them; they resume where they stopped). Later rescans keep the covers whose art didn't change, and Settings → Rescan library says "Library is up to date" when nothing changed. In the ARM emulator, on a generated card of 4,003 tracks in 349 albums (FLAC, MP3 and M4A with full tags, 24 CUE albums, 16 chaptered books, 303 covers of 500–1,500 px, median 183 KB, 25 % progressive): the library is browsable 29.6 s after the scan starts, the covers are done 135.8 s after it (103 s of background cover work, 314 ms per cover), and a requested rescan that finds nothing changed answers 1.5 s after the key. These are emulated times: one instruction per cycle at 200 MHz, the emulator's eMMC timings (250 µs per read command plus 25 µs per further sector, 900 µs per write command plus 70 µs per sector), a FAT32 internal volume with 32 KiB clusters. The player runs slower than one instruction per cycle, so expect longer times on the player; none of this has been timed on a player yet. A 20,000-track card hasn't been timed: in the emulator, on a 433 GB FAT32 volume, the first scan didn't start. `tools/echo_sync.py` can build the library and covers on a computer instead.
- **Library size:** the library file is 4 MB and the format holds 65,535 tracks. The builder is tested on a computer with 20,000 tracks. A larger library may stop with an error when the file is full. Podium's documentation reports 6,558 tracks and over 1,600 albums on a player.
- **Album art:** the covers file has room for 2,673 albums. Past that, the remaining albums show without art.
- **Cover Flow** orders albums by album artist, then year, not by album title like the Albums list.
- **Spoken-word classification:** top-level `Audiobooks`, `Audiobook`, `Podcasts` and `Podcast` folders classify their contents; `.m4b` files elsewhere are audiobooks too. Other files under similarly named nested folders remain music. An author with music too appears under Artists with the music only. Genre tags alone do not classify a file as spoken word. Music search covers the music partition; shelf-wide spoken-word search is not yet available.

## echo-sync

- **Run from the source only** (`python3 tools/echo_sync.py`); there are no packaged downloads. This project has run its tests, not the tool on a real card.
- **FAT32 and exFAT only.** On other file systems the file times may not match the player's, and the player then rescans anyway.
- **Copies that never finished** (a file whose size on the card is larger than what was written) are read as the player sees them; recopy such files from the computer.

## Not there yet

- **Playback speed** (0.5×–3×) is checked by native tests and the emulator only. Listening quality on both outputs, core 0 load on the player (3× on 44.1 kHz FLAC used 56.3 % of core 0 in the emulator, which does not model the player's memory waits or core 1's throughput) and the saved speed across power cycles still need player checks. Recordings above 48 kHz play at normal speed. ReplayGain reads prepared track/album metadata from a rescanned or rebuilt library; physical listening and headroom checks remain open.
- **Timed sidecar lyrics are implemented.** The missing-sidecar notice was checked on the player; timing and text from a real sidecar still need a device check.
- **The equalizer** leaves music above 96 kHz (176.4 and 192 kHz) unchanged, isn't applied in USB DAC mode or in the simulator, and a change is heard after the audio already buffered (about 0.3 s at 44.1 kHz).
- **Bluetooth and the jacks:** while music goes to Bluetooth the player can't read the headphone jack: pause, plug wired headphones in and press Play to switch.
- **Buttons on wired headphones** (3.5 mm) follow the readings of FiiO's firmware. Podium's author reports that on Apple EarPods the middle button works but + and − don't: Apple's remote signals them through a chip the player can't talk to ([`hardware.md`](hardware.md)). If buttons do nothing, Settings → About → Headset shows what the player reads while each button is pressed. The 4.4 mm jack has no headset buttons.
- **Settings → Output can't switch sound between the jacks:** both are driven by the same DACs, so it only picks the volume table (see [`user-guide.md`](user-guide.md)).

- **Bluetooth absolute volume and track metadata:** no command or report for absolute volume, volume buttons, or AVRCP title/artist has been established in the available evidence. The stock analysis in `docs/stock-firmware.md` does not supply such a command table. The stock-derived protocol description in `firmware/docs/hardware.md` and `firmware/docs/architecture.md`, and EchoPod branch `echopod/bluetooth-audio` (`platform/device/logic/bt_module.c`), establish `CP`/`CC` pause/play and `CA`/`CB` previous/next. `CV` is version, `CS` discovery, `CQ` link status, `CL`/`CH` connection and `CT` disconnect; recognising `CK` framing does not establish a volume meaning. `CY0 00` and `CY0 1E` stop and start streaming; they are not volume values. Gnarlyr therefore sends no speculative volume or metadata commands. Headphone volume remains independent of player volume; adjust both if playback is quiet. This is a limit of the recovered protocol evidence, not proof that the module hardware lacks AVRCP support.
- **Bluetooth play while paused:** after the existing three-second stream/link echo guard, a headset play report resumes a player-initiated pause as well as a headset pause, including pause standby. Lock and display sleep do not gate Bluetooth processing. Reports during the guard are ignored because the module also emits them in response to stream changes. Verify this distinction with the owner's headphones before release.


## USB DAC host acceptance

These checks require the parent’s separately approved player window. Keep the tested build tag, inspect USB enumeration at each speed and exercise both headphone outputs; do not infer physical acceptance from emulator PCM tests.

- **macOS:** use Audio MIDI Setup to select each of the six rates and available 16/24/32-bit formats. Confirm high-speed enumeration, clock RANGE/CUR, stable explicit feedback and restart after rate/width changes. Repeat through a full-speed hub for UAC1. Test ▶, Vol+ hold and Vol− hold in the intended media app.
- **Windows:** use the system UAC2 driver on a supported Windows release, inspect every format in Sound properties, and play through WASAPI exclusive. Check initial enumeration, unplug/replug, suspend/resume and endpoint stalls. Repeat full-speed UAC1 and the three consumer keys.
- **Linux:** inspect `lsusb -v` and `/proc/asound/card*/stream0`, then use ALSA `hw:` output at every rate and each packed PCM depth, bypassing host resampling. Inspect feedback and xrun counters during a long 192 kHz stream. Check consumer key press/release with an input-event tool and the chosen media player; repeat at full speed.
- **Android:** verify USB host/data-adapter support, high-speed enumeration and actual negotiated rate/width in a direct USB audio app. Check 192 kHz, app stop/start, unplug/replug and consumer key handling; system mixers and individual apps may constrain the available formats. Repeat with a full-speed hub where possible.
- **PCM and clocks:** play known stereo PCM test files containing nonzero low bits at all 18 high-speed format combinations. Disable host mixing/DSP, match the file format, set headphone profiles Off and capture I2S digitally to compare words and sample count. Measure LRCK/MCLK, especially the fractional 44.1 kHz family, and correlate feedback with consumed frames. An analog recording cannot prove PCM bit identity. Check startup silence, rate switches, long streaming, zero sink realignments/underruns, core 0 load and both outputs. Then complete the release power-cycle, persisted-state, charging and normal-file-transfer checks.
