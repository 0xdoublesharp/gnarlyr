Build from your checkout.

Get the Gnarlyr source on GitHub, then run these commands on macOS from the root of your checkout. The wrapper builds an image on your computer. Installation is a separate step.

  • Python 3.14 with the packages in firmware/tools/requirements.txt.
  • Build tools: CMake, SDL2, FFmpeg, clang-format and the Arm GNU cross-compiler.
  • Build-output storage: mount a volume at /Volumes/Scratch for generated files. The wrapper links firmware/build to this checkout’s output there, keeping builds separate from source.
Set up the build environment

Create a Python virtual environment on Scratch. Set ECHO_VENV to that folder and ECHO_ARM_BIN to the folder containing arm-none-eabi-gcc. Full prerequisite instructions are in the checkout’s README.md.

Build the release image 

python3 tools/firmware.py setuppython3 tools/firmware.py build --preset release

Record its SHA-256 

shasum -a 256 firmware/build/release/GNARLYR.img

The output is firmware/build/release/GNARLYR.img. SHA-256 is a fingerprint of the file: comparing fingerprints tells you whether the copy is identical.

Keep the build inputs in step.

Fonts, menu text and audio tables are generated from source files. One command refreshes them; another checks that they are current.

  • Regenerate: python3 tools/firmware.py regen --jobs 2 refreshes string headers, the browser language catalogue, fonts, glyph packs, Unicode search tables and audio tables.
  • Check without rewriting: python3 tools/firmware.py regen --check --jobs 2 reports stale generated files.
  • Check memory budgets: python3 tools/firmware.py sizes --jobs 2 builds both release and developer images, prints their memory use and fails if a slot or reserve limit is exceeded.
  • Read existing size reports: python3 tools/firmware.py sizes --existing --jobs 2 skips rebuilding. Rebuild after source changes before using those figures for an update.

The build uses sccache when it is available. Set ECHO_COMPILER_CACHE=0 to turn it off. Full workflow details are in docs/development.md in the checkout.

Repeat developer updates over USB.

Prepare a fixed firmware image, check the upgrade route and back up the player’s saved state before installing it.

Use a clean checkout with the player’s internal drive mounted in Connect to computer mode. Get the owner’s approval to access the player and have the full-size ECHO recovery procedure ready.

Prepare and check the upgrade

python3 tools/firmware.py install-device --dry-run --jobs 2

The dry run reads the installed build, builds and freezes the new image with its matching program files, and simulates that exact upgrade in the ARM emulator. It checks slot order, write readbacks and the resulting boot, then makes a verified backup of persistent state. It stops before copying firmware to the player or ejecting it.

Install the approved candidate

python3 tools/firmware.py install-device --owner-approved --jobs 2

The helper installs the checked candidate, requests a restart and waits for USB to reconnect. It checks that the new report identifies the candidate and contains no recorded faults or output underruns. Each frozen image uses its own program files, so leftovers from an older build are excluded.

Frozen candidates and reports stay on Scratch. Verified persistent-state backups stay under .local/device-backups/user-state/ in the checkout.

Ordinary manual updates use the player’s unplug-and-Power sequence. Automatic restart belongs to the developer workflow.

Language packs over USB

Build a pack in the browser builder, then run python3 tools/echo_debug.py language-install /path/to/es.pack --select with a developer player connected in Connect to computer mode. The helper checks the pack against the installed build, verifies the copied file and selects the language after reconnecting. Use language-select en to return to English.

List installed languages with language-list. Check a pack without installing it with language-inspect /path/to/es.pack. The matching echo_language_* MCP tools expose the same operations. Listing ignores macOS ._ metadata files, and selection resolves the current language’s setting label. Managed installation validates the installed catalogue and same-player music volume, keeping writes limited to language-pack paths. Full usage is in docs/language-packs.md.

Reversible display and audio previews

The settings source previews the highlighted Accent Color, Brightness, Text size, Orientation, Output, ReplayGain or Prevent clipping value while you browse. Play saves the choice; Back, leaving the picker or switching off restores the saved value. Accent Color affects Graphite’s highlights and decorative details.

Button-lock input handling

The key-lock source requires an uninterrupted Play+Power hold. Releasing and pressing either key again before completion resets the timer; after a successful toggle, both keys must be released before another hold can toggle it. This corrects interrupted presses being counted as one continuous hold. Hold, repeat and multiple-click delays are capped at the clock-comparison limit before use.

Audio processing and diagnostics

Audio processing remains available as interface modules change. A separate 8 KiB code bank holds sample-rate conversion and M4A/M4B parsing. Diagnostic counts exclude intentionally muted DMA pauses, so a normal pause is not reported as missing audio. Frame counters stop at their maximum instead of wrapping, and large duration and bitrate calculations use checked arithmetic. The debug event ring keeps its write position separately from its event count, preserving record order when the counter reaches its limit.

Matching CUE parsing on the player and computer

A CUE sheet splits one audio file into track ranges. Both parsers accept track numbers 1–99, require seconds below 60 and frame positions below 75, and reject extra text after a timestamp. Track starts must increase; invalid entries are dropped while valid neighbors remain. FLAC checks also validate ID3 headers, frame numbering and ranges against the declared total sample count.

Check files before decoding.

Audio files contain both sound and instructions for reading it. The readers check those instructions before using them to locate samples, choose a decoder or calculate a position.

  • FLAC framing. Tag headers, metadata order and frame numbering are validated. Frames must match the declared sample rate, bit depth and block limits, and stay inside a known total sample count.
  • M4A and M4B boundaries. Sample tables stay within their boxes. Media clocks, chunk descriptions and AAC/ALAC configuration are checked; truncated records fail instead of supplying incomplete audio.
  • Metadata bounds. MP3 APE footer lengths and WMA field lengths are checked before locating data. Unicode text keeps its original characters during whitespace trimming.
  • CUE track ranges. The player and desktop indexer use the same track-number and timestamp rules, dropping invalid entries while preserving valid neighbors.

See firmware/docs/architecture.md and firmware/docs/library-format.md in your checkout for reader formats and storage boundaries.

USB audio formats and timing.

In DAC mode, the computer sends decoded audio samples over USB. A buffer keeps the flow steady, and feedback tells the computer how quickly the player’s audio clock is consuming them.

ConnectionStereo PCMRates
High speed · UAC216, 24 or 32-bit44.1, 48, 88.2, 96, 176.4 and 192 kHz
Full speed · UAC116 or 24-bit44.1 and 48 kHz

The high-speed path uses asynchronous feedback with a 5 ms device-buffer target; full speed retains a 20 ms target with sample correction. Computer buffering adds delay. These targets are not end-to-end latency measurements.

Play sends a host play/pause command; holding Volume+ or Volume− sends next or previous. The host’s media app decides how to handle them. Headphone trim, balance and volume ceiling apply; EQ and ReplayGain bypass DAC mode.

Software checks cover USB menu drawing while audio polling continues. Physical host and playback acceptance remains separate.

Physical host compatibility, clock accuracy and playback on both outputs remain part of USB audio (DAC) acceptance. See firmware/docs/known-issues.md and firmware/docs/architecture.md in the checkout for the macOS, Windows, Linux and phone checks. A software PCM comparison alone does not establish analog performance.

Playback speed and passage repeat.

The decoder still reads the recording in its original time. A separate processing stage changes how quickly those samples reach the output, keeping chapter positions and bookmarks meaningful.

The integer time-stretching path offers 0.5×–3× without changing pitch for audio up to 48 kHz. It uses part of the existing PCM ring as workspace, with the remaining blocks feeding DMA. Higher-rate recordings retain normal speed and the full ring. The simulator uses the same processing kernel.

A–B repeat marks source-sample positions. Track changes, a USB handover and restart clear the loop. End-of-track or chapter sleep clears the loop so the recording can finish.

Native and emulator checks cover speed, timing and state. Crossfeed applies a delayed stereo blend; Skip silence and Speech boost apply only to spoken-word tracks. USB DAC bypasses these processing effects. Listening quality, processing load and saved settings across physical power cycles still need player checks. See firmware/docs/audio-tempo.md in the source for the algorithm and limits.

ReplayGain and speech files.

ReplayGain uses loudness tags already in your music to balance listening levels. Rescanning prepares those values for playback without rewriting the audio files.

ReplayGain controls and metadata

  • Off, Track and Album. Off is the default. Track uses each song’s gain; Album retains the tagged level relationships within an album. Missing preferred gain falls back to the other kind; untagged or unreadable gain data uses the normal level.
  • Peak-aware normalization. Prevent clipping is on by default. It uses peak tags to cap gain; without peaks it retains attenuation and caps boosts at unity. Turning it off allows the full tagged gain. EQ keeps its separate headroom policy.
  • Saved controls and continuous playback. Mode and clipping choices are persistent. Changes affect newly buffered audio without reopening the current track or restarting DMA, and each current/queued track carries its own gain.
  • Checked library data. Rescanning or desktop indexing prepares gain records without rewriting music files or changing the base library fingerprint used by queues and labels. Peak values round conservatively; removed tags clear stale gain data, and invalid caches do not supply unchecked amplification.

Preparing speech recordings

Use 32, 44.1 or 48 kHz recordings for listening. Convert files below 32 kHz to 44.1 or 48 kHz on your computer before copying them. For M4A or M4B, use AAC-LC or Apple Lossless audio.

See firmware/docs/replay-gain.md in your checkout for tag formats, gain limits and library storage.

Additional decoder paths

The integrated source adds mono/stereo 16/24-bit AIFF and uncompressed AIFF-C through the PCM path, plus DSF/DFF conversion to 88.2 kHz PCM. DSD64/128 accept mono or stereo; DSD256 accepts mono. Stereo DSD256, multichannel DSD and DST are refused. These paths have software coverage; physical playback remains unchecked, so the listening guide keeps its established format recommendations.

FormatIntegrated decoder limits
APE16/24-bit mono or stereo. Fast: up to 192 kHz. Normal: up to 192 kHz mono or 96 kHz stereo. High: up to 96 kHz mono or 48 kHz stereo. Extra High and Insane are refused.
WMA StandardVersion 1/2, mono or stereo at 8–48 kHz. Pro, Lossless, Voice and encrypted WMA are refused. Missing encoder-padding information can leave a gap.

These decoders have native/reference and ARM software checks. Physical playback and real-time margin on the ECHO remain unchecked. See firmware/docs/ape.md and firmware/docs/wma.md for details.

See firmware/docs/dsd.md for converter limits and the Hardware guide for cores, DMA and memory reuse.

Set the player’s time.

The companion can leave your Mac’s time on the drive before ejecting it. Gnarlyr reads that time when the USB session ends.

With a developer player connected in Connect to computer mode, run python3 tools/echo_debug.py set-time. Home → Clock then shows the time and date; Play opens Calendar. Settings → Date & time also sets the clock directly on the player. Settings → Clock format chooses 12-hour or 24-hour time. After a restart, Gnarlyr restores local time from the clock chip and saved UTC offset. A later Mac sync replaces the time and offset. Listening exports include UTC timestamps for plays made while the time is set.

How USB hands storage back to the player.

Eject completes host writes and returns storage to the player, allowing Gnarlyr to inspect the image and start installation.

  • Eject is the handover. The computer owns file access during a storage session. Eject every drive present at connection to return that access and start the update check.
  • The cable can stay connected while it writes. Ending the storage session leaves cable power connected. Wait for “Update installed” before unplugging.
  • The new USB code starts with the new firmware. The running firmware, its USB module and its updater must come from the same image. Restarting after installation ensures the running firmware and its USB module match.
  • Connection handling follows cable power. Gnarlyr keeps USB power control in sync with the cable state. The stack can retry at full speed if its first high-speed connection does not become usable.

For everyday music copying, eject every drive before unplugging too. Gnarlyr then checks whether the music changed and rescans when needed.

The cable-connected mode chooser is opened from Home, Settings or Menu on the charging screen. Eject storage volumes before switching back to Charge & play; choosing Connect to computer again re-enumerates the drives without a physical unplug. The charging lifecycle gates callbacks while the interface module is inactive.

Give the hardware less repeated work.

Gnarlyr uses dedicated transfers, reusable memory and workload-based scheduling to leave more processor time available.

  • Panel DMA. Changed windows of at least 256 pixels use DMA when aligned. Core 0 sleeps during the transfer; small windows and timed-out transfers use the CPU. The panel bus still sets the pixel rate. Player measurements showed lower CPU activity during screen slides with unchanged frame times.
  • Storage bursts. The compressed-input ring refills in larger bursts with the screen dark, leaving gaps between reads. A second FAT-cache window is borrowed during the music-change check, then returned before playback or a full rebuild.
  • Screen-off scheduling. Core 0 chooses a coast divider from the playback workload. The LCD controller clock is gated when the panel sleeps, unused boot clocks stay gated and an unconnected Bluetooth radio switches off after 30 seconds.
  • USB reconnects. Each fresh connection tries high speed before a timed full-speed fallback. Keeping the core clock undivided while USB is powered avoids changing the controller’s timing during enumeration. The FIFO allocation fits the player’s 308-word USB memory.

Battery runtime, analog performance and sustained USB-audio acceptance require separate player checks. Emulator instruction counts and USB link rates do not establish those results.

Try a version before replacing the backup.

Trial updates leave a known-good firmware copy on the player. The new version becomes the backup only after it starts and completes a USB session in which the computer wrote to internal storage.

  1. Install the candidate. The updater validates the image, writes slot 1 and reads it back. Slot 2 retains the previous firmware.
  2. Start and confirm. Restart into the candidate, reconnect over USB, copy a small file to internal storage and eject every drive. The player copies the confirmed build into slot 2. A session without a successful write, such as one where the drives mounted read-only, leaves the trial running. echo_debug.py commands write a file before they eject, so they confirm too.
  3. Recover a failed trial. A trial that starts without its language pack or without either copy of its extension module restarts at once and restores the backup. Otherwise three failed start or USB attempts trigger restoration. Starts that run for 20 seconds do not count as failures. Holding Power for 10 seconds restarts a stuck trial.

The updater already installed controls the first upgrade into this scheme; an older updater can still write both slots. A build that fails before the trial check runs, or that cannot read internal storage, still needs maskrom. Use the matching firmware/docs/device-install.md and recovery guide when preparing an image.

Migrate an older firmware identity.

An updater checks an image’s internal identity as well as its filename. A matching transition image starts Gnarlyr from an older custom build while you preserve the player’s data.

  1. Identify the installed build. Use its matching identity.json for the update filename, image brand and data-folder name.
  2. Back up the data on each volume. Keep the complete existing data folder and prepare its copy at /.gnarlyr. Preserve settings, EQ choices, queues, mixtapes, labels, favorites, bookmarks and listening records.
  3. Prepare the matching transition image. Its transport header uses the installed updater’s identity; its code and modules match the ordinary Gnarlyr image. Validate both update steps in the emulator before installation.
  4. Install in order. Install the transition image first, then the ordinary GNARLYR.img. Use the matching host tools and debug folder for each stage.
  5. Check the preserved state. Verify your settings, saved mixes, queue, bookmarks, playback and normal USB transfers before retiring the previous data folder.

Gnarlyr uses GNARLYR, the data folder /.gnarlyr and the CUE playlist directive #GNARLYR-START:. Ordinary music files keep their contents.

Keep the original backup and exact-model recovery files throughout the transition. Renaming an image alone cannot change the identity inside it.

Build the ECHO recovery tool.

The recovery tool talks to the chip before the player software starts. Build the patched version for the full-size ECHO from your Gnarlyr checkout on macOS.

Restore the original firmware.

The chip’s built-in recovery mode can reinstall stock firmware when the player cannot start normally.

Keep the full-size ECHO’s official ECHOV200.IMG and the exact-model recovery instructions from your checkout. The official V2.0 image is 39,845,892 bytes, with SHA-256: 

c6a3b6c86b141c0a428771f8a611fbd44cc12d561acb033a98640b0bf24f8d57

For a player that does not start, follow firmware/docs/device-recovery.md to restore the official image through maskrom, checking each complete slot readback. While Gnarlyr runs, holding Power and Vol+ for about 5 seconds with the cable in the computer, or a MASKROM.REQ file on internal storage, restarts into maskrom without the paperclip.

A running Gnarlyr also recognizes the official ECHO image through its updater. Follow the checkout’s return-to-stock instructions for that image; its on-screen messages and restart sequence differ from an ordinary Gnarlyr update.
