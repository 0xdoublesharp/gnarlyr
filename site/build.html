Build from your checkout.

Run these commands on macOS from the root of your Gnarlyr checkout. The wrapper builds an image on your computer. Installation is a separate step.

  • Python 3.14 with the packages in firmware/tools/requirements.txt.
  • Build tools: CMake, SDL2, FFmpeg, clang-format and the Arm GNU cross-compiler.
  • Build-output storage: mount a volume at /Volumes/Scratch for generated files. The wrapper links firmware/build to this checkout’s output there, keeping builds separate from source.
Set up the build environment

Create a Python virtual environment on Scratch. Set ECHO_VENV to that folder and ECHO_ARM_BIN to the folder containing arm-none-eabi-gcc. Full prerequisite instructions are in the checkout’s README.md.

Build the release image 

python3 tools/firmware.py setuppython3 tools/firmware.py build --preset release

Record its SHA-256 

shasum -a 256 firmware/build/release/GNARLYR.img

The output is firmware/build/release/GNARLYR.img. SHA-256 is a fingerprint of the file: comparing fingerprints tells you whether the copy is identical.

Repeat developer updates over USB.

The macOS helper copies and checks a developer image, ejects the drives, requests a restart and reports the running build after USB reconnects.

Build a developer image with python3 tools/firmware.py build --preset device, then use the matching checkout’s helper:

Install and request a restart 

python3 tools/echo_debug.py install firmware/build/device/GNARLYR.img --restart

Leave USB connected. The helper checks the copied file, requests the developer restart, ejects the drives and waits for the player to return with its running-build report.

Ordinary manual updates use the player’s unplug-and-Power sequence. Automatic restart is a developer-build workflow.

Language packs over USB

Build a pack in the browser builder, then run python3 tools/echo_debug.py language-install /path/to/es.pack --select with a developer player connected in USB storage mode. The helper checks the pack against the installed build, verifies the copied file and selects the language after reconnecting. Use language-select en to return to English.

List installed languages with language-list. Check a pack without installing it with language-inspect /path/to/es.pack. The matching echo_language_* MCP tools expose the same operations. Listing ignores macOS ._ metadata files, and selection resolves the current language’s setting label. Managed installation validates the installed catalogue and same-player music volume, keeping writes limited to language-pack paths. Full usage is in docs/language-packs.md.

Reversible display and audio previews

The settings source previews the highlighted Accent Color, Brightness, Text size, Orientation, Gain, Output, ReplayGain or Prevent clipping value while you browse. Play saves the choice; Back, leaving the picker or switching off restores the saved value. Accent Color affects Graphite’s highlights and decorative details.

Button-lock input handling

The key-lock source requires an uninterrupted Play+Power hold. Releasing and pressing either key again before completion resets the timer; after a successful toggle, both keys must be released before another hold can toggle it. This corrects interrupted presses being counted as one continuous hold.

Audio processing and diagnostics

Audio processing remains available as interface modules change. A separate 8 KiB code bank holds sample-rate conversion and M4A/M4B parsing. Diagnostic counts exclude intentionally muted DMA pauses, so a normal pause is not reported as missing audio.

Vorbis, Opus and the audio pipeline.

An Ogg file wraps compressed audio in packets; a decoder turns them into samples. The Vorbis source connects those pieces to the player, including file opening, duration, seeking and saved-position startup.

  • Checked Ogg input. The packet reader validates pages, CRC, sequence and continuation before forwarding audio. Large comments and embedded artwork stay out of the decoder workspace; the original file stays unchanged.
  • Bounded Vorbis decoding. A separate core-1 program uses pinned Xiph Tremor source, a 64 KiB workspace and a 32 KiB compressed-packet limit. The source handles mono/stereo configuration, refuses oversized setups and keeps duration and seek positions on the same sample timeline.
  • Safe track changes. Setup finishes before audio is released. Refills discard output from older track generations, and late setup results cannot abort a newer track.
  • Continuous conversion across queued files. Files with the same decoded input rate retain converter history and output boundaries. A rate change drains and restarts the filter. Initial current/next publication precedes DAC prefill; clearing an already-empty queue preserves prepared audio and position.
  • Metadata bounds. Unicode tag text is preserved during whitespace trimming. WMA fields, MP4 duration headers and MP3 APE footer lengths are checked before they affect metadata or audio bounds.

Vorbis is connected to the playback source. Listening, processing headroom and converted-file transitions still need checks on the ECHO.

Opus decoder and image bank

Opus is another audio format carried in Ogg files. The Opus development branch adds a fixed-point libopus decoder and a separate core-1 program stored in its own firmware-image bank.

  • Bounded decoding. The component handles SILK, CELT and hybrid packets, mono or stereo, with output rates from 8 to 48 kHz and packets up to 120 ms.
  • Track timing and output level. The core-1 program reads the channel configuration, initial samples to skip and header gain. It publishes long packets in pieces that fit the shared output buffers.
  • Shared packet transport. Vorbis and Opus use the same checked record reader. The image builder reserves the Opus bank separately from glyphs, language packs and other modules.

The decoder and image bank are components for player integration. They do not yet add Opus to the player’s supported formats. Opening files, seeking, resume and real-time playback need the completed integration and ECHO checks. See firmware/docs/opus.md alongside the Opus branch’s code and image configuration.

The host test utility ogg_packet_tool exports checked packets for decoder comparisons. See firmware/docs/ogg-packets.md and firmware/docs/ogg-vorbis.md in the matching audio source checkout.

Loudness and tempo processing in source.

ReplayGain uses stored loudness information to adjust a song’s level. Tempo processing changes pace while preserving pitch. The audio branch connects both to the playback engine; normal speed remains the default.

ReplayGain controls and metadata

  • Off, Track and Album. Off is the default. Track uses each song’s gain; Album retains the tagged level relationships within an album. Missing preferred gain falls back to the other kind; untagged or unreadable gain data uses the normal level.
  • Peak-aware normalization. Prevent clipping is on by default. It uses peak tags to cap gain; without peaks it retains attenuation and caps boosts at unity. Turning it off allows the full tagged gain. EQ keeps its separate headroom policy.
  • Saved controls and continuous playback. Mode and clipping choices are persistent. Changes affect newly buffered audio without reopening the current track or restarting DMA, and each current/queued track carries its own gain.
  • Checked library data. Rescanning or desktop indexing prepares gain records without rewriting music files or changing the base library fingerprint used by queues and labels. Peak values round conservatively; removed tags clear stale gain data, and invalid caches do not supply unchecked amplification.

Pitch-preserving tempo in the device engine

The fixed-memory kernel accepts signed 24-bit stereo samples at 8–48 kHz and integer speeds from 50 to 200 percent. At 100 percent it copies samples unchanged. Caller-owned storage bounds the working memory.

  • Stretch before conversion. The device engine applies track gain and volume, adjusts tempo at the decoded rate, converts lower-rate speech for output, then applies EQ.
  • Positions stay tied to the recording. Seeking and speed changes use the audible source position, preserve pause state and restore the prepared next track with its gain.
  • Continuous chapter and queue boundaries. Same-rate queued files and adjacent chapters keep processing history. Rate changes drain the pending audio before restarting the relevant stage.
  • Fixed working memory. Non-unity tempo reuses part of the audio ring and private processing storage. It accepts supported decoded rates up to 48 kHz; normal-speed rate support is unchanged.

Persistent speed controls and simulator integration are separate work. The engine connection does not yet provide a player speed setting. ReplayGain listening/headroom and tempo quality and throughput require ECHO checks.

Preparing lower-rate speech

The converter handles 8, 11.025, 12, 16, 22.05 and 24 kHz input in source, but hardware reports show dropouts in this playback path. For listening, convert recordings below 32 kHz to 44.1 or 48 kHz on your computer before copying them. Engine and decoder comparisons alone do not establish real-time performance on the player.

See firmware/docs/replay-gain.md and firmware/docs/audio-tempo.md in the audio source checkout.

How USB hands storage back to the player.

Eject completes host writes and returns storage to the player, allowing Gnarlyr to inspect the image and start installation.

  • Eject is the handover. The computer owns file access during a storage session. Eject every drive present at connection to return that access and start the update check.
  • The cable can stay connected while it writes. Ending the storage session leaves cable power connected. Wait for “Update installed” before unplugging.
  • The new USB code starts with the new firmware. USB and updater code load from the image into a shared memory region. Restarting after installation ensures the running firmware and its USB module match.
  • Connection handling follows cable power. Gnarlyr keeps USB power control in sync with the cable state. The stack can retry at full speed if its first high-speed connection does not become usable.

For everyday music copying, eject every drive before unplugging too. Gnarlyr then checks whether the music changed and rescans when needed.

The cable-connected mode chooser is opened from Home, Settings or Menu on the charging screen. Eject storage volumes before switching back to Player; choosing storage again re-enumerates the drives without a physical unplug. The charging lifecycle gates callbacks while the interface module is inactive.

Migrate an older firmware identity.

An updater checks an image’s internal identity as well as its filename. A matching transition image starts Gnarlyr from an older custom build while you preserve the player’s data.

  1. Identify the installed build. Use its matching identity.json for the update filename, image brand and data-folder name.
  2. Back up the data on each volume. Keep the complete existing data folder and prepare its copy at /.gnarlyr. Preserve settings, EQ choices, queues, mixtapes, labels, favorites, bookmarks and listening records.
  3. Prepare the matching transition image. Its transport header uses the installed updater’s identity; its code and modules match the ordinary Gnarlyr image. Follow firmware/docs/identity-transition.md to validate both update steps before installation.
  4. Install in order. Install the transition image first, then the ordinary GNARLYR.img. Use the matching host tools and debug folder for each stage.
  5. Check the preserved state. Verify your settings, saved mixes, queue, bookmarks, playback and normal USB transfers before retiring the previous data folder.

Gnarlyr uses GNARLYR, the data folder /.gnarlyr and the CUE playlist directive #GNARLYR-START:. The transition guide explains how to update older exported CUE playlists while preserving their paths and track positions. Ordinary music files keep their contents.

Keep the original backup and exact-model recovery files throughout the transition. Renaming an image alone cannot change the identity inside it.

Restore the original firmware.

The chip’s built-in recovery mode can reinstall stock firmware when the player cannot start normally.

Keep the full-size ECHO’s official ECHOV200.IMG and the exact-model recovery instructions from your checkout. The official V2.0 image is 39,845,892 bytes, with SHA-256: 

c6a3b6c86b141c0a428771f8a611fbd44cc12d561acb033a98640b0bf24f8d57

For a player that does not start, follow firmware/docs/device-recovery.md to restore the official image through maskrom, checking each complete slot readback.

A running Gnarlyr also recognizes the official ECHO image through its updater. Follow the checkout’s return-to-stock instructions for that image; its on-screen messages and restart sequence differ from an ordinary Gnarlyr update.
