# USB recording feasibility

## Decision

**Feasible with constraints for uncompressed WAV at 48 kHz or 44.1 kHz, 16-bit stereo.** This is an engineering assessment from source, not a demonstrated recording. Admission to implementation requires an exact-player USB/SD timing experiment. Calling the current file writer from the USB packet callback would lose audio: USB reception is polled, and the storage driver can block for hundreds of milliseconds or longer without polling USB.

Start with a fixed maximum duration, an explicitly selected microSD card, preallocated storage, local filesystem ownership, and optional wired monitoring. Do not combine recording with USB mass storage, music decoding, scanning the library, or Bluetooth. FLAC encoding is a separate feasibility gate; this tree contains FLAC decoders, not an encoder.

Source baseline: `a2d1a8b57726fc24a60280aa5843ba2b1c358715` on `main`. This research changed no firmware and ran no device, radio, build, CTest, or emulator operations. The coverage hold was not released during this study.

## Existing receive and output path

The relevant implementation is [USB DAC session](../firmware/platform/device/board/usb_dac_session.c), [DWC2 packet service](../firmware/platform/device/board/usb_port.c), [audio descriptors](../firmware/platform/device/logic/usb_audio.c), [sink](../firmware/platform/device/logic/usb_audio_sink.c), and [board audio](../firmware/platform/device/board/audio.c). The [architecture](../firmware/docs/architecture.md#echo-board-on-the-device) attributes successful Windows/Android DAC playback to Podium; it does not establish reception on the owner's current Gnarlyr image.

The actual path is:

1. `usb_poll` reads receive status and drains endpoint 1 into `UsbPort.out_packet`, a reusable 128-word buffer. `deliver` invokes `receive_stream` synchronously; the pointer is only usable during that callback and must not be retained.
2. The DAC loop calls `usb_poll` four times per pass. Endpoint 1 accepts one isochronous OUT packet per transfer and is rearmed after transfer completion, with frame parity handling for incomplete transfers. This is a polled controller, not an interrupt-driven receive queue or a USB DMA ring.
3. UAC1 offers full-speed adaptive OUT, 1 ms interval, 16-bit or packed 24-bit stereo, at 44,100 or 48,000 Hz. Endpoint hardware is armed for 294 bytes, the largest offered 24-bit packet; the 16-bit descriptor allows 196 bytes (49 stereo frames). At 44.1 kHz, packet frame counts vary; never assume every packet contains 48 frames.
4. `usb_audio_sink_write` converts packed little-endian samples into two 32-bit I2S words per frame in the board-owned `music_ring`. That ring is 28,000 words, 112,000 bytes, or 14,000 stereo frames. DMA channel 5 loops over seven descriptors and sends it to I2S1 and the two DACs.
5. `board_audio_stream_open` shuts down music, selects stream service, and raises core 0 to 200 MHz. During stream mode, `hal_audio_service` and DAC fade waits call `serve_usb` instead of pumping the music `AudioEngine`. The sink bypasses that engine, its source decoder, resampler and EQ.

The monitor sink is unsuitable as the recording source. Its drift controller deliberately drops or repeats a frame per packet when ring fill is outside its target window; it can realign and clear silence ahead. Capture **before** `usb_audio_sink_write`, once per validated USB packet. DAC drift corrections may continue for monitoring without changing the file. Host/device volume is applied at the DAC and need not alter raw recorded PCM; document that the file contains samples delivered by the host, which may already include host mixing or volume processing.

Validate format and `length % 4 == 0`, count every accepted frame, and copy the bytes before the callback returns. Do not silently floor malformed packet lengths as the present monitor sink does. Make capture independent of DAC-open success if recording without monitoring is supported. Rate, alternate-setting and bus-reset changes must end the current file at a frame boundary; never append a different format to one WAV stream.

## Storage ownership and latency

The SD controller and USB controller are separate, and the code provides local FAT16/FAT32/exFAT writes. There is no hardware fact here that forbids SD writes during a DAC session. There is also no measured worst-case SD latency.

Today [main](../firmware/platform/device/board/main.c) chooses either the storage session or the DAC session after stopping app playback. The [storage session](../firmware/platform/device/board/usb_session.c) exposes internal storage and SD as writable raw LUNs while app stepping is suspended; after host writes, `storage_reset` discards local mounts and handles. The DAC configuration exposes audio only and instantiates no MSC transport. Local and host filesystem ownership are therefore exclusive by session design, not protected by a general-purpose filesystem lock. A recorder must make that exclusion explicit through start, stop, repair and mode changes. Do not expose a mounted recording card to the host, even read-only with stale metadata.

Important limits in the current path:

- [Storage HAL](../firmware/platform/device/board/storage.c) has offset writes, but `hal_file_write_at` reopens the path on each call. Its normal mount selects SD, falling back to internal storage. A recorder must require `HAL_VOLUME_CARD`, retain a file/cursor or equivalent bounded extent mapping, and fail if the card is absent rather than silently changing destinations.
- [FAT writer](../firmware/platform/device/logic/fat.c) only overwrites within the existing file size. It has no append, grow, truncate or rename operation. Whole-sector writes use runs of at most eight sectors (4 KiB), limited by contiguity. Partial sectors require read-modify-write. [Cache commit](../firmware/platform/device/logic/fat_layout.c) copies data to its 4 KiB cache and synchronously calls the block writer.
- [Reservation](../firmware/platform/device/logic/fat_reserve.c), [FAT creation](../firmware/platform/device/logic/fat_create.c) and [exFAT creation](../firmware/platform/device/logic/exfat_create.c) seek one contiguous allocation. A fragmented card can fail despite enough total free space. FAT chains and allocation metadata are written before publishing the directory entry. Allocation scans, multiple FAT copies, FSInfo updates and exFAT bitmap work have no real-time bound. Reserve before recording begins. Existing files are returned as “exists” without guaranteeing the requested capacity; verify size and identity.
- Reservation clears only the first 4 KiB of a regular file and exposes its full reserved length (including exFAT valid length). Unwritten tail sectors may contain old card data. Prezero the complete reservation before accepting audio, or implement safe unpublished allocation/valid-length handling before exposing a partial recording. A `.part` suffix alone does not solve this.
- [SD writes](../firmware/platform/device/board/sd.c) use `card_write` with CMD24/CMD25, CMD12 for multi-block writes, then CMD13 readiness checks. [MMC](../firmware/platform/device/board/mmc.c) services its FIFO with CPU programmed I/O. Its busy waits allow 1,000 ms, command waits 100 ms, and data waits 500 ms; readiness can try 1,000 commands. These are software failure limits, not measured card stalls or a single aggregate deadline. No wait calls the USB service. `card_write_start`/`finish` do not make `mmc_write_blocks` asynchronous: it already waits for completion and card busy to clear.

Average card bandwidth greater than 192 kB/s is necessary but insufficient. A 4 KiB payload batch arrives every 21.33 ms at 48 kHz. A single synchronous card wait can miss USB's next 1 ms transfer even with megabytes of software buffering, because software cannot fill that buffer while the endpoint goes unserviced. USB isochronous delivery cannot retry missing audio through ordinary backpressure.

## Buffer and CPU budget

At 48 kHz, the packed input rate is `48,000 × 2 × 2 = 192,000 bytes/s`; at 44.1 kHz it is 176,400 bytes/s. The following are arithmetic ceilings at 48 kHz, not measured stall tolerance:

| Memory | Capacity or time | Availability |
| --- | --- | --- |
| Current I2S monitor ring | 14,000 frames, 291.67 ms | Already occupied; packed recording bytes cannot share its active DMA contents |
| MSC write buffer | 32 KiB, 170.67 ms packed PCM | Idle in DAC mode, but must be lent explicitly; debug reports also use it |
| Entire core-1 RAM | 384 KiB, 2.048 s packed PCM | Requires power domain on, core held/reset, no decoder |
| Proposed capture queue | 256 KiB, 1.365 s packed PCM | Fits in borrowed core-1 RAM with 128 KiB left for staging/control; exact layout still to link/check |

[Core-1 scratch borrowing](../firmware/platform/device/board/core1.c) already lets core 0 use the full `0x01000000`–`0x0105FFFF` bank while core 1 is held. Borrow before opening the DAC stream: the current helper shuts audio down. Keep the bank powered for the whole capture, return it only after draining, and audit stream shutdown paths so none power it off prematurely. Do not place the I2S DMA monitor ring there without separate bus/DMA proof; leave it in data RAM.

The USB overlay has a 64 KiB code/image limit and a shared 96 KiB code-plus-BSS window, overlaid on decoder/UI workspace. The MSC buffer already occupies 32 KiB there. Glyph/language RAM remains in use. Main static RAM has little margin; the numeric tables in `CLAUDE.md` and `architecture.md` differ and are historical build results. Do not budget an extra large resident buffer from them. Check the exact candidate maps and the project-required reserve when code is eventually built.

Core 0 currently handles USB, PCM packing, DMA position, DAC control and minimal UI at 200 MHz. Core 1 is stopped, so there is no concurrent decode load to preserve. There is **no measured USB-DAC CPU percentage** in the inspected material. WAV needs copies and sector writes rather than compression; CPU feasibility is plausible, but bus contention and SD programmed I/O must be measured. Core 1's configured ceiling is 100 MHz (`core1_divider_for`); “two cores” does not mean two available 200 MHz CPUs.

Do not promise FLAC to reduce the buffer requirement: compressed worst-case output and encoding stalls still need bounds. A future core-1 encoder would consume the RAM currently proposed for capture and need its own program, IPC, workspace and throughput proof. The FLAC LPC accelerator is used for decoding; encoding support has not been established.

## Architecture to implement if the timing probe passes

1. Add a recording session inside the USB overlay, with explicit ownership of SD, capture queue and monitor ring. Suspend normal app filesystem jobs. Prepare a unique bounded recording and a separate preallocated recovery checkpoint file before enabling the stream. Use a WAV `JUNK` chunk to align the PCM data offset to 512 bytes, then sector-aligned writes; account for the chosen header size exactly.
2. Borrow core-1 RAM and allocate a fixed 256 KiB single-producer/single-consumer packed-PCM queue there. The USB callback validates, copies and advances counters only. It must never allocate, traverse FAT, write storage or render UI. Preserve the incoming bytes before monitor drift processing. Queue exhaustion stops recording and records a discontinuity; never present a damaged stream as exact.
3. Keep core 0 as the sole controller/file owner. Add a bounded cooperative storage service or an audited receive interrupt so every MMC wait, command, FIFO transfer, metadata read and recovery wait can coexist with USB. For the cooperative option, use a callback that only services USB/capture; it must not reenter FAT or MMC. An incremental state machine gives clearer deadlines. Measure SD FIFO starvation as well as USB gaps. Using core 1 as an SD worker is a larger alternative requiring new peripheral/clock/IPC ownership, not an existing facility.
4. Drain one bounded batch at a time with a persistent file cursor, then service capture and low-rate UI. Rate-limit checkpoint writes and include them in the storage budget. Use monotonic 64-bit frame/byte counters and an explicit capacity limit. Split before the current 32-bit filesystem/RIFF size limit; a 30-minute file fits comfortably.
5. Keep two checkpoint records in separate sectors with sequence, format, committed whole-frame byte count and checksum. Publish a checkpoint only after the corresponding data write reports ready. On normal stop or USB unplug, stop acceptance, drain queued PCM using battery power, finalize WAV sizes and FAT/exFAT file length, then release ownership. A rate/alt change closes a segment. USB storage entry waits for this completion.
6. Add and test filesystem finalization/truncation for FAT and exFAT, including exFAT valid/data length and entry checksum, allocation release and cache invalidation. On restart, recover only through the last valid checkpoint, repair the WAV header and length, and keep an incomplete marker until repair succeeds. The present reserve/write/delete APIs cannot provide this on their own. SD removal/write failure preserves the last durable prefix; do not assume the inaccessible card can be finalized immediately. Arbitrary SD controller power-loss behavior remains a media limitation, so bound the promised recoverable interval by experiment.

With a 256 KiB queue, a proposed admission envelope is at least 64 KiB free at worst occupancy, hence at most 1.024 s worth of accumulated backlog at 48 kHz. Use the measured backlog across repeated stalls, not just the longest individual write. Service USB at a design target of at most 250 µs between receive-service opportunities under load, and confirm no missed payload frames; this is a proposed safety target, not a proven DWC2 tolerance. Abort cleanly before overflow. If allowed cards cannot meet the envelope, restrict supported media or reject recording; increasing buffering cannot fix a blocked receiver.

## Analog recording alternative

**Not feasible as a supported high-quality analog/line-input feature from the established board interfaces.** No schematic/BOM proving an audio ADC, line input, mic bias/audio preamp or I2S capture route is in the inspected repository/discovery material. Both jacks are documented outputs. The identified CS43198 parts are DACs with serial digital inputs and analog outputs, not audio ADCs ([Cirrus data sheet](https://statics.cirrus.com/pubs/proDatasheet/CS43198_DS1156F2.pdf)).

There is a physical 3.5 mm mic contact connected to SAR ADC channel 2 for headset **button resistance** measurements. The existing scan is 10-bit, ordinarily one headset conversion per 20 ms, with button thresholds. Battery and key channels are also control ADC paths. This establishes a contact, not a 44.1/48 kHz, 16-bit stereo recording front end. ACODEC register names or a generic SoC capability do not prove board wiring. An external audio ADC/front end would be hardware work; USB-host capture hardware is a separate unproven controller/board-power project.

## Exact device measurements and acceptance

These are instructions for the parent after separate owner authorization, an approved image and the exact-model recovery route. None was run here. Keep measurements under `/Volumes/Scratch/SnowskyEcho/reports/feasibility/`.

1. Validate the existing DAC path first at both rates and 16-bit stereo on the intended host. Record enumeration/alternate setting, received packet lengths and frame totals, malformed packets, resets, incomplete-ISO events, monitor dropped/repeated/realigned frames and I2S underruns. Silence and UI state alone are not reception proof.
2. Use a disposable FAT32 card and an exFAT card representative of intended support; add FAT16 only if it will be advertised. Before audio, reserve/initialize a fixed recording, verify all extents and record preparation time. Repeat near full and fragmented. Measure each 512-byte/4 KiB data write, FAT lookup, command, busy interval and checkpoint, including failures, with microsecond-resolution timestamps or cycle counters. Report maxima, distribution, total bytes and hardware error registers; no assumed card-speed-class latency guarantee.
3. Run USB capture and storage concurrently with monitoring on/off, screen drawing and volume changes. Measure longest interval between USB service, capture queue peak/free minimum and overflow, card/FIFO errors, and core-0 useful work versus busy waits. A polling loop's “busy” percentage is not its spare CPU capacity. Measure core-1 bank access latency and verify it remains powered. First require sustained drain throughput above input, then the backlog/service envelope above.
4. Send a deterministic stereo frame-counter/PRBS PCM stream with explicit start/end markers and unity host processing, using a direct/exclusive host route when available. Record **86,400,000 stereo frames / 345,600,000 payload bytes at 48 kHz for 1,800 s**, and separately **79,380,000 frames / 317,520,000 bytes at 44.1 kHz**. Compare every payload byte and WAV lengths/rate/block alignment with the reference. Align to markers and the host's actual USB payload log so host padding/startup latency cannot masquerade as firmware loss. Require zero lost, duplicated or reordered capture frames and zero queue overflow; DAC monitor corrections are counted separately.
5. With disposable media, exhaust the reserved capacity, start with insufficient contiguous space, pull USB during active writes, change rate/alt setting, reset the USB host and remove/reinsert SD. Full capacity must end at an exact frame boundary, leave earlier recordings unchanged and refuse an unsafe restart. USB unplug must drain/finalize from battery; verify the exact accepted-frame count. SD removal/write failure must retain and later recover the checkpointed prefix without invented silence or success. Test checkpoint/header interruption and cold restart, then copy recordings through normal storage mode and run host filesystem checks on images of the disposable cards. No writes outside the selected card user filesystem are permitted.

Failure of byte identity, uninterrupted reception or bounded storage backlog is a no-go for the exact-frame feature on that configuration. A recoverable partial recording is an explicit error outcome, not a passing 30-minute exact capture.

## Estimate and main risks

Allow **1–2 engineering days** for the bounded timing probe after owner access is available, then **8–15 days** for a constrained WAV implementation and focused software/recovery checks, plus owner test windows for the full recordings and failure cases. This is a planning estimate, not measured progress. It includes cooperative USB/storage work, file finalization and checkpoint recovery; a new interrupt driver or core-1 storage worker can extend it. Stop the probe at two days if it cannot establish the timing envelope, and name the failed measurement before widening scope. FLAC needs a separate encoder spike and estimate.

The largest risks are USB starvation in storage/control waits, long/repeated SD program stalls, borrowed-RAM lifetime, reopening/traversing FAT during streaming, non-atomic finalization under power loss, and insufficient candidate overlay/resident margins. These, rather than nominal USB bandwidth or WAV header generation, decide whether the feature is reliable.
